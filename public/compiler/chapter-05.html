5.1为什么需要 SDD：语法树只是骨架，翻译规则放哪

第4章给了我们两样东西：一棵语法分析树，和一套驱动它生长的分析机制（LL 自顶向下、LR 自底向上）。但分析器到头只回答了一个问题——"这个串合不合法"。编译器的使命却是翻译：算出一个表达式的值、检查类型是否匹配、最终生成目标代码。这些"计算"挂在哪儿？随手塞进分析器代码里，规则一多就会缠成一团。本章的第一步，就是把"翻译规则"变成文法的一等公民。

这就是语法制导定义（Syntax-Directed Definition, SDD）。一个 SDD 由三部分组成：

成分内容在本章计算器例子里
上下文无关文法产生式骨架（第2、4章已备）E → E₁ + T 等
属性（Attribute）挂在每个文法符号上的值，可任意多个E.val、T.val、digit.lexval
语义规则（Semantic Rule）挂在每条产生式上的等式，规定"左边的属性怎么由右部属性算出"E.val := E₁.val + T.val

属性按求值方向分成两类，这个区分是整章的轴心：

类别定义方向直觉例子
综合属性（Synthesized Attribute）节点 N 的属性值，只由 N 的子节点与 N 自身的属性算出自底向上，值从叶子往根汇总E.val := E₁.val + T.val
继承属性（Inherited Attribute）节点 N 的属性值，由 N 的父节点、兄弟节点与自身属性算出自顶向下或横向，值从上面/左边流入5.3 的 E′.i、类型声明里的 L.in

约定：终结符只有综合属性（由词法分析器直接给出，如 digit.lexval），没有继承属性。

例：桌面计算器的完整 SDD。文法处理以换行结尾的算术表达式（n 表示换行），全部使用综合属性 val：

产生式语义规则
L → E nprint(E.val)
E → E₁ + TE.val := E₁.val + T.val
E → TE.val := T.val
T → T₁ × FT.val := T₁.val × F.val
T → FT.val := F.val
F → ( E )F.val := E.val
F → digitF.val := digit.lexval

注意这张表的写法：规则写成"X.属性 := 表达式"的形式，读作"X 的这个属性定义为右端的值"。SDD 只声明了这些等式，没有规定它们谁先算、谁后算——那是 5.2 与 5.3 要解决的问题。

💡 关键一跃

SDD 就是给文法"装仪表盘"：每条产生式是一个小公式，树一旦建好，每个节点的读数由它周围节点的读数唯一决定。编译器剩下的工作只是找一个不违心的读表顺序。

⚠️ 常见误区

把语义规则当成"按书写顺序从上往下执行的程序语句"。错：SDD 是声明式的等式系统，书写顺序不构成执行顺序；真正的执行顺序由属性之间的依赖关系决定（5.3 的依赖图）。把 print(E.val) 写在第一行，不代表它最先执行——恰恰相反，它最后才能算。

5.2S 属性：为什么"只用综合"就和自底向上分析天生合拍

5.1 把规则挂好了，但留下一个问题：按什么顺序算？先看最顺的一种情形——SDD 里只出现综合属性。这种 SDD 叫S 属性定义（S-Attributed Definition）。

综合属性"只看孩子"，于是求值顺序一目了然：后序遍历分析树——先把所有子树算完，再算父节点。这恰好与 LR 分析器的节奏严丝合缝：LR 每次"归约"一个产生式时，右部符号对应的子树刚刚全部处理完，此刻执行这条产生式的语义规则，需要的值一个不缺。

完整手算例：对 3 × 5 + 4 求值。把每个节点算出的属性值写在节点旁边，得到的树叫注释分析树（Annotated Parse Tree）：

flowchart TB L["L 打印 19"] --> E["E.val = 19"] L --> NL["n 换行"] E --> EA["E.val = 15"] E --> PLUS["+"] E --> TB["T.val = 4"] EA --> TA["T.val = 15"] TA --> TAA["T.val = 3"] TA --> MUL["×"] TA --> FB["F.val = 5"] TAA --> FA["F.val = 3"] FA --> D1["digit.lexval = 3"] FB --> D2["digit.lexval = 5"] TB --> FC["F.val = 4"] FC --> D3["digit.lexval = 4"]
图 5.1　3 × 5 + 4 的注释分析树：每个非终结符节点旁标注它算出的 val。看值的流向——全部自叶向根。

自底向上逐个节点写出求值步骤（一步不跳）：

步骤用到的产生式求值动作结果
1F → digitF.val := digit.lexval（词法器给出 3）F.val = 3
2T → FT.val := F.valT.val = 3
3F → digitF.val := digit.lexval（5）F.val = 5
4T → T₁ × FT.val := T₁.val × F.val = 3 × 5T.val = 15
5E → TE.val := T.valE.val = 15
6F → digitF.val := digit.lexval（4）F.val = 4
7T → FT.val := F.valT.val = 4
8E → E₁ + TE.val := E₁.val + T.val = 15 + 4E.val = 19
9L → E nprint(E.val)输出 19

把这张表和第4章的 LR 分析轨迹对照看：每一次归约恰好对应表里的一行，顺序完全一致。这不是巧合，而是 S 属性定义的结构性福利。

💡 关键一跃

LR 的"归约时刻"就是"这棵子树的值全部备齐的时刻"。归约即计算——所以 S 属性 SDD 挂在 LR 分析器上，求值顺序连排都不用排，分析器走到哪算到哪。

⚠️ 常见误区

以为"3 × 5 + 4 得 19 而不是 35（先算 5+4）是语义规则里写对了优先级"。错：语义规则只有 + 和 × 两条干巴巴的等式，优先级全部编码在文法层级里——× 被压进 T → T₁ × F（离叶子近、先归约），+ 放在 E → E₁ + T（离根近、后归约）。改优先级要改文法，不是改规则。

5.3继承属性与 L 属性：左递归消除后，信息怎么"向右传"

上一节一切顺遂，但有个前提被悄悄打破了：第4章讲过，自顶向下（LL）分析必须消除左递归。E → E + T | T 要改写成 E → T E′，E′ → + T E′ | ε。改写之后，"从左到右累计的和"原本靠左递归自然携带，现在 E′ 孤零零地挂在 T 的右边——累计值进不去了。光靠综合属性，这账算不下去。

解决办法是引入继承属性：让父节点（或左侧兄弟）把"目前已累计的值"发下来。完整的 SDD 如下（i 是继承属性，表示"进入这个 E′ 时已累计的值"；s 是综合属性，表示"离开这个 E′ 时的总和"）：

产生式语义规则
E → T E′E′.i := T.val　；　E.val := E′.s
E′ → + T E′₁E′₁.i := E′.i + T.val　；　E′.s := E′₁.s
E′ → εE′.s := E′.i
T → F　/　F → digit同 5.1（综合属性 val 照常上传）

完整手算例：对 3 + 5 求值。分析树形状是 E → T E′，E′ → + T E′₁，E′₁ → ε。哪些属性必须先算、哪些后算？画依赖图（Dependency Graph）：为分析树中每个属性建一个节点，若属性 a 的定义式用到了属性 b，就画一条 b → a 的有向边（b 先算）。

flowchart TB T1["T.val = 3（左边那个 T）"] --> EI["E′.i = 3"] EI --> E1I["E′₁.i = 3 + 5 = 8"] T2["T.val = 5（右边那个 T）"] --> E1I E1I --> E1S["E′₁.s = 8"] E1S --> ES["E′.s = 8"] ES --> EV["E.val = 8"]
图 5.2　3 + 5 的依赖图：箭头方向 = "必须先算"。看 E′.i 这条竖线——继承属性把累计值一路向右下方传。

对依赖图做一次拓扑排序，就得到一条合法求值序列（一步不跳）：

步骤求值动作依据的语义规则
1T.val = 3（由 F.val 上传，词法器给出 3）T → F，F → digit
2E′.i := T.val = 3E → T E′ 的第一条规则
3T.val = 5（右操作数）T → F，F → digit
4E′₁.i := E′.i + T.val = 3 + 5 = 8E′ → + T E′₁ 的第一条规则
5E′₁.s := E′₁.i = 8E′ → ε
6E′.s := E′₁.s = 8E′ → + T E′₁ 的第二条规则
7E.val := E′.s = 8E → T E′ 的第二条规则

这个例子里继承属性 E′.i 依赖的是父节点 E 的左兄弟 T 的综合属性和自己的继承属性传来的值——依赖关系干干净净。可一旦允许继承属性随便依赖（比如依赖右侧兄弟），依赖图可能出现环，求值就死锁了。于是需要一个"够用又安全"的限制，这就是L 属性定义（L-Attributed Definition）：

✅ 判定规则

一个 SDD 是 L 属性定义，当且仅当每条产生式 A → X₁ X₂ … Xₙ 中，每个 Xⱼ 的继承属性只依赖：① A 的继承属性；② Xⱼ 左边的兄弟 X₁…Xⱼ₋₁ 的任意属性（综合或继承）。（L 取 Left 之意：信息只能从左往右流。）综合属性不受限制。S 属性定义天然是 L 属性定义的特例。

例：类型声明。L 属性的用武之地远不止左递归消除。声明 float x, y 时，类型信息在树的最左边（T 节点），却要送到右边一串 id 上——这是典型的"横向传播"：

产生式语义规则
D → T LL.in := T.type
T → intT.type := integer
T → floatT.type := float
L → L₁ , idL₁.in := L.in　；　addtype(id.entry, L.in)
L → idaddtype(id.entry, L.in)

对 float x, y 走一遍（分析树：D → T L；T → float；L → L₁ , y；L₁ → x）：

步骤求值动作结果
1T → float：T.type := floatT.type = float
2D → T L：L.in := T.typeL.in = float
3L → L₁ , y：L₁.in := L.inL₁.in = float
4L → L₁ , y：addtype(y.entry, L.in)y 登记为 float
5L₁ → x：addtype(x.entry, L₁.in)x 登记为 float

检验 L 属性限制：L₁.in := L.in 依赖父节点的继承属性（合法①）；addtype 用的是 L.in（父的继承属性，合法①）。全部通过。

💡 关键一跃

继承属性就是"往下、往右发的通知"：上面（或左边）已经知道的事，打包发给右下方的子树，免得它自己重算或无从得知。L 属性限制则是邮局的规定——只许从左往右寄，这样整棵树从左到右扫一遍（深度优先），所有信都能送达，永不死循环。

⚠️ 常见误区

以为"继承属性想依赖谁就依赖谁，反正最后总能算"。错：若允许 Xⱼ.i 依赖它右边兄弟的属性，依赖图可能成环（a 等 b、b 等 a），任何求值顺序都不存在。L 属性的"只向左看"正是无环的充分保证，同时足够表达几乎所有翻译任务——这是它被广泛采用的原因。

5.4SDT：把动作嵌进产生式体——从"算什么"到"何时算"

SDD 是一份漂亮的规格说明书，但编译器最终要的是能跑的程序：动作何时执行，必须白纸黑字写死。把语义规则改写成可直接执行的程序片段（叫"语义动作"），并把它们像符号一样嵌进产生式右部的具体位置，就得到语法制导翻译方案（Syntax-Directed Translation Scheme, SDT）。

SDT 与 SDD 的差别就一条：SDD 说"算什么"，SDT 额外说"在产生式的哪个位置执行"。位置即时机——分析器处理到产生式右部的那个位置时，就执行那段动作。

最重要的一类是后缀 SDT（Postfix SDT）：所有动作都贴在产生式右部的最右端。把 5.1 的计算器 SDD 原样改写：

后缀 SDT 的产生式对应语义规则
L → E n { print(E.val) }print(E.val)
E → E₁ + T { E.val := E₁.val + T.val }E.val := E₁.val + T.val
E → T { E.val := T.val }E.val := T.val
T → T₁ × F { T.val := T₁.val × F.val }T.val := T₁.val × F.val
T → F { T.val := F.val }T.val := F.val
F → ( E ) { F.val := E.val }F.val := E.val
F → digit { F.val := digit.lexval }F.val := digit.lexval

完整例：LR 分析 3 × 5 + 4 时，动作的触发顺序。后缀 SDT 的动作在最右端，意味着"右部全部进栈、即将归约"的那一刻触发。对照第4章的 LR 移进-归约轨迹：

序分析器动作触发的语义动作效果
1移进 3—（词法器已给 lexval = 3）—
2归约 F → digitF.val := digit.lexvalF.val = 3
3归约 T → FT.val := F.valT.val = 3
4移进 ×，移进 5——
5归约 F → digitF.val := digit.lexvalF.val = 5
6归约 T → T₁ × FT.val := T₁.val × F.valT.val = 15
7归约 E → TE.val := T.valE.val = 15
8移进 +，移进 4——
9归约 F → digitF.val := digit.lexvalF.val = 4
10归约 T → FT.val := F.valT.val = 4
11归约 E → E₁ + TE.val := E₁.val + T.valE.val = 19
12移进 n，归约 L → E nprint(E.val)输出 19

逐行对比 5.2 的求值步骤表：完全一致。S 属性 SDD 转成的后缀 SDT，挂到 LR 分析器上即可机械执行——属性值存在分析栈里与符号并列，归约时右部符号连同它们的值一起弹出，算好后把左部符号连同新值压回。这就是"yacc/bison 里写 { … } 动作"的全部原理。

LL（自顶向下）的情况稍微妙：动作可以出现在产生式右部的任意位置，分析器展开到那个位置时执行它。比如 L 属性的继承属性计算，动作要放在使用该属性的符号左边（先把 E′.i 算好，再展开 E′）；综合属性的汇总动作放在最右端。位置排错，用到的属性就还没出生。

💡 关键一跃

SDT = SDD + 时刻表。SDD 声明等式系统，依赖图给出"哪些顺序合法"；SDT 从中挑定一种与分析器同步的顺序，把动作钉死在产生式的具体位置上。后缀 SDT 配 LR，左中右排布动作的 SDT 配 LL——翻译方案的形状由分析器的形状决定。

⚠️ 常见误区

以为"动作插在产生式中间只是写法花哨，不影响结果"。错：动作位置 = 执行时机。LL 分析中，插在 X 左边的动作会在展开 X 之前执行；若这段动作要用 X 的综合属性，那时它根本不存在。排位置的硬约束：用继承属性的动作放该符号左边，算综合属性的动作放产生式最右端。

预告：本章的例子都只在"算一个值"。第6章会把同样的机制推进一步——语义动作不再是算数，而是发射三地址码指令：E → E₁ + T { E.addr := new Temp(); gen(E.addr := E₁.addr + T.addr) }。挂规则的框架不变，换的只是"值"的含义。

📝分层习题

L1 概念辨析判断正误并说明理由：（a）"继承属性的值只能由父节点传给子节点"；（b）"每个 S 属性定义都是 L 属性定义"。
提示

（a）回看 5.3 的 E′.i := T.val——T 是 E′ 的什么亲属？（b）回看 L 属性判定规则：它限制的是哪一类属性的依赖？S 属性定义里存在这类属性吗？

完整解答

（a）错误。继承属性还可以依赖左侧兄弟的属性：5.3 中 E′.i := T.val，T 是 E′ 的左兄弟而非父亲。甚至 L 属性定义明确允许"左侧兄弟的任意属性"。说"只能父传子"把继承属性想窄了。

（b）正确。L 属性的两条限制只管继承属性的依赖来源；S 属性定义里根本没有继承属性，限制自动（空虚地）满足。所以 S ⊂ L：S 属性定义是 L 属性定义的特例。反过来不成立——带 E′.i 的文法是 L 的但不是 S 的。

L1 概念辨析下列关于 SDD 与 SDT 的说法，哪一个是正确的？① 二者等价，只是写法不同；② SDD 规定求值顺序，SDT 不规定；③ SDD 只声明"算什么"，SDT 通过动作在产生式中的位置额外规定"何时执行"；④ SDT 不能含继承属性。
提示

回忆 5.4 开头："SDT = SDD + 什么？"再逐项核对。

完整解答

③ 正确。SDD 是声明式规格（等式系统），执行顺序由依赖图决定、本身不写死；SDT 把动作嵌进产生式右部具体位置，位置即时机。

① 错：二者相差的正是"时机"这一维，不是纯写法。② 错：说反了——不规定顺序的是 SDD。④ 错：SDT 完全可以配 L 属性（LL 分析上的翻译方案几乎都有继承属性），是否含继承属性与是不是 SDT 无关。

L2 手算推导用 5.1 的桌面计算器 SDD，对输入 2 + 3 × 4 画出注释分析树，并自底向上写出全部求值步骤。注意：优先级体现在文法层级里，请先想清楚 × 的子树挂在哪里。
提示

先按 E → E₁ + T、T → T₁ × F 的层级画出纯分析树：+ 的两个操作数分别是 E₁=2 与 T=3×4。然后从叶子 digit 开始，逐条产生式向上求值。

完整解答

注释分析树（属性值标在节点旁）：

flowchart TB L["L 打印 14"] --> E["E.val = 14"] L --> NL["n 换行"] E --> EA["E.val = 2"] E --> PLUS["+"] E --> TB["T.val = 12"] EA --> TA["T.val = 2"] TA --> FA["F.val = 2"] FA --> D1["digit.lexval = 2"] TB --> TAA["T.val = 3"] TB --> MUL["×"] TB --> FB["F.val = 4"] TAA --> FC["F.val = 3"] FC --> D2["digit.lexval = 3"] FB --> D3["digit.lexval = 4"]
习题 L2-1 解答图：3 × 4 整体是 + 的右操作数 T，所以先算完 12 再做加法。

求值步骤：

① F → digit：F.val := 2；② T → F：T.val := 2；③ E → T：E.val := 2（这就是 E₁.val）；④ F → digit：F.val := 3；⑤ T → F：T.val := 3（这是 T₁.val）；⑥ F → digit：F.val := 4；⑦ T → T₁ × F：T.val := 3 × 4 = 12；⑧ E → E₁ + T：E.val := 2 + 12 = 14；⑨ L → E n：print(14)。

关键点：步骤③在步骤⑦之前——左操作数 2 的子树先归约；但 + 的语义规则（步骤⑧）必须等右操作数 T=12 就绪，所以最终是 14 而非 20。若误把树画成 (2+3) × 4 的形状，说明没看清优先级在文法层级中的位置。

L2 手算推导小数十进制求值的继承属性 SDD：F → . R { R.i := 1; F.val := R.s }；R → digit R₁ { R₁.i := R.i + 1; R.s := digit.lexval ÷ 10^(R.i) + R₁.s }；R → ε { R.s := 0 }。其中 R.i 表示当前 digit 在小数点后第几位。对输入 .35 画出依赖图，给出拓扑求值序列，算出 F.val。
提示

先展开：F → . R，R → 3 R₁，R₁ → 5 R₂，R₂ → ε。继承属性 i 沿 R → R₁ → R₂ 一路向下传（1、2、3），综合属性 s 再一路向上回。依赖图节点 = 每个出现的属性。

完整解答

依赖图（箭头 = "必须先算"）：

flowchart TB RI["R.i = 1"] --> R1I["R₁.i = 2"] R1I --> R2I["R₂.i = 3"] R2I --> R2S["R₂.s = 0"] R2S --> R1S["R₁.s = 5 ÷ 100 + 0 = 0.05"] R1I --> R1S R1S --> RS["R.s = 3 ÷ 10 + 0.05 = 0.35"] RI --> RS RS --> FV["F.val = 0.35"]
习题 L2-2 解答图：i 自上而下传位次，s 自下而上回传加权和。

拓扑求值序列（一步不跳）：

① R.i := 1（F → . R 的规则）；② R₁.i := R.i + 1 = 2；③ R₂.i := R₁.i + 1 = 3；④ R₂.s := 0（R → ε）；⑤ R₁.s := 5 ÷ 10² + R₂.s = 0.05 + 0 = 0.05（此时 R.i 对 R₁ 而言等于 2，故除以 100）；⑥ R.s := 3 ÷ 10¹ + R₁.s = 0.3 + 0.05 = 0.35；⑦ F.val := R.s = 0.35。

检验：这正是 0.35 = 3/10 + 5/100。继承属性 i 把"第几位"逐层下发，综合属性 s 把"这一位及以后的加权和"逐层上交——一次下行、一次上行，是 L 属性求值的典型节奏。

L3 建模应用为一个迷你语言设计 SDD：程序 = 若干声明 + 若干赋值语句。声明形如 float x, y;（int / float 两种类型，逗号分隔多个变量）；赋值形如 x = e;，表达式 e 支持加法、变量、整数字面量。要求：声明语句用继承属性把类型传播到每个变量并登记符号表；赋值语句用综合属性从表达式上报类型，与左侧变量类型比较，输出 ok 或 error。
提示

声明部分直接搬 5.3 的 D → T L 方案。表达式部分仿 5.1：给 E 配综合属性 type，E → E₁ + E₂ 时比较两侧。赋值语句 A → id = E 的 ok 由什么决定？把它也设计成一个综合属性。

完整解答

文法与完整语义规则：

产生式语义规则
P → D S—（D 完成登记，S 完成检查）
D → D₁ ; T LL.in := T.type
D → T LL.in := T.type
T → intT.type := int
T → floatT.type := float
L → L₁ , idL₁.in := L.in　；　addtype(id.entry, L.in)
L → idaddtype(id.entry, L.in)
S → S₁ ; AS.ok := S₁.ok ∧ A.ok
S → AS.ok := A.ok
A → id = EA.ok := (gettype(id.entry) = E.type)；若不等则报错
E → E₁ + E₂E.type := 若 E₁.type = E₂.type 则 E₁.type，否则 type_error
E → idE.type := gettype(id.entry)
E → numE.type := int

属性清单：继承属性 L.in（类型下传）；综合属性 T.type、E.type、A.ok、S.ok。方向检验：全部继承属性只依赖父的继承属性（L₁.in := L.in），是 L 属性定义。

走一遍 int y; float x; x = y + 1;：① T→int：T.type=int；L→y：addtype(y, int)。② T→float：T.type=float；L→x：addtype(x, float)。③ E→id(y)：E.type=gettype(y)=int。④ E→num(1)：E.type=int。⑤ E→E₁+E₂：两侧都是 int，E.type=int。⑥ A→x = E：gettype(x)=float ≠ int，A.ok=false，输出 error：把 int 表达式赋给 float 变量（按本语言严格规则拒绝）。⑦ S.ok=false，整个程序检查失败。

这正是第8章类型检查器的骨架：符号表（addtype/gettype）+ 类型综合上报 + 语句级布尔汇总，全靠属性方向各就其位。

自测 1
综合属性的求值方向是？
  • A. 自顶向下，由父节点算给子节点
  • B. 自底向上，由子节点算给父节点

  • B. 因为 S 属性定义里没有属性需要计算

🗣️ 用自己的话，三句话讲完本章

对着空气（或室友）说出这三句。说卡壳的那句，回去重读对应小节。

句1：这章解决什么问题？——
参考答案：语法分析只判断"结构合不合法"，本章解决"结构之上怎么算"——把翻译（求值、登记类型、将来生成代码）所需的计算规则系统地挂到文法上，并保证这些计算有一个与分析过程兼容的执行顺序。
句2：核心机制是什么？——
