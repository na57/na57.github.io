1.1为什么需要编译器：从"机器只懂 0/1"说起

计算机的 CPU 是一台极其固执的机器：它只认识一串串 0 和 1 组成的指令——取数、加法、跳转，仅此而已。而人类写程序用的是 position = initial + rate * 60 这样的高级语言。两者之间隔着一道鸿沟：总要有人把高级语言翻译成机器码。这个"翻译官"就是本章的主角。

翻译官有两种工作方式：

  • 编译器（Compiler）：先把整份源代码翻译成一份完整的目标程序（通常是机器码），之后目标程序可以被反复运行。翻译是一次性的，运行是无数次的。C、C++、Go 是典型代表。
  • 解释器（Interpreter）：不产出目标程序，而是拿着源代码逐条"现场口译"——读一句、执行一句，源程序始终在翻译官手里。早期 BASIC、纯 Python 风格的执行是典型代表。

一个日常类比：编译器像"整本书的笔译"，交稿后读者随时翻看，翻得越多越划算；解释器像"会议同声传译"，每次开会都要重新请翻译。由此可以直接推出两者的开销模型：

编译：总开销 = 编译时间（一次） + 运行时间（每次）    解释：总开销 ≈ 每句解释开销 × 执行句数（每次都付）

所以同一个程序要跑一百万次时，编译方案把翻译成本摊薄到几乎为零，而解释方案每次都重新付"口译费"。这就是对性能敏感的系统软件几乎全部走编译路线的原因。

对比项编译器解释器
是否产出目标程序是（机器码文件，可反复运行）否（边译边执行）
运行时还需要翻译官吗不需要需要
典型速度快慢
报错时机编译期集中报告一批错误执行到哪句才发现哪句的错
代表gcc、clang早期 BASIC、交互式 shell

现实世界还有第三条路——混合模式。Java 先由编译器把 .java 编译成与机器无关的字节码（Bytecode），再由 Java 虚拟机（JVM）解释执行字节码；虚拟机里的即时编译器（JIT）还会把热点字节码进一步编译成真正的机器码。一次编译、处处运行，靠的就是把"翻译"拆成与机器无关的前半段和与机器相关的后半段——这个思想在 1.3 节会变成全书最重要的工程结论。

💡 关键一跃

编译器不是"一个翻译程序"，而是一条工程流水线：正因为整步翻译太复杂，工程上才把它切成一串小步骤，每步只做一种变换。本章剩下的全部内容，就是把这条流水线画出来。

⚠️ 常见误区

"Java 是解释型语言，C 是编译型语言"——这种说法是错的。语言本身不分编译型/解释型，分的只是它的主流实现方式：C 也可以写解释器，Python 也有编译实现（PyPy 带 JIT）。判断时问的是"这个实现产不产出可独立运行的目标程序"。

1.2一条流水线：七个阶段各吃什么、吐什么

上一节说编译器是一条流水线，但它带出一个问题：这条流水线具体切成哪几段？每段交什么东西给下一段？龙书给出的经典答案是七个阶段。先看全景，再用一个完整例子走全程。

图 1.1 七阶段主链（简化版）：前四个属"前端"，后三个属"后端"。龙书原图中目标代码生成后还有目标机相关的代码优化，本章用下面的总表统一呈现。

完整手算例来了。考虑赋值语句：

position = initial + rate * 60

假设 position、initial、rate 都是浮点变量，60 是整型常量。下面一个阶段一个阶段地走，每一步的输入和输出都写全。

第 1 步：词法分析（Lexical Analysis）——字符流 → 记号流

词法分析器（Lexer / Scanner）读入字符流，把字符分组为有意义的记号（Token）：标识符、运算符、常量。空白被丢弃，每个标识符同时在符号表（Symbol Table）里登记一个条目。本例输出：

⟨id, 1⟩ ⟨=⟩ ⟨id, 2⟩ ⟨+⟩ ⟨id, 3⟩ ⟨*⟩ ⟨60⟩

其中 id 后的数字是符号表条目编号。符号表此时内容：

条目编号标识符后续阶段会补充的信息
1position类型 float、存储地址（语义分析、代码生成时填）
2initial类型 float、存储地址
3rate类型 float、存储地址

第 2 步：语法分析（Syntax Analysis）——记号流 → 语法树

语法分析器（Parser）检查记号流是否符合文法，并把它组织成一棵语法树（Syntax Tree）：树的结构精确表达"先算乘法、再算加法、最后赋值"的运算次序。

flowchart TB A["="] --> B["⟨id,1⟩ position"] A --> C["+"] C --> D["⟨id,2⟩ initial"] C --> E["*"] E --> F["⟨id,3⟩ rate"] E --> G["60"]
图 1.2 position = initial + rate * 60 的语法树。乘法是加法的子树，所以 rate * 60 先算。

第 3 步：语义分析（Semantic Analysis）——语法树 → 带类型信息的语法树

语义分析器（Semantic Analyzer）做语法结构查不出来的检查，最重要的是类型检查（Type Checking）：rate 是 float，60 是 int，乘法要求两边类型一致，于是自动在 60 的父节点处插入一次类型转换 inttofloat。树的形状不变，只是 * 的右孩子从"60"变成了"inttofloat(60)"。

第 4 步：中间代码生成（Intermediate Code Generation）——树 → 三地址码

编译器把树翻译成一种低级的、与机器无关的中间表示（Intermediate Representation），常用形式是三地址码（Three-Address Code）：每条指令至多一个运算符、至多三个操作数，临时变量依次命名 t1、t2……本例得到：

t1 = inttofloat(60)    t2 = id3 * t1    t3 = id2 + t2    id1 = t3

第 5 步：机器无关代码优化（Machine-Independent Optimization）——三地址码 → 更好的三地址码

优化器发现 inttofloat(60) 是编译期就能算出的常量 60.0，且 t3 只被用了一次，于是合并：

t1 = id3 * 60.0    id1 = id2 + t1

四条指令变两条。注意：这一步不知道目标机长什么样，只做"任何机器上都划算"的改进。

第 6 步：代码生成（Code Generation）——三地址码 → 目标机器指令

代码生成器（Code Generator）把三地址码映射成具体机器的指令，并做寄存器分配（Register Allocation）：

LDF R2, id3    MULF R2, R2, #60.0    LDF R1, id2    ADDF R1, R1, R2    STF id1, R1

第 7 步：目标机相关优化（Machine-Dependent Optimization）——指令 → 更贴合硬件的指令

最后还可针对具体处理器做指令调度、窥孔优化等，本例已足够短，原样输出。

把七步放进一张总表，这就是本章要背下来的"主线地图"：

语法分析记号流语法树（图 1.2）

💡 关键一跃

七个阶段其实是同一条信息的七次"换表示"：字符 → 记号 → 树 → 带类型的树 → 三地址码 → 优化的三地址码 → 机器指令。每个阶段只负责一种变换，不越界——这就是它能被拆开单独实现、单独测试的原因。

⚠️ 常见误区

误区一："inttofloat 是中间代码生成阶段加的。"错——类型检查（含插入类型转换节点）属于语义分析，中间代码生成只是把它忠实地翻译成一条三地址指令。误区二："优化阶段会改变程序的结果。"错——优化必须保持语义不变，只改效率；本例 60→60.0 的常量折叠结果完全相同。

1.3前端 vs 后端：为什么这个划分省钱

上一节画出了七个阶段，但它带出一个工程问题：世界有几十种源语言、几十种目标机，难道每对组合都重写一个编译器？观察七阶段表会发现：前四个阶段（词法、语法、语义、中间代码生成）只关心源语言，不知道目标机长什么样；后面生成与目标相关优化的阶段只关心目标机，对源语言已经无感（它看到的是三地址码）。于是自然切成两块：

  • 前端（Front End）：词法 + 语法 + 语义 + 中间代码生成，外加机器无关优化的大部分。依赖源语言，不依赖目标机。
  • 后端（Back End）：代码生成 + 目标机相关优化。依赖目标机，不依赖源语言。
  • 两块之间只用一个约定好的中间表示（如三地址码）交接。

这条划分的回报是一笔账。设有 m 种源语言、n 台目标机：

不划分：编译器数量 = m × n    划分后：编译器数量 = m 个前端 + n 个后端

代入 m = n = 10：不划分要写 100 个编译器；划分后只需 10 + 10 = 20 个可拼接的部件，且任何一个新语言只要写 1 个前端就立刻获得全部 10 台机器的后端。GCC、LLVM 正是靠这个结构支持几十种语言 × 几十种架构。

还有两个角色不在流水线主链上，却从头到尾都在场：

  • 符号表（Symbol Table）：词法阶段登记标识符，语义阶段填类型，代码生成阶段填地址——每个阶段都读它、写它，是贯穿全程的共享数据库。
  • 错误处理器（Error Handler）：词法错误（非法字符）、语法错误（缺括号）、语义错误（类型不匹配）……任何阶段都可能报错，编译器被要求"尽可能多地报告错误并继续编译"，而不是遇到第一个错就罢工。
💡 关键一跃

前端/后端划分的本质是用中间表示当"标准接口"：接口定得越稳，两边越能独立演化。这和 1.1 节 Java"一次编译、处处运行"用的是同一个思想——字节码就是 Java 世界的中间表示。

⚠️ 常见误区

"符号表是词法分析阶段用完就扔的临时结构。"错。符号表在词法阶段创建，但它的生命贯穿整个编译过程：语义分析往里写类型，中间代码生成和代码生成往里查名字、写地址。把它当成某一个阶段的内部产物，是初学者最常见的结构误判。

1.4编译技术还用在哪 + 本书地图

前三节给出了编译器的骨架，但它带出一个收尾问题：学这套东西只能去写编译器吗？恰恰相反，"分阶段处理语言"的技术在很多地方复用：

  • 结构化查询的处理：数据库执行 SQL 同样经历"解析 → 语义检查 → 生成查询计划（中间表示）→ 优化 → 执行"，与编译器流水线同构。
  • 程序分析与验证：静态检查工具（找空指针、未初始化变量）复用编译器前端的词法/语法分析成果，在语法树上做检查而不生成代码。
  • 程序优化技术的外溢：常量折叠、公共子表达式消除等思想出现在解释器、JIT、甚至电子表格的重算引擎里。
  • 新硬件的配套软件：每出现一种新芯片（GPU、AI 加速器），第一件软件工作就是为它写后端——这正是 1.3 节 m + n 结构的现实生意。

🃏概念卡：本章概念的一分钟画像

翻面前先自问：这个概念我能用一句话讲清楚吗？

概念卡 1
编译器（Compiler）
点击翻面 →
定义把源语言程序整体翻译成等价的目标语言程序（通常是机器码）的程序。
解决问题弥合"人类写的高级语言"与"机器只懂的 0/1"之间的鸿沟。
直觉整书笔译：一次翻完，读者随时翻看。
误区以为"某语言天生是编译型"——编译/解释是实现方式的属性，不是语言的属性。
何时用全书主角；第 2 章亲手写一个迷你的。
概念卡 2
词法分析（Lexical Analysis）
点击翻面 →
定义把字符流分组为记号流（Token Stream），并登记符号表的第一阶段。
解决问题字符层面太琐碎，先把"字母数字串"聚合成有意义的单词。
直觉读书时的"断词"：把一连串字母切成单词再谈理解。
误区以为它检查拼写/括号配对——括号配对错是语法错误，不归它管。
何时用第 3 章整章：用正则表达式 + 有穷自动机实现它。
概念卡 3
语法分析（Syntax Analysis）
点击翻面 →
定义按文法把记号流组织成语法树，暴露运算次序与结构的阶段。
解决问题记号流是"一串单词"，不知道谁先算谁后算；树给出层次。
直觉给句子画语法成分图：主谓宾定状补各归其位。
误区以为它能发现类型错误——"int + 字符串"结构合法但语义错，归语义分析。
何时用第 4 章整章：自顶向下、自底向上、LR 分析器。
概念卡 4
中间代码 / 三地址码（Intermediate Code）
点击翻面 →
定义前端与后端之间、与具体机器无关的低级表示；三地址码每条指令至多一个运算符、三个操作数。
解决问题让前端不必懂机器、后端不必懂语言，是 m + n 结构的接口。
直觉国际贸易里的英语：任何语言先翻成英语，再由英语翻向任何语言。
误区以为只有一种中间表示——语法树、三地址码、字节码都是不同层次的 IR。
何时用第 6 章生成它，第 8–9 章优化它，第 8/9 章之后把它译成机器码。
概念卡 5
符号表（Symbol Table）
点击翻面 →
定义记录每个标识符的名字、类型、作用域、存储地址等信息的共享数据结构。
解决问题各阶段对"同一个名字"的信息要前后一致，需要一处公共档案。
直觉全班名册：报到（词法）登记，班主任（语义）填成绩，教务处（代码生成）分宿舍。
误区以为它是词法阶段用完即弃的临时产物——它贯穿编译全程。
何时用第 2 章就会实现一个简化版；第 6、8 章读写它。
概念卡 6
前端 / 后端划分（Front End / Back End）
点击翻面 →
定义前端 = 依赖源语言的各阶段；后端 = 依赖目标机的各阶段；两者用中间表示交接。
解决问题把 m 语言 × n 机器的 m×n 个编译器压缩成 m + n 个可拼接部件。
直觉耳机与插孔：3.5mm 标准接口让任何耳机配任何播放器等。
误区以为优化全在后端——机器无关优化（常量折叠等）通常算前端一侧。
何时用全书结构的脊梁：Ch2–7 是前端，Ch8–11 是后端。

📝分层习题

L1 概念辨析判断并说明理由：(a) "Python 是解释型语言，所以任何 Python 程序都不可能被编译。" (b) "javac 把 Java 源程序直接翻译成 x86 机器码，所以 Java 是编译执行的。"
提示

回到 1.1 的判断标准：这个"实现"产不产出可独立运行的目标程序？语言本身有没有编译/解释属性？Java 的字节码算不算目标机器码？

完整解答

(a) 错。编译/解释是实现方式的属性，不是语言的属性。PyPy 等实现就把 Python 字节码即时编译成机器码；完全可以为 Python 写一个传统编译器。

(b) 错。javac 的产物是与机器无关的字节码，不是 x86 机器码；字节码由 JVM 解释执行（热点代码再由 JIT 编译）。所以 Java 是"编译 + 解释"的混合模式，不是纯编译执行。易错点：把"编译过一次"当成"直接跑机器码"。

L1 概念辨析同学甲说："括号不匹配是词法错误，因为词法分析器读到了括号。"同学乙说："类型不匹配是语法错误，因为语法树里有这两个运算数。"两人各错在哪里？
提示

词法分析器输出的是记号，它理解"结构"吗？类型检查需要知道变量的声明类型，语法树本身带这个信息吗？

完整解答

甲错：词法分析只负责把字符切成记号，单个括号 ( 和 ) 都是合法记号；配对问题是结构问题，属于语法分析，由文法规则发现。

乙错：语法分析只看结构是否合文法，"int + string"在结构上完全合法；类型检查属于语义分析，要查符号表里的声明类型才能发现。口诀：词法管"词"、语法管"形"、语义管"义"。

L2 手算推导仿照 1.2 节的完整例子，把语句 x = a + b * 2（x、a、b 均为 float，2 为 int）走完七个阶段，写出每个阶段的输入与输出（含符号表）。
提示

先数记号、建符号表；画树时注意 * 是 + 的子树；语义分析在哪里插入 inttofloat；三地址码按"先转换、再乘、再加、最后赋值"的顺序；优化做常量折叠。

完整解答

① 词法分析：输入字符流 x = a + b * 2。输出记号流 ⟨id,1⟩⟨=⟩⟨id,2⟩⟨+⟩⟨id,3⟩⟨*⟩⟨2⟩。符号表：1↔x（float）、2↔a（float）、3↔b（float）。共 7 个记号、3 条符号表项。

② 语法分析：输出语法树——根是 =，左孩子 ⟨id,1⟩，右孩子是 +；+ 的左孩子 ⟨id,2⟩，右孩子是 *；* 的左孩子 ⟨id,3⟩，右孩子 2。

③ 语义分析：类型检查发现 b（float）* 2（int）类型不一致，在 2 处插入 inttofloat，得到 * 的右孩子 inttofloat(2)。

④ 中间代码生成：t1 = inttofloat(2)；t2 = id3 * t1；t3 = id2 + t2；id1 = t3。

⑤ 机器无关优化：常量折叠 inttofloat(2) → 2.0，合并单次使用的 t3，得 t1 = id3 * 2.0；id1 = id2 + t1。

⑥ 代码生成：LDF R2, id3；MULF R2, R2, #2.0；LDF R1, id2；ADDF R1, R1, R2；STF id1, R1。

⑦ 目标机相关优化：指令已足够短，原样输出（若目标机有乘加融合指令 FMA，可进一步合并 MULF 与 ADDF——这正说明第 ⑦ 步依赖具体硬件）。

L2 手算推导对语句 total = count + rate2 * 10：(a) 词法分析输出多少个记号？(b) 符号表建几个条目？分别是什么？(c) 若把语句改成 total = total + rate2 * 10，记号数和符号表条目数各变不变？为什么？
提示

逐字符扫描，数一数"单词"；符号表按"不同标识符"登记，同一个名字第二次出现时是新建条目还是查旧条目？

完整解答

(a) 记号流为 ⟨id,1⟩⟨=⟩⟨id,2⟩⟨+⟩⟨id,3⟩⟨*⟩⟨10⟩，共 7 个记号（3 个标识符、3 个运算符、1 个常量）。

(b) 符号表 3 个条目：1↔total、2↔count、3↔rate2。

(c) 改成 total = total + rate2 * 10 后：记号流为 ⟨id,1⟩⟨=⟩⟨id,1⟩⟨+⟩⟨id,3⟩⟨*⟩⟨10⟩——记号仍是 7 个；但符号表只剩 2 个条目（1↔total、3↔rate2，count 消失，total 第二次出现时查到已有条目）。关键结论：记号数按"出现次数"算，符号表条目按"不同名字"算，同一个标识符多次出现只登记一次。

L3 建模应用某创业团队设计了 3 门新语言（脚本语言 S、系统语言 C2、教学语言 T），希望它们都能跑在 4 款芯片（x86、ARM、RISC-V、自研 NPU）上。用本章的前端/后端思想给出开发方案：(a) 不划分时要写多少个编译器？(b) 划分后要写哪些部件、共多少个？(c) 若半年后新增第 4 门语言，两种方案各自要追加多少工作量？(d) 用一句话说明该方案对"自研 NPU"这种新硬件的意义。
提示

把 1.3 节的 m×n 与 m+n 公式代入 m=3、n=4，再讨论增量（m→m+1）时两种方案各加几个部件。中间表示是接口，新硬件只动接口哪一侧？

完整解答

(a) 不划分：3 × 4 = 12 个完整编译器。

(b) 划分后：3 个前端（S、C2、T 各一）+ 4 个后端（x86、ARM、RISC-V、NPU 各一）= 7 个部件，约定一个统一的中间表示（如三地址码）作为拼接接口。

(c) 新增第 4 门语言：不划分方案要为 4 款芯片各写 1 个编译器，追加 4 个；划分方案只需写 1 个新前端，立刻复用已有 4 个后端。

(d) 对自研 NPU 的意义：只需为它写 1 个新后端，现有 3 门（未来 n 门）语言立刻全部"免费"获得 NPU 支持——这就是 LLVM/GCC 生态能快速覆盖新硬件的原因，也是 m+n 结构从"省工作量"升级为"生态杠杆"的地方。

自测 1
编译器与解释器最本质的区别是：
  • A. 编译器运行快，解释器运行慢
  • B. 编译器先产出完整的目标程序再运行；解释器不产出目标程序，边翻译边执行

B 对：产出目标程序与否是定义性区别。A 错在把常见现象当定义（快慢是结果不是本质）；C 错，解释器同样报错，只是报错时机在执行中；D 错，"编译型/解释型语言"本身就是错误说法——语言不分型，分型的只是实现。
自测 2
下列哪个顺序正确描述了编译器的处理流程？
  • A. 语法分析 → 词法分析 → 语义分析 → 中间代码生成
  • B. 词法分析 → 语义分析 → 语法分析 → 代码生成
  • C. 词法分析 → 语法分析 → 语义分析 → 中间代码生成 → 优化 → 代码生成
  • D. 代码生成 → 优化 → 语义分析 → 语法分析
C 对，这是七阶段主链的标准顺序。A 错：必须先有记号流才能做语法分析，词法在语法之前；B 错：语义分析检查的是语法树，必须先有语法分析；D 错：代码生成是最后阶段，不可能排在最前，且语义在语法之后。
自测 3
关于符号表，下列说法正确的是：
  • A. 它只在词法分析阶段使用，之后即被销毁
  • B. 它是语法分析器的内部数据结构
  • C. 每个标识符每出现一次就要新建一个条目
  • D. 它由词法分析创建，贯穿编译全程，语义分析往里填类型、代码生成往里填地址
D 对：符号表是贯穿全程的共享数据库。A 错在"用完即弃"，代码生成还要查它分配地址；B 错，它不属于任何单一阶段；C 错，同一标识符多次出现只登记一次（见 L2 习题），条目按不同名字计。

自测 5

  • A. 词法分析——它读到了 int 常量 60
  • B. 语义分析——类型检查发现 float * int 不一致，决定插入转换节点
