主线

从「一份资源多种表示」走到「编码后发回」

1一个 URL 多种表示：资源与表示分离，先承认才有得选
2请求带 Accept 与 q 值：客户端把偏好声明清楚
3服务器给候选打分：选择权默认在服务器手里
4选出的表示加 Vary：让缓存按维度分副本，不串味
5编码后作为主体返回：内容编码与传输编码叠加
这条链就是本讲目录：资源与表示 → q 值择优 → 编码分层 → Vary → 客户端提示；支线是 UA 字符串猜能力。
动机

「一个网址一个文件」解释不了四副面孔

🙂 过于简略的解释
一个 URL 对应一个文件，请求谁就回谁。能说通一次点击，仅此而已。
🤔 解释不了的四个现象
为何同网址回 HTML 又回 JSON；为何手机收到压缩版；为何有的客户端拿到纯文本；为何换个浏览器就乱码。
💡 本讲方案：把选择权摆到桌面 —— 资源与表示分开，偏好由请求首部驱动，选完用 Vary 交代清楚。
定义

URL 指向资源，响应发回的是表示

📦 资源（Resource）
URL 命名的对象，是一项被命名的资源；一个 URL 只指向一项资源。
📄 表示（Representation）
这一次响应真正发回的字节，可能是 HTML、JSON，也可能是压缩过的版本。
资源与它的各种表示共享同一个 URL —— 「一个网址对应一个文件」是错的
内容协商（Content Negotiation）就是从多个表示里选出该返回哪一个的机制；偏好由 Accept 系列请求首部声明，选中的表示由 Content-Type 与 Content-Encoding 描述。
专题 · 协商方式

三种协商方式：谁做选择，代价各是什么

协商方式谁做选择怎么表达偏好代价
服务器驱动协商（Server-driven Negotiation）服务器客户端发 Accept 系列，服务器择优标准、最常用；首部冗长，带来指纹识别与缓存效率下降
代理驱动协商（Agent-driven Negotiation）用户或脚本服务器回 300、406、415 并给可选链接灵活但要多一次请求，链接格式没标准
透明协商（Transparent Negotiation）缓存代选靠 Alternates 等首部提案未被广泛采用，实际基本看不到
MDN 明确：服务器驱动是标准方式，代理驱动只是备选；300、406、415 属于后者。
规范并没规定服务器的择优算法，你能判定哪种表示更符合要求，却别指望全互联网有一套统一公式。
专题 · q 值

五条规则，一把只在本首部内部有效的尺子

q 值规则含义例子
取值 0 到 1，最多三位小数越大越优先，1 最高text/html;q=0.9
不写 q 默认为 1没标 q 的项最优先de 等价于 de;q=1
q=0 表示不可接受显式排除某一项image/webp;q=0
支持通配符精确优先于类型通配，再优先于全通配text/* 与 */*
只在同一个首部内部可比跨首部如何合成由服务器决定Accept 与 Accept-Language 的 q 不能比大小
质量因子（Quality Factor）常写作 q 值：一把只在同一首部内部有效的尺子
先立规矩再手算：q=0 是明确拒绝，不是优先级最低；没写 q 的项才是默认最优先。
例子 · 报文

一份带完整 q 值的请求与四种候选表示

GET /api/report HTTP/1.1 Host: example.com Accept: text/html;q=0.9, application/json;q=1.0, text/plain;q=0.6, */*;q=0.1 Accept-Language: zh-CN,zh;q=0.8,en;q=0.5 Accept-Encoding: br;q=1.0, gzip;q=0.7, identity;q=0.2, *;q=0 （空行：本请求无主体）
三个 Accept 首部分别在媒体类型、自然语言、内容编码三个维度上声明偏好；开头的项没写 q，默认取 1。
候选表示Content-Type语言内容编码
Atext/htmlzh-CNbr
Bapplication/jsonengzip
Ctext/plainzh-CNidentity
Dtext/htmlengzip
例子 · 手算

逐维取 q：最具体匹配优先

第一步 媒体类型：A 与 D 的 text/html 命中 0.9，B 的 application/json 命中 1.0，C 的 text/plain 命中 0.6；四种类型都被精确列出，兜底项 */*;q=0.1 用不上。

第二步 自然语言：zh-CN 命中首项默认 1.0，en 命中 0.5；zh;q=0.8 用于纯中文不带地区的表示，本例没有。

第三步 内容编码：br 得 1.0，gzip 得 0.7，identity 得 0.2；identity 即便不写也默认可接受，只是优先级最低。

表示媒体类型 q语言 q编码 q
A · HTML / 中文 / br0.91.01.0
B · JSON / 英文 / gzip1.00.50.7
C · 纯文本 / 中文 / identity0.61.00.2
D · HTML / 英文 / gzip0.90.50.7
三个维度的 q 各自只在本首部内部可比；表里的分数是下一页相乘的原料。
例子 · 结论

相乘排序，选出 A 并写出响应

表示综合分（相乘）排序
A · HTML / 中文 / br0.9 × 1.0 × 1.0 = 0.9001（最优）
B · JSON / 英文 / gzip1.0 × 0.5 × 0.7 = 0.3502
D · HTML / 英文 / gzip0.9 × 0.5 × 0.7 = 0.3153
C · 纯文本 / 中文 / identity0.6 × 1.0 × 0.2 = 0.1204
HTTP/1.1 200 OK Content-Type: text/html; charset=utf-8 Content-Language: zh-CN Content-Encoding: br Vary: Accept, Accept-Language, Accept-Encoding （主体：经 Brotli 压缩后的字节）
选中的表示 A：三个描述首部说清「是什么表示」「怎么压的」，Vary 告诉缓存下次按哪些请求首部匹配。
B 的媒体类型 q 是全场最高的 1.0 却不是最优：协商是多维度同时求满意，不是挑单项最高分。
专题 · 编码分层

内容编码是里层，传输编码是外层

flowchart LR A["原始 HTML"] --> B["gzip 压缩 内容编码"] --> C["chunked 分块 传输编码"] --> D["线上传输"] --> E["先去块拼回"] --> F["再 gzip 解压"]
对比项内容编码（Content-Encoding）传输编码（Transfer-Encoding）
作用对象资源主体，是表示本身的一部分报文主体，这一跳的承载形式
作用范围端到端，中间节点不得改变逐跳，每跳可解开再重新编码
协商首部Accept-EncodingTE
典型取值gzip、br、identity分块编码（Chunked Transfer Coding）即 chunked
口诀：内容编码是里层、端到端；传输编码是外层、逐跳。压文本，跳过已压缩的图片与视频。
例子 · 报文

gzip 与 chunked 叠加的完整响应

HTTP/1.1 200 OK Content-Type: text/html; charset=utf-8 Content-Encoding: gzip Transfer-Encoding: chunked Vary: Accept-Encoding 1A3F 十六进制块长 等于十进制 6719 字节 第一块 gzip 字节流 后跟 CRLF 0C80 十六进制块长 等于十进制 3200 字节 第二块 gzip 字节流 后跟 CRLF 0 最后一块 长度为零 表示数据结束
gzip 与 chunked 叠加：没有 Content-Length，每块以十六进制长度开头，1A3F 是 6719、0C80 是 3200，共 9919 字节；长度为 0 的块收尾。
注意：Content-Length 与 chunked 同时出现是错误配置；发送端先 gzip 压缩再切块，接收端先去块拼回字节流再 gzip 解压，顺序正好镜像。
例子 · 推演

Vary 参与缓存键：正确情形五步

GET /page HTTP/1.1 Host: example.com Accept-Encoding: br, gzip HTTP/1.1 200 OK Content-Encoding: br Vary: Accept-Encoding Cache-Control: max-age=3600
客户端 A 的请求与响应：源站选中 br，用 Vary: Accept-Encoding 声明这个选择依赖请求里的 Accept-Encoding。
步骤发生了什么缓存键 / 结果
① A 请求到达带 br, gzip，缓存里无副本未命中，转发源站
② 源站返回选 br，带 Content-Encoding 与 Vary缓存读出 Vary，键要含该首部
③ 缓存存副本按 URL 加 Vary 首部当前值登记键 =（/page, br, gzip）存 br
④ B 请求到达只带 gzip键不同 → 未命中
⑤ 各取所需B 转发源站取 gzip 并按自己的键存A 命中 br，B 命中 gzip
缓存键（Cache Key）原本常只用 URL；有了 Vary，键变成「URL + 该请求在 Vary 首部上的取值」。
例子 · 故障链

漏写 Vary：把 br 响应错发给只认 identity 的客户端

GET /page HTTP/1.1 Host: example.com Accept-Encoding: identity HTTP/1.1 200 OK Content-Encoding: br Cache-Control: max-age=3600 （这份响应的 Vary 首部缺失）
客户端 C 只声明接受 identity，却从缓存拿到一份 Content-Encoding: br 的响应，因为它对不上该用哪一版。
故障步骤发生了什么后果
① 源站出错返回 br 表示却不写 Vary缓存不知道它依赖 Accept-Encoding
② 按 URL 存键只有 /page，没有编码维度br 被登记成唯一答案
③ C 请求到达只认 identity，明说不会解 br算出键命中那份 br 副本
④ 错发给 C把 br 字节流发给不认识 br 的客户端无法解压，页面乱码或报错
⑤ 污染持续错误副本在 max-age 内一直被命中所有不接受 br 的用户都中招
专题 · 判定表

UA 检测 vs 特性检测 vs 客户端提示

要解决的问题UA 字符串检测特性检测客户端提示推荐做法
浏览器是否支持某 API猜版本，极易误判直接探测能力，最准不适用特性检测
按屏幕宽度或 DPR 选图猜机型，不可靠脚本晚一步Width、DPR 精确可用Client Hints
用户偏好减少动画完全猜不到能查但太晚Sec-CH-Prefers-Reduced-MotionClient Hints 加 Critical-CH
网络慢、想省流猜不到不适用Save-Data、ECT、DownlinkClient Hints
修某版本特定 bug唯一勉强合理处未必可行不针对 bugUA 检测，尽快淘汰
区分手机与桌面找 Mobi，有假阳性不适用Sec-CH-UA-Mobile 更干净响应式优先，其次 Client Hints
用户代理（User-Agent）字符串会互相劫持标记、可被伪造、还会被冻结精简；特性检测（Feature Detection）只回答能不能用，不回答你是谁；客户端提示（Client Hints）让服务器按能力索取。
判定顺序：先问是不是探测功能，再问是不是服务器响应前就要的能力信息，最后才考虑 UA 检测。
例子 · 报文

Client Hints：按能力而不是按浏览器选图

GET /hero.webp HTTP/1.1 Host: shop.example Width: 400 DPR: 2 Sec-CH-UA-Mobile: ?1 Width 是 CSS 像素下的资源宽度，DPR 是设备像素比，问号一表示是移动设备
客户端按上一轮的 Accept-CH 带回能力提示：没有一句我是某品牌某浏览器，只报出这次要展示的资源宽度与屏幕像素密度。
400 CSS 像素 × DPR 2 = 800 物理像素 → 选 800 像素宽的 WebP
响应带 Vary: Accept, Width, DPR 让缓存分版本存；换个品牌只要能力值相同结果就一样。Downlink、RTT 这类变化频繁的网络提示不宜放进 Vary。
推导

四步为什么：从选表示到拆包装

① 为什么不能按网址直接取一份固定文件：资源与表示分离，同一 URL 对应多种表示，先承认这一点才有得选。

② 为什么可用各维度 q 相乘择优：偏好分三个首部各自声明、只在内部可比，相乘把多维度满意度压成一个可排序分数。

③ 为什么 Vary 必须进缓存键：缓存只认键，键里不含协商首部就会把一种表示错发给另一种客户端。

④ 为什么先去块再解压：传输编码是最外层包装，没拼回连续字节流就无法 gzip 解压

规范对照

MDN 的说法 → RFC 怎么写 → 为什么值得知道

MDN 的说法RFC 怎么写为什么值得知道
内容协商为同一 URI 选一种表示，服务器驱动是标准方式RFC 9110 §12 总体框架，§12.1 区分资源与表示资源可有多种表示是协议层事实，不是某服务器特性
Accept 系列用 q 值表达偏好，q=0 表示不接受RFC 9110 §12.4 质量值，§12.5.1 媒体范围匹配与通配优先最具体者优先是规范要求，实现算法要照它定次序
identity 默认可接受，Content-Encoding 声明怎么解码RFC 9110 §12.5.3 与 §8.4解释不写 identity 也不会拒收不压缩的表示
Vary 列出参与协商的请求首部，缓存分版本存副本RFC 9111 §4.1 用 Vary 计算缓存键漏写 Vary 在规范层面就是不完整的键，属正确性缺陷
客户端提示让服务器用 Accept-CH 按需索取信息RFC 8942 定义 Accept-CH 与提示首部框架知道哪些提示需索取、哪些默认可发，理解隐私权衡
chunked 在长度未知时按块传输，不与 Content-Length 同用RFC 9112 §6.1 与 §7，TE 优先于 Content-Length分块边界问题去 HTTP/1.1 语法文档找规则
MDN 说怎么做，RFC 说什么算对；语义写在 9110 与 9111、与版本无关，chunked 的字节格式写在 9112。
避坑

三个把层次混为一谈的误解

❌ q 值可跨首部比较，q=0 是优先级最低
✅ q 只在同一个首部内部有意义，q=0 是明确拒绝，服务器不该返回该表示。
❌ gzip 与 chunked 都是压缩，作用一样
✅ gzip 是内容编码、端到端改表示字节；chunked 是传输编码、逐跳只管定界；Content-Length 与 chunked 同时出现自相矛盾。
❌ Vary 是客户端发的请求首部，漏写只是优化不足
✅ Vary 是响应首部，由服务器发出；漏写会让缓存用不完整的键错发表示，是正确性缺陷。
