主线

一次改道的五环因果链

1请求一个旧地址：资源可能已经搬走
2服务器返回 3xx：不交资源，请客户端去别处
3Location 指向新地址：回答去哪
4按状态码决定是否改写方法：本讲最该盯住的判据
5客户端重新发起请求：换地址重投一次
6地址互相指回无法收敛：形成重定向死循环
caption 口径：黄色节点是方法是否被改写的判据，红色节点是地址首尾相接的死循环。
动机

书签、收录与外链，你一个都改不了

🙂 过于省事的想法
旧地址直接回 404，站点重构就算完成。
🤔 解释不了的现实
用户书签、搜索收录、别人网站的外链都指旧地址，改不动。
💡 本讲方案：旧地址回一条「搬家了，去新地址拿」的响应，让旧链接继续可用。
除额外一次往返的性能损失外，重定向对用户不可见，地址栏最终显示新地址。
定义

3xx + Location：状态码决定怎么办，首部只答去哪

类别状态码核心暗示
永久重定向301、308原 URL 作废，爬虫更新收录，默认可长期缓存
临时重定向302、303、307资源暂时不在标准地址，爬虫不记录新地址
特殊重定向300、304让你选或用本地缓存，不是去另一个地址
决定「重定向之后怎么办」的是状态码，不是 Location
Location 只回答去哪；状态码回答永久还是临时、方法要不要保留——后者是事故总根源。
例子 · 报文

一条最小的重定向响应长什么样

HTTP/1.1 301 Moved Permanently Date: Mon, 16 Nov 2026 00:30:00 GMT Location: https://www.example.com/articles/42 Content-Length: 0 空行之后通常没有可渲染的主体
状态行给出 301 与原因短语，Location 给出新地址；浏览器不渲染它，而是朝新地址再发一次请求。
这等于把用户原本的请求「照原样、换个地址」重投一次；用户除多一次往返外毫无察觉。
例子 · 判定表

POST /submit 经五个状态码后的方法判定

状态码类别POST 后方法主体MDN 口径
301永久通常改 GET丢失规范无意改，用户代理常改
302临时通常改 GET丢失规范无意改，用户代理常改
303临时明确改 GET明确丢失用于 POST 完成后防刷新重复提交
307临时保持 POST保留方法与主体都不变，优于 302
308永久保持 POST保留方法与主体都不变，永久重组
分水岭：303 明确改 GET、307/308 明确保持，301/302 规范说不该改而现实常改，最不可靠。
例子 · 报文

301 / 302 / 303：三条带 Location 的响应

HTTP/1.1 301 Moved Permanently Location: https://www.example.com/submit-v2 Cache-Control: max-age=3600 Content-Length: 0 HTTP/1.1 302 Found Location: https://www.example.com/submit-temp Cache-Control: no-store Content-Length: 0 HTTP/1.1 303 See Other Location: https://www.example.com/order/42/done Cache-Control: no-store 随后浏览器发出 GET /order/42/done，方法已改为 GET，主体为空
301/302 下多数客户端把随后的 POST 改为 GET、原主体丢失；303 明确改 GET，构成 PRG 模式。
例子 · 报文

307 / 308：严格保持方法与主体的响应

HTTP/1.1 307 Temporary Redirect Location: https://www.example.com/submit-new Cache-Control: no-store Content-Length: 0 随后浏览器发出 POST /submit-new，主体仍为 name=alice&city=sz HTTP/1.1 308 Permanent Redirect Location: https://api.example.com/v2/submit Cache-Control: max-age=86400 Content-Length: 0 随后浏览器发出 POST /v2/submit，主体仍为 name=alice&city=sz
307/308 明确要求方法与主体都不变；选择指南：要保方法用 307/308，要改 GET 用 303。
专题 · 手算

Location 的六种相对值，逐一解析成绝对 URL

基准 https://www.example.com/docs/guide/intro.html Location: /new/guide.html → https://www.example.com/new/guide.html Location: ./next.html → https://www.example.com/docs/guide/next.html Location: ../index.html → https://www.example.com/docs/index.html Location: ?page=2 → https://www.example.com/docs/guide/intro.html?page=2 Location: #section-3 → https://www.example.com/docs/guide/intro.html#section-3 Location: //cdn.example.com/a.css → https://cdn.example.com/a.css
以基准各组成部分为参照，套用「scheme → authority → 绝对 path → 相对 path → query/fragment」优先级得到右侧目标。
术语首现：相对 URL（Relative URL）；解析按 RFC 3986 引用解析算法，不是字符串拼接。
专题 · 手算

四条判据与六种结果的逐条依据

相对值判据推导与结果
/new/guide.html绝对 path以斜杠开头，直接替换整个 path
./next.html相对 path去末段得 /docs/guide/，拼接消点段
../index.html相对 path消掉点点段回退一级，得 /docs/index.html
?page=2只带 query引用 path 为空，path 沿用基准只换 query
#section-3只带 fragment其余沿用基准，仅追加片段
//cdn.example.com/a.css带 authority沿用 https，换成 cdn.example.com
fragment 一律不沿用基准，query 在引用 path 为空时才沿用基准；双斜杠是协议相对 URL 的历史写法。
专题 · 故障链

误配 301 被长期缓存：修好了却仍跳失效目标

GET /sale HTTP/1.1 Host: old.example.com HTTP/1.1 301 Moved Permanently Location: https://new.example.com/sale Cache-Control: max-age=31536000 Content-Length: 0
本意只是临时导流，却用了 301 并给出长达一年的缓存时间。
1误配：/sale 被发成 301 加一年 max-age
2缓存：发请求前就命中跳转，旧服务器收不到请求
3改回 200 仍无效：残留缓存跳到已下线目标，看到 404
4症状在客户端：服务端日志里旧地址一条请求都没有
专题 · 故障链

误配 301 的四条清除手段与四条预防手段

🧹 清除 4 条
DevTools 禁用缓存重试；清站点缓存与站点数据；CDN/代理 purge；换全新 URL 如 /sale-v2 绕开。
🛡 预防 4 条
确定永不回头才用永久；拿不准先用 302 观察再升级；设置真正想要的 Cache-Control；上线前 curl -I 核对。
判定规则：这个新地址，我愿不愿意让搜索引擎和浏览器记一年？愿意才用永久。
永久重定向被缓存后客户端不再来问，所以「修好了却仍跳旧的」不是配置没生效，而是缓存残留。
专题 · 环路

A → B → C → A：四次请求响应序列

第 1 次请求 GET /a HTTP/1.1 Host: site.example 响应 HTTP/1.1 302 Found，Location: /b 第 2 次请求 GET /b HTTP/1.1 响应 HTTP/1.1 302 Found，Location: /c 第 3 次请求 GET /c HTTP/1.1 响应 HTTP/1.1 302 Found，Location: /a 第 4 次请求 GET /a HTTP/1.1 响应 HTTP/1.1 302 Found，Location: /b 如此往复，永远等不到一个 2xx
每一跳都是合法的 302 加 Location，但地址首尾相接，重发链无法收敛到任何资源。
专题 · 环路

两种发现方式、用户可见错误与定位打破

环节内容
服务器可检测同一台服务器发现路径回到已访问地址，返回 500
服务器检测不到跨多台服务器时由浏览器跟踪重复地址或超过跳转上限，中止并报错
用户可见错误Firefox 报无限循环重定向，Chrome 报该网页将你重定向的次数过多
定位curl -I -L 跟每一跳，画地址到目标的有向图找环
打破清冲突的 meta 与 JS、修正协议跳转方向、purge 陈旧缓存
常见成因：http 与 https 互跳写反、HTTP/meta/JS 三处目标不一致、陈旧永久缓存与当前配置打架。
推导

一次重定向就是把三阶段再走一遍

① 第 1 讲的三阶段：建立连接 → 客户端发送请求并等待应答 → 服务器处理并返回响应；之后连接关闭或复用。

② 重定向插在哪：客户端发请求（阶段二）后，服务器不交资源，用 3xx 加 Location 回一条「去别处」。

③ 开启新一轮：换了主机要重新建连，再发请求并等待、服务器再返回响应——三阶段再走一遍。

成环 = 三阶段被卡在中间，永远走不到终点

规范对照

MDN 的说法 / RFC 怎么写 / 为什么值得知道

MDN 的说法RFC 怎么写为什么值得知道
3xx 需进一步动作，Location 给目标RFC 9110 第 15.4 节定义 3xx；第 10.2.2 节 Location 是 URI 引用「进一步动作」是规范性定义，URI 引用才知相对解析必须按算法
301/302 无意改方法，307/308 消除歧义第 15.4.2/15.4.3 节 MAY 允许改 GET；15.4.7/15.4.8 节 MUST NOT 不得改方法MAY 与 MUST NOT 强度不同，实现客户端必须照此办理
303 用于 POST 完成后防刷新重复提交RFC 9110 第 15.4.4 节指示用 GET 或 HEAD 取目标「改 GET」是规范要求，可放心用于 PRG 模式
浏览器会缓存永久重定向RFC 9111 第 3 节可缓存性、第 4 节新鲜度，301/308 默认可长期存储能用 Cache-Control 精确控制，理解误配 301 为何长期作祟
互相指向成环，浏览器负责检测RFC 9110 第 15.4 节首段 SHOULD detect 检测无限循环SHOULD 解释了各浏览器阈值与文案不同，检测责任在客户端
MDN 说「通常」「建议」处，规范里往往藏着 MAY / SHOULD / MUST 的精确分级。
避坑

三个把方法、缓存与层数混为一谈的误解

❌ 重定向方法无所谓
✅ 给接收 POST 的回调配 302，可能被改 GET，参数跑到 URL、服务端收不到数据；保方法要用 307/308。
❌ 把 301 改回 302，用户马上走新配置
✅ 缓存旧 301 的浏览器不再问服务器，修改对它们无效，收录更新以周计。
❌ HTTP 跳转再加 meta 或 JS 做双保险
✅ HTTP 永远先触发，两处目标不一致互相指回就成无限循环，只在 HTTP 层做一处。
