课程 · 定位

这门课练的是「读懂协议」，不是「记住词条」

✅ 要练会的三件事
逐行读懂报文；判断故障出在哪一层；查到规范条文。
❌ 不做的三件事
不讲框架 API；不背状态码表；不做协议考古。
面向：写过代码、调过接口，但没系统读过协议的人。不需要会运维，也不需要数学。
判断标准：拿到一条 curl 的详细输出，你能不能逐行说清它在干什么。
课程 · 设计思路 ①

组织法决定了知识有没有地方挂

组织法顺序依据学习时的毛病
照 RFC 章节定义无歧义概念互相引用，第一页就撞上未定义术语
照协议史时间线大量篇幅给已退场的实现，今天用不上
照接口清单字母或分类记住一堆词，遇到组合问题仍不会判断
本课程一次请求的三阶段每讲都是往骨架上插一条规则
MDN 22 篇是「查询式」的，一篇解决一个问题；课程要改成「递进式」，于是合并为 12 讲、分 4 组。

第 1 讲是全课骨架，不是第一个知识点

flowchart LR A["第1讲 会话骨架"]:::here --> B["第2到3讲 报文与表示"] --> C["第4到6讲 连接与缓存"] --> D["第7到10讲 状态与安全"] --> E["第11到12讲 中间层与重定向"] classDef here fill:#2b6cb0,color:#ffffff,stroke:#1a365d,stroke-width:3px

本讲解决「命名」：把一次会话切成能指认的阶段，后面十一讲才有挂载点。

本讲对应的 MDN 原文：Overview / Session / Evolution of HTTP。
主线

一次会话的五环因果链

1用户想看某个资源：输入一个 URL
2名字要变成可连接的目标：DNS → TCP → TLS
3HTTP 才登场：客户端发请求，服务器回响应
4页面要取很多子资源：连接被复用
5无状态留下债：登录和购物车要另外造状态
这条链就是本讲目录：链路 → 事务 → 演进 → 状态难题。
动机

「发个请求、回个页面」解释不了四种常见现象

🙂 过于简略的解释
浏览器发请求，服务器回页面。能说通一次点击，但仅此而已。
🤔 解释不了的四个问题
刷新为何变快；手机为何收到压缩表示；换网络为何卡在证书；关掉页面为何还认得你。
💡 本讲方案：把这次点击拆成连接建立 / 事务交换 / 复用收尾三段，每段指定负责的对象。
定义

HTTP 在应用层：每层只解决一类问题

🧱 下层负责字节
IP 找机器，TCP 保证不丢不乱，TLS 保证不被偷看与篡改。
📨 HTTP 负责语义
方法、请求目标、首部、状态码、主体，以及无状态这条约定。
请求由客户端发起 · 响应由服务器返回 · 协议不记上一次
读法：下层不知道什么是资源，上层不关心字节怎么走；故障定位先判断坏在哪一层。
定义

URL 指向资源，响应发回的是表示

概念是什么由谁说明
资源 Resource被 URL 命名的对象请求目标
表示 Representation这次真正发回的字节Content-Type / Content-Encoding
偏好客户端想要哪种表示Accept 系列首部
缓存里存的是表示，不是抽象资源；漏写 Vary 就会把一种表示发给要另一种的客户端。
例子 · 报文

一次事务 = 一段请求 + 一段响应

GET /docs/guide HTTP/1.1 Host: www.example.com Accept: text/html User-Agent: DemoClient/1.0 空行之后没有主体
请求：起始行 + 若干首部 + 空行 + 可选主体；空行是首部结束的唯一标志。
HTTP/1.1 200 OK Content-Type: text/html; charset=UTF-8 Content-Length: 17 Cache-Control: max-age=3600 <p>Hello HTTP</p>
响应：状态行 + 首部 + 空行 + 主体；主体正好 17 字节，与 Content-Length 一致。
例子 · 逐行

每一行都有职责，空行和长度最容易出事

行职责写错会怎样
GET /docs/guide HTTP/1.1方法 / 目标 / 版本目标形式错，代理无法转发
Host指定虚拟主机同 IP 多站点时会落到默认站
空行首部结束标志解析错位，主体被当成首部
Content-Length: 17主体定界写大等到超时，写小粘下一条
口诀：起始行定动作，首部定条件，空行定边界，长度定主体。
推导

三阶段：建连 → 发请求并等待 → 返回响应

① 建立连接：DNS → TCP 三次握手 → TLS 握手；此时还没有 HTTP 字节。

② 客户端发送请求并等待：起始行、首部、空行、可选主体；发完即进入等待。

③ 服务器处理并返回响应：状态行、首部、空行、主体按顺序回传。

三阶段走完后：复用连接取子资源，或关闭连接

链路

每层只解决一个问题，故障才能定位

flowchart LR A["输入网址"] --> B["DNS 得到 IP"] --> C["TCP 三次握手"] --> D["TLS 协商密钥"] --> E["HTTP 请求与响应"] --> F["解析并渲染"]
层解决的问题典型故障
DNS / TCP找到机器、可靠传字节首开慢、连接超时
TLS防偷看与篡改证书告警
HTTP资源、表示、结果404、304、跨域被拦
演练

读一段响应，自己把边界数出来

HTTP/1.1 200 OK Content-Type: text/html; charset=UTF-8 Content-Length: 17 Cache-Control: max-age=3600 <p>Hello HTTP</p>

① 首部共 3 行，空行在 Cache-Control 之后，主体从下一行开始。

② 主体 17 字节 与 Content-Length 一致，接收方读完即结束，不会多等。

③ 请求必须带 Host：同一 IP 可能托管多个站点，服务器靠它选虚拟主机。

状态

无状态是优点，会话是后来造出来的

手段放在哪解决的问题哪一讲展开
Cookie请求首部每次把标识带回来第 7 讲
认证挑战响应证明标识属于谁第 8 讲
会话存储服务端或客户端保存真正的内容第 7 讲
无状态带来的红利：任意服务器可处理任意请求，中间层可转发与缓存，扩容不必同步会话。
演进

换的是地基，房子没换

版本关键变化变的是哪层
HTTP/0.9单行 GET，只有 HTML报文形态
HTTP/1.0首部、状态码、版本、MIME语义扩充
HTTP/1.1Host 必需、持久连接、管道化连接与语义
HTTP/2二进制帧、多路复用、首部压缩编码
HTTP/3传输层换成 QUIC传输
不变的：方法、状态码、首部语义、缓存模型。所以本讲建立的骨架到 HTTP/3 仍然成立。

避坑

三个把不同层次混为一谈的误解

❌ 无状态 = 每次都新建连接
✅ 无状态指服务器不记上次请求；连接复用是传输与连接管理的事，HTTP/1.1 默认复用。
❌ 本机测试能通，Host 可以省
✅ 同 IP 多站点时服务器靠 Host 选虚拟主机，缺了它只会落到默认站。
❌ HTTP/2 改了方法和状态码的含义
✅ 换的是二进制帧与多路复用，方法、状态码、首部语义基本不变。
