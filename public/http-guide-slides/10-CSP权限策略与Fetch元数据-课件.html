主线

一条五环因果链：下发策略，再拦自己

1服务器下发策略首部：CSP 与 Permissions-Policy 随响应到达
2浏览器解析 CSP 指令：给脚本、样式、图片、连接立白名单，拦违规加载
3权限策略限制 API：第三方 iframe 能否用摄像头由允许列表决定
4Fetch 元数据说明来源：请求自带上下文，服务器据此挡 CSRF
5配置过严先把自己拦在门外：策略必须先用仅报告模式试运行
这条链就是本讲目录：下发 → 解析 → 限制能力 → 自证来源 → 谨慎上线。
动机

净化是容易漏的第一道防线，还需要第二道

😨 攻击现场
评论区允许留 HTML，过滤百密一疏，注入脚本就在站点上下文里执行，拿到 cookie 与权限。
🛡 两道防线
净化输入是第一道；CSP 是第二道——即使代码混进来了，也让它跑不起来。
<script src="https://evil.example.com/hacker.js"></script> <script>console.log("你已被入侵")</script> <img onmouseover="..." src="thumb.jpg" />
外链脚本、内联脚本、内联事件处理器，三种伪装任漏一种就出事。这正是跨站脚本攻击（Cross-site scripting，XSS）的入口。
💡 本讲方案：用响应首部给页面立一份白名单，把能加载什么、能调用什么写死在浏览器里。
定义

三套策略，方向不同但都借首部下发

📜 内容安全策略（Content Security Policy，CSP）
由一串指令（directive）组成的白名单，控制文档能加载与执行哪些资源，主防跨站脚本。
🎛 权限策略（Permissions Policy）
限制页面与第三方 iframe 能调用哪些 API，比如摄像头、全屏、地理定位。
CSP 管「能加载什么」· 权限策略管「能按哪些按钮」· Fetch 元数据（Fetch metadata）让请求「自证来源」
三者都借 HTTP 首部这个通用载体：前两者是服务器发给浏览器的约束，第三个是浏览器回给服务器的线索。
例子 · 报文

一条完整 CSP，六条指令逐条拆

HTTP/1.1 200 OK Content-Type: text/html; charset=utf-8 Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-416d1177-4d12-4e3b-b7c9-f6c409789fb8'; style-src 'self'; img-src 'self' example.com; connect-src 'self'; report-uri /csp-report
为便于阅读折成多行，真实首部是一行、指令间用分号隔开。前五条是 Fetch 指令（fetch directive），最后一条把违规送到 /csp-report。
指令允许的来源解读
default-src 'self'仅同源兜底，没单列的类型都只准同源
script-src 'self' nonce同源脚本或带匹配 nonce 的标签覆盖脚本后备，放行特定内联脚本
style-src 'self'仅同源样式表不继承 script-src 的 nonce
img-src 'self' example.com同源图片加 example.com单独给图片开外部域名
connect-src 'self'仅同源连接挡住 fetch 把数据外传
report-uri /csp-report上报端点不参与放行判定
例子 · 推演

同一段内联脚本，三种凭据三种命运

<script>console.log("你好")</script> 情形一：无 nonce、无散列 → 被拦截 <script nonce="416d1177-4d12-4e3b-b7c9-f6c409789fb8">...</script> 情形二：带匹配 nonce → 放行 script-src 'sha256-H/eahVJiG1zBXPQyXX0V6oaxkfiBdmanvfG9eZWSuEc=' 情形三：内容散列匹配 → 放行
策略含 script-src 时，内联 JavaScript 默认不允许执行；nonce 与散列（hash）是不放开 unsafe-inline 的两条合法通道。
情形凭据判定与前提
无凭据无拦截：内联默认禁止，并生成违规报告
加 nonce每次响应随机、不可预测放行：首部与标签一致，需动态生成页面
用 sha256 散列脚本内容的 Base64 散列放行：内容不变则散列不变，适合静态站点
专题 · 判定

把脚本能不能跑，画成三步

flowchart TD A["浏览器准备执行一段脚本"] --> B["查有没有脚本相关指令"] B --> C["没有指令则正常执行"] B --> D["有指令则检查三种凭据"] D --> E["同源外部或带匹配凭据则放行"] D --> F["都不满足则拦截并生成违规报告"]
判断三步：先看有没有 script-src 或兜底的 default-src；没有就放行，有再看是不是同源外部脚本、带匹配 nonce、或散列匹配；都不满足就拦。
CSP 是纵深防御：MDN 反复强调它不能替代输入净化，正确姿势是净化加上 CSP 双管齐下。
例子 · 报文

一份违规报告，八个字段逐字段读

POST /csp-report HTTP/1.1 Content-Type: application/csp-report { "csp-report": { "document-uri": "https://example.com/post/1", "referrer": "https://www.google.com/", "violated-directive": "script-src 'nonce-416d1177-4d12-4e3b-b7c9-f6c409789fb8'", "effective-directive": "script-src-elem", "original-policy": "default-src 'self'; ...", "blocked-uri": "inline", "status-code": 200, "script-sample": "console.log(...)" } }
由 report-uri 上报、以 application/csp-report 类型 POST 的违规报告（violation report）。浏览器把在哪一页、违反哪条指令、被拦的是什么、策略原文打包送回。
字段含义
document-uri发生违规的文档地址，定位到 /post/1
referrer来源页，这里来自 Google 搜索
violated-directive被违反的指令及其值
effective-directive实际拦下资源的指令 script-src-elem
original-policy触发违规时的完整策略原文
blocked-uri被拦资源，inline 表示内联脚本
status-code被保护文档的状态码 200
script-sample被拦代码的前若干字符
例子 · 对照

report-uri 与 report-to，两代上报

Reporting-Endpoints: csp-endpoint="https://example.com/csp-reports" Content-Security-Policy: default-src 'self'; report-to csp-endpoint Content-Type: application/reports+json
report-to 不直接写 URL，而是引用报告 API（Reporting API）里 Reporting-Endpoints 预先命名好的端点；新的报告类型是 application/reports+json。
维度report-uri 老report-to 新推荐
端点声明指令值直接是 URL先声明命名端点再引用名字
Content-Typeapplication/csp-reportapplication/reports+json
JSON 结构单个 csp-report 对象，连字符字段带 type、url、age、user_agent 的信封，详情在 body 里驼峰命名
状态MDN 标注已弃用基于报告 API 的推荐方式
迁移建议逐步退场过渡期与 report-uri 同时声明，两种都收
例子 · 判定表

父页策略配 iframe allow，逐项判能不能用

Permissions-Policy: camera=(self), fullscreen=(self "https://partner.example"), geolocation=() <iframe src="https://partner.example" allow="camera *; fullscreen *; geolocation 'self'"></iframe>
父页对摄像头只放行同源、全屏放行同源与 partner.example、地理定位全局禁用；iframe 来自 partner.example，allow 三项都想要。
特性父页allow判定
摄像头 camera(self)*不可用：跨源不在父页列表，allow 再宽也越不过
全屏 fullscreen(self 及 partner)*可用：两边交集含该源
地理定位 geolocation()'self'不可用：父页空列表禁用，单向不可覆盖
专题 · 规则

允许列表五种取值，还有一条继承铁律

取值含义能否组合
星号本文档及所有嵌套 iframe 都可用只能单独用
空括号顶层与嵌套环境全禁用只能单独用
self仅本文档与同源 iframe可与具体源组合
src与 iframe 的 src 同源即可，仅用于 allow可与具体源组合
具体源如 https://a.example.com可与 self、src 组合
最终权限 = 父页允许列表与 iframe allow 的交集，且任一方的显式禁用不可被覆盖
允许列表（allowlist）之外更要紧的是继承：所有 iframe 继承父页策略；子框架被父框架禁用的特性不能重新启用，它的后代也不能，禁用是单向的。
例子 · 报文

四个 Sec-Fetch 首部，让请求自证来源

GET /home HTTP/1.1 Sec-Fetch-Site: none Sec-Fetch-Mode: navigate Sec-Fetch-Dest: document Sec-Fetch-User: ?1 用户在地址栏敲入网址，浏览器自动附加
用户直接发起的导航：Site 为 none、Mode 为 navigate、Dest 为 document、User 为 ?1。四个首部都由浏览器按真实上下文附加，属于禁止修改的请求首部（forbidden request header），JS 一个字都改不了。
首部回答什么主要取值
Sec-Fetch-Site请求方与资源的关系cross-site / same-site / same-origin / none
Sec-Fetch-Mode以什么模式发起navigate / no-cors / cors / same-origin
Sec-Fetch-Dest资源用在哪里document / image / script / empty
Sec-Fetch-User是否用户行为触发触发时恒为 ?1，否则不携带
例子 · 判定表

五种组合逐项判，资源隔离挡下 CSRF

场景SiteModeDestUser判定
地址栏输入银行网址nonenavigatedocument?1导航，放行
从 evil 点链接进银行cross-sitenavigatedocument?1跨站顶层导航，GET 放行
加载自家 logo 图片same-originno-corsimage无同源图片子资源，放行
evil 自动 fetch 转账cross-sitecorsempty无CSRF 写操作，拒绝
evil 自动提交表单cross-siteno-corsdocument无跨站表单提交，拒绝
资源隔离策略（resource isolation policy）：放行同源与用户直接发起的请求、以及跨站的 GET 导航，拒绝跨站的 POST 与脚本请求。跨站请求伪造（CSRF）靠 cookie 自动带上得逞，而 Sec-Fetch-Site 被浏览器标记成 cross-site、攻击者改不了。但不能拒绝全部跨源，否则外部链接跳不进来；缺首部的老浏览器按不可信处理，响应还要带 Vary。
推导

把资源隔离策略写成三步判定

① 先看 Sec-Fetch-Site：等于 same-origin 或 none 就放行——同源请求与用户直接发起的请求可信。

② 否则看是不是跨站顶层导航：Sec-Fetch-Mode 为 navigate 且方法是 GET，放行，好让外部链接能跳进来。

③ 其余一律拒绝：跨站 POST、cors 或 no-cors 的脚本请求、dest 为 empty 的请求，返回 403。

响应带上 Vary: sec-fetch-site, sec-fetch-mode，避免缓存串味

规范对照

MDN 的说法 → RFC 怎么写 → 为什么值得知道

MDN 的说法RFC 怎么写为什么值得知道
CSP 由 Content-Security-Policy 首部下发，一串分号分隔的指令规范是 W3C 的 CSP Level 3，不是 IETF RFC；RFC 9110 只定字段通用语法查指令语义去 W3C，别去找 RFC 编号
nonce 每个响应都要不同且不可预测CSP3 把 nonce source 与 hash source 定为正式语法，要求密码学强度随机用递增计数器当 nonce 直接违背规范
report-to 配合 Reporting-Endpoints，report-uri 已弃用report-to 由 W3C 报告 API 定义，report-uri 是 CSP2 老机制、CSP3 标记弃用两代格式不同，接收端要都能解析
权限策略允许列表有星号、空括号、self、src、具体源规范是 W3C 的 Permissions Policy，头语法与 iframe allow 不同是历史遗留src 只在 allow 里有效，头里没有
Sec-Fetch 是禁止修改的请求首部，由浏览器附加W3C 的 Fetch Metadata 定义取值算法；禁止修改由 Fetch 规范保证配合 Vary 用的是 RFC 9110 第 12.5.5 节的缓存机制
这些策略都由首部下发，写法看着和普通首部一样RFC 9110 第 5 节定字段名大小写不敏感、同名字段可合并、值用 ABNF 描述怎么写看 RFC 9110，写什么含义看对应 W3C 规范
一条判断原则：把字段怎么在网上传输与字段对浏览器意味着什么分开看——前者归 RFC 9110，后者分属三份 W3C 规范。
避坑

三个把机制混为一谈的误解

❌ 嫌麻烦就加 unsafe-inline 放行内联脚本
✅ 它会破坏 CSP 的大部分意义；而且指令里一旦出现 nonce 或散列，浏览器会忽略 unsafe-inline。
❌ 写了 report-to 就该收到报告
✅ 端点必须先用 Reporting-Endpoints 声明；两代 Content-Type 与 JSON 都不同，接收端得都能解析。
❌ 把三套策略当 RFC 去查，或拒绝全部跨源请求
✅ 它们是 W3C 规范；拒绝一切跨源会让外链跳不进来，跨站 GET 导航必须放行。
