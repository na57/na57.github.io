本讲处在第③组状态与安全：前面几讲解决服务器怎么认出用户，本讲划出浏览器允许跨源读取的边界。

主线

一条五环因果链：默认拒绝，再逐个开口子

1页面发起跨源请求：脚本想读另一个源的数据
2浏览器判断是否简单请求：方法、首部、媒体类型逐项过筛
3简单请求直接带 Origin：不预检，在响应阶段检查 ACAO
4非简单请求先发 OPTIONS 预检：问方法与首部，放行才发真实请求
5凭据与通配符冲突：带 Cookie 时 ACAO 必须具体且 ACAC 为 true
主线一句话：先用同源策略设默认拒绝，再由服务器首部逐个开口子；红色节点是带凭据场景里通配符失效的陷阱。
动机

请求到了、响应也回了，脚本却读不到

🙂 你以为会发生
在 app.shop.example 的页面里 fetch 天气接口，拿到 JSON 直接渲染到页面上。
🤔 实际发生
请求真的发到了 api.weather.example，服务器也回了 JSON，控制台却只留下一行模糊的报错。
💡 根因：出于安全，浏览器限制脚本发起的跨源 HTTP 请求，Fetch API 与 XMLHttpRequest 都遵循同源策略（Same-origin policy）。
请求没有被挡在门口，被挡的是「把响应交给脚本」这最后一步，这个区分是本讲的地基。
定义

源是三元组，CORS 只为「读」开一扇门

🧱 源（Origin）
两个 URL 的协议、主机、端口三项都相同才同源，合称协议主机端口元组；路径、查询串、片段一律不参与。
🚪 跨源资源共享（Cross-Origin Resource Sharing，CORS）
基于 HTTP 首部的机制，服务器声明哪些源可以加载自己的资源，浏览器据此决定是否共享响应。
跨源写一般允许 · 跨源嵌入一般允许 · 跨源读取默认被同源策略拦截
同源策略（Same-origin policy）只在一类交互上较真：脚本把另一个源响应的字节读进内存。CORS 正是为这一类开的受控口子。
例子 · 判定表

以 store.company.com 为基准，逐行比对三元组

候选 URL归一化元组判定逐项说明
http://store.company.com/dir2/other.html{http, store.company.com, 80}同源只有路径不同，路径不参与判定
http://store.company.com/dir/inner/another.html{http, store.company.com, 80}同源查询串与片段也同样不影响
https://store.company.com/secure.html{https, store.company.com, 443}跨源协议不同，默认端口随之变 443
http://store.company.com:81/dir/etc.html{http, store.company.com, 81}跨源端口不同，81 ≠ 80
http://news.company.com/dir/other.html{http, news.company.com, 80}跨源主机不同，news 与 store 是两个名字
http://store.company.com:80/dir/page.html{http, store.company.com, 80}同源显式 80 就是 http 默认端口，与省略等价
http://STORE.company.com/dir/page.html{http, store.company.com, 80}同源主机大小写不敏感，归一后小写再比
http://store.company.com.evil.net/x{http, store.company.com.evil.net, 80}跨源主机是完整字符串，多了 evil.net 就是另一台
基准元组 {http, store.company.com, 80}；三步归一：协议小写、主机小写、空端口补默认值（http=80，https=443）。
例子 · 对照

同源三元组 vs cookie 的 Domain 判定

比较维度同源判定cookie 的 Domain 判定
主机必须完全相等，子域与父域不同源可放宽到父域，shop.example.com 可设 Domain=example.com
协议严格比较，http 与 https 不同源不参与；不设 Secure 时 http 下发的 cookie 可能被 https 读到
端口严格比较，80 与 8080 不同源完全不参与，cookie 没有端口概念
路径完全不参与有独立的 Path 属性可缩小发送范围
父域边界无父域概念，一律不等受公共后缀列表约束，不能给 com 这种后缀设 cookie
一句话：同源是三元组严格相等，cookie 的 Domain 是本域或合法父域的包含关系；共享 cookie 不等于同源。
例子 · 报文

一个带 Origin 的简单跨源 GET 与它的响应

GET /v1/today HTTP/1.1 Host: api.weather.example User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) Accept: */* Accept-Language: zh-CN,zh;q=0.9 Accept-Encoding: gzip, deflate, br Connection: keep-alive Origin: https://app.shop.example （空行：首部结束，GET 无主体）
简单跨源 GET：最关键的是 Origin，由浏览器自动加上，只有协议主机端口、不带路径，脚本无法伪造。这类简单请求（simple request）不预检，直接抵达服务器。
HTTP/1.1 200 OK Date: Mon, 16 Nov 2026 01:05:00 GMT Server: nginx Access-Control-Allow-Origin: * Content-Type: application/json Content-Length: 29 Connection: keep-alive {"city":"shenzhen","temp":26}
服务器用 Access-Control-Allow-Origin 回答「谁可以读这份响应」。这里用 * 表示任意源，前提是请求不携带身份凭据。
例子 · 逐行

浏览器放行脚本的四步，与一张 ACAO 判定表

  1. 识别跨源：比较页面源与目标源，主机不同即跨源，自动附加 Origin。
  2. 判定是否预检：方法 GET、首部全在安全列表、无 Content-Type，不预检，请求直接抵达服务器。
  3. 做 CORS 检查：读响应 ACAO，星号且无凭据匹配成功；具体源须与 Origin 逐字符相等；缺失或不匹配即失败。
  4. 决定交给谁：成功才把响应体交给 fetch 的 Promise，脚本拿到 29 字节；失败则丢弃，脚本只收到笼统网络错误。
ACAO 响应值是否带凭据CORS 检查脚本能否读到
*否匹配成功能
https://app.shop.example否与 Origin 相等，成功能
https://other.example否与 Origin 不等，失败不能
首部缺失否无可匹配值，失败不能
*是失败，凭据与通配符冲突不能
脚本层看不到失败细节，唯一办法是查浏览器控制台；返回具体源时还要带 Vary: Origin，否则中间缓存会把给 A 源的响应端给 B 源。
例子 · 报文

OPTIONS 预检请求与它的 204 响应

OPTIONS /v1/forecast HTTP/1.1 Host: api.weather.example User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) Accept: */* Accept-Language: zh-CN,zh;q=0.9 Accept-Encoding: gzip, deflate, br Connection: keep-alive Origin: https://app.shop.example Access-Control-Request-Method: PUT Access-Control-Request-Headers: X-API-Key, Content-Type （空行：预检请求没有主体）
这趟 预检请求（preflight request）用 OPTIONS 先问方法与首部是否被允许；两行新首部是整场问答的核心，真实请求的路径只用于定位资源。
HTTP/1.1 204 No Content Date: Mon, 16 Nov 2026 01:06:00 GMT Server: nginx Access-Control-Allow-Origin: https://app.shop.example Access-Control-Allow-Methods: PUT, GET, OPTIONS Access-Control-Allow-Headers: X-API-Key, Content-Type Access-Control-Max-Age: 86400 Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers Connection: keep-alive （204 响应无主体）
预检响应把「源、方法、首部、缓存时长」四项一次答齐。Max-Age 是 86400 秒即 24 小时，默认只有 5 秒；ACAO 给具体源而不是 *，因为真实请求要带自定义首部。
例子 · 逐行

两问四答：把预检的每个首部对上号

首部出现在问什么 / 答什么
Access-Control-Request-Method预检请求问：真实请求将用 PUT，语法是单个方法值
Access-Control-Request-Headers预检请求问：将带哪些非安全首部，逗号分隔，此处 X-API-Key 与 Content-Type
Access-Control-Allow-Origin预检响应答：可读的源限定为 https://app.shop.example
Access-Control-Allow-Methods预检响应答：允许 PUT、GET、OPTIONS，类似 Allow 但带访问控制含义
Access-Control-Allow-Headers预检响应答：正是对 ACRH 的回应，列出 X-API-Key 与 Content-Type
Access-Control-Max-Age预检响应答：结果可缓存 86400 秒，默认 5 秒，且受浏览器上限约束
Vary预检响应把 Origin 与两项请求首部写进缓存键，避免串味
读预检记「两问四答」：两问是 ACRM 与 ACRH，四答是 ACAO、Allow-Methods、Allow-Headers、Max-Age。缺一项或不匹配，真实请求就不会发出。
例子 · 报文

预检放行后的真实 PUT 与它的响应

PUT /v1/forecast HTTP/1.1 Host: api.weather.example User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) Accept: */* Accept-Language: zh-CN,zh;q=0.9 Content-Type: application/json Content-Length: 28 Origin: https://app.shop.example X-API-Key: demo-7f3a {"city":"shenzhen","days":3}
预检通过后的真实 PUT：方法、自定义首部与 JSON 主体原样发出，Origin 仍在，但两个 Access-Control-Request 首部已消失。
HTTP/1.1 200 OK Date: Mon, 16 Nov 2026 01:06:01 GMT Server: nginx Access-Control-Allow-Origin: https://app.shop.example Vary: Origin Content-Type: application/json Content-Length: 23 Connection: keep-alive {"ok":true,"updated":3}
真实请求的响应同样要做一次 CORS 检查：ACAO 与 Origin 匹配，脚本才能读到结果。预检放行不等于真实响应自动放行，两道检查各做各的。
例子 · 流程

CORS 两条路径：一个在响应阶段拦，一个更早拦住真实请求

flowchart LR A["页面发起跨源请求"] --> B{"是否命中预检条件"} B -->|否 简单请求| C["直接发送并携带 Origin"] B -->|是 非简单请求| D["先发 OPTIONS 预检"] D --> E{"预检响应是否放行方法与首部"} E -->|否| F["真实请求不发出 脚本收到笼统错误"] E -->|是| G["发送真实请求"] C --> H{"ACAO 是否匹配 Origin"} G --> H H -->|否| F H -->|是| I["响应体交给脚本"]
图 9.3 CORS 两条路径：简单请求在响应阶段检查，非简单请求多一道 OPTIONS 关卡；任一检查失败，脚本都只能看到笼统错误。
例子 · 报文

带凭据的跨源 GET：具体源 ACAO 加 ACAC 为 true

GET /v1/account HTTP/1.1 Host: api.weather.example Accept: */* Connection: keep-alive Referer: https://app.shop.example/ Origin: https://app.shop.example Cookie: session=abc123 （空行：GET 无主体）
带凭据的跨源 GET：Cookie 是浏览器在 credentials 设为 include 时附上的，Origin 仍在。这类附带身份凭证的请求（credentialed request）默认不发凭据，要显式表达意图。
HTTP/1.1 200 OK Date: Mon, 16 Nov 2026 01:07:00 GMT Server: nginx Access-Control-Allow-Origin: https://app.shop.example Access-Control-Allow-Credentials: true Cache-Control: no-cache Set-Cookie: session=def456; Path=/; HttpOnly; Secure Vary: Origin Content-Type: application/json Content-Length: 14 {"user":"ada"}
服务器必须同时给出「具体源的 ACAO」与「ACAC 为 true」，浏览器才把这 14 字节交给脚本；少任何一项，响应都会被忽略。
例子 · 判定

三类常见 CORS 报错的定位步骤

控制台 Reason 关键字先查哪个首部定位步骤
'Access-Control-Allow-Origin' missingACAO 是否存在① 控制台重现；② Network 逐字查响应有无 ACAO；③ 分清看的是 OPTIONS 预检还是真实请求；④ 端点补 ACAO，4xx/5xx 分支也要补；⑤ 动态源补 Vary: Origin
does not match 'xyz'ACAO 与 Origin 是否逐字符相等① 抄下 xyz 即发出的 Origin；② 逐字符比对，留意斜杠与大小写；③ 按三元组查协议与端口；④ 查是否出现两条 ACAO；⑤ 清缓存再试
Credential is not supported / expected 'true'ACAO 是否为星号、ACAC 是否为 true① 确认是否设了 credentials include 或带 Authorization；② ACAO 由星号改具体源；③ 预检与真实响应都补 ACAC true；④ 查 Allow-* 是否误用星号；⑤ 并查第三方 cookie 策略与 SameSite
总原则：JavaScript 拿不到 CORS 出错的详细信息，确定原因唯一办法是看控制台的 Reason；另需并查 Vary、重复首部与第三方 cookie 策略。
推导

四步推出：带凭据时通配符为什么失灵

① ACAO 为星号的语义：任意源都可以读取这份响应。

② 带凭据让响应变成用户相关：本例返回某个登录用户的私人信息，不再是公开的天气数据。

③ 两者叠加的后果：任意站点发一条带 Cookie 的跨源请求，就能读到已登录用户的数据，等于让 CORS 推翻自己的边界。

④ 规范的取舍：把「允许带凭据」与「允许读」拆成两道独立肯定，ACAC 为 true 只确认凭据，ACAO 用具体源点名读取者。

星号表达「一律允许」，与凭据场景要求的「逐一确认」语义互斥

规范对照

MDN 的说法 → RFC 怎么写 → 为什么值得知道

MDN 的说法RFC 怎么写为什么值得知道
同源 = 协议、主机、端口三者都相同RFC 9110 第 4.3.1 节把 origin 定义为 scheme、host、port 三元组；第 4.2.3 节规定大小写与默认端口归一比较函数要先归一化再逐项比，不能做字符串相等
Origin 首部总随访问控制请求发送，值可为 nullRFC 9110 不定义 Origin 请求首部；它由 RFC 6454 第 7 节定义，现行由 Fetch 标准维护到 9110 里翻 CORS 首部会一无所获，找准规范才算找对答案
把请求分为简单请求与需要预检的请求Fetch 标准不再用「简单请求」，改用 CORS 安全列表首部判定，并定义预检与 CORS check 算法按安全列表与算法逐步判定，别按「简单」二字望文生义
预检用 OPTIONS，服务器回 Allow-Methods 与 Allow-HeadersFetch 标准规定预检响应须逐项通过方法与首部检查，任一未获允许即失败，真实请求不发出实现网关要按算法顺序查全部项，不能只验 ACAO
ACAO 为具体源时带 Vary: Origin；带凭据不能通配缓存键由 RFC 9111 第 4.1 节 Vary 机制决定；凭据场景 Fetch 标准把星号判为不匹配CORS 与缓存是两套规范的交点，漏配会让正确首部在 CDN 上失效
跨源请求由浏览器施加限制，脚本看不到失败细节Fetch 标准把 CORS 建模为用户代理在读取响应环节执行的检查，服务器侧始终按普通 HTTP 处理用 curl 拿到 200 不能证明浏览器可读，能读也不代表服务器做了授权
CORS 是浏览器约束，不是服务器约束：服务器照常执行请求并生成响应，是用户代理在把响应交给脚本前执行 CORS check，不通过就丢弃；curl 不受此限。
避坑

三个把「谁在拦、拦在哪」搞混的误解

❌ 同源就是同一个站，看域名就够
✅ http 与 https 不同源，显式 8443 与省略端口也不同源；子域共享 cookie 用的是另一套 Domain 规则，不等于同源。
❌ 报了 CORS 错，说明服务器没收到请求
✅ 简单请求照常抵达、副作用可能已发生，被拦的是「把响应交给脚本」；curl 能拿到 200，正因为它不执行 CORS 检查。
❌ CORS 是服务器用来防跨站攻击的安全功能
✅ 服务器用 ACAO 只做「是否共享响应」的声明，执行拦截的是浏览器；对不遵守的客户端毫无强制力，防写仍靠 CSRF 令牌。
