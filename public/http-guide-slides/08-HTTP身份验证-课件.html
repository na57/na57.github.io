定位

第 8 讲站在「认出你」和「划边界」之间

本讲解决「证明」：用一套标准流程把凭据送到服务器校验，而不是只认出浏览器。

本讲对应的 MDN 原文：Authentication 一篇；承第 7 讲 cookie，启第 9 讲 CORS。
主线

认证主线的六环因果链

1请求受保护资源：客户端先发一条裸请求
2服务器返回 401 挑战：用 WWW-Authenticate 说明方案与 realm
3客户端带凭据重试：把凭据放进 Authorization 首部
4校验通过返回资源：200 加主体，闭环完成
5realm 决定复用哪份凭据：同源同 realm 才自动带，路径无关
6明文或弱凭据的风险：Base64 可逆，离开 TLS 就是明文
这条链就是本讲目录：报文闭环 → 编码手算 → realm 判定 → 代理与安全。
动机

「认出浏览器」解释不了两道追问

🙂 以为的终点
cookie 认出这是同一个浏览器，服务器就该放行。
🤔 解释不了的两道追问
你凭什么说你是 alice？就算你是 alice，能看报表、能改报表吗？
写字楼：报名字是识别，查工牌是认证，刷卡只上 3 楼是授权；cookie 像访客手环，认得出你却证明不了你没借给别人。
定义

识别、认证、授权，加一副通用骨架

🧾 三个概念别混着用
识别（Identification）：声称自己是谁，一句声明。
认证（Authentication）：证明这句声明成立。
授权（Authorization）：确认身份后决定能访问什么。
🔐 HTTP 的通用框架
质询—响应（Challenge–Response）：服务器先用 401 拒绝并说明方案，客户端再用 Authorization 带凭据重试一次。
先挑战、后凭据、方案由服务器定
判断标准：分不清时问一句，这是在声明身份、证明身份，还是分配权限；本讲主线只解决中间那一环。
例子 · 报文 ①

前两步：裸请求 → 401 挑战

GET /admin/report HTTP/1.1 Host: app.example.com User-Agent: DemoClient/1.0 Accept: text/html （空行：本请求没有任何凭据首部）
裸请求：客户端不知道这个路径受保护，所以没有 Authorization 首部，它并不知道自己马上会被挑战。
HTTP/1.1 401 Unauthorized Date: Mon, 16 Nov 2026 00:30:00 GMT WWW-Authenticate: Basic realm="Admin Area" Content-Length: 63 Content-Type: text/html; charset=utf-8 <html><body><h1>401 Unauthorized</h1></body></html>
401 挑战：状态码说明未提供有效凭据，WWW-Authenticate 说明用 Basic 方案、保护区域 realm 叫 Admin Area；主体尖括号已按 HTML 规则转义。
例子 · 报文 ②

后两步：带凭据重试 → 200

GET /admin/report HTTP/1.1 Host: app.example.com User-Agent: DemoClient/1.0 Authorization: Basic dXNlcjpwYXNz Accept: text/html （空行：凭据已随本次请求发出）
重试请求：Authorization 的格式是「方案名 + 空格 + 凭据」，Basic 后面那串就是 Base64 编码后的 user:pass。
HTTP/1.1 200 OK Date: Mon, 16 Nov 2026 00:30:01 GMT Content-Type: text/html; charset=utf-8 Content-Length: 42 <html><body>季度报表数据…</body></html>
校验成功返回 200。整个交互用了两条请求、两条响应，这就是通用框架的最小完整闭环。
专题 · 状态码

401 / 403 / 404 先分流，再决定重试还是放弃

状态码服务器想表达什么客户端会怎么做是否带挑战首部
401 Unauthorized未提供或提供了无效凭据提示用户重新输入，可重试必须带 WWW-Authenticate
403 Forbidden凭据有效，但权限不足不再尝试，直接告知失败不需要
404 Not Found可能真不存在，也可能刻意隐藏当作资源不存在不需要
判定：401 是认证没过（找挑战首部看方案）；403 是授权没过（换账号或申请权限，重试无意义）。
带了正确凭据却一直收到 401，先怀疑 Base64 编码、realm 是否对得上，或是否被中间代理拦下，而不是继续傻等。

专题 · 安全

Base64 是编码不是加密，凭据等价于明文

🔁 编码（Encoding）
换一种表示方便传输，算法与字母表公开，无密钥，人人可还原。
🔑 加密（Encryption）
依赖密钥，没有密钥的第三方无法还原，才谈得上保密。
Base64 可逆、无密钥 → Basic 凭据 = 明文 → 必须靠 TLS
认证方案（Scheme）是插进 RFC 9110 框架的插件：Basic、Bearer 令牌（Bearer Token）、Digest 都共用同一副挑战—响应骨架；Basic 方案（Basic authentication scheme）由 RFC 7617 定义，把全部安全责任推给了 TLS。
例子 · 判定

realm 与四元组：六个 URL 逐行判凭据复用

后续请求 URL该路径的 realm与缓存四元组是否相同是否自动带 Admin 凭据
https://app.example.com/admin/page2Admin Area四元组全同会，直接带上
https://app.example.com/admin/deep/reportAdmin Area同四元组，路径更深不影响会，路径不是键
https://app.example.com/docs/apiDocs Arearealm 不同不会，另行挑战
https://app.example.com:8443/admin/page2Admin Area端口 8443 不等于 443不会，端口不同
http://app.example.com/admin/page2Admin Area协议 http 不等于 https不会，协议不同
https://other.example.com/admin/page2Admin Area主机名不同不会，主机不同
保护空间（Protection Space）由 scheme、host、port、realm 四元组决定，路径不在键里；口诀：同源加同 realm 才复用，路径无关。排障先核对四项里到底哪一项变了。
推导

挑战—响应为什么是「先拒绝、后凭据」

① 先发裸请求：凭据不该无谓出现在每个 URL，先探一步，只在确需保护的页面上传递。

② 服务器 401 挑战：用 WWW-Authenticate 写明方案与 realm，把「怎么证明、属于哪个空间」的决定权交给服务器。

③ 带 Authorization 重试：客户端按题目拼好凭据，这是凭据唯一该出现的位置，校验通过才回到 200。

两条请求 + 两条响应 = 最小完整闭环

专题 · 代理

401 属于源站，407 属于代理：两条平行车道

维度401 源站认证407 代理认证
挑战方目标源服务器路径上的代理服务器
状态码401 Unauthorized407 Proxy Authentication Required
挑战首部（响应）WWW-AuthenticateProxy-Authenticate
凭据首部（请求）AuthorizationProxy-Authorization
语法Basic 加 realm 参数Basic 加 realm 参数
能否并存可以：两套首部独立，一条请求可分别向代理与源站证明身份
HTTP/1.1 407 Proxy Authentication Required Proxy-Authenticate: Basic realm="Corporate Proxy" Content-Length: 0 （由代理返回，要求先向代理证明身份）
407 挑战：首部名带 Proxy 前缀，说明这是代理而非源站的要求。
GET http://example.com/report HTTP/1.1 Host: example.com Proxy-Authorization: Basic YWxpY2U6czNjcjN0 Authorization: Basic dXNlcjpwYXNz （前者给代理，后者给源站，互不混淆）
两套凭据并存：Proxy-Authorization 交给代理，Authorization 由代理转发给源站，各走各的车道。
专题 · 攻击链

无 TLS 时 Basic 凭据被窃取的六步链

步骤发生了什么攻击者获得什么
1客户端发裸 GET 到明文 http 地址看到路径与目标，确认有受保护资源
2源站返回 401 加 Basic realm 叫 Intranet 的挑战知道需要 Basic 凭据
3浏览器弹框，用户输入 alice 与 s3cr3t用户毫无察觉，以为只是普通登录
4客户端算 Base64 并发出 Authorization: Basic YWxpY2U6czNjcjN0抓到整条报文，读到那串可逆字符
5对 Base64 做逆向，还原出 alice:s3cr3t拿到明文用户名与口令，无需任何密钥
6用凭据向源站重放请求，或去其他系统撞库完全冒充 alice，横向扩大战果
传输层安全协议（TLS，Transport Layer Security）：链条在第 4 步截断，整条报文被封装进加密记录，观察者看不到 Authorization 首部，证书校验还挡住主动冒充。Base64 可逆，等于把口令写在明信片背面——Basic 必须搭配 TLS。
规范对照

MDN 的说法 → RFC 怎么写 → 为什么值得知道

MDN 的说法RFC 怎么写为什么值得知道
服务器质询、客户端提供凭据，正文引 RFC 7235现行框架在 RFC 9110 第 11 章；401 / 403 / 407 见第 15 章7235 已被 9110 取代，写实现要查现行编号
Basic 用 Base64 编码凭据，不安全，应与 TLS 搭配RFC 7617：凭据为 base64 的用户名加冒号加口令；用户名不得含冒号，realm 区分大小写这些边界只有规范写死，解析器按它写才能互通
realm 描述受保护的区域或范围RFC 7617 第 2 节与 9110 第 11.5 节：realm 与规范化根 URI 共同定义保护空间这是六网址判定表的规范依据，解释了改端口就重新挑战
Bearer 令牌通过 OAuth 2.0 保护资源RFC 6750：凭据为持有即有权令牌，形式是 Authorization: Bearer 加令牌凭据从用户名口令换成短期令牌，同样强制要求 TLS
权限不足返回 403，也可能用 404 隐藏页面RFC 9110 第 15.5.2 节要求 401 必须发送 WWW-Authenticate401 带挑战首部是 MUST，404 隐藏只是工程权衡
三份文档按职责摆好：RFC 9110 定义通用框架，RFC 7617 填进 Basic，RFC 6750 填进 Bearer，框架与方案是「插槽与插件」的关系；分清 MUST 与实践建议，评审才有依据。
避坑

三个把机制混为一谈的误解

❌ HTTP 认证 = 登录表单
✅ 表单是应用层流程，POST 到 /login 换回 cookie 靠它识别你；HTTP 认证是协议内置的质询—响应，凭据走 Authorization 首部，每条请求显式携带。
❌ Base64 后是乱码，口令被藏住了
✅ 看不懂不等于不可读：纯可逆变换、无密钥，抓包一行命令就还原。Basic 凭据等价于明文，必须搭配 TLS。
❌ realm 只是登录框上的提示文字
✅ 它同时是凭据缓存键的一部分，直接决定浏览器发不发口令；给不同安全等级的区域起同一个 realm 名，等于主动拆掉隔离。
