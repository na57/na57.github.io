本讲解决「多跳」：一条连接被拆成两段之后，谁能改它、谁能看见什么。

主线

中间层的五环因果链

1请求经代理：一条端到端连接被拆成两段
2代理改写并转发：请求目标从路径升级成完整 URL
3Via 逐跳追加：每一跳把路径戳进报文
4CONNECT 建隧道 / Upgrade 切协议：代理要么只搬字节，要么交出连接
5逐跳首部被误转发：本跳语义落到错误的连接上，故障由此开始
代理在应用语义层插手，隧道在字节层透传，Upgrade 在两者之间切换协议；最后一环是逐跳首部越过一跳后的故障。
动机

「客户端到源站一条直线」解释不了两种反常

🛰 熟悉的直线模型
浏览器发请求，源站回响应，中间谁也没有。一次点击说得通，却解释不了代理的存在。
🧩 中间层进场后
出口代理读不到加密目标却要转发；站点入口的反向代理对访客透明，后端还藏着多台机器。
💡 本讲方案：正向代理替客户端「出去」，反向代理替服务器「进来」，隧道借一条 TCP 给两端，升级把连接换协议。
定义

代理既当客户端又当服务器

🌐 正向代理（forward proxy）
代表客户端、隐藏客户端，公司出口、匿名访问；客户端通常知道它。
🏢 反向代理（reverse proxy）
代表服务器、隐藏服务器，负载均衡、缓存、压缩；客户端通常毫无察觉。
代理（proxy）= 对着客户端当服务器 · 对着源站当客户端 · 一条连接拆成两段
拆开之后，被抹掉的客户端信息用 Forwarded 或 X-Forwarded-For 补回，代理自己的路径用 Via 补回；只对本跳有效的首部必须每跳消费并重新生成。
例子 · 报文①

直连与经代理：请求目标为何从路径变完整 URL

GET /index.html HTTP/1.1 Host: www.example.com Accept: text/html （直连源站：origin-form，只有路径）
直连：TCP 已锁定对端，请求目标用 源点形式（origin-form），域名交给 Host 首部。
GET http://www.example.com/index.html HTTP/1.1 Host: www.example.com Accept: text/html （经正向代理：absolute-form，带 scheme 与主机）
经代理：请求目标从路径变成完整 URL，代理据此知道往哪转；Host 仍保留以区分虚拟主机。
判据：请求行的接收者与 URI 权威是否同一个。直连二者合一用 origin-form，经代理二者分离用 绝对形式（absolute-form）。
例子 · 报文②

Via 逐跳追加：0 跳 / 1 跳 / 2 跳三条报文

GET http://www.example.com/index.html HTTP/1.1 Host: www.example.com （第 0 跳 · 客户端 → 代理 A：还没有 Via）
第 0 跳：客户端刚发出请求，Via 为空。
GET http://www.example.com/index.html HTTP/1.1 Host: www.example.com Via: 1.1 proxy-a.example.com （第 1 跳 · 代理 A 追加自己的标识）
第 1 跳：Via 第一次出现，只有 A 这一段。
GET http://www.example.com/index.html HTTP/1.1 Host: www.example.com Via: 1.1 proxy-a.example.com, 1.1 proxy-b.example.net （第 2 跳 · 代理 B 在末尾追加，A 在前 B 在后）
第 2 跳：列表变两段，顺序就是报文走过的方向；响应沿原路返回时同样逐跳追加。
专题 · 判定表

四种请求目标形式，一张表记全

请求目标形式长什么样什么时候用
源点形式 origin-form/index.html?q=1直连源站时的绝大多数请求
绝对形式 absolute-formhttp://www.example.com/index.html向正向代理发请求时
权威形式 authority-formwww.example.com:443CONNECT 方法专用
星号形式 asterisk-form*OPTIONS 星号，询问服务器整体能力
判定只问一句：请求行接收者与 URI 权威是否同一？同一用 origin-form，分离用 absolute-form，建管道用 authority-form。
例子 · 报文③

CONNECT 建隧道：请求与 200 响应

CONNECT www.example.com:443 HTTP/1.1 Host: www.example.com:443 Proxy-Connection: Keep-Alive （① 客户端 → 代理：请连到 www.example.com:443）
第一步：CONNECT 请求目标是 权威形式（authority-form），语义是建立到目标的 TCP 连接，而非取资源。
HTTP/1.1 200 Connection established Proxy-Agent: ProxyGateway/1.0 （② 代理 → 客户端：隧道就绪，之后字节直接透传）
第二步：200 Connection established 不是普通 200 OK，它标志连接用途改变，此后不再有 HTTP 响应主体。
隧道不是透明管道，是代理主动放弃应用层解析权：只保留建 TCP、转发字节、最后关闭这层连接管理。
专题 · 视野边界

隧道里代理看得到什么、看不到什么

③ 隧道内字节透传，代理不解析 → TLS ClientHello ...随机数与加密套件... ← TLS ServerHello + Certificate ...证书链... → TLS Finished 随后才是加密后的 HTTP： → [加密] GET /index.html HTTP/1.1 ← [加密] HTTP/1.1 200 OK ...
第三步：TLS 握手与之后的 HTTP 全部以密文字节流通过，代理只搬运字节，看不到明文请求行、首部或正文。
信息项正向代理能否看到原因
CONNECT 的目标主机与端口能看到在请求行权威形式里，是明文
客户端真实 IP能看到客户端与代理直连，TCP 对端就是客户端
密文流量大小与时序能看到长度和时间特征，无需解密
隧道内 HTTP 方法与路径看不到被 TLS 加密，代理没有会话密钥
请求首部、Cookie、网页正文看不到同上，无法解读
例子 · 报文④

Upgrade: websocket 握手请求与 101 响应

GET /chat HTTP/1.1 Host: server.example.com Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== Sec-WebSocket-Version: 13 （客户端 → 服务器：请升级到 WebSocket）
升级请求：Upgrade 指明目标协议，Connection 声明它逐跳，Key 是校验用随机密钥，Version 为 13。
HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo= （服务器 → 客户端：此后是 WebSocket 帧，不再是 HTTP 报文）
101 响应：状态行宣告切换，Upgrade 与 Connection 必须同时出现，Accept 由客户端密钥经固定算法算出。
专题 · 首部判定

五个首部逐个判：全是逐跳首部

首部是否逐跳说明
Connection是逐跳首部的总开关，并列出本跳其他逐跳首部
Keep-Alive是本跳连接保活参数，只对本跳有意义
Proxy-Authenticate是代理的认证挑战，只在客户端与代理一跳间使用
Transfer-Encoding是本跳主体如何分块，下一跳要重新编码
Upgrade是逐跳首部，必须在 Connection 中列出
判据：描述「这一跳怎么传」的是逐跳，描述「资源本身是什么」的是端到端。正确模式永远是每跳消费并重新生成，绝不原样转发。
Upgrade 说想切到什么协议，Connection: Upgrade 说这个首部到我为止；缺了后者，源站回 101 讲 WebSocket 帧，中间代理还在按 HTTP 解析，连接立即错乱。
专题 · 故障链

误转发 Connection: close 的五步故障链

客户端 → 代理（本跳想关闭） GET /page HTTP/1.1 Host: www.example.com Connection: close 代理 → 源站（错误：原样转发了逐跳首部） GET /page HTTP/1.1 Host: www.example.com Connection: close ← 本该被消费并重新生成
故障起点：代理把只对本跳有效的 Connection: close 原样转发，源站误以为这条连接用完要关。
步骤发生了什么后果
① 客户端发请求带 Connection: close，只想关客户端到代理这一跳意图只作用第一跳
② 代理错误转发未消费，原样写进代理到源站的请求第一跳意图误植到第二跳
③ 源站照做当作针对自己的指令，响应后关闭到代理的 TCP代理复用的源站连接池被拆掉一条
④ 客户端意图落空代理只顾转发，没在本跳执行 close客户端以为会关的连接还开着，语义错乱
⑤ 连锁反应代理下次想复用那条连接，发现已被关闭请求失败或被迫重连，延迟抖动与偶发错误
根治办法只有一句：每一跳消费上游逐跳首部，再为下游重新生成自己的，绝不跨跳传递。
推导

Sec-WebSocket-Accept 的四步推导

① 取客户端密钥：dGhlIHNhbXBsZSBub25jZQ==，base64 编码的 16 字节随机值，先拿到输入。

② 拼接固定 GUID：与 258EAFA5-E914-47DA-95CA-C5AB0DC85B11 拼成一串——GUID 写死，保证只有懂 WebSocket 的一方算得出应答。

③ 取 SHA-1：对拼接结果散列，得 20 字节 b3 7a 4f 32 65 82 f6 3f 27 98 a1 44 3b 7c f9 8a 3e 2c 3f 0a，把长串压成定长摘要。

④ base64 编码：20 字节编码成 s3pPLMBiTxaQ9kYGzzhZRbK+xOo=，即 Sec-WebSocket-Accept，客户端据此校验。

算法公开固定，MDN 明说密钥「不提供安全性」：只确认「我确实在发起 WebSocket 握手」、挡住无意滥用；机密性来自 wss 之下的 TLS。

规范对照

MDN 的说法 → RFC 怎么写 → 为什么值得知道

MDN 的说法RFC 怎么写为什么值得知道
Via 逐跳追加，Upgrade 是逐跳首部RFC 9110 §7.6.1 给出 Via 语法与逐跳首部完整清单，转发时 MUST 在末尾追加哪些首部要消费并重新生成有规范答案，故障链正是违反它
经代理用绝对形式，直连用源点形式RFC 9112 §3.2 定义四种请求目标，向代理 MUST 用 absolute-form，CONNECT 用 authority-form请求行形式不是风格而是合规要求，把 origin-form 发给代理可被拒绝
CONNECT 打开隧道，成功回 200 Connection establishedRFC 9112 §9.3.6 规定目标为权威形式，建 TCP 后发 2xx 切换隧道模式，此后不得再解析字节解释为何 2xx 却无响应主体：标记的是连接用途改变
Upgrade 须在 Connection 列出，同意回 101RFC 9110 §7.8 定义 Upgrade，发送方 MUST 在 Connection 一并列出；101 在状态码章节；HTTP/2 的 RFC 9113 禁用此机制把「必须同时出现」落实为 MUST，少写不是小疏漏
WebSocket 密钥经固定算法算出 AcceptRFC 6455 §1.3 定义打开握手：密钥拼 GUID 取 SHA-1 再 base64，版本 13，不支持回 426自实现握手或排查握手失败时，能逐步验证推导
延伸板块在每讲末尾出现一次：MDN 给方向，RFC 给裁决，两条口径对齐才能既把事做成又说清为什么。
避坑

三个把隧道、请求目标与安全混为一谈的误解

❌ 200 之后代理还在转发 HTTP 报文
✅ 那之后是一对裸 TCP 字节流，代理放弃解析权；CONNECT 也不是取资源，成功 2xx 语义是「管道就绪」。
❌ 有了 absolute-form，Host 就多余了
✅ 绝对形式解决「代理往哪转」，Host 解决「目标主机上哪个虚拟主机」，维度不同，规范都要求带。
❌ Sec-WebSocket-Key 是加密机制，HTTP/2 也能 Upgrade
✅ 算法公开固定、不提供安全性，安全来自 wss 的 TLS；MDN 明确 HTTP/2 禁用升级机制。
