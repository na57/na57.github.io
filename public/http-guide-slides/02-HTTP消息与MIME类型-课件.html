主线

报文解析的六环因果链

1会话中的一次事务：网络上流动的是一段报文
2起始行给出意图或结果：请求说做什么，响应说成败
3首部携带元数据：主机名、可接受表示、长度
4空行划出边界：首部结束、主体开始的唯一标志
5主体承载表示字节：按长度或分块读到结束
6类型声明与嗅探的冲突：缺失或被改就出故障
解析顺序：先读起始行，再逐行读首部，遇空行停止，最后按长度读主体并按类型解析。
动机

TCP 只搬字节，回答不了三个追问

🙂 过于简略的解释
连接上写下 GET 加路径，服务器自然回一个页面。能说通一次点击，仅此而已。
🤔 黑盒留下的三问
字节到哪儿算一条完整指令（边界）？是读还是写（意图）？后面的内容多长（定界）？
💡 本讲方案：给每次交换套一个固定四段结构，让收发双方把无边界的字节流切成一条条报文。
TCP 保证按序、不丢、不重，但不解释字节；解释工作全部交给 HTTP 的报文结构。
定义

四段骨架：起始行 / 首部 / 空行 / 主体

HTTP 报文（HTTP message）只有两种：客户端发出的请求（request），与服务器给出的响应（response）。

🧱 头：起始行 + 首部
起始行（start-line）永远单行；首部是可选的一组键值对，二者合称「请求头」。
📨 载荷：空行 + 主体
空行宣告元数据结束；主体（body）承载文档字节，大小由首部指定。
起始行 → 首部 → 空行 → 主体　·　顺序不可交换
起始行与首部合称「请求头」，主体叫「有效载荷」；谈缓存、谈编码时，先分清动的是头还是载荷。
例子 · 报文

一次事务 = 一段请求 + 一段响应

GET /index.html HTTP/1.1 Host: www.example.com Accept: text/html,application/xhtml+xml User-Agent: Mozilla/5.0 (X11; Linux x86_64) Firefox/128.0 （空行之后 GET 无主体）
请求：起始行 + 请求首部 + 空行 + 可选主体；Host / Accept / User-Agent 各司其职。
HTTP/1.1 200 OK Date: Mon, 16 Nov 2026 08:00:00 GMT Content-Type: text/html; charset=utf-8 Content-Length: 19 <html>你好</html>
响应：状态行 + 首部 + 空行 + 主体；主体正好 19 字节，与 Content-Length 一致。
例子 · 逐行

每行都有职责，19 字节要手算

行职责写错会怎样
GET /index.html HTTP/1.1方法 / 目标 / 版本目标形式错，代理无法转发
Host指定虚拟主机，非目标 IP同 IP 多站点落到默认站
空行首部结束的唯一标志主体首行被误当首部
Content-Length: 19主体定界，UTF-8 字节数写大等到超时，写小粘下一条
19 字节 = <html> 6　+　你好 6　+　</html> 7
口诀：起始行定动作，首部定条件，空行定边界，长度定主体。
专题 · 起始行

请求目标四形式，是四种连接拓扑

形式长什么样什么时候用
原始形式 origin formGET /background.png HTTP/1.0直连源站，最常见；可跟问号查询串
绝对形式 absolute formGET http://example.com/docs HTTP/1.1经代理，代理要靠完整 URL 定去向
authority 形式CONNECT example.com:80 HTTP/1.1仅 CONNECT 建隧道，只要域名端口
星号形式 asterisk formOPTIONS * HTTP/1.1问整台服务器支持什么方法
目标和「连谁」绑在一起：直连给路径、经代理给全址、建隧道给 authority、问全局打星号。
四种形式由语法产生式固定，不是写法偏好；第 11 讲代理与隧道会原样回归。
例子 · 状态码

1xx–5xx 九码分流判定表

状态码 · 类别触发方与条件客户端该做什么
100 · 1xx 信息服务器收到 Expect: 100-continue 后回临时响应继续发主体，过渡响应非最终
200 · 2xx 成功服务器成功处理并带回主体按 Content-Type 解析主体
301 · 3xx 重定向资源永久迁走，通常带 Location更新书签，跟 Location 再发一次
304 · 3xx 重定向条件请求判定副本仍有效，不回主体直接用缓存，再验证成功非错误
400 · 4xx 客户端错服务器认为请求语法有误改请求，不要原样重试
401 · 4xx 客户端错要求先认证，缺凭据或凭据无效带 Authorization 重发，缺的是身份
403 · 4xx 客户端错理解请求但拒绝授权，与身份无关换身份或放弃，重试无意义
404 · 4xx 客户端错找不到可用表示且不愿说明核对 URL，重试通常无益
500 · 5xx 服务端错服务器遇到阻止完成的意外状况幂等请求可稍后重试，要修服务端
三位状态码（status code）口诀：1xx 继续发、2xx 收结果、3xx 去别处、4xx 改请求、5xx 服务端修；只有 5xx 配幂等方法才值得自动重试。
例子 · 定界

同一份内容：Content-Length 与 chunked

POST /upload HTTP/1.1 Host: www.example.com Content-Type: text/plain; charset=utf-8 Content-Length: 11 hello world
路线 A · Content-Length 定界：读完空行再读恰好 11 字节即结束，长度必须事先算准。
POST /upload HTTP/1.1 Host: www.example.com Content-Type: text/plain; charset=utf-8 Transfer-Encoding: chunked 5 hello 6 world 0
路线 B · chunked 定界：每块先写十六进制长度再写数据，0 块收尾，拼出同样是 hello world。
专题 · 手算

分块主体逐块解析，一步不跳

① 读块大小 5：十六进制 5 = 十进制 5，表示紧接 5 字节数据。

② 读 5 字节 hello：随后一个 CRLF 作块结束符，不计入块大小，累计 hello。

③ 读块大小 6：十六进制 6 = 十进制 6，下一块 6 字节。

④ 读 6 字节「 world」：一个空格加 world 五字母，累计 hello world，与路线 A 一致。

⑤ 读块大小 0：主体结束；0 块后可跟尾部首部，本例没有，一个空行收尾。

长度头 + 数据 + CRLF 三段式重复 · 0 块是唯一正文结束信号

专题 · 正交

类型、变换、长度：三条首部互不替代

HTTP/1.1 200 OK Content-Type: text/html; charset=utf-8 Content-Encoding: gzip Content-Length: 843 （843 字节是 gzip 压缩后的字节，不是解压后 HTML 大小）
内容编码（Content-Encoding）管「做了什么变换」，Content-Type 管「是什么」，二者正交、可叠加。
解析顺序：按 Content-Length 读出字节 → 按 Content-Encoding 解压 → 按 Content-Type 解析；先解码、后解析，反过来就是乱码。
charset 是 Content-Type 的参数，不是 Content-Encoding；压缩编码与字符编码是两码事。
例子 · MIME

四种高频 MIME 类型的判定表

MIME 类型（MIME type，MDN 又称媒体类型 media type）由 Content-Type 声明，结构是 type/subtype，可带参数。

Content-Type归类浏览器默认处理声明错误时的风险
text/htmltext 独立类型解析成 DOM 并渲染，脚本可执行纯文本被嗅探成 HTML，内容被执行
application/jsonapplication 独立类型当数据交给脚本或触发下载被嗅探成 HTML 时可控文本可能被执行
image/svg+xmlimage 独立类型，+xml 后缀作矢量图渲染，内部可含脚本顶层打开时脚本可执行，嵌入受限
application/octet-stream未知二进制兜底弹出另存为，不自动执行安全默认值：不猜用途就不会误当可执行
text 类最常用参数 charset，缺省 US-ASCII；UTF-8 纯文本应写 text/plain;charset=UTF-8。浏览器看 MIME 而非扩展名。
专题 · 嗅探

有无 nosniff：声明与猜测的对照

场景没有 nosniff带 X-Content-Type-Options: nosniff
完全缺 Content-Type读开头字节嗅探，可能猜成 HTML 或脚本并执行按保守类型处理，不升级成可执行类型
脚本错发成 text/plain可能嗅出是脚本照常执行，掩盖配置错误声明与执行要求不符，拒绝执行
API 返回 JSON 类型写错可能被当 HTML 渲染，引入脚本执行面按保守类型处理，不升级为可执行类型
用户上传文件下载可能据内容猜测而尝试就地打开更可能走另存为，减少就地执行
内容嗅探（MIME sniffing）：类型缺失或被认为设错时浏览器读字节猜类型，各家行为不同；nosniff 只是「别猜、按标签来」，不会自动修正写错的类型。
推导

解析流水线：先定界，后解释

① 读起始行：请求拆方法 / 目标 / 版本，响应拆版本 / 状态码 / 状态文本。

② 逐行读首部：每行一个冒号分隔的键值对，按作用域归到通用 / 请求 / 响应 / 表示四类（旧称实体首部已并入表示首部）。

③ 遇空行停止：它是首部结束、主体开始的唯一语法标志，全流程的转折点。

④ 按长度或分块读主体：Content-Length 读固定字节，chunked 逐块读到 0 块。

⑤ 先按 Content-Encoding 解码 → 再按 Content-Type 解析表示

规范对照

MDN 的说法 → RFC 怎么写 → 为什么值得知道

MDN 的说法RFC 怎么写为什么值得知道
报文由起始行、首部、空行、主体四部分组成RFC 9112 用 ABNF 逐字节约束顺序与空行 CRLF 位置写解析器时据此定位报错，空行缺失是语法违规
请求行三要素、请求目标四种形式RFC 9112 把目标定为四种语法产生式，RFC 9110 定义方法语义不会发明第五种写法，懂 HTTP/2 改编码不改语义
状态码首位分五类，常见 200、404、302RFC 9110 建注册表、逐码定语义，并定义 safe 与 idempotent 属性能否自动重试、能否缓存的权威依据
长度未知用 chunked，0 块结束RFC 9112 定义 chunk = 十六进制 chunk-size + CRLF + data + CRLF手算分块边界、排查多一个 CRLF 就错位
MIME 形如 type/subtype，IANA 跟踪RFC 6838 定义注册树、命名语法与 +xml / +json 结构化后缀懂厂商类型来路，为第 3 讲内容协商打底
类型缺失会嗅探，nosniff 可禁止判定算法不在核心 HTTP RFC，由 Fetch 规范与浏览器实现定义排查时用对文档：语法 9112、语义 9110、类型 6838
MDN 告诉你「是什么」，RFC 告诉你「精确到字节是什么」；写解析器或判重试时，最终要落到右列规范字句。
避坑

三个把边界与类型混为一谈的误解

❌ 空行只是排版，删掉也能解析
✅ 它是首部结束、主体开始的唯一语法标志；缺了它，主体第一行会被当成又一个首部，整条报文全乱。
❌ Content-Length 随便写、块大小按十进制读
✅ 长度写小会粘包、写大会挂到超时，因为 TCP 是字节流、长度是唯一边界；chunked 块大小是十六进制，1A 是 26 不是 10。
❌ 按文件后缀判断类型，把 charset 当 Content-Encoding
✅ 浏览器看 MIME 不看扩展名，同一 URL 可协商出不同表示；charset 是 Content-Type 的参数，压缩编码与字符编码两码事。
