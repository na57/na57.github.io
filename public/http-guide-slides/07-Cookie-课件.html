本讲是状态与安全四讲的第一环：先造出状态，再证明身份、划边界。

对应的 MDN 原文：Cookies。高亮节点就是本讲。
主线

cookie 的六环因果链

1服务器下发 Set-Cookie：把状态压成键值
2浏览器保存 cookie：凭据收在本地
3后续请求带 Cookie：浏览器主动交回
4作用域匹配决定是否发：Domain / Path / SameSite 三闸门
5服务器恢复用户状态：读标识查会话
6属性配错反成攻击面：记忆机制变成风险
cookie 的主线：状态从服务器转移到客户端并在每次请求显式带回；属性配置不当时，这套记忆机制反过来变成攻击面。
动机

「服务器忘干净」与「应用要记住」隔着一道缝

🧊 协议的事实
无状态：请求之间彼此独立，服务器不保留上一次的任何信息。
🛒 应用的期待
登录态、购物车、主题偏好，都要跨多次请求延续。
💡 本讲方案：把状态压成一小段键值交给浏览器，每次请求由浏览器显式带回；协议本身不变。
定义

Cookie：状态在浏览器手上，服务器只校验

📤 下发与保存
服务器用 Set-Cookie 写一张身份凭条，浏览器把它存进 cookie 罐。
📥 带回与恢复
后续请求由浏览器用 Cookie 首部交回，服务器读编号恢复状态。
状态不在服务器的连接记忆里，而在浏览器手上，每次请求显式带回
术语首现：Cookie（HTTP cookie，也称 Web Cookie）是一小块数据；Set-Cookie 首部（Set-Cookie response header）与 Cookie 首部（Cookie request header）是承载它的两个首部。cookie 是架在 HTTP 之上的能力，不是协议语义的一部分。
定义 · 生存期

会话 cookie 与持久 cookie：活多久

🕐 会话 cookie（session cookie）
不设过期时间，会话结束即删；会话恢复可能把它延长。
📅 持久 cookie（persistent cookie）
靠 Expires 绝对日期或 Max-Age 相对秒数指定寿命。
Set-Cookie: theme=dark; Path=/ Set-Cookie: id=a3fWa; Expires=Wed, 21 Oct 2026 07:28:00 GMT; Path=/
两条 Set-Cookie 并列：第一条无过期时间是会话 cookie，第二条带 Expires 是持久 cookie。一条响应可以同时下发多个 Set-Cookie。
MDN 归纳三类用途：会话状态管理、个性化设置、浏览器行为跟踪；第三类正是隐私争议的源头。
例子 · 报文

最短往返：状态到底存在谁手上

GET /dashboard HTTP/1.1 Host: app.example.com Accept: text/html HTTP/1.1 200 OK Content-Type: text/html; charset=utf-8 Set-Cookie: sid=9f3a2b; Path=/; HttpOnly Content-Length: 96 请登录。
第一次请求：服务器在 200 响应里用 Set-Cookie 下发会话标识 sid=9f3a2b，回复请登录。协议不要求服务器记住这次下发动作。
POST /login HTTP/1.1 Host: app.example.com Cookie: sid=9f3a2b Content-Type: application/x-www-form-urlencoded Content-Length: 27 user=alice&pass=correct
第二次请求：浏览器主动把 sid=9f3a2b 放进 Cookie 首部带回。服务器读到它，才知道这次登录属于刚才那位访客；主体用和号连接两个字段。
例子① · 报文

一条完整 Set-Cookie 的七个开关

HTTP/1.1 200 OK Date: Mon, 16 Nov 2026 00:30:00 GMT Content-Type: text/html; charset=utf-8 Set-Cookie: sid=9f3a2b; Domain=app.example.com; Path=/account; Expires=Wed, 21 Oct 2026 07:28:00 GMT; Max-Age=604800; Secure; HttpOnly; SameSite=Lax Cache-Control: no-store Content-Length: 214 登录成功，这是你的账户首页。
例子① 完整 Set-Cookie：键值 sid=9f3a2b 之后紧跟 Domain、Path、Expires、Max-Age、Secure、HttpOnly、SameSite 七个属性，用分号分隔。
GET /account/profile HTTP/1.1 Host: app.example.com Cookie: sid=9f3a2b Accept: text/html Sec-Fetch-Site: same-origin HTTP/1.1 200 OK Set-Cookie: sid=7c81de; Domain=app.example.com; Path=/account; Max-Age=604800; Secure; HttpOnly; SameSite=Lax Cache-Control: no-store 个人资料页。
后续请求：Cookie 首部只带名字与值，七个属性都不回传；属性是浏览器存 cookie 时的规则。响应再次下发新 sid 是防会话固定的做法。
专题 · 逐属性

七属性各把一道关，先手算寿命优先级

属性回答的问题取值与含义不设会怎样
Domain哪些主机可以收指定主机名，通常连子域一并包含默认同一主机，不含子域
Path路径里必须出现什么如 /account，子路径一并匹配默认取设置请求路径的目录
Expires绝对过期是哪天GMT 日期，只与客户端时钟相关该维度不产生过期
Max-Age还能活多少秒相对秒数，优先于 Expires与 Expires 都不设即会话 cookie
Secure能不能走明文无取值，只在 HTTPS 发送明文请求可能暴露给中间人
HttpOnly脚本能不能读无取值，Document.cookie 读不到脚本可读，XSS 可窃取标识
SameSite跨站要不要带Strict / Lax / None按新默认行为当 Lax
Expires 只看客户端时钟；Max-Age 是相对秒数不依赖时钟；两者同现 Max-Age 优先
手算：Expires 写 2026 年 10 月 21 日已过去；Max-Age 等于 604800 秒等于 7 天，从 11 月 16 日收到响应算到 11 月 23 日，浏览器按 7 天保存。
专题 · 安全开关

Secure 管路上，HttpOnly 管页面后

开关挡住的攻击作用机理挡不住什么
Secure明文窃听、中间人篡改只在 HTTPS 加密请求里发送能读硬盘或用脚本读取的人
HttpOnly跨站脚本窃取会话Document.cookie 读不到它网络窃听，也挡不住 CSRF
一个管路上不被偷看，一个管到页面后不被脚本偷走，两者缺一不可
术语首现：跨站脚本（XSS，Cross-Site Scripting）、中间人（man-in-the-middle）、会话固定攻击（session fixation attack）。MDN 建议承载会话的 cookie 两者都加，且每次认证重发新值。
例子② · 作用域

Domain → Path → Secure：八个 URL 逐一判定

Set-Cookie: sid=9f3a2b; Domain=shop.example.com; Path=/docs; Secure
待判定 cookie：主机限定 shop.example.com 及其子域，路径限定 /docs 及其子路径，且只在 HTTPS 下发送。
候选请求 URL① Domain 闸门② Path 闸门③ Secure 闸门结果
https://shop.example.com/docs通过：主机完全相同通过：/docs 精确相等通过：HTTPS发送
https://shop.example.com/docs/Web/HTTP通过：主机完全相同通过：以 /docs/ 开头属子路径通过：HTTPS发送
https://www.shop.example.com/docs通过：显式 Domain 含子域通过：路径精确相等通过：HTTPS发送
https://shop.example.com/docsets通过：主机完全相同拦截：/docsets 不以 /docs/ 开头，仅字符串前缀相同不判定不发
https://shop.example.com/fr/docs通过：主机完全相同拦截：/fr/docs 不以 /docs 开头不判定不发
https://shop.example.com/通过：主机完全相同拦截：根路径 / 不在 /docs 作用域内不判定不发
https://example.com/docs拦截：example.com 是父域，作用域不向上冒泡不判定不判定不发
http://shop.example.com/docs通过：主机完全相同通过：路径精确相等拦截：明文 HTTP，Secure 要求加密不发
术语首现：作用域（scope）由 Domain 与 Path 共同界定；规范算法是域名匹配（domain-match）与路径匹配（path-match）。三个反直觉点：/docsets 不匹配、父域不冒泡、明文被 Secure 拦。
例子③ · SameSite

Strict / Lax / None：四类场景的携带判定

取值MDN 的口径典型用途
Strict只发送到来源站点，最严格高敏感操作，宁可多点一次
Lax放行从外站链接进来的顶层导航主流默认，兼顾体验
None同站跨站都发，必须配 Secure第三方登录回调等嵌入场景
请求场景是否跨站StrictLaxNone 配 Secure
站点内 fetch：fetch('/api/cart')同站发送发送发送
外站链接跳转：顶层 GET 导航跨站，安全方法不发发送发送
跨站 POST 表单：提交到 /transfer跨站，非安全方法不发不发发送
跨站子资源：外站引用本站图片脚本跨站，子资源不发不发发送
错误：None 少了 Secure，浏览器拒绝这枚 cookie Set-Cookie: sid=9f3a2b; SameSite=None 正确：None 必须搭配 Secure，且页面本身需为 HTTPS Set-Cookie: sid=9f3a2b; SameSite=None; Secure
None 与 Secure 是捆绑关系：第一行会被丢弃，第二行才在跨站场景正常携带。术语首现：跨站请求伪造（CSRF，Cross-Site Request Forgery）、站点（site for cookies）。
未设置 SameSite 按新的默认行为当 Lax 处理；None 必须配 Secure，本地 http 环境常因此调不通跨站 cookie。
例子④ · 职责边界

cookie、认证凭据、localStorage 的八维对照

维度Cookie认证凭据localStorage
存在哪里cookie 罐，按域与路径组织由客户端代码掌握浏览器本地，按源隔离
谁写入服务器 Set-Cookie 或脚本客户端代码显式设置JavaScript 显式写入
自动随请求发送是，按作用域规则否，每次显式加首部否，永不进网络请求
脚本能否读取能，除非加 HttpOnly取决于代码如何保管能
能否设 HttpOnly能不适用不能
容量量级很小，约 4 KB无存储概念，首部受大小限制大得多，通常 5 MB 以上

专题 · 故障链

把会话标识写进 URL：两条链同时踩雷

情形 A：用 cookie，URL 稳定，共享缓存可复用一份响应 GET /cart HTTP/1.1 Host: shop.example.com Cookie: sid=9f3a2b HTTP/1.1 200 OK Cache-Control: private, no-store 情形 B：把 sid 拼进 URL，缓存键被每个人的标识污染 GET /cart?sid=9f3a2b HTTP/1.1 Host: shop.example.com 同一份 /cart 被拆成 /cart?sid=9f3a2b 与 /cart?sid=7c81de 等无数个缓存键
cookie 让 URL 保持稳定，缓存键只认资源本身；把 sid 拼进 URL 则让每个用户都产生一个新缓存键。
泄露链环节谁能看到会话标识
① 浏览器历史共用这台电脑的下一位使用者
② 服务器访问日志运维、日志采集与分析系统
③ Referer 首部第三方站点、广告与分析服务
④ 复制分享任何收到链接的人
1缓存键被污染：sid 不同键不同，一份 /cart 拆成无数键
2命中率暴跌：共享缓存人人一份，回源量激增
3串号风险：A 的带 sid 页面被缓存后发给 B
4陈旧凭据：缓存放大早已失效的旧 sid 泄露
会话标识属于状态，不该成为资源地址的一部分 —— 术语首现：会话劫持（session hijacking）
推导

三步收成可复用的判定动作

① 读 Set-Cookie 固定七问：键名、Domain、Path、Expires 与 Max-Age、Secure、HttpOnly、SameSite。

② 属性名只在 Set-Cookie：回传的 Cookie 首部只有名字与值，别去那里找 Path 或 Secure。

③ 排查没带上按四闸门：Domain → Path → SameSite → Secure，主机、路径、跨站、明文依次过。

四步都过才发送，任一拦下即不发

五个 URL，自己把三闸门推一遍

规范对照

MDN 的说法 → RFC 怎么写 → 为什么值得知道

MDN 的说法RFC 怎么写为什么值得知道
Set-Cookie 下发、Cookie 首部带回，属性不回传RFC 6265 §3 两套语法、§5 存储模型属性是存储规则不是回传内容，别去 Cookie 首部解析属性
未设 SameSite 按 Lax、None 必须配 Secure2011 年原始 RFC 6265 无 SameSite，6265bis 引入并规定缺省 Lax新默认行为是规范演进，移植老代码须显式写 SameSite
Domain 含子域、Path 子路径匹配，/docs 不匹配 /docsetsRFC 6265 §5.1.3 域名匹配、§5.1.4 路径匹配要加斜杠实现匹配算法照抄两节，别用简单字符串前缀比较
__Host- 与 __Secure- 前缀作深度防御6265bis 前缀校验，不符条件浏览器拒绝保存把设置要求变成浏览器强制校验，__Host- 锁死 Domain
站点由可注册域与方案定义，区分第一方与第三方6265bis 引入 site for cookies 与可注册域，依赖公共后缀列表方案也算站点一部分，http 与 https 同名主机不再同站
术语首现：可注册域（registrable domain）、公共后缀列表（Public Suffix List）。RFC 里 MUST、SHOULD、MAY 有严格区别；None 必须配 Secure 是强制要求，浏览器据此直接丢弃违规 cookie。
专题 · 前缀

__Host- 与 __Secure-：把设置要求写成钢印

🔒 __Secure-
只要求带 Secure、来自安全来源。
🔐 __Host-
再加两道锁：不带 Domain、Path 精确为 /，与主机锁死。
__Secure-：带 Secure 且来自安全来源即可 Set-Cookie: __Secure-sid=9f3a2b; Secure; Path=/account; SameSite=Lax __Host-：还要求不带 Domain、Path 精确为 / Set-Cookie: __Host-sid=9f3a2b; Secure; Path=/; SameSite=Lax
两条合规的前缀 cookie：__Host- 因锁死主机更安全；任何一条不满足各自条件，浏览器都会拒绝保存。
术语首现：深度防御（defense in depth）、与主机锁死（domain-locked）。应用服务器须比对完整 cookie 名，因为 Cookie 首部不会把前缀剥掉。
避坑

三个把不同层次混为一谈的误解

❌ cookie 是加密的，能存密码这类敏感信息
✅ 它只是普通文本，用户可读可改；应放不透明标识符（opaque identifier），真实数据留在服务端。
❌ Expires 与 Max-Age 都写了，以 Expires 为准
✅ Max-Age 优先，它是相对秒数不依赖客户端时钟，Expires 只与客户端相关。
❌ 加了 HttpOnly 就万事大吉
✅ 它挡 XSS 窃取，挡不住 CSRF，后者靠 SameSite 与令牌；单独写 None 不带 Secure 会被直接丢弃。
