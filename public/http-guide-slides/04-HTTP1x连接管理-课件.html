本讲对应的 MDN 原文：Connection management in HTTP/1.x。
主线

成本 → 复用 → 流水线 → 队头阻塞

1每条事务新建连接：最朴素的短连接模型
2三次握手与慢启动很贵：冷连接前期传得慢
3持久连接复用 TCP：省掉反复握手，让连接变热
4流水线连续发请求：省掉发一个等一个的空等
5响应按序形成队头阻塞：队首慢堵住后面全部
6连接何时关闭：逐跳首部与复用判定
成本逼出复用，复用逼出流水线，流水线又留下队头阻塞；这是 HTTP/2 多路复用要解决的核心痛点。
动机

带宽再大，也压不掉一个来回的时间

📶 常见误判
首屏慢就怪带宽小，于是升级链路；可小图标只有几十字节，照样要等。
⏱ 真正的两笔账
每个资源先付一次握手 RTT；新连接还卡在慢启动（slow start），拥塞窗口（congestion window，cwnd）没涨起来。
一次请求的成本 ≈ 三次握手 1 RTT + 慢启动若干 RTT + 请求响应 1 RTT
💡 本讲方案：先把连接当成有生命周期的稀缺资源，再算三种模型怎样把成本摊到更多请求上。
定义

三种模型，只差两件事：握手与等待

🔌 短连接（short-lived connection）
每条事务新建并关闭一条 TCP，请求前握手、应答后立即关，成本最高。
♻️ 持久连接（persistent connection）
一条 TCP 保持一段时间，重复服务多条请求，省掉反复握手。
🚀 流水线（HTTP pipelining）
不等响应就连续发多个请求，响应仍按请求顺序返回。
📏 往返时延（RTT，Round-Trip Time）
一个包从客户端到服务器再回来的时间，是本讲所有手算的尺子。
要不要反复握手，要不要发一个等一个 —— 两问定模型
版本默认值要记牢：HTTP/1.0 默认短连接，HTTP/1.1 默认持久连接，只有写 Connection: close 才退回短连接。
专题 · 参数

先把尺子固定：RTT、MSS、cwnd、慢启动

参数取值含义
往返时延 RTT（Round-Trip Time）50 ms一个包从客户端到服务器再回来的时间
最大分段大小 MSS（Maximum Segment Size）1460 字节一条 TCP 段能承载的最大应用层数据
拥塞窗口 cwnd（congestion window）初始 10 MSS收到确认前发送方被允许发出的数据量
慢启动（slow start）每轮翻倍cwnd 按 10、20、40、80 MSS 指数增长
🎫 三次握手（three-way handshake）
发 SYN、回 SYN-ACK、再发 ACK；发出第一个请求字节前先付 1 个 RTT。
🐢 慢启动（slow start）
连接刚建好时 cwnd 很小，每收到一轮确认就翻倍，传大对象尤其吃亏。
关键区分：握手是固定门票，与资源大小无关；慢启动是加速过程，决定一条冷连接前几轮能发多少数据。
例子 · 报文

短连接：一条连接只服务一次事务

—— 连接 A：为 /style.css 而生 —— [客户端发 SYN → 服务器回 SYN-ACK → 客户端发 ACK，三次握手完成] GET /style.css HTTP/1.1 Host: www.example.com Connection: close HTTP/1.1 200 OK Content-Type: text/css Content-Length: 128 body { color: #333; } [服务器发 FIN，连接 A 关闭] —— 连接 B：为 /app.js 重新建一条 —— [又一次三次握手……] GET /app.js HTTP/1.1 Host: www.example.com Connection: close HTTP/1.1 200 OK Content-Type: application/javascript Content-Length: 64 [又一次关闭……]
两个资源走了两条完整连接：握手、传输、关闭三步重复两遍，第二条连接享受不到第一条积累的任何 TCP 状态。
例子 · 报文

持久连接：握手一次，两条请求复用同一条 TCP

[一次三次握手，此后两条请求复用同一条连接] GET /style.css HTTP/1.1 Host: www.example.com Connection: keep-alive HTTP/1.1 200 OK Content-Type: text/css Content-Length: 128 Keep-Alive: timeout=5, max=100 [没有关闭！连接保持打开……] GET /app.js HTTP/1.1 Host: www.example.com Connection: keep-alive HTTP/1.1 200 OK Content-Type: application/javascript Content-Length: 64 Keep-Alive: timeout=5, max=100 [连接继续保持，直到空闲超时或任一方要求关闭]
两条请求共用一条 TCP，只在开头握手一次；Connection 是开关，Keep-Alive 的 timeout 与 max 是具体参数。
版本差异：HTTP/1.0 要显式写 keep-alive 才得到长连接，HTTP/1.1 默认就是，只有 Connection: close 才退回短连接。
例子① · 手算

取 4 个资源：8 RTT / 5 RTT / 2 RTT

模型握手开销传输开销（逐项）总耗时
短连接（4 条连接逐个取）4 × 50 = 200 ms资源1 50 + 资源2 50 + 资源3 50 + 资源4 50 = 200 ms400 ms = 8 RTT
持久连接（1 条连接发一个等一个）1 × 50 = 50 ms等响应1 50 + 等响应2 50 + 等响应3 50 + 等响应4 50 = 200 ms250 ms = 5 RTT
流水线（请求连发、响应按序回）1 × 50 = 50 ms4 个请求背靠背发出约 0；4 个响应连续回，最后一个约在 1 RTT 末到 = 50 ms100 ms = 2 RTT
长连接省握手（省 3 次）· 流水线省等待（省 3 个空等 RTT）
注意：长连接仍要逐个等响应，四个 RTT 一个不少；流水线的收益全来自把请求提前塞进网络。
例子② · 手算

冷连接 5 RTT，热连接 1 RTT

轮次本轮 cwnd本轮可发数据累计已发
第 1 轮10 MSS10 × 1460 = 14600 字节14600 字节
第 2 轮20 MSS（翻倍）20 × 1460 = 29200 字节43800 字节
第 3 轮40 MSS40 × 1460 = 58400 字节102200 字节
第 4 轮80 MSS只剩 102400 − 102200 = 200 字节，1 个段发完102400 字节（完成）
冷连接 ≈ 握手 1 RTT + 慢启动 4 RTT = 5 RTT = 250 ms　｜　热连接 ≈ 1 RTT = 50 ms
冷连接比热连接慢整整 4 个 RTT：短连接的病根不只是多一次握手，而是让每条连接永远停在慢启动的开头几轮。
例子 · 报文

流水线：请求连发，响应按序

[同一条长连接上，四个请求背靠背发出，中间不等响应] GET /slow-report HTTP/1.1 Host: www.example.com GET /logo.png HTTP/1.1 Host: www.example.com GET /style.css HTTP/1.1 Host: www.example.com GET /app.js HTTP/1.1 Host: www.example.com HTTP/1.1 200 OK （/slow-report，慢） Content-Length: 90000 HTTP/1.1 200 OK （/logo.png，已就绪但必须排在后面） Content-Length: 2048 HTTP/1.1 200 OK （/style.css） Content-Length: 128 HTTP/1.1 200 OK （/app.js） Content-Length: 64
请求可连续写入管道，但响应必须按同样顺序写回；即使 logo.png 早已缓存，也只能排在慢报告之后。
判定口诀：第二个请求是否必须等第一个响应回来？必须等是普通长连接，不必等、连续发才是流水线。另外只有幂等（idempotent）方法 GET、HEAD、PUT、DELETE 能安全进流水线，POST 这类写入请求不行。
例子③ · 时序

慢响应 R1 拖住早已就绪的 R2 / R3 / R4

时刻客户端侧服务器侧关键点
t = 0连续发出 R1 R2 R3 R4尚未收到全部进管道，不用等
t = 0.5 RTT等待收齐 4 个请求；R2/R3/R4 已就绪，R1 开始慢处理快响应其实早可发
t = 0.5 → 3.5 RTT一直等待，看不到任何响应R1 耗时 3 RTT 才产出R2/R3/R4 只能干等
t = 4 RTT收到 R1此刻才轮到发 R2R2 被堵 3.5 RTT
t = 4.5 / 5 / 5.5 RTT依次收到 R2 / R3 / R4依次发 R3 / R4 / 完成4 个资源才全部到齐
GET /slow-report GET /logo.png GET /style.css GET /app.js ↑ 四个请求 t=0 全部背靠背进管道 200 /slow-report （3 RTT 后才就绪） 200 /logo.png 200 /style.css 200 /app.js （早已就绪却被排在后面）
队头阻塞（head-of-line blocking，HOL）：队首一个慢元素，把后面所有已就绪元素全部堵住；TCP 丢包重传还会让整条连接一起等，更顽固。
例子④ · 逐跳

Connection 与 Keep-Alive 在代理处被剥离重建

【第 1 跳：客户端 C → 代理 P，客户端发出】 GET /index.html HTTP/1.1 Host: www.example.com Connection: keep-alive, X-Debug Keep-Alive: timeout=5, max=100 X-Debug: trace-me
客户端到代理这一跳：希望 keep-alive，timeout=5、max=100；X-Debug 被 Connection 列为逐跳首部。
【第 2 跳：代理 P → 源站 S，代理重建后发出】 GET /index.html HTTP/1.1 Host: www.example.com Via: 1.1 proxy-1.example.com Connection: keep-alive Keep-Alive: timeout=30, max=1000
代理重建：timeout 从 5 改 30、max 从 100 改 1000，因为这是代理到源站的策略；X-Debug 已剥离，Via 逐跳追加。
逐跳首部（hop-by-hop header）只对当前一跳有效，须在此消费、按本跳重建；端到端首部（end-to-end header）如 Host 应原样传到最终接收方。
专题 · 故障链

误转发逐跳首部：四类后果

误转发的内容源站的误解实际故障
Keep-Alive: timeout=5以为这条连接闲置 5 秒就关代理按 30 秒复用却已被关，写请求收到 RST，请求失败
Connection: close 被原样转发关闭它与代理的连接客户端到代理这一跳还开着，两跳状态不一致，留下半死连接
X-Debug: trace-me执行不该执行的调试逻辑调试信息泄露到源站日志，或触发额外行为
Connection: Upgrade尝试协议切换升级状态混乱、连接不可用，第 11 讲展开
flowchart LR C["客户端"] --> P["中间代理"] P -->|"剥离逐跳首部并重建"| S["源站"] P --> D["逐跳首部到此消费"] S -->|"按新首部响应"| P P -->|"按另一套首部响应"| C
Via 恰好相反：它是端到端地逐跳追加，每跳把自己的标识加到列表末尾，用来追踪经过了哪些代理；一个被剥离重建，一个被追加保留，方向相反。
推导

约束 → 对策 → 新约束，按空格逐步展开

① 成本来自反复新建：握手 1 RTT 加慢启动数 RTT 每个请求付一遍，对策是让连接活得久一点。

② 持久连接复用 TCP：省掉反复握手，但仍是发一个等一个，等待的 RTT 一个不少。

③ 流水线连发请求：把等待压成一个 RTT，代价是响应必须按请求顺序返回。

④ 按序带来队头阻塞：队首慢堵住全部，流水线挖到头，必须换模型。

每拆一层约束，性能上一台阶，代价是实现更复杂、对中间层要求更高

专题 · HTTP/2

多路复用解决应用层，TCP 层留待 HTTP/3

flowchart LR A["流水线 响应一 慢"] -->|"必须等它发完"| B["响应二 已就绪被堵"] B -->|"依次排队"| C["响应三 被堵"] D["HTTP2 流一 慢"] -->|"帧可交错"| E["HTTP2 流二 先行"] E -->|"互不阻塞"| F["HTTP2 流三 先行"]
✅ 应用层已解决
多路复用（multiplexing）把消息拆成带编号的流与可交错的帧，响应不必按序，快流不等慢流。
⚠️ 传输层仍在
所有流共享一条 TCP，一个包丢失就整条连接等重传，要等 HTTP/3 的 QUIC 才把流在传输层分开。
队头阻塞（head-of-line blocking）：流水线按序堵应用层，HTTP/2 治应用层，HTTP/3 的 QUIC 治 TCP 层。靠多开域名凑并发的域名分片（domain sharding）在 HTTP/2 下反而损害连接聚合，是过时技巧。
规范对照

MDN 的说法 → RFC 怎么写 → 为什么值得知道

MDN 的说法RFC 怎么写为什么值得知道
HTTP/1.1 默认长连接，除非写 Connection: closeRFC 9112 §9.6：默认持久，带 close 的一方在该响应后不得再复用连接close 是强制信号，连接池收到就该立即回收
Connection、Keep-Alive 是逐跳首部，值可被中间节点修改RFC 9110 §7.6.1：代理必须移除 Connection 列出的首部与 Connection 本身，再逐跳重建代理的强制步骤，漏做剥离会让参数泄漏到下一跳
空闲会被关闭，Keep-Alive 可指定保持时间RFC 9112 §9.6：timeout 与 max 是 advisory 建议性，接收方不保证遵守不能当精确契约，客户端要有自己的超时与重连
响应必须按请求顺序返回，于是有队头阻塞RFC 9112 §9.5.2：响应按接收顺序发送，且不推荐新实现启用流水线按序是规范要求，框架内绕不过，只能换 HTTP/2 模型
只有幂等（idempotent）方法能安全地流水线化RFC 9110 §9.2.2 定义幂等；RFC 9112 §9.5.2 禁止对非幂等方法用流水线把幂等从概念变成合规约束，写入型 API 不能假设低时延
读法：MDN 说通常或可以，而你需要确定的对错时，去 RFC 9110 系列找 MUST、SHOULD、MAY 这层规范性措辞。
避坑

三个把层次混为一谈的误解

❌ 流水线解决了队头阻塞
✅ 它只是把请求提前发，响应仍按序，队头阻塞原封不动；解决应用层这层的是 HTTP/2 多路复用。
❌ 长连接永不关闭，连接越多越好
✅ 空闲也占服务器资源，可能被当成拒绝服务攻击（Denial of Service，DoS）的载体；同域名并发连接数有上限，尽快关空闲反而有利。
❌ 逐跳首部应原样转发到源站
✅ 它是「在此消费、按本跳重建」；原样转发会造成参数错配、连接被意外关闭等连锁故障。
