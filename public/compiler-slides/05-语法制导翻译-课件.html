动机

分析器只判「合不合法」，翻译规则随手塞代码里会缠成一团

第4章给了我们两样东西：一棵语法分析树，和驱动它的 LL / LR 机制。但编译器的使命是翻译——

$$\text{算出表达式的值}\quad\text{检查类型匹配}\quad\text{生成目标代码}$$

这些「计算」挂在哪儿？两条旧路都别扭：

😇 随手塞进分析器代码
移进归约的骨架里混进求值、登记、报错，规则一多就缠成一团，改一条牵连一片
🙂 建完树再单独写遍历
每加一种翻译就新写一套遍历，规则与产生式的对应全靠脑子记
💡 本章方案：把翻译规则变成文法的一等公民——每条产生式配一组等式，这就是语法制导定义（Syntax-Directed Definition）
定义

SDD = 文法骨架 ＋ 符号的属性 ＋ 产生式上的语义规则

成分内容在本章计算器例子里
上下文无关文法产生式骨架（第2、4章已备）E → E₁ + T 等
属性（Attribute）挂在每个文法符号上的值，可任意多个E.val、T.val、digit.lexval
语义规则（Semantic Rule）挂在产生式上的等式：左边属性怎么由右部算出E.val := E₁.val + T.val
$$\boldsymbol{\mathrm{SDD} = \mathrm{CFG} + \text{属性} + \text{语义规则（挂产生式）}}$$
读法：给文法「装仪表盘」——每条产生式一个小公式，树一旦建好，每个节点的读数由周围节点唯一决定；编译器只剩一件事：找一个不违心的读表顺序
⚠️ SDD 是声明式的：书写顺序 ≠ 执行顺序——print 写在第一行，恰恰最后才能算
例子

桌面计算器：七条产生式、七条规则，全部只用综合属性

产生式语义规则
L → E nprint(E.val)
E → E₁ + TE.val := E₁.val + T.val
E → TE.val := T.val
T → T₁ × FT.val := T₁.val × F.val
T → FT.val := F.val
F → ( E )F.val := E.val
F → digitF.val := digit.lexval
约定：终结符只有综合属性（digit.lexval 由词法器直接给出），n 是换行；优先级藏在文法层级里——× 离叶子近，+ 离根近
方向

属性按求值方向分两类：综合向上汇总，继承向下、向右下发

flowchart TB C1[子 C₁] --> P[父节点 P] C2[子 C₂] --> P
综合属性 Synthesized Attribute
只由子节点（与自身）算出，自底向上
flowchart TB P2[父节点 P] --> N[节点 N] S[左兄弟 S] --> N
继承属性 Inherited Attribute
由父节点、兄弟节点（与自身）算出，自顶向下或横向
口诀：综合看孩子，继承看爸爸和左哥；终结符只有综合属性（词法器直接给值）
S 属性

只用综合属性的 SDD：后序遍历就是天然求值顺序

SDD 里只出现综合属性 → 称为 S 属性定义（S-Attributed Definition）

$$\text{求值顺序} = \text{分析树的后序遍历（先子后父，自底向上）}$$
💡 关键一跃：LR 的「归约时刻」就是「这棵子树的值全部备齐的时刻」——归约即计算，求值顺序连排都不用排
⚠️ × 比 + 先算，不是规则写对了优先级：× 压在 T → T₁ × F（离叶近、先归约），+ 放在 E → E₁ + T（离根近、后归约）——优先级在文法里，不在规则里
手算

3 × 5 + 4 的注释分析树：每个节点旁标出它算出的值

flowchart TB E1[E.val = 15] --> T1[T.val = 15] T1 --> T2[T.val = 3] T1 --> M[×] T1 --> F2[F.val = 5] T2 --> F1[F.val = 3] F1 --> D1[digit.lexval = 3] F2 --> D2[digit.lexval = 5]
左操作数子树
× 的子树先整体算完（15）
flowchart TB L[L 打印 19] --> E[E.val = 19] L --> N[n 换行] E --> E1[E.val = 15] E --> P[+] E --> T[T.val = 4] T --> F[F.val = 4] F --> D[digit.lexval = 4]
整棵树骨架
+ 等右侧 T 就绪才算（15 + 4）

注释分析树（Annotated Parse Tree）= 节点旁标注属性值的分析树；看值的流向——全部自叶向根

手算

自底向上九步求值：每行恰好对应 LR 的一次归约

步骤用到的产生式求值动作结果
1F → digitF.val := digit.lexval（词法器给出 3）F.val = 3
2T → FT.val := F.valT.val = 3
3F → digitF.val := digit.lexval（5）F.val = 5
4T → T₁ × FT.val := T₁.val × F.val = 3 × 5T.val = 15
5E → TE.val := T.valE.val = 15
6F → digitF.val := digit.lexval（4）F.val = 4
7T → FT.val := F.valT.val = 4
8E → E₁ + TE.val := E₁.val + T.val = 15 + 4E.val = 19
9L → E nprint(E.val)输出 19
与第4章 LR 分析轨迹逐行对照：每次归约恰好对应表里一行，顺序完全一致——S 属性的结构性福利
难点

消除左递归后，累计值在 E′ 左边——综合属性传不进去

LL（自顶向下）必须消除左递归：$E \to E + T \mid T \;\Rightarrow\; E \to T\,E',\ \ E' \to +\,T\,E'_1 \mid \varepsilon$

$$\text{累计值在 } E' \text{ 左边的 } T \text{ 子树里；综合属性只能「子传父」，进不了 } E'$$
💡 出路：引入继承属性 $E'.i$（进入时已累计的值）——父节点把累计值发下来；$E'.s$（离开时的总和）再传回去
记号：$E'_1$ 表示同一条产生式右部里「下一个」$E'$；i 是继承属性，s 是综合属性
SDD

E → T E′ 的完整 SDD：i 向下发累计值，s 向上回总和

产生式语义规则
E → T E′E′.i := T.val　；　E.val := E′.s
E′ → + T E′₁E′₁.i := E′.i + T.val　；　E′.s := E′₁.s
E′ → εE′.s := E′.i
T → F　/　F → digit同计算器文法（综合属性 val 照常上传）
读法：i 是「进门时已累计的值」（继承），s 是「出门时的总和」（综合）；ε 产生式把入口值原样封口上交

L 属性

L 属性只许「向左看」：两条来源限制换无环保证

$$\text{产生式 } A \to X_1 X_2 \cdots X_n \text{ 中，} X_j \text{ 的继承属性只依赖：}$$
  1. 父节点 A 的继承属性；
  2. Xⱼ 左边兄弟 X₁…Xⱼ₋₁ 的任意属性（综合、继承都行）。
💡 L 取 Left 之意：信息只从左往右流。综合属性不受限制；S 属性定义天然是 L 属性的特例
⚠️ 禁止「向右看」：依赖右侧兄弟可能成环（a 等 b、b 等 a），任何求值顺序都不存在
例子

float x, y：类型在最左，靠继承属性横向送到每个 id

产生式语义规则
D → T LL.in := T.type
T → intT.type := integer
T → floatT.type := float
L → L₁ , idL₁.in := L.in　；　addtype(id.entry, L.in)
L → idaddtype(id.entry, L.in)
  1. T → float：T.type = float
  2. D → T L：L.in = float
  3. L → L₁ , y：L₁.in = float
  4. addtype(y.entry, L.in)：y 登记为 float
  5. L₁ → x：x 登记为 float
检验：全部继承属性只依赖父节点的继承属性（合法①）——L 属性限制通过
SDT

SDT = SDD ＋ 时刻表：动作嵌进产生式右部，位置即时机

把语义规则改成可执行的语义动作，嵌进产生式右部的具体位置 → 语法制导翻译方案（Syntax-Directed Translation Scheme, SDT）；动作全贴最右端 = 后缀 SDT（Postfix SDT）

后缀 SDT 的产生式对应语义规则
L → E n { print(E.val) }print(E.val)
E → E₁ + T { E.val := E₁.val + T.val }E.val := E₁.val + T.val
T → T₁ × F { T.val := T₁.val × F.val }T.val := T₁.val × F.val
LR 分析 3 × 5 + 4：归约 F→digit（得 3、5、4）→ 归约 T→T₁×F（得 15）→ 归约 E→E₁+T（得 19）→ 归约 L 触发 print——与 5.2 的九步求值表完全一致。这就是 yacc / bison 里写 { … } 动作的原理
⚠️ LL 中动作可放任意位置：用继承属性的放该符号左边，算综合属性的放最右端——排错位置，用到的属性还没出生
避坑

本章三个高频误区，个个都和「顺序」有关

❌ 语义规则按书写顺序从上往下执行
✅ SDD 是声明式等式系统，执行顺序由依赖关系决定；print(E.val) 写在第一行，恰恰最后才算
❌ 优先级是语义规则里 +、× 写对了
✅ 规则只有两条干巴巴的等式；优先级编码在文法层级：× 离叶近先归约，+ 离根近后归约。改优先级改文法
❌ 继承属性只能父传子，想依赖谁都行
✅ 左侧兄弟传值更常见（E′.i := T.val）；但依赖右侧兄弟可能成环——L 属性「只向左看」正是无环的充分保证
收束

主线问题的答案：挂在产生式上，让依赖图和分析器决定顺序

❓ 本章问题：怎样把翻译规则系统地挂在文法上，让属性求值顺序与语法分析自动匹配？
✅ 答案：规则写成产生式上的语义规则（SDD）；属性分方向——综合自底向上（S 属性，与 LR 归约同步）、继承受 L 限制（只向左看，保证无环）；依赖图拓扑序给出合法顺序；SDT 把动作钉在产生式位置上，时机随分析器
⚠️ 遗留问题：SDD 只说「算什么」，没说「何时算」——SDT 补上时刻表；第6章把语义动作从「算数」换成「发射三地址码」

小结

三句话讲完第5章

1解决什么：语法分析只判结构合法，本章解决「结构之上怎么算」——翻译规则系统挂上文法，顺序与分析兼容
2核心机制：SDD = CFG + 属性 + 语义规则；综合向上（S 属性配 LR），继承受 L 限制只向左看；依赖图拓扑序定顺序；SDT 把「算什么」落实为「何时算」
3承上启下：第4章给挂点与时钟，本章给框架，第6章让动作发射三地址码
$$\boldsymbol{\mathrm{SDD} = \mathrm{CFG} + \text{属性} + \text{语义规则}}\;\; \text{综合向上} \cdot \text{继承向左}\;\;\text{——合上书也要能默写}$$
