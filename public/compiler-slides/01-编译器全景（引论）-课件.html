主线

机器只懂 0/1，逼着翻译被拆成七步流水线

1机器只懂 0 和 1，人写高级语言——必须有人翻译
2一步直译太复杂——工程上只能拆成小步骤
3拆成七个阶段：每步只做一种变换，输入输出明确
4同一份信息换七次表示：字符→记号→树→三地址码→机器指令
5代价：各阶段内部怎么实现——留给第 2–11 章
这条链就是本章的目录：1→动机页，2→编译 vs 解释，3→七阶段总览与手算，5→收束页。
动机

机器只懂 0/1，而一句赋值里藏着四件性质不同的事

中央处理器只认识 0 和 1 组成的指令：取数、加法、跳转。人却写这样的代码：

position = initial + rate * 60
😇 幻想：一步直译
直接把这行字符翻译成机器指令——断词、运算次序、类型转换、寄存器分配四件事缠在一起，做一次就是灾难。
🙂 现实：拆成小步
每步只做一种变换：先断词，再认结构，再查类型，再摊平，最后落指令——每步简单到可以实现。
💡 本章方案：把翻译做成一条七个阶段的流水线，每段交什么、接什么都写死。
定义

编译器产出目标程序，解释器边译边执行——Java 走中间路

📖 编译器（Compiler）
先整体翻成目标程序，再反复运行。总开销 = 编译时间（一次）+ 运行时间（每次）。代表：gcc、clang。
🗣️ 解释器（Interpreter）
不产出目标程序，逐句现场口译。总开销 ≈ 每句解释开销 × 执行句数。代表：早期 BASIC、交互式 shell。
Java 混合模式：javac → 字节码（Bytecode）→ JVM 解释 + JIT 即时编译热点
读法：语言不分编译型/解释型，分型的只是「实现」——判断标准是运行时还需不需要翻译官在场。

手算①

词法分析：字符流切成记号流，顺手登记符号表

输入字符流：position = initial + rate * 60（三个变量为 float，60 为 int）

⟨id, 1⟩ ⟨=⟩ ⟨id, 2⟩ ⟨+⟩ ⟨id, 3⟩ ⟨*⟩ ⟨60⟩
条目编号标识符后续阶段会补充的信息
1position类型 float、存储地址（语义分析、代码生成时填）
2initial类型 float、存储地址
3rate类型 float、存储地址
💡 id 后面的数字是符号表条目编号，不是值；空白被丢弃，括号配对不归这步管。
手算②

语法分析：树的形状精确编码「先乘后加再赋值」

flowchart TB A["="] --> B["⟨id,1⟩ position"] A --> C["+"] C --> D["⟨id,2⟩ initial"] C --> E["*"] E --> F["⟨id,3⟩ rate"] E --> G["60"]

记号流按文法组织成语法树（Syntax Tree）：

  • 根是 =：赋值最后发生
  • * 是 + 的子树 → rate * 60 先算
  • 叶子是三个标识符与常量 60
树的高低 = 运算次序。类型合不合法，这一步还不管。
手算③

语义分析：类型检查在 60 处插入 inttofloat

flowchart TB A["="] --> B["⟨id,1⟩ position"] A --> C["+"] C --> D["⟨id,2⟩ initial"] C --> E["*"] E --> F["⟨id,3⟩ rate"] E --> G["inttofloat"]:::chg G --> H["60"] classDef chg fill:#fffaf0,stroke:#dd6b20,stroke-width:3px,color:#744210

rate 是 float，60 是 int，乘法要求两边类型一致：

* 的右孩子：60 ⟹ inttofloat(60)
归属判定：插入转换是语义分析（类型检查）的决定；中间代码生成只是忠实翻译它。
手算④

三地址码四条进、两条出：常量折叠把翻译挪到编译期

④ 中间代码生成：树 → 三地址码（每条至多一个运算符、三个操作数）

t1 = inttofloat(60)　　t2 = id3 * t1　　t3 = id2 + t2　　id1 = t3

⑤ 机器无关优化：inttofloat(60) 是编译期可算的常量 → 折叠为 60.0；t3 只用一次 → 合并

t1 = id3 * 60.0　　id1 = id2 + t1
✍️

手算⑤

代码生成：三地址码落成五条浮点机器指令

指令含义
LDF R2, id3rate 装入浮点寄存器 R2
MULF R2, R2, #60.0R2 ← R2 × 60.0
LDF R1, id2initial 装入 R1
ADDF R1, R1, R2R1 ← R1 + R2
STF id1, R1结果写回 position

这一步做两件事：指令选择（用哪条机器指令）与寄存器分配（值放哪个寄存器）。

第⑦步目标机相关优化再做指令调度、窥孔优化——本例已足够短，原样输出。
一句高级语言 → 五条机器指令，主线问题已亲手答完。

划分

前端只懂语言、后端只懂机器，中间表示当接口

🗺️ 前端（Front End）
词法 + 语法 + 语义 + 中间代码生成，外加机器无关优化的大部分。依赖源语言，不依赖目标机。
⚙️ 后端（Back End）
代码生成 + 目标机相关优化。依赖目标机，不依赖源语言。
两块之间只用一个约定好的中间表示（如三地址码）交接
接口定得越稳，两边越能独立演化——字节码就是 Java 世界的中间表示。
算账

m×n 对 m+n：新增一门语言只写 1 个前端

😇 不划分
每对「语言 × 机器」一个编译器
总数 = m × n = 10 × 10 = 100 个
🙂 划分后
m 个前端 + n 个后端，接口拼接
总数 = m + n = 10 + 10 = 20 个
$$m=n=10:\quad \boldsymbol{m \times n = 100} \;\;\text{vs}\;\; \boldsymbol{m + n = 20}$$
💡 新增一门语言：不划分追加 n=10 个；划分后只写 1 个前端，立刻获得全部 10 台机器的后端。GCC、LLVM 靠这个结构覆盖几十种语言 × 几十种架构。
伴生

符号表与错误处理器贯穿全程，不是流水线的一环

📋 符号表（Symbol Table）
词法阶段创建并登记标识符 → 语义分析往里填类型 → 代码生成往里查名字、写地址。贯穿全程的共享数据库。
🚨 错误处理器（Error Handler）
词法错误（非法字符）、语法错误（缺括号）、语义错误（类型不匹配）……任何阶段都可能报错，且要求尽可能多报错并继续编译。
记忆口诀：词法管「词」、语法管「形」、语义管「义」；符号表和错误处理在流水线旁边，伴生全程。
外溢

「分阶段处理语言」的技术，远不止编译器在用

  • 数据库 SQL 引擎：解析 → 语义检查 → 生成查询计划（中间表示）→ 优化 → 执行，与编译器流水线同构。
  • 静态检查工具：找空指针、未初始化变量——只复用前端，在语法树上检查，不生成代码。
  • 优化思想外溢：常量折叠、公共子表达式消除出现在解释器、JIT、电子表格重算引擎里。
  • 新硬件配套软件：每出一种新芯片（GPU、AI 加速器），第一件软件工作就是为它写后端。
💡 本章地图不只属于编译器——凡是「把一种语言变成另一种可执行形式」的地方，它都在。
避坑

三个高频误区：语言不分型、inttofloat 归语义、符号表贯穿全程

❌ 「Java 是解释型语言，C 是编译型语言」
✅ 语言本身不分编译型/解释型，分型的只是实现方式。判断标准：这个实现产不产出可独立运行的目标程序。
❌ 「inttofloat 是中间代码生成阶段加的」
✅ 插入类型转换属语义分析（类型检查）；中间代码生成只是忠实翻译，是执行者不是决策者。
❌ 「符号表是词法阶段用完即弃的临时结构」
✅ 符号表由词法阶段创建，但贯穿全程：语义分析写类型、代码生成查名字写地址。
收束

主线问题已答：七次换表示；遗留问题：各方框内部怎么实现

答一步直译太复杂 → 拆成七阶段，每阶段只做一种变换，输入输出严格衔接

小结

三句话讲完第1章

1解决什么：机器只懂 0/1，高级语言必须被翻译——本章回答翻译为什么被做成七阶段流水线，每阶段吃什么、吐什么，并给出全书地图。
2核心机制：七阶段依次换表示（字符→记号→树→带类型的树→三地址码→优化三地址码→机器指令）；前端/后端用中间表示当接口，m×n 省成 m+n；符号表与错误处理贯穿全程。
3承上启下：本章是起点、只画地图；第2章用一个小翻译器跑通全流程，第3、4章把词法、语法做成严肃算法。
七个阶段：词法 → 语法 → 语义 → 中间代码生成 → 机器无关优化 → 代码生成 → 目标机相关优化　——合上书也要能默写
