4.1为什么需要哈希：直接寻址表的空间困境

第3章给了我们 O(n lg n) 的排序和 O(lg n) 的二分查找。但很多应用——编译器的符号表、数据库的索引、路由器的转发表——要的不是"排好序"，而是频繁的三种操作：插入一条记录、删除一条记录、按关键字查一条记录。支持这三种操作的数据结构叫字典（Dictionary）。问题是：单次查找能不能比 O(lg n) 更快？

最快的查找是"根本不查"：直接按关键字当下标。假设关键字的全域 U = {0, 1, …, 999}，就开一个 1000 格的数组 T，键为 k 的记录直接放 T[k]。这就是直接寻址表（Direct-Address Table）：查找、插入、删除都是一次数组访问，严格 O(1)，连"期望"都不需要。

代价立刻显现。假设我们只在表里存 5 个键 {10, 230, 451, 672, 999}：

指标数值说明
全域大小 |U|1000数组必须开 1000 格
实际存储的键数 n5只有 5 格真的有用
空间利用率5 / 1000 = 0.5%995 格（99.5%）被浪费
查找时间Θ(1)一次数组下标访问
空间复杂度Θ(|U|)与全域成正比，与 n 无关

1000 格浪费 995 格还只是难看。换成真实的键就灾难了：如果键是 64 位整数，|U| = 2⁶⁴ ≈ 1.8 × 10¹⁹，哪怕只存 5 条记录，直接寻址表也要 1.8 × 10¹⁹ 格——按每格 1 字节算是 180 亿 GB，地球上没有任何机器装得下。

💡 关键一跃

直接寻址的浪费来自"表的大小跟着全域走，而不是跟着实际数据走"。出路只有一条：造一个函数 h，把大全域 U 压缩到一张只与 n 相称的小表 {0, …, m−1}。这个 h 就是散列函数（Hash Function），小表就是散列表（Hash Table），查找变成查 T[h(k)]。

⚠️ 常见误区

以为散列函数能"设计得足够巧"从而避免冲突。错。鸽巢原理堵死了这条路：|U| > m 时，至少有两个键被压进同一格。本例 |U| = 1000、m 若取 10，则至少有一格要承接 ⌈1000/10⌉ = 100 个键。冲突不是设计失误，是压缩的必然代价——所以本章的重心不是"避免冲突"，而是"冲突来了怎么办"。

4.2链接法：冲突了，就在槽上挂一条链

上一节说冲突必然发生。第一个应对方案最直白：既然多个键会落到同一格，就让每格不是一个记录，而是一条链表的头指针。所有散列到槽 j 的键都串在 T[j] 的链表上。这就是链接法（Chaining）：插入先算 h(k) 再插到链头（O(1)）；查找先算 h(k) 再顺链逐个比较；删除同理。

查找快不快，取决于平均每条链有多长。设表有 m 个槽、存了 n 个键，定义装载因子（Load Factor）：

α = nm = 平均每槽链长

在简单均匀散列假设（Simple Uniform Hashing，每个键等可能落到任一槽）下，不成功查找要扫完整条链，期望探查约 1 + α；成功查找平均只扫半条链，期望探查约：

1 + α2

✅ 判定规则

链接法下：不成功查找期望探查 ≈ 1 + α；成功查找期望探查 ≈ 1 + α/2。只要 α 保持常数（常用约定 α ≤ 1，即 n ≤ m），两者都是 O(1)。所以工程对策是：n 快超过 m 就换更大的表重新散列（rehash）。

⚠️ 常见误区

把"期望 O(1)"记成"最坏 O(1)"。错。若所有 n 个键碰巧散列到同一槽，链长为 n，一次查找就是 Θ(n)——这是最坏情况。期望 O(1) 说的是"对平均的键、在均匀散列假设下"。4.4 节的全域散列正是为了堵这个最坏情况的口子。

4.3开放寻址：不挂链，就在表里继续探

链接法用指针和堆内存，缓存不友好。开放寻址（Open Addressing）走另一条路：所有元素都存在表本身里，不放链表；h(k) 的槽被占了，就按一个确定规则去找下一个槽，直到撞见空槽。查找时沿同一条"探查序列"走，遇空槽即判定不存在。因为元素不超出表，必有 n ≤ m，即 α ≤ 1。

探查序列由散列函数扩展而来：h(k, i) 表示键 k 的第 i 次探查（i = 0, 1, …, m−1）。三种经典规则：

线性探测（Linear Probing）：h(k, i) = ( h′(k) + i ) mod m
二次探测（Quadratic Probing）：h(k, i) = ( h′(k) + c₁i + c₂i² ) mod m
双重散列（Double Hashing）：h(k, i) = ( h₁(k) + i · h₂(k) ) mod m

线性探测每次往后挪 1 格；二次探测按平方步长跳；双重散列用第二个函数 h₂ 决定步长——不同键的步长不同，探查序列也最"散"。注意双重散列必须保证 h₂(k) 与 m 互质且永不为 0，否则探查序列会卡死或漏槽；常用技巧就是 m 取 2 的幂、或像下面这样让 h₂ 输出落在 {1, …, m−2}。

完整例子（手算全程）。m = 13，h₁(k) = k mod 13，h₂(k) = 1 + (k mod 11)，空表插入 14 和 79。

插入 14：i = 0，h(14, 0) = h₁(14) = 14 mod 13 = 1（14 = 1×13 + 1）。槽 1 为空，直接放入。共探查 1 次。

插入 79：

  • i = 0：h(79, 0) = h₁(79) = 79 mod 13。79 = 6×13 + 1，所以 h₁(79) = 1——槽 1 已被 14 占了，冲突。
  • 算步长：h₂(79) = 1 + (79 mod 11)。79 = 7×11 + 2，所以 h₂(79) = 1 + 2 = 3。
  • i = 1：h(79, 1) = (1 + 1×3) mod 13 = 4。槽 4 为空，放入。共探查 2 次，序列是 1 → 4。

此后查找 79 必须重走同一条序列：先看槽 1（是 14，不是），再跳 3 格看槽 4（命中）。若走到某个空槽还没命中，就断定 79 不在表里。

探查次数到底多少？这是开放寻址的核心账目。在均匀散列假设（每个键的探查序列等可能是 m! 种排列之一）下：

不成功查找期望探查 ≤ 11 − α

代入实数感受它有多敏感：α = 0.5 时 1/(1−0.5) = 2 次；α = 0.9 时 1/(1−0.9) = 10 次；α = 0.99 时 1/0.01 = 100 次。表装到九成满，代价翻五倍；装到九成九，直接退化到没法用。所以开放寻址的工程铁律是 α 控制在 0.5～0.7 以下。

线性探测不用均匀假设也能算，常用近似公式：成功查找约 ½(1 + 1/(1−α))，不成功约 ½(1 + 1/(1−α)²)。代入 α = 0.5：成功 ≈ ½(1+2) = 1.5 次，不成功 ≈ ½(1+4) = 2.5 次；代入 α = 0.9：成功 ≈ ½(1+10) = 5.5 次，不成功 ≈ ½(1+100) = 50.5 次——比双重散列的 10 次差得多。

线性探测为什么更吃亏？因为聚集（Clustering）：已占用的槽会连成越来越长的"堵塞段"，新键落进堵塞段的任何位置都要一路走到段尾，而走完之后又让段更长——堵的越堵。准确说这是一次聚集（Primary Clustering）：线性探测中，长为 L 的占用段以 (L+2)/(2m) 左右的概率被下一个键加长，雪球越滚越大。二次探测缓解了它，但若两个键起点相同，整条序列仍相同（二次聚集）；双重散列让步长随键变化，把聚集压到最轻，因此最接近均匀假设。

💡 关键一跃

开放寻址的全部学问就浓缩在 1/(1−α) 这一条曲线上：代价不取决于 n 或 m 的绝对值，只取决于"表有多满"。看住 α，就看住了性能。

⚠️ 常见误区

在开放寻址表里"直接删掉"一个键。错。把槽清空会斩断别人的探查序列——上例中若把槽 1 的 14 直接抹掉，查找 79 时会在槽 1 遇空而误判"不存在"。正确做法是放一个特殊标记 DELETED：查找时跳过它继续探，插入时可复用它。但 DELETED 多了同样拖慢查找，所以开放寻址不适合频繁删除的场景。

4.4全域散列：把"运气"从输入手里夺回来

到目前为止，所有"期望 O(1)"都建立在均匀散列假设上。但假设可能靠不住：散列函数是固定的，而现实输入往往有规律，甚至更糟——如果对手知道你的 h，他可以故意挑选全部散列到同一槽的 n 个键，把你的链接法打成 Θ(n) 链表（这正是 2011 年针对多种语言哈希表的 HashDoS 攻击的原理）。固定函数 + 最坏输入 = 必输。出路是：函数不固定，运行时随机选。

全域散列（Universal Hashing）的做法：备一个散列函数的集合 H，每次建表时从 H 里随机抽一个 h 来用。H 满足全域性质——

✅ 定义

若对任意两个不同的键 k ≠ l，从 H 中随机选 h 时二者冲突的概率满足 Pr[ h(k) = h(l) ] ≤ 1/m，则称 H 是全域的（universal）。注意 1/m 正是"随机瞎撞"的冲突率——全域族把任何一对键的冲突率压到了理论下限。

一个经典的可构造全域族：取素数 p ≥ |U| 能覆盖所有键，对 a ∈ {1, …, p−1}、b ∈ {0, …, p−1} 定义

hab(k) = ( ( ak + b ) mod p ) mod m

所有这样的 hab 构成全域族。小例子（手算全程）：p = 17，m = 6，取 a = 3、b = 5，即 h(k) = ((3k + 5) mod 17) mod 6。

键 k3k + 5mod 17mod 6h(k)
103535 − 34 = 111
2111111 − 6 = 55

看结果：h(10) = 1、h(2) = 5 不冲突；h(27) = 1 与 h(10) 冲突。这正说明全域散列不承诺"哪个函数永远不冲突"——对这一个 (a, b) = (3, 5)，键对 {10, 27} 就是撞了。全域性质承诺的是另一件事：让 (a, b) 在 a ∈ {1,…,16}、b ∈ {0,…,16} 共 16×17 = 272 个函数里均匀随机抽，任何固定键对（包括 {10, 27}）撞上它的概率 ≤ 1/6。对手不知道你抽中哪个函数，就无法准备必撞的输入——最坏输入被随机化消解成了期望保证。

✅ 判定规则

链接法 + 全域散列 ⇒ 每个键所在链的期望长度 ≤ 1 + α，从而查找、插入、删除的期望时间都是 O(1)（α = O(1) 时）。这个期望是对"随机选函数"取的，对任何输入序列都成立——不再需要对输入做任何假设。

⚠️ 常见误区

以为全域散列是"找一个更好的固定函数"。恰恰相反：它承认没有固定函数能对所有输入都好，于是把随机性从"输入分布"转移到"函数选择"上。期望是抛自己的硬币，不是赌对手的善意。

4.5哈希在字典问题上的地位：用顺序换速度

至此本章拿到了期望 O(1) 的字典。把它放回阶段②的版图里，和第3章的排序、第5章的红黑树对比，分工就清楚了：

操作已排序数组（第3章）哈希表（本章）红黑树（第5章）
查找 SEARCHO(lg n) 最坏O(1) 期望O(lg n) 最坏
插入 INSERTO(n)（要挪位置）O(1) 期望O(lg n) 最坏
删除 DELETEO(n)O(1) 期望O(lg n) 最坏
最小值 MINIMUMO(1)不支持（只能全表扫 Θ(n)）O(lg n) 最坏
前驱/后继 SUCCESSORO(1)（按下标）不支持O(lg n) 最坏
按序遍历O(n) 且天然有序输出顺序无意义O(n) 中序遍历即有序

看表就明白：哈希表赢得 SEARCH/INSERT/DELETE 的期望常数，付出的代价是整张表"忘记了键之间的顺序"——散列函数把相近的键打散到远处，是有意为之（打得越散越均匀）。所以问"比 1000 小的最大键是谁"，哈希表只能一格一格翻。

💡 关键一跃

一句话记住本章：哈希表用"放弃顺序"换来"期望常数"。不需要顺序的操作（纯成员查询、去重、计数）全用哈希；需要 MINIMUM、SUCCESSOR、范围查询、按序输出时，请等第5章的红黑树——它用 O(lg n) 的存取代价保住全序。

🃏概念卡：本章概念的一分钟画像

翻面前先自问：这个概念我能用一句话讲清楚吗？

概念卡 1
直接寻址表（Direct-Address Table）
点击翻面 →
定义键 k 直接存数组 T[k]，键就是下标。
解决问题全域小时提供最纯粹的 O(1) 字典，连冲突概念都没有。
直觉酒店按房号入住：报 305 直接上 3 楼，不用找。
误区以为它"最快所以最好"——空间 Θ(|U|)，全域一大就报废。
何时用键域极小且稠密时（如 ASCII 字符计数，|U| = 128）。
概念卡 2
散列函数（Hash Function）
点击翻面 →
定义把全域 U 映射到 {0,…,m−1} 的函数 h，查找改为查 T[h(k)]。
解决问题让表的大小跟 n 走而不是跟 |U| 走，治直接寻址的空间爆炸。
直觉把全国 14 亿人按生日分到 366 个柜子，柜小但必撞人。
误区以为能设计出无冲突的 h——鸽巢原理：|U| > m 时冲突必然。
何时用一切哈希表的心脏；4.4 还要给它再加一层"随机选函数"。
概念卡 3
链接法（Chaining）
点击翻面 →
定义每个槽挂一条链表，同槽键串在链上；查找 = 定位槽 + 顺链扫。
解决问题最直接的冲突解决方案，删除干净，α 可以大于 1。
直觉同一信箱格塞多封信，翻一摞总能找到。
误区把期望 1+α/2 当最坏——全撞一槽时查找退化为 Θ(n)。
何时用删除频繁、或不想操心 α 上界的场景（Java HashMap 即此法）。
概念卡 4
装载因子（Load Factor）
点击翻面 →
定义α = n/m，键数比槽数，衡量表"有多满"。
解决问题把所有哈希表的性能公式统一成一个变量：代价都是 α 的函数。
直觉停车场上座率：九成满时找车位要绕十圈（1/(1−0.9) = 10）。
误区以为 n 大就慢——n = 10⁶ 但 α = 0.5，照样期望 2 次探查。
何时用决定何时 rehash 扩容的唯一指标（链接法 ≤1，开放寻址 ≤0.7）。
概念卡 5
开放寻址（Open Addressing）
点击翻面 →
定义元素全存表内，冲突时按探查序列 h(k,0), h(k,1), … 找下一空槽。
解决问题不开堆内存、不用指针，缓存友好，适合超大规模紧凑存储。
直觉电影院对号入座，座位被占就按约定往后找空位。
误区直接删键清空槽——会斩断他人探查序列，必须置 DELETED 标记。
何时用插入多删除少、内存敏感（Python dict、Redis 的哈希）。
概念卡 6
全域散列（Universal Hashing）
点击翻面 →
定义函数族 H 满足：任意 k ≠ l，随机取 h 时冲突概率 ≤ 1/m；建表时随机抽一个用。
解决问题固定 h 会被恶意输入打成最坏 Θ(n)；随机选 h 让最坏输入无处下手。
直觉抽签决定分柜规则：对手不知道规则，就没法故意挤同一个柜子。
误区以为它保证每次运行都快——它保证的是对函数选择的期望，不消最坏槽。
何时用任何输入不可信的公开服务（防 HashDoS）；理论证明期望 O(1) 的基石。

📝分层习题

L1 概念辨析

判断对错并说明理由：(1) "只要散列函数设计得足够均匀，链接法的最坏查找时间也可以是 O(1)。" (2) "装载因子 α = 2 对链接法来说一定意味着性能崩溃，必须立刻扩容。"

提示

(1) 区分"期望"与"最坏"：最坏情况由什么决定？(2) 把 α = 2 代进 1 + α/2，看看到底是多少次。

完整解答

(1) 错。最坏情况指"所有 n 个键落进同一槽"，此时链长 n，查找 Θ(n)。散列函数再均匀也改变不了一个固定函数存在最坏输入这一事实（鸽巢原理）；均匀性只能让期望探查 = 1 + α/2，期望不是最坏。要把最坏也消掉，只能靠 4.4 的随机化（全域散列），且那也只是期望意义。

(2) 说法过头，错在"崩溃"。α = 2 时成功查找期望探查 = 1 + 2/2 = 2 次，不成功 ≈ 1 + 2 = 3 次——仍是常数，只是比 α = 1 的 1.5 次差了约三分之一。链接法允许 α > 1，是否扩容是时间/空间的权衡，不是硬性崩溃点。（若是开放寻址则不同：α 必须 < 1，α → 1 时 1/(1−α) 才会真的"崩溃"。）

L1 概念辨析

下列场景中，哪些适合用哈希表、哪些应当等第5章的红黑树？说明一句话理由：(a) 编译器查变量名是否已声明；(b) 每分钟输出当前在线人数最少的服务器；(c) 判重：10 亿条日志里去掉重复 IP；(d) 按分数段查询"排名在 [100, 200] 的考生"。

提示

对每个场景问一句：它需要"顺序"吗（最小值/区间/排名），还是只需要"按 key 存取"？

完整解答

(a) 哈希表：纯成员查询，不需要顺序。(b) 红黑树：反复要 MINIMUM，哈希表取最小值要全表扫。(c) 哈希表：判重只需"在不在"，期望 O(1) 最优；10 亿条若用排序是 O(n lg n) 还多花内存。(d) 红黑树：排名/区间是典型有序操作，哈希表完全无法支持。一句话：要顺序选树，不要顺序选哈希。

L2 手算推导

m = 11，h(k) = k mod 11，链接法（新键插链头），依次插入 10, 22, 31, 4, 15, 28, 17。(1) 画出最终 11 个槽的链内容；(2) 求 α；(3) 求成功查找与不成功查找的期望探查数；(4) 实测：计算查找每个已存键所需的比较次数，求平均，与公式对比。

提示

先逐个算 k mod 11 落槽（注意 22 = 2×11 + 0，槽 0 也是合法槽）；再数每条链上各键离链头的距离。

完整解答

(1) 逐键计算：10 mod 11 = 10；22 mod 11 = 0（22 = 2×11 + 0）；31 mod 11 = 9（31 = 2×11 + 9）；4 mod 11 = 4；15 mod 11 = 4（15 = 1×11 + 4）；28 mod 11 = 6（28 = 2×11 + 6）；17 mod 11 = 6（17 = 1×11 + 6）。

最终表（链头在左）：槽 0 → [22]；槽 4 → [15, 4]；槽 6 → [17, 28]；槽 9 → [31]；槽 10 → [10]；槽 1、2、3、5、7、8 为空。

(2) n = 7，m = 11，α = 7/11 ≈ 0.636。

(3) 成功查找期望探查 = 1 + α/2 = 1 + 7/22 ≈ 1.32 次；不成功查找期望探查 ≈ 1 + α = 1 + 7/11 ≈ 1.64 次。

(4) 实测各键比较次数：22→1，31→1，10→1，15→1（链头），4→2，17→1（链头），28→2。合计 1+1+1+1+2+1+2 = 9 次，平均 9/7 ≈ 1.29。与公式值 1.32 接近——公式是期望，单个实例允许在其上下波动。

L2 手算推导

开放寻址，m = 13，双重散列 h₁(k) = k mod 13，h₂(k) = 1 + (k mod 11)。表中已有：槽 1 存 14，槽 4 存 79（即正文例子）。(1) 插入 40，写出完整探查序列（每步给出算式）；(2) 此时 n = 3，求 α，并给出均匀散列假设下"下一次不成功查找"的期望探查上界；(3) 若继续装到 α = 0.75，上界变为多少？说明趋势。

提示

40 mod 13 的余数；h₂ 的步长；逐 i = 0, 1, 2 … 算 (h₁ + i·h₂) mod 13 直到撞空槽。

完整解答

(1) h₁(40) = 40 mod 13：40 = 3×13 + 1，故 h₁(40) = 1。i = 0：槽 1 被 14 占用，冲突。算步长：40 = 3×11 + 7，h₂(40) = 1 + 7 = 8。i = 1：(1 + 1×8) mod 13 = 9，槽 9 为空，插入。探查序列：1 → 9，共 2 次探查。

(2) n = 3，m = 13，α = 3/13 ≈ 0.231。不成功查找期望探查上界 = 1/(1−α) = 1/(1 − 3/13) = 13/10 = 1.3 次。

(3) α = 0.75 时，1/(1−0.75) = 1/0.25 = 4 次。从 1.3 → 4：α 不到三倍地增长，上界却超过三倍——1/(1−α) 是双曲线，越接近 1 越陡，这就是开放寻址必须把 α 压在 0.7 左右的原因。

L3 建模应用

你在为校园一卡通系统设计"刷卡判重"模块：全校约 30,000 张有效卡，卡号是 9 位十进制数（000000001–999999999）。高峰期每秒要处理 5,000 次"此卡号是否有效"的查询，要求单次查询平均不超过约 2 次探查，且卡号段分布有明显规律（连号发放）。请给出方案：选直接寻址、链接法还是开放寻址？表长 m 取多少？如何抵御"卡号连号导致分布不均"？估算你的方案是否达标。

提示

先算直接寻址要多少空间；再由目标"约 2 次探查"反推 α 的上限；最后想：输入有规律时，靠什么把"期望"保住？

完整解答

排除直接寻址：卡号全域 |U| = 10⁹，直接寻址要 10⁹ 格（按每格 4 字节约 4 GB），却只存 3×10⁴ 张卡，利用率 0.003%——空间爆炸，否决。

选型与定 m：查询极高频、无删除外的复杂操作，选开放寻址（缓存友好）或链接法均可；这里取开放寻址双重散列。目标：不成功查找（多数刷卡其实对应有效卡，但按上界设计更稳）期望探查 ≤ 2，即 1/(1−α) ≤ 2 ⟹ α ≤ 0.5。于是 m ≥ n/0.5 = 30,000/0.5 = 60,000，取 2 的幂或素数，如 m = 65,521（素数，α = 30,000/65,521 ≈ 0.458）。代入上界：1/(1−0.458) ≈ 1.84 次 ≤ 2，达标。每秒 5,000 次 × 1.84 ≈ 9,200 次探查，常数级开销，轻松满足。

对抗连号规律：输入有规律意味着"简单均匀散列假设"不可靠——若用固定 h 且 h 与连号模式共振，某段槽会被打爆。对策是全域散列：h_ab(k) = ((ak+b) mod p) mod m（p 取大于 10⁹ 的素数），每次服务启动随机抽 (a, b)，使任何固定卡号集合的期望链长/探查数都 ≤ 设计值，连号也奈何不了随机函数。再配一条运维规则：监控实际 α，超过 0.5 即扩容 rehash 到下一个素数表长。

对着空气（或室友）说出这三句。说卡壳的那句，回去重读对应小节。

句1：这章解决什么问题？——
参考答案：字典问题——动态集合的插入、删除、按 key 查找。排序加二分只能做到 O(lg n)，本章问能否更快：答案是期望 O(1)，代价是放弃键之间的顺序。
句2：核心机制是什么？——
参考答案：散列函数把大全域压进 m 槽小表（空间从 Θ(|U|) 降到 Θ(n)）；冲突必然发生，用链接法（槽上挂链，期望探查 1+α/2）或开放寻址（表内探查，上界 1/(1−α)）解决；装载因子 α 是唯一要盯住的变量；全域散列通过随机选函数，把期望保证从"靠输入善良"变成"靠自己抛硬币"。
句3：它和前后章怎么分工？——
参考答案：第3章排序管"批量整理"、给 O(lg n) 查找；本章哈希管"高频按 key 存取"，期望 O(1) 但不支持 MINIMUM、前驱后继、按序遍历；需要有序操作的字典交给第5章红黑树，它用 O(lg n) 最坏代价保住全序。
