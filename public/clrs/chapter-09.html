9.1贪心何时是对的：活动选择问题

第8章的矩阵链乘里我们看到："先乘最小相邻对"这个贪心直觉是错的。它带出一个问题：到底什么问题允许每步只拿当前最优？最干净的正面例子是活动选择（Activity Selection）。

问题。n 个活动争用同一间教室，活动 i 占用区间 [sᵢ, fᵢ)。选最多的互不重叠活动。CLRS 的经典实例（已按结束时间排序）：

i1234567891011
sᵢ130535688212
fᵢ4567991011121416

贪心策略：每步选"结束最早且与已选兼容"的活动。完整手算：

  • 选 a₁（结束 4）。跳过 a₂（开始 3 < 4）、a₃（0 < 4）。
  • 选 a₄（开始 5 ≥ 4，结束 7）。跳过 a₅（3<7）、a₆（5<7）、a₇（6<7）。
  • 选 a₈（开始 8 ≥ 7，结束 11）。跳过 a₉（8<11）、a₁₀（2<11）。
  • 选 a₁₁（开始 12 ≥ 11，结束 16）。

结果 {a₁, a₄, a₈, a₁₁}，共 4 个活动，即最优。总耗时排序 Θ(n log n) + 扫描 Θ(n)。

💡 关键一跃

贪心 = DP 的特权版。DP 在每个决策点枚举所有选择并比较子问题结果；有贪心选择性质的问题里，有一个选择可以直接判定为安全，于是每步只看一个分支，表都不用填。

⚠️ 常见误区

以为"直观的贪心规则"都行。活动选择还有三个看似合理的规则全部失败：选开始最早（反例：一个占全天的活动）、选时长最短（反例：短活动卡在两个长活动中间，挤掉两个）、选冲突最少（可构造反例）。只有"结束最早"正确——直觉不值钱，证明才算数。

9.2贪心的正确性：两种证明套路

上一节给了"结束最早"这个规则，但它带出一个问题：凭什么相信它？贪心算法的工程难度为零，全部难度在证明。需要两个性质，对应两种论证技术。

性质一：贪心选择性质（Greedy-Choice Property）—— 用交换论证（Exchange Argument）证明。要证：存在某个最优解包含贪心选择。以活动选择为例：

  1. 设 a₁ 是结束最早的活动，OPT 是任意一个最优解，设 OPT 中最早结束的活动是 aₖ。
  2. 若 aₖ = a₁，得证。否则 f₁ ≤ fₖ（a₁ 结束最早）。
  3. 交换：把 OPT 中的 aₖ 换成 a₁。OPT 中其余活动都在 fₖ 之后开始，因而也在 f₁ 之后开始，与 a₁ 兼容。
  4. 交换后解仍合法、大小不变——得到一个包含 a₁ 的最优解。∎

剩下的子问题（与 a₁ 兼容的活动）与原问题同构，配合第二张入场券最优子结构（第8章已讲），归纳即得全局正确性。

性质二的推广：拟阵（Matroid）直觉。CLRS 指出：一大类贪心问题（最小生成树、单位时间任务调度等）的底层结构都是拟阵——一个集合系统，满足"遗传性"（独立集的子集仍独立）与"交换性"（小的独立集总能从大的独立集里借一个元素扩充）。对拟阵，"按权重贪心选取"被统一证明最优——这就是第7章 Kruskal 算法正确的深层原因。懂拟阵不是为了证明更快，而是为了知道"贪心何时一定有救"。

✅ 判定规则

判断一个贪心策略对不对的流程：① 猜测规则；② 试图构造反例（10 分钟找不到再进③）；③ 交换论证：任取最优解，把它的第一个非贪心选择换成贪心选择，证明解不变差；④ 换完确认剩余是同类子问题。③过不去就回第8章填表。

⚠️ 常见误区

把"交换后没有变差"误证成"交换后一样好"。交换论证只需要"不差"，因为我们只要证明存在含贪心选择的最优解，不需要所有最优解都长这样。这个"存在性"定位是整个证明最常被写错的地方。

9.3Huffman 编码：完整建树手算

交换论证说服了我们"结束最早"安全。上一节留下一个问题：贪心选择性质在长不出"区间排序"形态的问题里还找得到吗？Huffman 编码（Huffman Coding）给出的答案是：找得到，只是贪心的对象从"选哪个"变成"合并哪两个"。

问题。给 6 个字符的出现频率（单位：千次），设计二元前缀码（Prefix Code：任何码字不是另一码字的前缀，可无歧义解码），使总码长最小。目标等价于：建一棵二叉树，使 Σ f(c)·depth(c) 最小。

字符abcdef
频率（千次）4513121695

贪心规则：每步合并频率最小的两棵树（用最小堆维护）。完整过程：

  1. 堆中：f5, e9, c12, b13, d16, a45。合并 f+e → 14。堆：c12, b13, 14, d16, a45。
  2. 合并 c+b → 25。堆：14, d16, 25, a45。
  3. 合并 14+d → 30（即子树 (f+e) 与 d）。堆：25, 30, a45。
  4. 合并 25+30 → 55。堆：a45, 55。
  5. 合并 a+55 → 100。结束。

读码（左 0 右 1，从根到叶）：

字符abcdef
码字010110011111011100
码长 × 频率1×45=453×13=393×12=363×16=484×9=364×5=20

总码长 = 45+39+36+48+36+20 = 224 千位。对比定长 3 位编码需 3×100 = 300 千位，省约 25%。贪心正确性的证明仍是交换论证：频率最低的两个字符必可作为最深层的兄弟出现在某棵最优树中（把最优树里最深的兄弟叶子与它们交换，总代价不增）。建堆 Θ(n)，共 n−1 次合并，每次 O(log n)，总 Θ(n log n)。

💡 关键一跃

Huffman 把"编码问题"翻译成"树的代价问题"后，贪心对象变成了合并操作：每次合并最小两棵，等于让最稀有的字符待在最深的层。前缀码与二叉树一一对应——这是"问题翻译"比"算法设计"更重要的又一例。

⚠️ 常见误区

以为 Huffman 码唯一。同频率节点的左右位置、同值合并的先后都可以不同，得到不同码字表——但所有最优树的总码长相同。考试写码字时注明左右约定即可，不必和别人逐位一致。

9.4摊还分析：动态表扩容的三本账

换个话题。第4、5章的数据结构操作大多代价平稳，但有一类操作单次代价剧烈波动：动态数组（如 vector、ArrayList）容量满时翻倍扩容，一次插入要搬移全部旧元素。它带出一个问题：最坏一次 O(n) 的操作，能对外报价多少？摊还分析（Amortized Analysis）给出三本记账法。

设定。表从容量 1 开始，插入元素；满则容量翻倍并把旧元素全部复制过去。复制 k 个元素计代价 k。连续插入 n 个元素，扩容发生在第 2、3、5、9、…（即 2^j+1）次插入，复制量 1、2、4、8、…

账法一：聚合分析（Aggregate Analysis）——算总账再平摊。

总代价 = n（每次插入本身）+ Σj=0..⌊lg n⌋ 2j（扩容复制） < n + 2n = 3n

n 次操作总代价 < 3n，故每次插入摊还代价 3。例如 n=9：插入 9 次计 9；扩容复制 1+2+4+8 = 15？不对——第 9 次插入时表容量 8 已满，扩到 16 复制 8。9+1+2+4+8 = 24 < 27 = 3×9 ✓。

账法二：记账法（Accounting Method）——每次收费 3 元。给每次插入收 3 元摊还费：1 元付本次插入；1 元存起来付"自己将来被搬移"；1 元存给"表中某个老元素将来被搬移"。扩容从 k 扩到 2k 时，需搬 k 个元素：其中 k/2 个是上一轮扩容后新插入的（各带 1 元自用存款），另外 k/2 个老元素靠新一轮 k/2 次插入各存的 1 元支付。账永远平衡，故摊还代价 3。

账法三：势能法（Potential Method）——给数据结构定义"势能"Φ。取

Φ(T) = 2·num − size（num 为元素数，size 为容量）

摊还代价 ĉ = 实际代价 + ΔΦ：

  • 不扩容的插入：ĉ = 1 + [2(num+1)−size] − [2·num−size] = 1+2 = 3。
  • 触发扩容的插入（插入前 num = size = k）：实际代价 k+1（搬 k 个+插 1 个）；扩容后 size′=2k，num′=k+1，Φ′=2(k+1)−2k=2；扩容前 Φ=2k−k=k。ĉ = (k+1) + (2−k) = 3。

两种情形摊还代价都是 3。总摊还 = Σ实际 + Φ(末) − Φ(初) ≥ Σ实际（Φ 非负），故摊还代价是实际总代价的上界。

💡 关键一跃

三种方法算的是同一笔账，只是记账视角不同：聚合看总量，记账法给每次操作发"货币"，势能法把存款挂在数据结构状态上。势能法最抽象也最强大——复杂结构（斐波那契堆、伸展树）只有它算得动。

⚠️ 常见误区

误以为扩容"扩 1.5 倍"摊还代价会变坏。设增长因子为 r，总复制量约为 n/(r−1)·……精确说：r 倍扩容的总复制量上界为 r·n/(r−1)，r=1.5 时为 3n，摊还约 4——仍是常数。任何大于 1 的固定增长因子都给常数摊还，只有"加固定大小"（如每次 +100）才是灾难：那时总代价 Θ(n²)，摊还 Θ(n)。

9.5摊还 ≠ 平均：两种"听起来很像"的代价

上一节算出"摊还 3"。它带出一个极易混淆的问题：这和第3章快排的平均情况 O(n log n) 有什么区别？区别在"保证"二字上。

维度摊还代价（Amortized）平均情况代价（Average-Case）
是否涉及概率完全不涉及对输入分布取期望
保证对象任何操作序列的总代价上界随机输入下期望代价
最坏序列依然成立（如动态表连插 n 次）不成立（快排遇坏划分退到 Θ(n²)）
典型例子动态表插入摊还 O(1)快排平均 O(n log n)
证明工具聚合 / 记账 / 势能概率期望（第1、3章）

一句话：摊还是对"最坏的操作序列"打包报价，平均是对"随机的单次运行"取期望。动态表的摊还 O(1) 意味着：哪怕对手故意构造最坏插入序列，总账仍不超过 3n；而快排的平均分析管不了恶意输入（这才需要随机化快排把"坏运气"转移到算法内部）。

✅ 判定规则

面试/论文里写复杂度时自检：如果说的是"任何操作序列的总代价 ÷ 操作数"，用摊还；如果依赖"输入随机/哈希随机"，用期望（平均）。混用会被追问到哑口无言。

定义把任意最优解逐步"交换"成贪心解且不变差，证明贪心选择安全的证明技术。
解决问题贪心算法几乎全部的正确性证明都靠它。
直觉你的最优解和我的贪心解第一个不同处，我换成我的选择，不亏。
误区证成"交换后一样好"——只需"不差"，因为只要存在性。
何时用活动选择、Huffman、调度类问题；第10章近似算法分析也用类似思想。
概念卡 3
拟阵（Matroid）
点击翻面 →
定义满足遗传性（独立集的子集仍独立）与交换性（小独立集可从大独立集借元素扩充）的集合系统。
解决问题统一回答"贪心何时必有救"：拟阵上按权重贪心恒最优。
直觉线性无关向量组的抽象化——"无关性"的两个基本法则。
误区以为所有贪心问题都是拟阵——活动选择严格说是拟阵的推广（且需额外论证），背包问题则不是。
何时用解释 Kruskal（第7章）、单位时间任务调度的贪心正确性。
概念卡 4
前缀码与 Huffman 编码（Prefix Code / Huffman Coding）
点击翻面 →
定义任何码字不是其他码字前缀的可变长编码；Huffman 用"合并最小两棵树"构造最优前缀码。
解决问题按字符频率最小化总码长 Σf·depth。
直觉常见字给短码、生僻字给长码——莫尔斯电码的严格最优版。
误区以为最优码唯一——左右约定不同码字不同，但总码长唯一。
何时用gzip、JPEG 等压缩标准的内层；信息论中逼近熵的构造性方案。
概念卡 5
摊还分析（Amortized Analysis）
点击翻面 →
定义对任意操作序列的总代价取上界再平摊到单次操作的代价分析框架。
解决问题单次最坏代价剧烈波动（如扩容搬移）时给出诚实的对外报价。
直觉月底看总账：偶尔大出血没关系，全年平均下来每天花得不多。
误区与平均情况分析混淆——摊还不含任何概率假设，对最坏序列也成立。
何时用vector/ArrayList 扩容、并查集、伸展树、斐波那契堆。
概念卡 6
势能法（Potential Method）
点击翻面 →
定义给数据结构状态定义势函数 Φ，摊还代价 = 实际代价 + ΔΦ 的摊还分析技术。
解决问题操作类型多、相互预付关系复杂时仍能算清账。
直觉把"未来要花的钱"存进结构的高度/混乱度里，便宜操作存钱、昂贵操作取钱。
误区忘记验证 Φ 非负且 Φ(初)≤Φ(任意)——否则摊还不是实际的上界。
何时用动态表（Φ=2·num−size）、伸展树、斐波那契堆摊还界。

📝分层习题

L1 概念辨析判断：只要问题有最优子结构，就一定存在正确的贪心算法。
提示

矩阵链乘有最优子结构（第8章），它有正确的贪心算法吗？

完整解答
错。最优子结构只是必要条件之一，还需要贪心选择性质。矩阵链乘有最优子结构但贪心（先乘最小相邻对）必错——第8章正是为此用 DP。易错点：最优子结构是 DP 和贪心共用的地基，区分两者的是"贪心选择性质"。
L1 概念辨析判断：动态表插入的摊还代价 O(1)，意味着任何一次插入都不会超过常数时间。
提示

摊还是对谁的上界？单次还是序列总和？

完整解答
错。摊还保证的是任意 n 次操作的总代价 ≤ 3n，单次扩容插入的实际代价仍是 Θ(k)（搬移 k 个元素）。对延迟敏感的实时系统（如游戏主循环、嵌入式中断）不能只看摊还界——这正是惰性重建、渐进式扩容等技术的存在理由。易错点：把"序列平均"当成"单次上界"。
L2 手算推导活动选择：s = [1, 3, 0, 5, 8, 5]，f = [2, 4, 6, 7, 9, 9]（活动 a₁…a₆）。先按结束时间排序，再完整执行贪心，给出选中集合。
提示

排序后依次为 a₁(1,2)、a₂(3,4)、a₃(0,6)、a₄(5,7)、a₅(8,9)、a₆(5,9)。

完整解答
排序后顺序：a₁[1,2) → a₂[3,4) → a₃[0,6) → a₄[5,7) → a₅[8,9) → a₆[5,9)。
① 选 a₁（结束 2）；
② a₂ 开始 3 ≥ 2，选 a₂（结束 4）；
③ a₃ 开始 0 < 4，跳过；a₄ 开始 5 ≥ 4，选 a₄（结束 7）；
④ a₅ 开始 8 ≥ 7，选 a₅（结束 9）；a₆ 开始 5 < 9，跳过。
结果 {a₁, a₂, a₄, a₅}，共 4 个活动（兼容区间 [1,2)、[3,4)、[5,7)、[8,9)，即为最优）。
L2 手算推导对字符频率 {a:7, b:3, c:2, d:2, e:1} 完整执行 Huffman：写出每次合并、最终码字表与总码长。
提示

每步合并最小两个频率；总频率 15，需合并 4 次。

完整解答
合并过程：e1+d2 → 3；3(ed) + b3 → 6（取并列最小，e、d 子树与 b）；c2 与刚才的 3？——需严格按堆序：堆 [c2, d2, b3, e1, a7]，第一步 e1+d2=3 → 堆 [c2, b3, 3, a7]；第二步 c2+3(ed)=5 → 堆 [b3, 5, a7]；第三步 b3+5=8 → 堆 [a7, 8]；第四步 a7+8=15。
读码（左 0 右 1）：a = 0；b = 10；c = 110；e = 1110；d = 1111。
总码长 = 7·1 + 3·2 + 2·3 + 2·4 + 1·4 = 7+6+6+8+4 = 31。定长 3 位需 3×15 = 45，省 14。
（注：第二步若合并次序不同，码字表可能不同，但总码长 31 不变。）
L3 建模应用你在设计一个日志系统的内存缓冲队列：写少读多，但每天 0 点要把缓冲批量落盘一次（代价与缓冲中条目数成正比）。老板要求"对外承诺每次写入的代价上限"。请说明：该用摊还、平均还是最坏分析来报价？若用记账法，每次写入应收多少"费用"，存款在 0 点怎么花？
提示

"承诺上限 + 偶发大清理"是哪种分析的标准场景？参考动态表扩容的账法二。

完整解答
用摊还分析——它是唯一不依赖概率假设、能对"最坏写入序列"给出承诺的工具（平均分析需要假设写入到达的分布，最坏分析则必须按落盘那次报价，过于悲观）。
记账法建模：设每条日志落盘代价 1。每次写入收 2 元：1 元付"写入缓冲"本身，1 元存为"该条目将来落盘"的费用。0 点批量落盘 k 条，恰好由这 k 条各自存的 1 元支付。账平衡，故摊还代价 = 2 = O(1)。
对老板的报价口径："任何连续 n 次写入的总代价 ≤ 2n"，而非"单次写入永远 ≤ 2"——这正是摊还承诺与单次承诺的区别。

点击选项判分，答错会给出原因。

自测 1
活动选择问题中，被证明正确的贪心规则是？
  • A. 选开始最早的活动
  • B. 选时长最短的活动
  • C. 选结束最早且兼容的活动
  • D. 选与其他活动冲突最少的活动
解析：C 对，交换论证可证。A 错——一个占全天的活动即可构造反例；B 错——短活动可能挤掉两个兼容活动；D 错——可构造冲突最少但非最优的实例。三个"直觉规则"全部阵亡，说明贪心规则必须证明。
自测 2
交换论证证明"存在含贪心选择的最优解"时，交换后需要保证解？
  • A. 严格更好
  • B. 不变差（保持合法且大小不减小）
  • C. 与贪心解完全相同
  • D. 包含所有贪心选择
解析：B 对——只需"不差"即可推出"存在含贪心选择的最优解"。A 错——若严格更好则与 OPT 最优矛盾，反而证不下去；C 错——交换只处理第一个分歧点，归纳继续；D 错——一步到位证明过强且不必要。
自测 3
频率 {45,13,12,16,9,5} 的 Huffman 编码总码长（千位）是？
  • A. 224
  • B. 300
  • C. 100
  • D. 248
解析：A 对（45·1+13·3+12·3+16·3+9·4+5·4=224）。B 错——那是定长 3 位码的长度，没压缩；C 错——100 是总频率，把"字符数"当成了"位数"；D 错——常见算错：给 a 也分配 2 位（a 频率 45 应得最短码长 1）。
自测 4
动态表翻倍扩容，用势能法 Φ=2·num−size，触发扩容的那次插入摊还代价为？
  • A. num+1（即实际代价）
  • B. O(n)
  • C. 2
  • D. 3
解析：D 对——实际代价 k+1，势能下降 k−2，ĉ=(k+1)+(2−k)=3。A 错——那是实际代价，忘了势能释放；B 错——把单次实际代价当摊还代价；C 错——2 是不扩容情形中势能增量的数值，不是摊还代价。
自测 5
关于摊还代价与平均情况代价，正确的是？
  • A. 两者都需要对输入分布做概率假设
  • B. 摊还不涉概率、对最坏操作序列也成立；平均是对随机输入取期望
  • C. 摊还代价一定不小于平均代价的期望
  • D. 快排的 O(n log n) 是摊还界
解析：B 对。A 错——摊还不含任何概率；C 错——两者作用对象不同（序列总量 vs 单次期望），没有这种普适大小关系；D 错——快排是平均情况界（随机划分），最坏仍是 Θ(n²)，"摊还"概念不适用于它。
