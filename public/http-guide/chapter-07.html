7.1服务器把一小段状态托付给浏览器保管

第 1 讲在拆会话三阶段时留下一笔账：HTTP 是无状态协议，服务器处理完一条请求就"忘干净"了，可 Web 应用偏偏能认出老用户、保住购物车。第 6 讲把条件请求与范围请求讲完，是时候回头偿还这笔账了。MDN 把偿还这笔账的机制叫作 Cookie（Cookie，也叫 Web Cookie 或浏览器 Cookie）——它的定义只有一句话：服务器发送到用户浏览器并保存在本地的一小块数据，浏览器会存储它，并在下次向同一服务器发起请求时把它带上。

这句话里藏着一个反直觉的转折。既然服务器"忘干净"了，那"认出你"这件事由谁来做？答案是浏览器。服务器在下发响应时，把一小段数据写进 Set-Cookie（Set-Cookie）响应首部，相当于开了一张写着身份编号的凭条递给浏览器；浏览器把凭条收好，此后每一次朝同一服务器发出的请求，都主动把凭条夹在 Cookie（Cookie）请求首部里交回去。服务器不必记得任何人，只要每次读一读凭条上的编号，就能把散落的请求重新串成同一个用户。

先看一组最短的往返，把这个过程钉死。假设用户第一次访问一个需要登录的面板，服务器还不知道他是谁：

GET /dashboard HTTP/1.1 Host: app.example.com Accept: text/html HTTP/1.1 200 OK Content-Type: text/html; charset=utf-8 Set-Cookie: sid=9f3a2b; Path=/; HttpOnly Content-Length: 96 请登录。
第一次请求：服务器在 200 响应里用 Set-Cookie 下发一枚会话标识 sid=9f3a2b，回复"请登录"。协议没有要求服务器记住这次下发动作。
POST /login HTTP/1.1 Host: app.example.com Cookie: sid=9f3a2b Content-Type: application/x-www-form-urlencoded Content-Length: 27 user=alice&pass=correct
第二次请求：浏览器主动把 sid=9f3a2b 放进 Cookie 首部带回。服务器读到它，才知道这次登录尝试属于刚才那位访客；主体里的表单数据用 & 连接两个字段。

请盯住这两条请求的关系：状态不在服务器的连接记忆里，而在浏览器手上，并由浏览器在每次请求里显式带回。这正是无状态协议维持状态的通用套路——Web 应用自己造出一层"记忆"，HTTP 协议本身一点没变。MDN 明确写道，Cookie 让基于无状态 HTTP 协议记录稳定状态信息成为可能；换言之，Cookie 是架在 HTTP 之上的能力，不是 HTTP 语义的一部分。

MDN 把 Cookie 的用途归纳成三类，理解这三类，就明白它为什么既无所不在又备受争议：

MDN 归纳的用途典型例子为什么需要"记住"
会话状态管理登录状态、购物车、游戏分数、表单草稿把同一浏览器发出的多次请求归到同一个会话
个性化设置深浅色主题、语言偏好、布局选择让站点下次打开时呈现用户上次选过的样子
浏览器行为跟踪广告画像、访问路径分析、转化率统计跨多个页面甚至多个站点拼出用户的浏览习惯

前两类是"帮忙"，第三类却是隐私争议的源头。同一套技术既能让你免于重复登录，也能让广告网络跨站追踪你——区别只在于谁在设置、设置了什么、发往哪里。这个双重身份，就是本讲主线里"为什么它又成了安全重灾区"的伏笔。

按生存期，Cookie 还分两大家族。会话 cookie（session cookie）不设过期时间，浏览器关闭当前会话时就删除——但要注意 MDN 的提醒：一些浏览器重启时会用"会话恢复"把会话续上，导致会话 cookie 被无限延长。持久 cookie（persistent cookie）则靠 Expires（绝对日期）或 Max-Age（相对秒数）指定寿命，到期后由浏览器清除：

Set-Cookie: theme=dark; Path=/ Set-Cookie: id=a3fWa; Expires=Wed, 21 Oct 2026 07:28:00 GMT; Path=/
两条 Set-Cookie 首部并列放在同一响应里：第一条是没有过期时间的会话 cookie，关掉会话就没；第二条带 Expires，是持久 cookie，会一直留到指定日期。一条响应可以同时下发多个 Set-Cookie。
💡 关键一跃

Cookie 不是服务器"记住用户"，而是服务器"把记忆的载体交给用户保管"。状态被压缩成一小段键值，放在浏览器里，每次请求再由浏览器显式交回。理解了"载体在客户端、服务器只校验"这个分工，后面所有属性（Domain、Path、Secure、HttpOnly、SameSite）就都只是在回答同一个问题：这段托付出去的状态，谁能看、发往哪里、发多久、跨不跨站。

⚠️ 常见误区

"Cookie 是加密的，所以能存密码这类敏感信息"——错。Cookie 只是普通文本，浏览器能看到、终端用户也能改；它既不加密，也不防篡改。MDN 特别提醒：不能在 Cookie 里存储或传输敏感信息，正确做法是放一个服务器可查的不透明标识符（opaque identifier），真实数据留在服务端。此外，Cookie 曾一度是唯一的客户端存储手段，今天已被 Web Storage API（localStorage / sessionStorage）与 IndexedDB 取代——因为浏览器每次请求都自动带 Cookie，会带来额外开销。

7.2一条 Set-Cookie 的七个开关，各自把住一道关

上一节证明了"存一个键值对"就能让无状态协议记住用户。但紧接着的问题是：这枚凭条谁能读？会发给哪台主机、哪条路径？活多久？会不会跟着跨站请求跑出去？光有 sid=9f3a2b 这样赤裸裸的键值远远不够——它像一张没写有效期、没写使用范围、谁都能捡去用的白条。MDN 把 Set-Cookie 设计成"键值 + 一串属性"，每个属性都是一道可拨动的开关。

把最常见的七个属性和键名放在一起，一条完整的 Set-Cookie 长这样。这是本讲第一个必须逐字读懂的报文：

HTTP/1.1 200 OK Date: Mon, 16 Nov 2026 00:30:00 GMT Content-Type: text/html; charset=utf-8 Set-Cookie: sid=9f3a2b; Domain=app.example.com; Path=/account; Expires=Wed, 21 Oct 2026 07:28:00 GMT; Max-Age=604800; Secure; HttpOnly; SameSite=Lax Cache-Control: no-store Content-Length: 214 登录成功，这是你的账户首页。
例子① 完整 Set-Cookie：键值 sid=9f3a2b 之后紧跟 Domain、Path、Expires、Max-Age、Secure、HttpOnly、SameSite 七个属性，每个属性用分号分隔。浏览器据此决定把它存在哪、发给谁、发多久、跨不跨站。

浏览器收好这条 cookie 后，之后每一次匹配的请求都会自动把它夹带回来：

GET /account/profile HTTP/1.1 Host: app.example.com Cookie: sid=9f3a2b Accept: text/html Sec-Fetch-Site: same-origin HTTP/1.1 200 OK Set-Cookie: sid=7c81de; Domain=app.example.com; Path=/account; Max-Age=604800; Secure; HttpOnly; SameSite=Lax Cache-Control: no-store 个人资料页。
后续请求：Cookie 首部只带"名字=值"，所有属性都不会出现在 Cookie 首部里——属性是浏览器存Cookie 时的规则，不随报文回传。响应里再次下发新 sid，是 MDN 推荐的防会话固定做法（每次认证都重新生成会话 cookie）。

现在逐属性拆解这七个开关。它们各自回答一个独立的问题，互不替代：

属性回答的问题取值与含义不设会怎样
Domain哪些主机可以收这枚 cookie指定主机名，如 app.example.com；一旦指定，通常连子域一起包含默认为设置它的同一主机，且不含子域
Path请求路径里必须出现什么才发送如 /account，以 / 作分隔符，子路径一并匹配默认取设置它的请求路径的目录
Expires绝对过期时间是哪一天一个 GMT 日期，只与客户端时钟相关不设则该维度不产生过期，配合 Max-Age 判断
Max-Age从现在起还能活多少秒相对秒数，如 604800 表示 7 天；优先级高于 Expires与 Expires 都不设即为会话 cookie
Secure能不能走明文传输无取值，写上即生效：只在 HTTPS 请求里发送http: 页面无法设置；明文请求可能把 cookie 暴露给中间人
HttpOnlyJavaScript 能不能读无取值，写上即生效：Document.cookie 读不到它脚本可读，XSS 攻击可窃取会话标识
SameSite跨站请求要不要带Strict / Lax / None；未设置按 Lax 处理按新的默认行为当 Lax，挡下大部分跨站携带

先说寿命，这里有个容易踩的坑。Expires 给的是绝对时间，MDN 强调它设定的日期和时间只与客户端相关，而不是服务端——用户把本机时钟调快，就能让一枚本该过期的 cookie 提前或延后失效。Max-Age 给的是相对秒数，从浏览器收到响应的那一刻开始倒数，不依赖时钟，因此更可靠。两者同时出现时，Max-Age 优先。上例里 Expires 写的是 2026 年 10 月 21 日，而 Max-Age=604800 是 7 天，从 11 月 16 日算起应到 11 月 23 日——真正生效的是后者，浏览器按 7 天寿命保存。

再说两个"无取值"的安全开关，它们各挡住一类攻击，切勿混用：

开关挡住的攻击作用机理挡不住什么
Secure明文窃听、中间人（man-in-the-middle）篡改只在 HTTPS 加密请求里发送，http: 请求不带（本地主机除外）挡不住能读硬盘或能用脚本读取的人
HttpOnly跨站脚本（XSS, Cross-Site Scripting）窃取会话Document.cookie API 无法访问带此属性的 cookie，它只对服务器可见挡不住网络窃听，也挡不住 CSRF

MDN 举的典型用法是：承载服务器端会话的 cookie 不需要对 JavaScript 可用，就应加上 HttpOnly。这样即使页面被注入恶意脚本，脚本也读不到那枚会话标识。而 Secure 挡的是另一个方向——它保证凭条不会在去往服务器的路上以明文裸奔。一个管"路上不被偷看"，一个管"到了页面不被脚本偷走"，两者缺一不可。

还有一个 MDN 特别强调的运维细节：如果站点对用户进行身份验证，那么每次认证时都应重新生成并重新发送会话 cookie，哪怕用户已经带着一枚旧的。这一步防的是会话固定攻击（session fixation attack）——第三方若能事先塞给你一个他知道值的会话标识，而你登录后站点继续沿用这个值，他就能拿同一个值冒充你。上面第二条报文里响应再次下发新 sid，正是这个动作的体现。

✅ 判定规则

读一条 Set-Cookie，按固定顺序问七个问题：键名是什么、发给哪些主机（Domain）、哪些路径（Path）、活到何时（Expires / Max-Age）、是否只走 HTTPS（Secure）、是否禁脚本读取（HttpOnly）、跨站带不带（SameSite）。属性名写在 Set-Cookie 里，但回传的 Cookie 首部只有键值——别在 Cookie 首部里去找 Secure 或 Path，它们从来不随请求回传。

⚠️ 常见误区

"Expires 和 Max-Age 都写了，以 Expires 为准"——错，Max-Age 优先。另一个误区是以为 Secure 能保护 cookie 的内容：MDN 明说 Secure 不会阻止对敏感信息的访问，能接触客户端硬盘或能用脚本的人照样可以读取和修改；它只保证传输通道是加密的。还有人以为给 cookie 加 HttpOnly 就万事大吉——它挡 XSS，却对 CSRF 无能为力，后者要靠下一节的 SameSite 来治。

7.3Domain、Path 与 SameSite 是三道闸门，决定 cookie 发往何处

上一节把七个属性拆成了开关，但真正决定一枚 cookie"会不会出现在某条请求的 Cookie 首部里"的，是三道串联的闸门：Domain 管主机、Path 管路径、SameSite 管跨站。三者是与的关系——任何一道拦下，cookie 就不发。本节用两张判定表把这些规则算清楚；这两张表是本讲的第二、第三个完整例子，也是排查"cookie 怎么没带上"这类线上问题的标准动作。

先看 Domain 与 Path。MDN 的定义很干脆：作用域（scope）就是"允许 Cookie 应该发送给哪些 URL"，由这两个属性共同界定。Domain 指定哪些主机可以接受 Cookie：不指定时默认为设置它的同一主机、不含子域；指定了就一般包含子域。Path 指定请求路径中必须出现的字符串：以 / 作分隔符，子路径也会被匹配。规范底层对应两个算法——域名匹配（domain-match）与路径匹配（path-match），我们在 7.5 节对照 RFC 6265 时再拆算法细节，这里先按 MDN 的口径判定。

例子②：Domain 与 Path 的分步判定表。假设浏览器保存了这样一枚 cookie：

Set-Cookie: sid=9f3a2b; Domain=shop.example.com; Path=/docs; Secure
待判定的 cookie：主机限定 shop.example.com 及其子域，路径限定 /docs 及其子路径，且只在 HTTPS 下发送。下面对八个候选 URL 逐一过三道闸门。

判定方法固定为三步：① 主机是否是 shop.example.com 或其子域（Domain 闸门）；② 路径是否落在 /docs 作用域内（Path 闸门）；③ 是否走 HTTPS（Secure 闸门）。三步全过才发送：

候选请求 URL① Domain 闸门② Path 闸门③ Secure 闸门结果
https://shop.example.com/docs通过：主机与 Domain 完全相同通过：/docs 与 Path 精确相等通过：HTTPS发送
https://shop.example.com/docs/Web/HTTP通过：主机完全相同通过：/docs/Web/HTTP 以 /docs/ 开头，属子路径通过：HTTPS发送
https://www.shop.example.com/docs通过：www.shop.example.com 是 shop.example.com 的子域，指定 Domain 后包含子域通过：路径精确等于 /docs通过：HTTPS发送
https://shop.example.com/docsets通过：主机完全相同拦截：/docsets 不以 /docs/ 开头，也不是 /docs 本身，只是字符串前缀相同不判定不发
https://shop.example.com/fr/docs通过：主机完全相同拦截：/fr/docs 不以 /docs 开头不判定不发
https://shop.example.com/通过：主机完全相同拦截：根路径 / 不在 /docs 作用域内不判定不发

这张表里有三个最值得记住的判定。第一，/docsets 不发：Path 匹配是按路径分段走的，/docs 后面必须跟上 / 才算子路径，单纯的字符串前缀相同不算。第二，www.shop.example.com 会发：因为显式指定了 Domain，子域被包含进来；如果当初省略 Domain，这一行就会被拦下。第三，父域 example.com 拿不到子域的 cookie——作用域只向下包含，不向上冒泡。MDN 给出的 Path 例子与此完全一致：Path=/docs 匹配 /docs、/docs/、/docs/Web/、/docs/Web/HTTP，却不匹配 /、/docsets、/fr/docs。

接下来是第三道闸门 SameSite。MDN 说它让服务器指定"是否/何时通过跨站请求发送"，提供的正是针对跨站请求伪造（CSRF, Cross-Site Request Forgery）的一层保护。要判定跨站，先得知道"站"是什么：MDN 的口径是站由注册的域和方案（http 或 https）共同定义。这意味着 http://example.com 与 https://example.com 因为方案不同，已经不算同一站点——这是 MDN 特别点出的新变化。SameSite 取三个值：

✅ 判定规则

排查"cookie 没带上"，按 Domain → Path → SameSite → Secure 四步逐闸门过：主机对不对、路径落不落在作用域、是不是跨站请求、是不是明文。四步都过才发送。尤其记住两个反直觉点：显式 Domain 会向下包含子域但不向上冒泡到父域；Path 匹配要按路径分段，/docs 不匹配 /docsets。

⚠️ 常见误区

"SameSite=Lax 就能防住所有 CSRF"——过于乐观。Lax 只放行安全的顶层导航，挡住了跨站 POST 表单，但对某些顶层 GET 触发的状态改变仍无能为力，因此敏感操作还要配合 CSRF 令牌与二次确认。另一个误区是把 None 单独写上：不带 Secure 的 None 会被直接丢弃，且 http: 页面根本无法设置 Secure，导致本地开发环境跨站 cookie 频频"失效"——这不是代码 bug，而是安全上下文的硬性要求。

7.4cookie 不是认证，也不是本地存储：别让会话标识爬进 URL

前三节把 cookie 的机制讲透了，最后一节要划清它的职责边界。实践中最常见的两类混淆是：把 cookie 当成"认证本身"，以及把 cookie 与 localStorage 当成可以互换的存储。这两类混淆一旦落到代码里，就会催生本讲主线里"安全重灾区"的具体事故。MDN 在《在浏览器中存储信息的其他方式》一节里，恰好给了我们把三者摆在一起比较的线索。

先把概念掰开：cookie 是"认出你"的载体，认证是"证明你是你"的过程。cookie 里通常只装一枚会话标识，它本身不证明任何身份；真正的校验发生在服务器拿着这枚标识查会话存储、确认它对应一个已登录用户时。第 8 讲会专门讲认证框架——cookie 与认证是搭挡，不是同一件事。而 localStorage 属于 Web 存储 API，是浏览器本地的键值仓库，它永远不会自动发往服务器，这与 cookie 的"每次请求自动携带"形成根本区别。

最后补上 MDN 里与隐私相关的两个话题，它们解释了"重灾区"的另一面。其一是第三方 cookie（third-party cookie）：如果 cookie 的域和方案与当前页面相同，就是第一方 cookie（first-party cookie）；不同则是第三方 cookie。页面里来自其他域的广告或脚本可以设置第三方 cookie，从而跨站点拼出用户画像——Firefox 默认会阻止已知的跟踪类第三方 cookie，其他浏览器与扩展也提供拦截。其二是法规：GDPR、欧盟电子隐私权指令、加州消费者隐私法等要求站点告知用户 cookie 的使用、允许拒绝、并尽量在不接受 cookie 时仍提供主要服务。技术上还有所谓僵尸 cookie（zombie cookie）——在被删除后自我重建的技术，它违反用户控制原则，可能触犯隐私法规。

💡 关键一跃

Cookie、认证凭据、localStorage 不是三选一的竞争关系，而是分工：cookie 负责在浏览器与服务器之间自动往返小段状态；认证凭据由代码在需要时显式出示，用来证明身份；localStorage 只在本机存放、永不进网络。把"认出你"（cookie）和"证明你是你"（认证）分开，再把状态从 URL 里请出去，是避免本讲大多数安全事故的总原则。

⚠️ 常见误区

"用 localStorage 存会话标识比 cookie 更安全，因为 HttpOnly 的 cookie 会被自动发送"——两个判断都站不住。localStorage 里的值脚本随时可读，XSS 一来直接被端走；HttpOnly cookie 恰恰是防 XSS 窃取会话的武器，而它带来的 CSRF 风险由 SameSite 去挡，这是分工而非缺陷。真正的错误是把标识写进 URL：既不加密也不私密，还顺手毁掉缓存。安全不是选一个"最安全的容器"，而是让每类数据在正确的通道里流动。

7.5延伸：规范怎么写：从 RFC 6265 看 cookie 的规范口径

MDN 是面向开发者的工程文档，它告诉你"该怎么做"，却刻意省略了"规范上到底怎么定义"。当你需要实现浏览器、写 cookie 库，或者判定一个边界行为（比如路径匹配的精确算法、cookie 前缀的校验条件），就得去看 IETF 的规范。cookie 的规范是 RFC 6265，以及正在取代它的 RFC 6265bis 草案；本讲出现的 SameSite、cookie 前缀、新默认行为，大多是 6265bis 相对原始 6265 的增补。下面这张表把 MDN 的工程口径与 RFC 的规范口径对齐。

MDN 的说法RFC 怎么写为什么值得知道
服务器用 Set-Cookie 下发 cookie，浏览器用 Cookie 首部带回RFC 6265 §3 定义 Set-Cookie 与 Cookie 两套语法；§5 定义"存储模型"，规定用户代理如何接收、保存与回送 cookie，属性只出现在 Set-Cookie，不随 Cookie 首部回传理解"属性是存储规则、不是回传内容"是规范结论，而非浏览器习惯；写客户端/服务器时别去 Cookie 首部里解析属性

站点由注册域和方案定义；第一方/第三方 cookie 据此区分RFC 6265bis 引入 "site for cookies" 与可注册域（registrable domain，依赖公共后缀列表）判定，并把方案纳入同一站点的判断因为方案也算站点的一部分，http 与 https 的同名主机不再同站；这解释了为什么跨站 cookie 在混合内容或本地 http 环境里行为诡异

这张表的价值不在让你去背 RFC 章节号，而在给你一个判断依据：当 MDN 说"通常""建议"而你需要一个确定的对错时，去 RFC 找规范性措辞。RFC 里 MUST、SHOULD、MAY 有严格区别——比如"None 必须配 Secure"是带强制意味的要求，浏览器据此直接丢弃违规 cookie，而不是"建议"。同样，cookie 前缀不符合条件时被"拒绝保存"，也是规范层面的硬性动作。

把两个前缀再展开一点，因为它们是 MDN 明确推荐、却常被忽视的防御手段。__Secure- 只要求两件事：带 Secure、来自安全来源。__Host- 在这之上再加两道锁：不许带 Domain、Path 必须精确到 /。效果是——子域想伪造一枚 __Host- cookie 时，要么被限制在它自己的子域里，要么因为带了 Domain 而被整个丢弃，无法冒充父域的会话 cookie。应用服务器检查时必须比对完整 cookie 名（含前缀），因为用户代理在发送 Cookie 首部时不会把前缀剥掉。

__Secure-：带 Secure 且来自安全来源即可 Set-Cookie: __Secure-sid=9f3a2b; Secure; Path=/account; SameSite=Lax __Host-：还要求不带 Domain、Path 精确为 /，是与主机锁死的写法 Set-Cookie: __Host-sid=9f3a2b; Secure; Path=/; SameSite=Lax
两条合规的前缀 cookie：__Host- 因锁死主机（无 Domain、Path=/）而更安全；任何一条不满足各自条件，浏览器都会拒绝保存。
✅ 判定规则

遇到 cookie 的边界行为争议，按三层找答案：MDN 给工程结论，Set-Cookie / Cookie 参考页给各属性的浏览器兼容与取值细节，RFC 6265 与 6265bis 给规范性算法与强制要求。尤其记住规范演进带来的差异：原始 6265 没有 SameSite，缺省 Lax、None 配 Secure、cookie 前缀都是 6265bis 才系统化的能力。

⚠️ 常见误区

别把 __Host- 与 __Secure- 当成"自动防住一切攻击"的护身符。它们只是深度防御：帮助浏览器确保 cookie 确实来自安全来源、没有被子域用 Domain 越权设置，但应用服务器仍必须校验完整 cookie 名、校验登录态与 CSRF 令牌。另一个误区是照搬旧教程里"缺省全发送"的 SameSite 说法——那是老行为；现行规范与浏览器缺省已是 Lax，写代码时要显式指定以避免歧义。

Cookie 与 Set-Cookie / Cookie
点击翻面 →

概念卡 2
会话 cookie 与持久 cookie
点击翻面 →
定义会话 cookie 不设过期时间、会话结束即删；持久 cookie 靠 Expires 或 Max-Age 指定寿命。

概念卡 3
作用域 Domain / Path
点击翻面 →
定义Domain 决定哪些主机可收 cookie，指定则含子域；Path 决定哪些请求路径可带，含子路径。

误区以为 Domain 向上冒泡到父域；其实只向下含子域。/docs 也不匹配 /docsets。
何时用排查"cookie 没带上"时先过 Domain 再过 Path；规范算法在 RFC 6265 §5.1.3/5.1.4。
概念卡 4
Secure 与 HttpOnly
点击翻面 →
定义Secure 让 cookie 只在 HTTPS 请求发送；HttpOnly 让脚本 Document.cookie 读不到它。
解决问题Secure 挡明文窃听与中间人，HttpOnly 挡 XSS 窃取会话标识。
直觉Secure 管路上不被偷看，HttpOnly 管到页面后不被脚本偷走。
误区以为 Secure 加密了 cookie 内容；它只保证通道加密，且挡不住 CSRF。
何时用承载会话的 cookie 应两者都加；http: 页面无法设置 Secure。
概念卡 5
SameSite 与 CSRF
点击翻面 →
定义约束跨站请求是否携带 cookie，取 Strict / Lax / None；未设置按 Lax 处理。
解决问题为跨站请求伪造 CSRF 提供一层保护，控制认证 cookie 是否随跨站请求发出。
直觉Strict 闭门不出，Lax 只给安全导航开门，None 门户大开但须 Secure 把关。
误区把 None 单独写上会被丢弃；以为 Lax 能防住所有 CSRF，敏感操作仍需令牌。
何时用默认 Lax；仅跨站嵌入场景用 None 且必须配 Secure。
概念卡 6
cookie 前缀 __Host- / __Secure-
点击翻面 →
定义名称带前缀的 cookie 须满足额外条件才被接受：__Secure- 要 Secure 与安全来源，__Host- 还要无 Domain 且 Path 为 /。
解决问题作为深度防御，防止子域用 Domain 越权设置会话 cookie，抵御会话固定与劫持。
直觉给重要凭条盖一个"必须这样开"的钢印，浏览器见到不合规就拒收。
误区以为前缀自动防住一切；应用服务器仍须校验完整 cookie 名与登录态。发送时前缀不会被剥掉。
何时用为认证类 cookie 加前缀；属 RFC 6265bis 能力，不符合条件即被拒绝。
概念卡 7
cookie / 认证 / localStorage 的分工
点击翻面 →
定义cookie 自动往返小段状态；认证凭据由代码显式出示证明身份；localStorage 只存本地、永不进请求。
解决问题划清"认出你""证明你是你""本地存放"三件事，避免把标识塞进 URL 或用错容器。
直觉cookie 是通行证，认证是验明正身，localStorage 是自家抽屉。
误区把会话标识写进 URL：泄露到历史、日志、Referer、分享链接，还毁掉缓存键。
何时用会话标识放 HttpOnly cookie 或认证首部；本地数据放 Web Storage；第 8、9 讲展开。

✍️分层习题：先自己写，再点开核对

L1 概念辨析判断下列说法的正误并说明理由：①「cookie 是无状态协议的一部分，HTTP 规范里定义了它」；②「给 cookie 加 HttpOnly 后，跨站脚本就偷不走它，也顺带防住了 CSRF」；③「会话 cookie 关掉浏览器一定会被删除」。
提示

逐句抓住被混淆的那对关系：协议核心 vs 扩展能力、XSS vs CSRF、会话结束 vs 会话恢复。

完整解答
① 错。cookie 是架在 HTTP 之上的能力，让无状态协议能记录状态；HTTP 核心语义并不包含它，它由独立的 RFC 6265 系列定义（本讲 7.5 节）。② 前半对、后半错。HttpOnly 让 Document.cookie 读不到该 cookie，确实缓解 XSS 窃取；但 CSRF 借用的是浏览器"自动携带"的机制，脚本根本不需要读到值，HttpOnly 挡不住，要靠 SameSite 与 CSRF 令牌。③ 错。MDN 提醒某些浏览器重启时会用"会话恢复"把会话续上，导致会话 cookie 被无限延长，并非"一定删除"。
L1 概念辨析有人说：「我把会话标识从 cookie 挪到 localStorage，就不用管 Secure 和 SameSite 了，更安全。」指出这句话里对 localStorage 特性的正确之处，以及它忽略的两个致命问题。
提示

先确认 localStorage 是否自动随请求发送；再想脚本能否读取它，以及"自动携带"消失后换来的是什么风险。

完整解答
正确之处：localStorage 属于 Web Storage API，它的数据永不自动发往服务器，所以确实不再有 cookie 那种"每次请求自动携带"带来的 Secure / SameSite 配置问题。但忽略了两件事：其一，localStorage 里的值脚本随时可读，一旦发生 XSS，攻击者用一行 JavaScript 就能把会话标识端走，而 HttpOnly cookie 恰恰能挡住这种窃取；其二，若改用 Authorization 首部显式携带令牌，凭据仍可能泄露到前端代码或日志，需要另行管理。安全不是换个容器就成立，而是让数据在正确通道里流动：会话标识通常放带 HttpOnly、Secure、SameSite 的 cookie，或由代码显式管理的认证首部。
L2 手算推导浏览器保存了一枚 cookie：Set-Cookie: sid=k9; Domain=app.example.com; Path=/docs; Secure。请对下列五个请求逐一判定是否携带该 cookie，并写出每一步的判定理由：① https://app.example.com/docs/a；② https://app.example.com/docsets；③ https://sub.app.example.com/docs；④ https://example.com/docs；⑤ http://app.example.com/docs。
提示

完整解答
① 发送。Domain：主机 app.example.com 与 Domain 完全相同，过；Path：/docs/a 以 /docs/ 开头，属子路径，过；Secure：HTTPS，过。② 不发。Domain 过；Path 拦下——/docsets 不以 /docs/ 开头，也不是 /docs 本身，只是字符串前缀相同，path-match 要求按路径分段匹配。③ 发送。Domain：sub.app.example.com 是 app.example.com 的子域，显式 Domain 向下包含子域，过；Path：/docs 精确相等，过；Secure：HTTPS，过。④ 不发。Domain 拦下——example.com 是父域，作用域不向上冒泡；后面无需再判。⑤ 不发。Domain 过、Path 过，但 Secure 闸门拦下：明文 HTTP 请求不发送 Secure cookie。结论：只有 ① 和 ③ 携带。
L2 手算推导用户在 https://shop.example.com 登录，拿到认证 cookie。请就 SameSite 的三种取值，判定下列场景是否携带该 cookie，并说明理由：① 从 https://news.other.org 点链接进入 shop.example.com（顶层 GET 导航）；② news.other.org 上的表单以 POST 提交到 shop.example.com/transfer；③ shop.example.com 页面内的 fetch('/api/cart')。再回答：若想让场景 ② 也携带 cookie，该把 SameSite 设成什么、必须搭配什么属性？
提示

先分清哪个场景是同站、哪些跨站；跨站里再分"安全方法顶层导航"与"非安全方法 POST"；最后回忆 None 的硬性搭配。

完整解答
场景 ③ 是同站请求（fetch 从 shop.example.com 页面发往自身），三种取值一律携带。场景 ① 是跨站、但为安全的顶层 GET 导航：Strict 不发（连导航也拦，用户会看到未登录）、Lax 发（正是为安全导航放行）、None 发。场景 ② 是跨站 POST（非安全方法）：Strict 不发、Lax 不发（POST 不属于放行的安全导航）、None 发——这正是 CSRF 想利用的场景。若要让场景 ② 也携带，需设 SameSite=None，且必须同时设置 Secure（仅在 HTTPS 安全上下文生效）；单独写 None 会被浏览器拒绝保存。补充：未设置 SameSite 时按新默认行为当 Lax 处理。

提示

把"属性开关""作用域向下不向上""SameSite 安全梯度""标识与地址分离"四组概念分别套到四个问题上。

完整解答
① 会话 cookie 取形如 Set-Cookie: sid=…; Path=/; Secure; HttpOnly; SameSite=Lax；可再加 __Host- 前缀（无 Domain、Path=/）锁死主机。Secure 挡明文窃听与中间人，HttpOnly 挡 XSS 窃取，SameSite=Lax 挡大部分跨站 CSRF 又不破坏从外站点链接进站的体验，每次认证重发新值防会话固定。② 主题偏好若要子域共享，应显式设 Domain=example.com（向下包含所有子域）；而会话 cookie 应省略 Domain，把它锁在 app.example.com 本机，缩小被其他子域越权读取的面——两者策略相反，正体现"按敏感度收紧作用域"。③ 跨站 POST 回调要携带，只能用 SameSite=None; Secure，代价是这类 cookie 也会跟随其他跨站请求，CSRF 风险升高；补偿手段是校验 state 参数、使用一次性 CSRF 令牌、校验完整 cookie 名并缩短存活期。④ 会话标识进 URL 会经浏览器历史、服务器日志、Referer 与复制分享四路泄露导致会话劫持，同时污染缓存键、拉低命中率、可能串号并放大旧凭据泄露；标识必须与地址分离，放 HttpOnly cookie 或显式认证首部。
