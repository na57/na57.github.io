11.1中间人已经进场：代理同时对两边说谎，却让整条链路成立

前面十讲始终把 HTTP 画成一条直线上的两个端点——客户端发请求，服务器回响应。但从这一讲起，要把中间人请进画面。你在公司内网点开一个外网页面，请求未必直接从浏览器飞到目标服务器；它先到公司出口的一台机器，再由那台机器转发出去。你在手机上浏览网页，响应也未必来自网站自己的机房，而可能来自离你几十公里的一个缓存节点。这些夹在中间的机器，MDN 统称为代理（proxy）。

代理之所以能存在，靠的是一个有点「两面派」的事实：它对着客户端时扮演服务器，接受请求、回响应；它对着目标服务器时又扮演客户端，发出请求、等待响应。两端都以为自己在跟真正的对端说话，中间那台机器却把两条连接缝在了一起。MDN 的《代理服务器与隧道》正是从这个视角切入：代理位于用户本地机器与目标服务器之间的任何位置，它替某一方做事，也因此改变了「谁被隐藏、谁能看见什么」。

MDN 把代理分成两大类，判据只有一条——它代表谁。代表客户端的叫正向代理（forward proxy），代表服务器的叫反向代理（reverse proxy）。注意 MDN 在括号里还给了正向代理两个别名：隧道、网关；这不是随口一提，而是预告了本讲后两节——隧道（11.3）正是正向代理的一种高级形态。

对比维度正向代理（forward proxy）反向代理（reverse proxy）

把这张表读成一句话：正向代理替客户端「出去」，反向代理替服务器「进来」。MDN 特别点出正向代理可以是匿名的——它把请求的地址改写成自己的 IP，于是目标站点只能看到代理，看不到真正的访客；TOR 就是把流量在多个代理之间反复转发来隐藏来源的极端例子。反过来，反向代理站在网站最前面，访客以为自己连的就是 example.com，实际上连的是反向代理，后端可能有十台机器在分担流量。

反向代理的三项用途，MDN 一条条列得很清楚，值得展开成具体场景。负载均衡：把请求按轮询或最少连接分发到多台后端，任何一台挂了就摘掉，访客无感。缓存静态内容：图片、样式表这些不常变的东西放在反向代理本地，命中就直接回，不必每次都回源，这正是后面缓存讲义里「共享缓存」的落地形态。压缩：在离用户更近的地方压缩和优化内容，减少传输字节。你会发现这三项都不是改 HTTP 语义，而是把同一条请求—响应事务换个地方处理——这与第 1 讲「变的是承载，不变的是事务模型」完全一致。

代理夹在中间，带来一个直接的副作用：原始请求的信息会丢。正向代理把请求地址改写成自己的 IP，目标服务器就看不见真正的客户端了。可这份信息对调试、统计、按地区生成内容又很关键。MDN 因此列出一组专门用来「把被代理抹掉的信息补回来」的首部，并明确区分了标准与事实标准：

首部作用地位
Forwarded携带代理参与路径时被更改或丢失的信息，如原始客户端 IP、原始主机、原始协议标准首部
X-Forwarded-For标识经由代理或负载均衡连到服务器的客户端源 IP事实标准
X-Forwarded-Host标识客户端原本请求连接的主机事实标准
X-Forwarded-Proto标识客户端连代理时用的协议，HTTP 还是 HTTPS事实标准
Via提供代理自己的信息（而非客户端的），请求与响应中都可出现，由代理逐跳追加标准首部

这里最关键的一行是 Via。前面四个 X-Forwarded-* 与 Forwarded 回答的是「客户端本来是谁」，而 Via 回答的是「请求经过了哪些代理」。MDN 特别强调它同时出现在请求首部与响应首部里，且由正向、反向代理都会添加。11.2 节会亲手推演它逐跳追加的全过程。

客户端怎么知道该直连还是走代理？MDN 提到一个配置选项：代理自动配置（Proxy Auto-Configuration，PAC）文件。它是一个 JavaScript 函数，扩展名 .pac，MIME 类型为 application/x-ns-proxy-autoconfig，核心是一个叫 FindProxyForURL 的函数，返回 DIRECT（直连）或 PROXY 主机:端口。MDN 给的例子里，内部 DNS 能解析的主机就直连，解析不了的才走代理：

function FindProxyForURL(url, host) { if (isResolvable(host)) { return "DIRECT"; } return "PROXY proxy.mydomain.com:8080"; }
MDN 的 PAC 示例：能解析的内部主机直连，其余交给代理。注意这是浏览器配置层面的逻辑，与 HTTP 报文本身无关。

💡 关键一跃

代理不是「多了一跳」这么简单，而是把一条端到端连接拆成了两条各自独立的连接。正因为被拆开，代理才有机会在中间做缓存、压缩、改写首部，也才有必要用 Via、Forwarded 之类的首部把被切断的信息重新串起来。11.3 的隧道与 11.4 的升级，本质上都是在回答「连接被拆开之后，怎么让两端重新建立某种端到端的关系」。

⚠️ 常见误区

「代理就是中转站，两端完全感知不到」——这句话错。正向代理客户端通常知道（浏览器里配了），反向代理客户端通常不知道；更关键的是，很多 HTTP 首部是只对本跳有效的（11.4 会系统讲逐跳首部），代理必须正确处理它们，否则连接行为会被意外改变。把代理当成透明管道，是后面所有故障推演的根源。

11.2请求目标为何变形：连的是代理，就得把完整地址写进请求行

上一节把代理的定位讲清了，但还留着一个具体的报文问题：客户端一旦把请求发给正向代理而不是源服务器，请求行该怎么写？这不是格式洁癖，而是代理能不能正确转发的前提。先看一个最朴素的反例。

客户端直连源服务器时，TCP 连接已经确定了「跟谁说话」，所以请求行只需要给出资源在这台服务器上的路径。这就是 MDN 与规范里说的源点形式（origin-form）：只带路径与查询串，不带域名。

GET /index.html HTTP/1.1 Host: www.example.com Accept: text/html （直连：请求目标是 origin-form，只有路径）
直连源服务器的请求：TCP 已锁定对端，请求目标用 origin-form，域名放在 Host 首部里就够了。

现在把场景换成「客户端配置了正向代理」。浏览器发出请求时，它建立 TCP 连接的对象是代理，而不是 www.example.com。如果请求行还是 GET /index.html，代理收到后根本无从判断这个 /index.html 属于哪台服务器——它可能服务成千上万个域名。于是客户端必须把完整 URL 写进请求行，这叫绝对形式（absolute-form）：

GET http://www.example.com/index.html HTTP/1.1 Host: www.example.com Accept: text/html （经正向代理：请求目标升级为 absolute-form，带 scheme 与主机）
经正向代理的请求：请求目标从路径变成完整 URL，代理据此知道要把请求转发到哪里。Host 依然保留。

两条报文对照，结论就出来了：请求目标从 origin-form 变成 absolute-form，根本原因是「TCP 对端」和「URI 权威」不再是同一个对象。直连时二者合一，路径足够；经代理时二者分离，必须把 scheme、主机、端口写全，代理才知道下一步往哪连。这也解释了为什么 Host 首部不能省——它依旧标识「这个请求属于哪个虚拟主机」，绝对形式只是把选择权也交给了代理。

请求目标的另外两种形式也一并记全，它们会在本讲后面反复出现：权威形式（authority-form）只写 主机:端口，是 CONNECT 方法专用（11.3 展开）；星号形式（asterisk-form）写单个 *，用于 OPTIONS * 这种针对服务器整体而非某个资源的问题。

接下来是本节的重头戏：Via 首部如何逐跳追加。MDN 说它由代理添加、可出现在请求与响应里，但没有展开格式。Via 的每一段记录两件事——这一跳用的协议版本和对端标识，形如 1.1 proxy-a.example.com。代理转发报文时，把自己这一段追加到列表末尾。我们用一条经过两个正向代理的请求来全程推演。

第 0 跳 · 客户端发出。客户端直连代理 A，请求里还没有 Via：

GET http://www.example.com/index.html HTTP/1.1 Host: www.example.com （此时还没有 Via 首部）
客户端 → 代理 A：请求刚发出，Via 为空。

第 1 跳 · 代理 A 转发。代理 A 以 HTTP/1.1 收到请求，决定转发给代理 B。它把自己的一段 1.1 proxy-a.example.com 追加进去，于是转发报文里出现 Via：

GET http://www.example.com/index.html HTTP/1.1 Host: www.example.com Via: 1.1 proxy-a.example.com （代理 A 追加了自己的标识）
代理 A → 代理 B：Via 第一次出现，只有 A 这一段。

第 2 跳 · 代理 B 转发。代理 B 同样以 HTTP/1.1 收到，转发给源服务器时不是覆盖，而是在已有列表后面追加自己的一段。于是列表变成两段，顺序记录了真实路径：

GET http://www.example.com/index.html HTTP/1.1 Host: www.example.com Via: 1.1 proxy-a.example.com, 1.1 proxy-b.example.net （代理 B 在末尾追加，A 在前、B 在后）
代理 B → 源服务器：Via 变成两段，从客户端往服务器方向依次是 A、B。源服务器据此知道请求途经了谁。

把三步连起来看，Via 的追加规律有三条：① 每次转发追加而不是覆盖，所以列表是路径的历史记录；② 顺序是「离客户端近的在前，离服务器近的在后」，读起来就是报文走过的方向；③ 每段带上协议版本，因此 1.0 old-proxy 与 1.1 new-proxy 并列时，还能看出哪一跳是旧设备。响应沿原路返回时，Via 同样由沿途代理追加，让客户端也能看到回程路径——这正是 MDN 说它「请求与响应中都可出现」的含义。Via 有两个实用价值：排查「请求到底经过了哪些代理」，以及让代理检测环路（看到自己的标识再次出现，就知道报文绕了回来）。

✅ 判定规则

要判断一条请求该用哪种请求目标，只问一句：请求行的接收者，和 URI 里的权威（主机），是不是同一个？是同一个（直连源站），用 origin-form；不是同一个（发给正向代理），用 absolute-form。至于 CONNECT，接收的是代理、要连的是权威，但语义是「建管道」而非「取资源」，所以规范单独给了 authority-form。这条判据能覆盖本讲所有请求目标问题。

⚠️ 常见误区

「经代理时有了 absolute-form，Host 就多余了」——错。absolute-form 解决的是「代理往哪转」，Host 解决的是「目标主机上哪个虚拟主机」，两者维度不同，规范都要求带上。另一个误区是以为 Via 只加一次或会被后面的代理覆盖；事实上每一跳都追加，列表长度等于经过的代理数。抓包时看到 Via 有五六段，说明请求穿过了长长的代理链，而不是配置错误。

11.3CONNECT 与隧道：把 TCP 借给 HTTPS，代理从此只看得见字节

上一节解决了明文的转发，但马上撞上一堵墙。HTTPS 的 TLS 是端到端的：加密连接建立在浏览器和目标网站之间，中间的正向代理手里没有会话密钥，既不能解密，也不能改写里面的请求行。可代理的工作恰恰是「改写并转发 HTTP」。矛盾出现了：客户端想通过代理访问一个 HTTPS 站点，代理却连请求要发往哪里、请求里写了什么都读不到，怎么转发？

MDN 给出的答案是隧道（tunneling）：「通过封装数据，在公共网络中传输专用网络数据和协议信息」，而 HTTP 隧道就是「用高层协议 HTTP 去传输低层协议 TCP」。更具体地说，HTTP 定义了一个专门的请求方法 CONNECT，MDN 的描述是「启动与请求资源的双向通信，可用于打开隧道」。这就是「HTTP 代理后面的客户端如何用 SSL（即 HTTPS，端口 443）访问网站」的标准做法。MDN 同时提醒：并非所有代理都支持 CONNECT，有的还把它限制在 443 端口。

现在把交互拆成完整报文。设想浏览器要通过正向代理访问 www.example.com:443。第一步，浏览器不发送 GET，而是向代理发一条 CONNECT，请求目标用上一节说的 authority-form，只写 主机:端口：

CONNECT www.example.com:443 HTTP/1.1 Host: www.example.com:443 Proxy-Connection: Keep-Alive （客户端 → 代理：请为我连到 www.example.com:443）
第一步：客户端向代理发 CONNECT，请求目标是权威形式。语义不是「给我资源」，而是「替我建立一条到该主机的 TCP 连接」。

第二步，代理解析出目标主机与端口，自己新建一条到 www.example.com:443 的 TCP 连接。如果连得上，代理回一条 200 Connection established：

HTTP/1.1 200 Connection established Proxy-Agent: ProxyGateway/1.0 （代理 → 客户端：隧道已建立，接下来的字节请直接透传）
第二步：代理返回 200 Connection established。注意这不是普通的 200 OK 响应——它表示「从现在起这条连接变成管道」，后面不再有 HTTP 响应主体。

第三步是关键。代理不再解析这条连接上的任何 HTTP，它只做一件事：把客户端发来的字节原样转发给目标服务器，把目标服务器返回的字节原样转发给客户端。于是浏览器开始在这条管道里跟目标网站做真正的 TLS 握手：

客户端 → 代理 → 目标站（字节透传，代理不解析） → TLS ClientHello ...随机数与加密套件... ← TLS ServerHello + Certificate ...证书链... → TLS Finished 隧道内随后才是加密后的 HTTP： → [加密] GET /index.html HTTP/1.1 ← [加密] HTTP/1.1 200 OK ...
第三步：TLS 握手及之后的 HTTP 全部在隧道内以密文字节流通过。代理只搬运字节，看不到明文请求行、首部或网页内容。

把这条链路上「代理能看到什么、看不到什么」列成表，隧道的价值与边界就一目了然：

信息项正向代理能否看到原因
CONNECT 的目标主机与端口能看到它在 CONNECT 请求行的权威形式里，是明文
客户端真实 IP能看到客户端与代理直连，TCP 对端就是客户端
TLS 握手是否发生、流量大小与时序能看到这些是密文字节的长度和时间特征，无需解密
隧道内的 HTTP 方法与路径看不到被 TLS 加密，代理没有会话密钥
请求首部、Cookie、网页正文看不到被 TLS 加密，代理没有会话密钥，无法解读

这张表说明一件重要的事：隧道不是「代理升级成了透明管道」，而是代理主动放弃了应用层解析权。它只保留最外层的连接管理（建立到目标的 TCP、转发字节、最后关闭），把 HTTP 语义原封不动地交还给两端。这也解释了 MDN 为什么把隧道归在正向代理名下——它仍代表客户端出去，只是这次「出去」的方式是借一条 TCP 给客户端自己用。

MDN 还提到 CONNECT 的一个现实约束：有的代理只允许连 443 端口。原因不难理解——隧道一旦建立，代理就看不到里面跑的是什么协议，如果允许连任意端口，代理就可能沦为绕过网络策略的通用通道。因此很多企业代理把 CONNECT 白名单化，只放行 443，把「看不见内容」的风险限制在 HTTPS 这一个已知场景里。

💡 关键一跃

把 11.2 与 11.3 对照：普通代理是「代理替你解析并改写 HTTP」，CONNECT 隧道是「代理只替你建立 TCP，HTTP 由你自己端到端地谈」。前者的代价是代理看得见明文、也改得动；后者的代价是代理无法缓存、无法压缩、无法按内容做策略，但换来了端到端的机密性。选哪种，取决于你要的是「中间可优化」还是「两端可加密」。

⚠️ 常见误区

「200 Connection established 之后代理仍在转发 HTTP 报文」——错。这条响应之后，连接已经不是 HTTP 连接，而是一对 raw TCP 字节流；代理再按 HTTP 去解析 TLS 记录只会出错。另一个误区是把 CONNECT 当成「取资源的方法」：它不取任何资源，请求目标是 主机:端口 而不是路径，成功状态码虽是 2xx，语义却是「管道已就绪」。

11.4就地换协议：一条 HTTP/1.1 连接如何变成 WebSocket 双向管道

上一节的隧道解决的是「HTTPS 怎么穿过代理」，手段是把 HTTP 藏进 TCP。本节处理一个不同但相关的问题：有些应用（聊天、实时推送、在线游戏）需要双向长连接，而 HTTP 的请求—响应模型是客户端问一句、服务器答一句，服务端无法主动推。有没有办法不新开端口、就在已经建立的那条 HTTP/1.1 连接上，把它切换成另外一种协议？MDN 的《协议升级机制》给出的答案就是协议升级（protocol upgrade）。

MDN 的开场定义很精确：HTTP/1.1 提供一种用 Upgrade 首部字段的特殊机制，允许把一条已建立的连接升级成新的、不相容的协议。这句话里三个词要点出来：「已建立」——先有普通 HTTP 连接；「不相容」——新协议不是 HTTP 的小改版，而是另一套规则；「特殊机制」——它是可选的、不能强制，且通常由客户端发起。MDN 还明确加了一条警告：HTTP/2 明确禁止使用此机制，它只属于 HTTP/1.1。实践中它主要用来引导 WebSocket。

先看通用流程。客户端在请求里列出想切换到的协议，按优先级从高到低排列；服务器若同意，回 101 Switching Protocols 并在响应里带上 Upgrade 首部确认切换到哪一个；服务器若不同意，就忽略 Upgrade，返回一个常规响应（例如 200 OK）。发出 101 之后，服务器就开始使用新协议，连接变成一条双向管道。MDN 强调，一旦升级完成，连启动升级的那条请求也会被新协议接管——HTTP 至此退场。

现在看本节第一个完整例子：Upgrade: websocket 的握手。客户端先发一条普通的 HTTP/1.1 GET，但带上四个关键首部：

GET /chat HTTP/1.1 Host: server.example.com Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== Sec-WebSocket-Version: 13 （客户端 → 服务器：请把这条连接升级到 WebSocket）
WebSocket 升级请求：Upgrade 指明目标协议，Connection 声明 Upgrade 逐跳，Sec-WebSocket-Key 是校验用的随机密钥，Version 为 13。

服务器同意后，返回 101 响应，并回一个由密钥算出的 Sec-WebSocket-Accept：

HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo= （服务器 → 客户端：从现在起是 WebSocket 帧，不再是 HTTP 报文）
101 响应：状态行宣告切换，Upgrade 与 Connection 必须同时出现，Accept 是客户端密钥经固定算法算出的应答值。

这里有两个必须讲透的细节。第一，Sec-WebSocket-Key 与 Sec-WebSocket-Accept 的关系。MDN 说得很直白：这个密钥「不提供安全性」，它的作用是确认「是的，我真的是要打开一个 WebSocket 连接」，防止非 WebSocket 客户端无意或滥用请求 WebSocket。计算过程由 WebSocket 规范定义：取客户端密钥值，与固定字符串 258EAFA5-E914-47DA-95CA-C5AB0DC85B11 拼接，对拼接结果取 SHA-1 散列，再把得到的 20 字节做 base64 编码，结果就是 Accept。用上面的密钥走一遍：

① 客户端密钥 dGhlIHNhbXBsZSBub25jZQ== ② 拼接固定 GUID dGhlIHNhbXBsZSBub25jZQ==258EAFA5-E914-47DA-95CA-C5AB0DC85B11 ③ 取 SHA-1（20 字节） b3 7a 4f 32 65 82 f6 3f 27 98 a1 44 3b 7c f9 8a 3e 2c 3f 0a ④ base64 编码 → Sec-WebSocket-Accept s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
Sec-WebSocket-Accept 的四步推导（这是 RFC 6455 给出的标准示例值）。注意算法是公开固定的，它证明「握手方懂 WebSocket」，不是加密，也不认证身份。

第二，Upgrade 与 Connection 为什么必须同时出现。MDN 给出的理由只有一句，但分量很重：Upgrade 是一个逐跳（hop-by-hop）首部，因此还必须在 Connection 首部里把它列出来。这句话把两个首部的分工讲清了：Upgrade 说「我想切到什么协议」，Connection: Upgrade 说「这个 Upgrade 首部只在本跳有效，请中间节点消费掉、别往下传」。缺了 Connection 这一行，中间代理可能把 Upgrade 当作端到端首部原样转发给下一跳，而下一跳并没有参与这次升级协商，行为就不可控了。

这就引出本节第二个完整例子：逐跳首部的处理推演，以及一个代理错误转发导致的故障链。先把待判定的五个首部摆上桌，逐个判断是不是逐跳首部：

首部是否逐跳首部说明
Connection是逐跳首部的「总开关」，它自己也是逐跳的，并列出本跳的其他逐跳首部
Keep-Alive是描述本跳连接的保活参数，只对本跳有意义
Proxy-Authenticate是代理发给客户端的认证挑战，只在客户端—代理这一跳之间使用
Transfer-Encoding是描述本跳消息主体如何分块定界，下一跳要用自己的方式重新编码
Upgrade是MDN 明确指出它是逐跳首部，必须在 Connection 中列出

答案是五个全是逐跳首部。这一点常被答错，尤其是 Transfer-Encoding——很多人以为它跟着主体端到端传递，其实它只描述「这一跳的主体怎么定界」，代理转发时必须按下一跳的情况重新编码（比如把 chunked 换成定长）。判据可以浓缩成一句：凡是描述「这一跳怎么传」的首部，都是逐跳的；凡是描述「资源本身是什么」的首部，才是端到端的。

现在推演故障链。场景是客户端通过正向代理访问源站，客户端在本跳请求里带了 Connection: close，意图是「我这一跳用完就关」。正确的做法应该是：代理消费掉客户端的 Connection 首部，按自己与源站之间的连接策略重新生成（比如对自己复用的源站连接用 keep-alive）。但假设这个代理实现有 bug，把 Connection: close 原样转发给了源站：

客户端 → 代理（本跳想关闭） GET /page HTTP/1.1 Host: www.example.com Connection: close 代理 → 源站（错误：原样转发了逐跳首部） GET /page HTTP/1.1 Host: www.example.com Connection: close ← 本该被消费并重新生成
故障起点：代理把只对本跳有效的 Connection: close 原样转发，源站误以为「代理这条连接用完要关」。

故障链逐步展开：

步骤发生了什么后果
① 客户端发请求带 Connection: close，只想关闭「客户端—代理」这一跳意图本身没错，只作用于第一跳
② 代理错误转发未消费该逐跳首部，原样写进「代理—源站」请求把第一跳的意图误植到第二跳
③ 源站照做源站把 close 当作针对自己的指令，响应后关闭到代理的 TCP 连接代理复用的源站连接池被无故拆掉一条
④ 客户端意图落空代理因为只顾转发、没在本跳执行 close，反而没按客户端要求关闭客户端连接客户端以为会关闭的连接还开着，语义错乱
⑤ 连锁反应代理下次想复用那条源站连接时，发现它已被源站关闭请求失败或被迫重连，出现延迟抖动与偶发错误

把这条链看到底，你会明白为什么逐跳首部必须由每一跳「消费并重新生成」：它们描述的是本跳的连接状态，一旦跨跳，语义就会落到错误的连接上。同样的机制如果发生在升级场景，后果更严重：代理若把 Connection: Upgrade 与 Upgrade: websocket 错误转发给源站，源站会回 101 并开始说 WebSocket 帧，而夹在中间的代理还在按 HTTP 解析字节，连接立即错乱。这正是 MDN 强调「Upgrade 必须在 Connection 里列出」的工程原因——它提醒每一跳：这个首部到我为止。

MDN 补充说，WebSocket 连接几乎总是通过升级 HTTP 或 HTTPS 建立，而用 WebSocket() 构造 API 时这些握手细节都被库代劳了；只有自己从头实现 WebSocket 客户端时，才需要亲手处理升级过程。这也提示了本节与前后讲的分工：升级是 HTTP/1.1 的遗产，而 HTTP/2、HTTP/3 有自己的多路复用机制，不再需要这种「把连接改成另一套协议」的把戏。

✅ 判定规则

看到 Upgrade，立刻检查两件事是否成对出现：Connection: Upgrade 在不在（否则逐跳语义没声明，中间节点可能误转发）？响应是不是 101 Switching Protocols（否则说明服务器没同意升级，仍是普通 HTTP）？看到任意逐跳首部，问「谁消费、谁重新生成」——正确模式永远是每一跳消费上游的、再为下游生成自己的，绝不原样转发。

⚠️ 常见误区

「Sec-WebSocket-Key 是用来加密或认证的安全机制」——错。MDN 明说它「不提供安全性」，算法公开固定，只用于确认对方确实在发起 WebSocket 握手、挡住无意的滥用；真正的安全来自 wss:// 之下的 TLS。另一个误区是以为 HTTP/2 也能用 Upgrade 升级——MDN 明确禁止，该机制只属 HTTP/1.1。

11.5延伸：规范怎么写：逐跳首部、CONNECT 与握手在 RFC 里的精确定义

前四节始终以 MDN 为口径，但 MDN 是面向开发者的文档，刻意省略了规范性细节——它说 Via「由代理添加」，却没给格式；说 CONNECT「打开隧道」，却没定义状态码的精确语义；说 Upgrade 是逐跳首部，却没列全逐跳首部清单。当你要实现一个真正合规的代理或客户端时，就必须去看 IETF 的规范。本节把这些细节对齐到现行 RFC：RFC 9110（HTTP 语义）、RFC 9112（HTTP/1.1 线上格式）与 RFC 6455（WebSocket 协议）。

MDN 的说法RFC 怎么写为什么值得知道
代理用 Via 首部提供自身信息，请求与响应中都可出现，逐跳追加RFC 9110 §7.6.1 定义 Via 的语法为「收受协议 + 收受者 + 可选注释」的列表，并规定代理转发时必须在列表末尾追加自己的一段；同一节给出逐跳首部完整清单：Connection、Keep-Alive、Proxy-Authenticate、Proxy-Authorization、TE、Trailer、Transfer-Encoding、Upgrade实现代理时，哪些首部要消费并重新生成、Via 每段怎么写，都有规范性答案。MDN 的「逐跳追加」在这里变成了 MUST 级别的操作要求，11.4 的故障链正是违反它的后果
经代理的请求目标用绝对形式（absolute-form），直连用源点形式RFC 9112 §3.2 定义四种请求目标；客户端向代理发请求时 MUST 使用 absolute-form（CONNECT 除外），向源服务器发时 MUST 用 origin-form；CONNECT 的目标必须用 authority-form写代理客户端或抓包分析时，请求行的形式不是风格选择而是合规要求。把 origin-form 发给代理，代理有权拒绝
CONNECT 启动双向通信、打开隧道，成功返回 200 Connection establishedRFC 9112 §9.3.6 规定 CONNECT 的目标是 主机:端口 的权威形式，代理建立到目标的 TCP 连接后，发送 2xx（通常是 200）响应表示「切换到隧道模式」；一旦隧道建立，代理不得再解析该连接上的字节解释了为什么成功状态码是 2xx 却没有任何响应主体——它标记的是「连接用途改变」而非「资源取回」；也说明端口白名单与隧道滥用防护的规范依据
Upgrade 是逐跳首部，必须在 Connection 中列出；服务器同意则回 101RFC 9110 §7.8 定义 Upgrade 机制：客户端用 Upgrade 列出候选协议，发送方 MUST 在 Connection 中一并列出 Upgrade；101 Switching Protocols 在 RFC 9110 的状态码章节定义，表示服务器理解并愿意切换；HTTP/2 的 RFC 9113 明确禁用此机制把 MDN 的「必须同时出现」落实为 MUST 条款。少写 Connection: Upgrade 不是小疏漏，而是违反规范，中间节点的行为将不可预测
WebSocket 密钥经固定算法算出 Accept，防止滥用但不提供安全性RFC 6455 §1.3 定义打开握手：客户端密钥是 base64 编码的 16 字节随机值，服务器把它与固定 GUID 258EAFA5-E914-47DA-95CA-C5AB0DC85B11 拼接，取 SHA-1 后 base64 得 Accept；版本为 13，不支持时回 426 Upgrade Required 并列出支持的版本MDN 说「算法由规范定义」，这里就是那个算法。自己实现握手或排查「握手失败」时，能逐步验证密钥到 Accept 的推导，也能正确处理 426 与 Sec-WebSocket-Version

这张表反复出现一个词：MUST。这正是 RFC 与 MDN 的语气差别——MDN 用「应该」「通常」，RFC 用 MUST / SHOULD / MAY 严格分级。当你需要判定一个实现「合规还是违规」时，MDN 给方向，RFC 给裁决。11.4 的故障链在 RFC 口径下其实是一次违规：代理没有按 §7.6.1 消费并重新生成逐跳首部。

💡 关键一跃

把三份 RFC 按职责对号入座，本讲的全部细节就归位了：RFC 9110 管语义（逐跳首部清单、Via / Upgrade 的含义、101 的意义），RFC 9112 管 HTTP/1.1 的线上格式（四种请求目标、CONNECT 的权威形式与隧道切换），RFC 6455 管 WebSocket（握手算法、密钥到 Accept、版本与 426）。MDN 把这些揉成一篇好读的指南，RFC 则把它们拆成可执行、可判定的条款。

⚠️ 常见误区

别再引用旧编号。网上大量文章仍把 CONNECT、Upgrade 的细节写在 RFC 2616 或 RFC 7230 里——它们已被 2022 年的 RFC 9110 系列取代；WebSocket 握手请认准 RFC 6455。查规范先看 httpwg.org/specs 的现行列表，再读具体章节，避免把已作废的说法当成现行要求。

🃏概念卡：本讲概念的一分钟画像

翻面前先自问：这个概念我能用一句话讲清楚吗？

概念卡 1
正向代理（Forward Proxy）
点击翻面 →
定义代表客户端、替客户端访问互联网的中间节点，MDN 也称隧道或网关。
解决问题节省与控制带宽、隐藏客户端身份（如 TOR 匿名路由）、突破访问限制。
直觉你托朋友替你跑腿，对方只看见朋友，看不见你。
误区以为正向代理隐藏服务器；它隐藏的是客户端，服务器身份与它无关。
何时用公司出口、VPN、需要匿名或带宽管控的场景；11.2 绝对形式、11.3 隧道。
概念卡 2
反向代理（Reverse Proxy）
点击翻面 →
定义代表服务器、替服务器接住客户端请求的中间节点，对客户端隐藏后端。
解决问题负载均衡、缓存静态内容、压缩与优化，分担后端压力并提升可用性。
直觉你打电话到公司总机，被转给某个分机，你并不知道后面有几个人。
误区以为客户端知道它的存在；反向代理通常对客户端透明，看起来就是目标站。
何时用网站入口、CDN 边缘、网关层；与第 5 讲共享缓存相衔接。
概念卡 3
请求目标形式（origin / absolute / authority-form）
点击翻面 →
定义请求行的目标有四种写法：路径、完整 URL、主机端口、星号。
解决问题区分「发给谁」与「找哪个资源」：对端不同，写法不同。
直觉直连说门牌号，找代理要说完整地址，建管道只报主机和端口。
误区以为经代理有绝对形式就不用 Host；两者维度不同，都要带。
何时用11.2 全节；写代理客户端、分析抓包时判定请求行是否合规。
概念卡 4
Via 首部
点击翻面 →
定义由代理逐跳追加的首部，每段记录一跳的协议版本与代理标识，请求与响应中都出现。
解决问题记录报文走过的代理路径，用于排障与环路检测，补回被代理切断的链路信息。
直觉像快递包裹上每一站盖的戳，串起来就是完整路线。
误区以为 Via 只加一次或被下游覆盖；每一跳都追加，列表长度等于代理数。
何时用11.2 两代理推演；排查多层代理、CDN 链路时读它。
概念卡 5
CONNECT 与隧道（Tunneling）
点击翻面 →
定义用 HTTP 传输 TCP 的机制；CONNECT 让代理建立到目标的连接，随后只透传字节。
解决问题让 HTTPS 穿过正向代理：TLS 端到端加密，代理无法解析却仍需转发。
直觉代理借你一根管子，管子里的东西它不拆不看，只管运。
误区以为 200 之后代理还在转发 HTTP；那之后是 raw TCP，代理放弃解析权。
何时用11.3 三步交互；理解代理能看见目标主机端口、看不见隧道内明文。
概念卡 6
逐跳首部（Hop-by-hop Header）
点击翻面 →
定义只对本跳连接有效的首部，每跳消费后重新生成；Connection 列出本跳的其他逐跳首部。
解决问题让每段连接各自管理自己的传输状态，不把本跳语义误植到下一跳。
直觉行李转运时每一段换一次运输单，而不是把上一段的单子一路贴到底。
误区以为 Transfer-Encoding 端到端；它只描述本跳主体如何定界，是逐跳的。
何时用11.4 故障链；实现代理、排查连接被意外关闭时必查。
概念卡 7
协议升级与 WebSocket 握手（Upgrade / 101）
点击翻面 →
定义HTTP/1.1 用 Upgrade 请求切换协议，服务器以 101 同意，连接随即变成双向管道。
解决问题在既有连接上支持 WebSocket 等双向协议，不新开端口；Upgrade 必须与 Connection 同现。
直觉同一条电话线，谈完开场白后双方约定改说另一种暗号。
误区以为 Sec-WebSocket-Key 是安全机制或 HTTP/2 也能升级；它不提供安全性，且 2 禁用升级。
何时用11.4 握手与密钥推导；自实现 WebSocket 或排查 101 / 426 时。

完整解答
① 错。隐藏客户端身份是正向代理的作用；反向代理隐藏的是服务器身份。② 错。代表服务器、做负载均衡是反向代理的职责；正向代理代表客户端，典型用途是节省带宽与匿名访问。③ 对。反向代理部署在站点入口，对客户端透明，访客以为自己连的就是目标站，并不知道后面还有后端机器。三句的判断都取决于「代表谁」这一条判据，把它记牢就不会被「代理」这个笼统的词绕晕。
L1 概念辨析下列首部哪些是逐跳首部哪些是端到端首部：Connection、Transfer-Encoding、Upgrade、Host、Cache-Control？并回答：为什么说逐跳首部必须「每跳消费并重新生成」？
提示

判据：描述「这一跳怎么传」的是逐跳的，描述「资源本身是什么」的是端到端的。

完整解答
逐跳首部：Connection、Transfer-Encoding、Upgrade（此外还有 Keep-Alive、Proxy-Authenticate、Proxy-Authorization、TE、Trailer）。端到端首部：Host（描述目标主机）、Cache-Control（描述资源的缓存语义）。逐跳首部描述的是本跳的连接状态——比如 Transfer-Encoding 只说「本跳主体怎么分块」，Upgrade 只说「本跳想切协议」。一旦被原样转发到下一跳，这些语义就会落到一条不同的连接上，造成 11.4 里「源站误关连接」那类故障。因此正确模式永远是：每一跳消费上游的逐跳首部，再根据自己的连接状况为下游重新生成，绝不原样传递。
L2 手算推导一条请求从客户端出发，依次经过正向代理 P1、P2 到达源站，P1 与客户端之间、P1 与 P2 之间用 HTTP/1.1，P2 与源站之间用 HTTP/1.0。客户端请求里没有 Via。请逐步写出：① P1 转发时请求里 Via 的值；② P2 转发时 Via 的值；③ 源站收到的 Via 有几段、各代表什么？

① P1 以 HTTP/1.1 收到请求，转发给 P2 时追加自己的一段：Via: 1.1 p1.example。② P2 以 HTTP/1.1 收到（P1—P2 这一跳是 1.1），转发给源站时在末尾追加自己的一段：Via: 1.1 p1.example, 1.1 p2.example。注意第二段写的是 P2 收到请求时用的版本 1.1，而不是它转发给源站用的 1.0——Via 记录的是收受协议。③ 源站收到的 Via 有两段：第一段 1.1 p1.example 代表 P1 这一跳，第二段 1.1 p2.example 代表 P2 这一跳。列表顺序从客户端往服务器方向排列，正好是报文实际走过的路径。如果 P2 转发时用的是 HTTP/1.0，这只是「P2—源站」这一跳的版本，会体现在源站随后回程时 P2 追加的那段 Via 里，而不是去程列表里。

问自己：请求行的接收者与 URI 权威是不是同一个？直连用 origin-form，经代理用 absolute-form，建 HTTPS 隧道用 authority-form。

完整解答
场景 A（直连）：请求行 GET /a/b.html HTTP/1.1，配 Host: www.site.org。TCP 对端就是目标站，路径即可定位资源，用 origin-form。场景 B（经代理）：请求行 GET http://www.site.org/a/b.html HTTP/1.1，仍带 Host: www.site.org。TCP 对端是代理而 URI 权威是目标站，二者分离，必须用 absolute-form 让代理知道往哪转；Host 仍要带以区分虚拟主机。场景 B 改为 HTTPS：浏览器不能直接发 GET（代理读不到加密目标），第一步发 CONNECT www.site.org:443 HTTP/1.1，配 Host: www.site.org:443，请求目标用 authority-form。代理回 200 Connection established 后只做字节透传。此后代理看得到目标主机与端口、客户端 IP、密文流量大小与时序；看不到隧道内的 HTTP 方法、路径、首部、Cookie 与正文——那些都被 TLS 端到端加密了。
L3 建模应用某公司的内网用户要通过一台正向代理访问外网，公司还有一个对外的 Web 服务部署了反向代理。请设计一个方案并回答：① 内网用户访问外网 HTTPS 站点时，代理用哪种方法和请求目标？代理能看到什么、看不到什么？② 外网访客访问公司 Web 服务时，反向代理能起到哪三种作用？③ 后端想知道「访客原本的 IP 和协议」，该用哪些首部补回被代理抹掉的信息？④ 若代理实现有 bug，把客户端的 Connection: close 原样转发给源站，会发生什么？给出完整故障链。
提示

把「正向代理出去」「反向代理进来」「逐跳首部每跳消费」三个模型分别套到对应环节。

完整解答
① 内网用户访问外网 HTTPS，客户端先向正向代理发 CONNECT 目标主机:443 HTTP/1.1（authority-form），代理建 TCP 后回 200 Connection established，随后纯透传。代理看得到目标主机端口、客户端 IP、密文流量大小与时序；看不到隧道内的方法、路径、首部与正文，因为 TLS 端到端加密。② 反向代理对外可：负载均衡（分发到多台后端）、缓存静态内容（图片等不常变资源命中即回）、压缩与优化内容（加快传输）。③ 用 Forwarded（标准）或事实标准的 X-Forwarded-For（源 IP）、X-Forwarded-Host（原始主机）、X-Forwarded-Proto（原始协议）补回被抹掉的信息；代理自身路径信息用 Via。④ 故障链：客户端带 Connection: close，只想关闭「客户端—代理」这一跳；代理若有 bug 未消费而原样转发给源站，源站会把 close 当作针对自己的指令，响应后关闭「代理—源站」连接，无故拆掉代理复用的连接池；同时客户端第一跳的 close 意图因代理只顾转发而没执行；最终代理下次复用那条源站连接时发现已关闭，请求失败或被迫重连，出现延迟抖动与偶发错误。根治办法是每一跳消费并重新生成逐跳首部——这正是 RFC 9110 §7.6.1 的要求。

自测 1
客户端通过正向代理发送 HTTP 请求时，请求目标通常采用哪种形式？
  • A. origin-form（只有路径）
  • B. absolute-form（完整 URL）
  • C. authority-form（主机:端口）
  • D. asterisk-form（星号）
解析：B 对。发给代理时 TCP 对端是代理、URI 权威是目标站，二者分离，必须用完整 URL 让代理知道往哪转。A 是直连源站时的写法；C 是 CONNECT 专用的权威形式；D 只用于 OPTIONS *。把请求目标形式与场景对应起来是关键。
自测 2
CONNECT 隧道建立后，正向代理能看到什么？
  • A. 隧道内的 HTTP 方法与路径
  • B. 请求首部里的 Cookie 与网页正文
  • C. CONNECT 的目标主机与端口，以及密文流量的大小与时序
  • D. 目标站返回的明文响应内容
解析：C 对。目标主机端口在 CONNECT 请求行里是明文，密文的长度与时序无需解密即可观察。A、B、D 都在 TLS 加密的隧道内，代理没有会话密钥，看不到——这正是隧道「放弃应用层解析权」的含义。
自测 3
为什么 Upgrade 首部必须同时出现在 Connection 首部里？
  • A. 因为 Upgrade 是逐跳首部，列入 Connection 才能声明它只在本跳有效，让中间节点消费而非误转发
  • B. 因为 Connection 负责加密升级后的数据
  • C. 因为 Connection 用来协商 TLS 版本
  • D. 因为少了 Connection，服务器就无法返回 200 OK
解析：A 对，这是 MDN 与 RFC 9110 §7.8 的明确要求。B 错，加密由 TLS 负责，与 Connection 首部无关；C 错，TLS 版本在握手里协商，不是这个首部；D 错，升级成功返回的是 101 Switching Protocols 而非 200，且不写 Connection 的问题是逐跳语义丢失、中间节点行为不可控。
自测 4
下列哪一项不是逐跳首部？
  • A. Transfer-Encoding
  • B. Keep-Alive
  • C. Proxy-Authenticate
  • D. Cache-Control
解析：D 对。Cache-Control 描述资源本身的缓存语义，是端到端首部。A、B、C 加上 Connection、Upgrade、TE、Trailer、Proxy-Authorization 都是 RFC 9110 §7.6.1 列出的逐跳首部。尤其 A 常被误判为端到端——它其实只描述本跳主体如何定界，代理转发时要按下一跳重新编码。
自测 5
关于 Sec-WebSocket-Key 与 Sec-WebSocket-Accept，下列说法正确的是？
  • A. 密钥经「拼接固定 GUID → SHA-1 → base64」得到 Accept，用于确认握手意图，不提供安全性
  • B. 密钥是加密 WebSocket 数据的对称密钥
  • C. Accept 由服务器随机生成，与客户端密钥无关
  • D. 该机制在 HTTP/2 上同样适用
解析：A 对，这是 RFC 6455 定义的算法，MDN 也强调密钥「不提供安全性」。B 错，WebSocket 数据的机密性来自 wss:// 下的 TLS，不靠这个公开算法的密钥；C 错，Accept 必须由客户端密钥算出，客户端会验证；D 错，MDN 明确 HTTP/2 禁止使用升级机制。
