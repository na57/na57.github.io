2.1报文的四段骨架：把会话里流动的东西逐行拆开

上一讲把一次 Web 访问拆成了「建立连接—交换报文—复用或结束」三个阶段。中间那个阶段里真正在网络上流动的，就是本讲的主角——HTTP 报文（HTTP message）。MDN 的定义很朴素：报文是服务器与客户端之间交换数据的方式，只有两种——客户端发出、用来触发服务器动作的请求（request），以及服务器给出的响应（response）。这一节先把它拆成一副人人都能默写的骨架，再逐行读一条真实事务。

先问一个反例。假设客户端想告诉服务器「把 /index.html 给我」，它在这条 TCP 连接上写下字节 GET /index.html。TCP faithfully 保证这串字节按序、不丢、不重地到达，可服务器拿到后面对三个无解的追问：这串字节到哪儿算一条完整的指令（边界）？它是一条读请求还是一次写入（意图）？回答完之后跟着的内容是多长（定界）？TCP 一概不回答，因为它只搬运字节、不解释字节。HTTP 的解决办法，是给每次交换套一个固定四段结构，让接收方按规则把字节流切成一条条报文。

请求与响应结构相似，都由四部分组成，顺序不可交换：

  1. 一行起始行（start-line），描述要执行的请求或对应的成败状态，永远是单行；
  2. 一组可选的 HTTP 首部（header），指明请求的属性或描述消息主体；
  3. 一个空行，指示所有元数据已经发送完毕；
  4. 一个可选的主体（body），承载请求相关数据或响应文档；主体大小由首部指定。

MDN 还给出一个统称：起始行与首部合称「请求头」，有效载荷称为「消息主体」。记住这个统称有好处——后面谈缓存、谈编码时，你要能分清「我在动报文的头，还是动它的载荷」。

图 2.1 报文的解析流水线：先读起始行，再逐行读首部，遇空行停止，最后按长度读主体并按类型解析。红色的空行是全流程的转折点——没有它，解析器不知道首部读到哪一行算完。

完整例子①：一条 GET 请求与它的 200 响应，逐行解析。浏览器向 www.example.com 请求首页，线上字节如下（每一行的 CRLF 已省略显示）：

GET /index.html HTTP/1.1 Host: www.example.com Accept: text/html,application/xhtml+xml User-Agent: Mozilla/5.0 (X11; Linux x86_64) Gecko/20100101 Firefox/128.0 HTTP/1.1 200 OK Date: Mon, 16 Nov 2026 08:00:00 GMT Content-Type: text/html; charset=utf-8 Content-Length: 19 <html>你好</html>
图 2.2 一次最小但完整的请求—响应事务：上半是请求报文，下半是响应报文，中间那一行空行各自把首部与主体隔开。

逐行拆解请求报文，一步都不能跳：

  1. GET /index.html HTTP/1.1 是起始行，也叫请求行。按空格切成三段：GET 是方法，声明「读」这个意图；/index.html 是请求目标，指出要哪份资源；HTTP/1.1 是版本，承诺剩余报文按 1.1 的语法解析，也暗示期望的响应版本。三段的顺序与分隔由语法固定，这就是「请求行三要素」。
  2. Host: www.example.com 是请求首部。它不指出 IP——IP 由 TCP 层已经连好的对端决定；它指出「我原本要访问哪个主机名」。同一台服务器托管几百个站点，靠 Host 才能选到正确的虚拟主机。这就是上一讲留下的那个问题的答案。
  3. Accept: text/html,application/xhtml+xml 声明客户端愿意接收的表示类型，是第 3 讲内容协商的输入。
  4. User-Agent: … 报出客户端身份字符串，服务器可据此做统计或兼容处理（第 3 讲会讲它为什么不再是可靠的选型依据）。
  5. 接下来是空行（一个只有 CRLF 的行）。解析到此停止读首部。GET 通常不带主体，所以空行之后没有字节——但「没有主体」与「还没读完」必须由首部说清楚。

再拆响应报文：

  1. HTTP/1.1 200 OK 是响应的起始行，专名状态行（status line）：协议版本 + 三位状态码（status code）200 + 给人看的状态文本（status text）OK。200 宣告请求成功，状态文本只是注释，客户端判断成败只读数字。
  2. Date 是通用的时间首部；Content-Type: text/html; charset=utf-8 是表示首部，声明主体的媒体类型是 HTML、字符编码是 UTF-8；Content-Length: 19 给出主体的字节数。
  3. 又一个空行，之后是主体 <html>你好</html>。它正好是 19 字节：<html> 6 字节，你好 两个汉字在 UTF-8 下各 3 字节共 6 字节，</html> 7 字节，合计 6+6+7=19。接收方读完这 19 字节就知道报文结束，可以把连接交还给下一条请求。

这条事务把四段结构演示得很干净，但真实报文的首部远不止这几行。首部怎么归类，直接决定「谁能读它、能读几跳」。MDN 把首部按作用域分成四类：

首部类别作用域例子出现位置
通用首部（General header）适用于整条消息，既不专属于请求也不专属于响应Via、Date请求与响应都可
请求首部（Request header）描述请求本身或客户端，进一步定义、给定上下文或加条件限制User-Agent、Accept-Language、Referer、If-None-Match仅请求
响应首部（Response header）提供状态行放不下的服务器附加信息Vary、Accept-Ranges仅响应
表示首部（Representation header）描述消息数据的原始格式与应用的编码，仅在消息有主体时出现Content-Type、Content-Encoding请求与响应都可（有主体时）

要注意一处口径演进：更老的资料里还有「实体首部」（entity header）这一类，MDN 现在把其中描述数据格式的部分并入了表示首部。所以你在旧文档里看到的「实体首部」，今天的对应物多半是表示首部。至于 Content-Length，MDN 把它和 Content-Type 一起作为定义主体的两个首部来介绍——它描述的是载荷有多长，课堂上我们按「与主体定界相关」单独记忆。

✅ 判定规则

拿到任意一行首部，先问三个问题：它只在某一方向出现吗（请求首部 / 响应首部）？它描述的是整条消息还是载荷（通用 / 表示）？它有没有主体才有意义（表示首部依赖主体存在）？三问下来，99% 的首部都能归位，也就能推出「代理转发时该不该改它」。

⚠️ 常见误区

「空行只是排版，删掉也能解析」——大错。空行（CRLF CRLF）是首部结束、主体开始的唯一语法标志：解析器逐行读首部，直到读出空行才停。没有它，接收方会把主体的第一行当作又一个首部去解析，整条报文全乱。另一个高频错：把 Host 当成「目标 IP 地址」。它只是主机名，解析与建连发生在 HTTP 之下的一层。

2.2起始行：请求行三要素、请求目标四形式与状态码分流

上一节把报文拆成四段，最先被读到的那一行——起始行——信息密度最高：请求里它一次讲清「做什么、对谁做、按什么版本」，响应里它一句宣告「成了还是败了」。这一节把这一行彻底展开，并顺势把全书反复要用的状态码五类立起来。

MDN 说，请求的起始行含三个元素：HTTP 方法（HTTP method）、请求目标（request target）与 HTTP 版本（HTTP version）。方法是一个动词（GET、PUT、POST）或名词（HEAD、OPTIONS），描述要执行的动作；版本定义剩余消息的结构，并指示期望的响应版本。三者顺序固定为：

<方法> <请求目标> <HTTP 版本>
图 2.3 请求行的语法骨架：三个空格分隔的记号，从左到右依次是动作、对象、版本。

三要素里最容易被低估的是请求目标。多数人以为它永远是一个以 / 开头的路径，MDN 明确列出四种形式，各有各的出场场合：

形式长什么样什么时候用为什么是这种形式
原始形式（origin form）GET /background.png HTTP/1.0；末尾可跟 ? 与查询串，如 HEAD /test.html?query=alibaba HTTP/1.1GET、POST、HEAD、OPTIONS 直接连源站时，最常见主机名已由 Host 首部给出，目标只需指出资源路径
绝对形式（absolute form）GET http://developer.mozilla.org/zh-CN/docs/Web/HTTP/Messages HTTP/1.1GET 连接代理时代理可能同时服务多个源站，必须给出完整 URL 才能确定去向
authority 形式（authority form）CONNECT developer.mozilla.org:80 HTTP/1.1仅 CONNECT 建立 HTTP 隧道时此刻要的是「和谁建隧道」，只需要域名与可选端口，不需要路径
星号形式（asterisk form）OPTIONS * HTTP/1.1仅 OPTIONS 询问服务器整体能力时问的是「整台服务器支持什么」，不针对某个具体资源

把这张表读成一句话：目标和「连谁」绑在一起。直连源站，路径够了；经代理，要给完整 URL；建隧道，只给 authority；问全局能力，用星号。第 11 讲讲代理与隧道时，这四种形式会原封不动地回来。

响应的起始行叫状态行，MDN 给出三件信息：协议版本（通常 HTTP/1.1）、状态码（表明成功或失败，常见 200、404、302）、状态文本（对状态码的简短文字描述，帮人理解）。典型写法是 HTTP/1.1 404 Not Found。客户端判成败只读三位数字，状态文本可以替换、可以本地化，不具备机器语义。

状态码按首位分成五类，每类回答一类问题、规定「下一步该谁行动」。下面这张分流判定表把五类和九个高频码放在一张纸上，含各自的触发方与客户端动作：

状态码类别触发方与触发条件客户端该做什么
100 Continue1xx 信息性服务器在收到带 Expect: 100-continue 的请求头后，先回临时响应说「可以继续发主体」继续发送请求主体；这是过渡响应，不是最终结果
200 OK2xx 成功服务器确认请求已成功处理，并带回表示的主体读取并处理主体，按 Content-Type 解析
301 Moved Permanently3xx 重定向服务器宣告资源已永久迁到新位置，通常带 Location更新书签，跟随 Location 再发一次请求；后续都用新地址
304 Not Modified3xx 重定向服务器收到条件请求后判定本地副本仍有效，故不回主体直接用本地缓存副本；这是再验证成功，不是错误
400 Bad Request4xx 客户端错误服务器认为请求语法有误，无法理解检查并修改请求，不要原样重试
401 Unauthorized4xx 客户端错误服务器要求先认证，请求缺少或凭据无效带 Authorization 凭据重新发起；真正缺的是身份
403 Forbidden4xx 客户端错误服务器理解请求，但拒绝授权，与身份无关也可拒绝换身份或放弃；原样重试没有意义，问题在权限不在语法
404 Not Found4xx 客户端错误服务器找不到可用的表示，且不愿说明是暂时还是永久核对 URL；重试通常无益（与 403 的差别见 warning）
500 Internal Server Error5xx 服务器错误服务器遇到阻止其完成请求的意外状况，属服务端故障幂等请求可稍后重试；真正要修的是服务端

完整例子②（分流手算）。把五个类别抽象成一棵判定树，从「谁需要采取下一步动作」出发：拿到一个状态码，先看首位——1xx 说明事情还没完，客户端继续发；2xx 说明成了，客户端处理结果；3xx 说明「去别处」，客户端再发一次请求（304 是特例：去的是自己的缓存）；4xx 说明请求有问题，客户端改请求；5xx 说明服务端有问题，服务端修、客户端可重试。这棵树的价值在重试决策：网络抖动没收到响应时，只有 5xx 与幂等方法的组合才值得自动重试，4xx 重试一百次还是 4xx。

💡 关键一跃

请求目标四种形式不是四种「写法偏好」，而是四种「连接拓扑」的投影：直连、经代理、建隧道、问全局。看到 CONNECT host:port 就该想到 authority form；看到 OPTIONS * 就该想到星号形式。形式与拓扑一一对应，这比死记例子可靠得多。

⚠️ 常见误区

「404 就是服务器上没有这个文件」「403 就是没登录」——都不精确。403 是服务器知道你要什么但就是不给，401 才是「先证明你是谁」；404 是服务器不愿说明有没有，可能出于安全故意隐藏存在性。另一个高频错：把 304 当错误。它是 3xx 里唯一「不用去别处」的码，表示缓存副本经再验证仍然有效，响应的主体是空的。

2.3空行之后：主体定界、分块手算与两种「编码」的分工

上一节停在空行之前。空行一过，接收方面对的是一串没有天然边界的字节——TCP 是流，它不知道「这条消息到此为止」。这一节回答本讲的主线问题的一半：主体从哪儿开始、到哪儿结束。答案只有两条路：Content-Length 给出已知长度，或 Transfer-Encoding: chunked 用分块编码处理未知长度。

MDN 把主体按规模分两类：单一资源主体（一个文件）与多资源主体（多部分主体，常见于 HTML 表单）。对单一资源主体，长度已知时用 Content-Type 与 Content-Length 两个首部定义；长度未知时，把 Transfer-Encoding 设为 chunked。响应的主体还多一种单资源、已知长度的明确说法——MDN 特意把「已知长度」与「未知长度」拆成两条，就是在提醒你定界方式取决于长度能否预先算出。

完整例子③：同一份内容的两种定界方式对照。客户端要上传一段纯文本 hello world（11 字节），服务端在生成响应前不一定知道总长。两条路并列如下：

路线 A：Content-Length 定界（长度已知）。

POST /upload HTTP/1.1 Host: www.example.com Content-Type: text/plain; charset=utf-8 Content-Length: 11 hello world
图 2.4 用 Content-Length 定界：读完空行后，接收方再读恰好 11 字节即结束。主体字节数必须事先算准。

路线 B：Transfer-Encoding: chunked 定界（长度未知）。

POST /upload HTTP/1.1 Host: www.example.com Content-Type: text/plain; charset=utf-8 Transfer-Encoding: chunked 5 hello 6 world 0
图 2.5 用分块编码定界：主体被切成若干块，每块先写十六进制长度、再写数据；大小为 0 的块表示主体结束。

逐块解析手算（一步不跳）。接收方在空行之后按下面的循环读，直到读到一个大小为 0 的块：

  1. 读第一行 5：这是一个块大小，十六进制的 5 等于十进制 5，表示紧接着有 5 字节数据。
  2. 紧接着读恰好 5 字节：hello，正好 5 字节。随后读一个 CRLF 作为块结束符（它不计入块大小）。累计主体 = hello。
  3. 读下一行 6：十六进制 6 = 十进制 6，表示下一块 6 字节。
  4. 读恰好 6 字节： world（一个空格 + world 五个字母 = 6 字节）。读块结束 CRLF。累计主体 = hello world，与路线 A 完全一致。
  5. 读一行 0：大小为 0，表示主体到此结束，后面不再有数据块。
  6. 0 块之后可以跟若干尾部首部（trailer），本例没有，所以直接是一个空行；读到这个空行，整条消息解析完毕。

手算结论：分块编码用「长度头 + 数据 + CRLF」的三段式重复，把未知长度的内容边生成边发送；0 块是唯一的「正文结束」信号。这解释了为什么动态生成的大响应偏爱 chunked——服务端一边算一边发，不必先把全部内容攒起来数出总字节数。

⚠️ 常见误区

两个高频错误。其一：Content-Length 写小于实际字节。接收方按声明长度读完就停，多出来的字节会被误当成下一条报文的起始行，造成「粘包式」错乱。写大于实际字节则相反，接收方会一直等那些永远不来字节，连接挂到超时。因为 TCP 是字节流，长度是唯一依据。其二：把分块编码的块大小当十进制。它是十六进制，例如 1A 表示 26 字节，不是 1 也不是 10。

还有一个必须与内容类型分清的概念：内容编码（Content-Encoding）与 Content-Type 是两个正交维度。Content-Type 声明表示本身是什么（HTML、JSON、PNG），Content-Encoding 声明对这份表示施加了什么变换（最常见是 gzip 压缩）。二者可以叠加在同一条响应上：

HTTP/1.1 200 OK Content-Type: text/html; charset=utf-8 Content-Encoding: gzip Content-Length: 843 （843 字节是 gzip 压缩后的字节，不是解压后的 HTML 大小）
图 2.6 Content-Type 与 Content-Encoding 正交：客户端先按 Content-Encoding 解压得到 HTML 字节，再按 Content-Type 把字节渲染成页面。压缩是传输时的外衣，类型才是内容的身份。

解析顺序很关键：客户端先按 Content-Encoding 逆变换（解压），得到原始字节，再按 Content-Type 决定用哪个解析器。反过来做——先按 HTML 解析一堆 gzip 字节——只会得到乱码。第 3 讲讲压缩协商、第 6 讲讲范围请求时，都会回到这条「先解码、后解析」的顺序。

💡 关键一跃

定界与类型是两件独立的事：Content-Length/chunked 回答「到哪儿结束」，Content-Type 回答「用什么解析」，Content-Encoding 回答「先做什么逆变换」。三条首部分工清晰，正是 HTTP 可扩展性的来源——换压缩算法不必动解析器，换媒体类型不必动传输层。

2.4MIME 类型：一条 type/subtype 如何决定字节的命运

上一节解决了「主体到哪儿结束」，还剩主线问题的最后一问：接收方凭什么知道该用什么解析这些字节？答案写在 Content-Type 里，而它的值就是一个 MIME 类型（MIME type），MDN 又称媒体类型（media type）——全称多用途互联网邮件扩展（Multipurpose Internet Mail Extensions），由 IETF 的 RFC 6838 定义与标准化，IANA 负责跟踪所有官方类型。这一节把它拆开，并讲清浏览器「声明与猜测」之间的博弈。

MDN 特别警告：浏览器通常用 MIME 类型而不是文件扩展名来决定如何处理一个 URL，所以服务器在 Content-Type 响应首部中给出正确类型非常重要；配错会让浏览器曲解内容、网站失常、下载被错误处理。为什么不能靠扩展名？因为同一路径可以按协商返回不同表示，而 URL 里的 .html 与实际字节并无必然联系——扩展名只是名字，MIME 才是声明。

MIME 类型的结构只有两部分：type/subtype，斜杠两边无空白。类型（type）是大类，子类型（subtype）是大类里的精确种类；二者必须成对出现。此外可带一个可选参数（parameter），写法是 type/subtype;parameter=value。对 text 类，最常用的参数是 charset：它指定字符所使用的字符集，缺省为 US-ASCII（除非被用户代理设置覆盖）。所以明确写 UTF-8 的纯文本应写成 text/plain;charset=UTF-8。MDN 还提醒：MIME 类型大小写不敏感、传统写小写，但参数值可能大小写敏感。

类型又分两类：独立类型（discrete type）表示单一文件或媒介，多部分类型（multipart type）表示由多个部件组成的复合文档。对 Web 开发者最重要的独立类型包括 application（不明确属于其他类型的二进制数据）、text（人类可读文本、源代码）、image、audio、video、font、model。两条兜底规则要记牢：没有明确子类型的文本用 text/plain，未知或真实类型未知的二进制用 application/octet-stream。

完整例子④：四种高频 MIME 类型的判定表。下表把类型归类、浏览器默认处理，以及「类型缺失或被篡改时」的风险摆在一起：

Content-Type归类浏览器默认处理声明缺失/错误时的风险
text/htmltext 独立类型按 HTML 解析成 DOM 并渲染，脚本可执行若一个本该是纯文本的响应被嗅探成 HTML，其中内容可能被当作标记与脚本执行，形成注入风险
application/jsonapplication 独立类型当作数据：交给脚本解析或触发下载，不渲染成页面历史上若被嗅探成 HTML，JSON 里的可控文本可能被执行；正确声明并配合 nosniff 可堵住这条路
image/svg+xmlimage 独立类型（+xml 结构化后缀）作为矢量图渲染；SVG 内部可含脚本作为顶层导航文档直接打开时，其中脚本可执行；嵌入为图片时通常受限，用途不同风险不同
application/octet-streamapplication 独立类型，未知二进制兜底浏览器视为应保存到本地，弹出「另存为」，不自动执行这是安全默认值：正因为不猜用途，未知二进制不会被误当可执行内容

表中的 +xml 后缀值得单独说：image/svg+xml 说明 SVG 是一种基于 XML 的结构化格式，而不是像 image/png 那样的位图。IANA 用这种结构化后缀标记「本类型遵循某个基础语法」，同类还有 +json、+zip。看到后缀，你就知道这类内容有可解析的结构。

现在讲内容嗅探（MIME sniffing）。MDN 说：在 MIME 类型缺失，或客户端认为文件设置了错误类型时，浏览器可能通过查看资源本身来猜测类型。每个浏览器在不同情况下行为不同（例如 Safari 会在收到的类型不合适时去看扩展名）。问题在于某些 MIME 类型代表可执行内容，让浏览器自由猜测就带来安全风险。服务器可以用 X-Content-Type-Options: nosniff 首部禁止嗅探。

把有无 nosniff 的差别列成对照表，安全意义一目了然：

场景没有 nosniff带 X-Content-Type-Options: nosniff
响应完全缺失 Content-Type浏览器读取开头字节进行嗅探，可能猜成 HTML/JavaScript 并执行按保守类型（如 application/octet-stream 或 text/plain）处理，不嗅探成可执行类型
脚本文件被错发成 text/plain浏览器可能嗅探出它是脚本并照常执行，掩盖了配置错误浏览器拒绝执行该脚本，因为声明类型与执行要求不符
API 返回 JSON 但类型写错可能被当成 HTML 渲染，引入脚本执行面按声明的保守类型处理，不升级为可执行类型
用户上传文件下载浏览器可能据内容猜测而尝试打开配合正确类型时更可能走「另存为」，减少就地执行

MDN 还列出 MIME 类型之外的两种判定手段，但都不可靠：文件扩展名（不是所有系统都认，且不能保证正确）与魔数（magic number，看文件头结构，如 GIF 以十六进制 47 49 46 38 开头、PNG 以 89 50 4E 47 开头，但并非所有类型都有魔数）。这正是「必须显式声明 Content-Type」的根本理由——猜测手段都只是近似。

顺带补一个容易被问到的类型：text/javascript。MDN 明确，按照 IANA 注册表、RFC 9239 与 HTML 规范，JavaScript 内容应始终以 text/javascript 提供，其他类型可能导致脚本无法加载或运行；而且 JavaScript 内容不该带 charset 参数，那在多数情况下会导致加载失败。这与前面 text/plain;charset=UTF-8 形成对照：charset 对文本文档有意义，对脚本反而是坑。

✅ 判定规则

看到 Content-Type 就按三步走：① 读 type/subtype 判大类与精确格式，遇到 +xml/+json 想到结构化后缀；② 读参数，文本类看 charset，脚本类警惕多余的 charset；③ 问「有没有 nosniff」——可执行内容（HTML/JS/JSON/SVG）强烈建议带，防止嗅探把声明绕过。

⚠️ 常见误区

「根据文件后缀就能判断类型」——这是把 URL 名字当内容声明，协商一份资源多种表示时立刻失效。另一个错：给所有未知二进制都发 application/octet-stream 就万事大吉——对真正未知的文件它是安全默认值，但对已知类型（如 RAR、音视频、专有文档）应给出更具体的类型（如 application/x-rar-compressed、application/vnd.mspowerpoint），否则用户得不到「用某程序打开」的体验。第三个别把它和上一节混了：charset=utf-8 是 Content-Type 的参数，不是 Content-Encoding；压缩编码和字符编码是两码事。

2.5延伸：规范怎么写：从 MDN 的说法回到 RFC 的字句

前面四节按 MDN 的口径把报文与 MIME 讲透了。MDN 是面向开发者的指南，它把规范的严苛语法藏在了通俗表述背后。这一节做本讲唯一允许的事：翻开底层规范，看同样一件事 RFC 是怎么逐字定义的。对照三份规范——报文语法看 RFC 9112、方法与状态码的语义看 RFC 9110、媒体类型注册看 RFC 6838——你会发现 MDN 的每句「说法」背后都有一条精确的「写法」。理解它，才能在报文解析报错、类型注册争论时知道根在哪。

MDN 的说法RFC 怎么写为什么值得知道
请求与响应都由起始行、首部、空行、主体四部分组成，空行表示元数据结束RFC 9112 用 ABNF 规定报文 = start-line 后跟若干 field-line、一个空行（CRLF）与可选 message-body，对各部分的顺序与 CRLF 位置逐字节约束解析错误都能定位到某条 ABNF 规则：「空行缺失」不是风格问题而是语法违规，写解析器时据此决定报错位置
请求起始行含方法、请求目标、版本；请求目标有原始/绝对/authority/星号四种形式RFC 9112 把 request-target 明确定义为 origin-form、absolute-form、authority-form、asterisk-form 五种语法产生式并分述约束；RFC 9110 则把方法定义为可独立命名的语义操作知道形式由语法产生式固定，就不会发明第五种写法；理解方法语义与报文编码解耦，才能看懂 HTTP/2 改编码不改语义
状态码首位分五类，表明成功或失败；常见 200、404、302RFC 9110 为状态码建立注册表与类别定义，逐码规定语义，并定义 safe（安全）与 idempotent（幂等）等方法属性供缓存与重试判定判断「能否自动重试」「能否缓存」的权威依据在 RFC 的属性定义里，而不在数字的记忆里；这正是第 5、6 讲的底座
主体长度未知时用 Transfer-Encoding: chunked，分块编码用大小 0 的块结束RFC 9112 定义 chunked-body = 若干 chunk 后跟 last-chunk、trailer-section 与 CRLF；chunk = chunk-size CRLF chunk-data CRLF，其中 chunk-size 是十六进制手算分块边界、排查「多一个 CRLF 就错位」的经典 bug，都要回到这条产生式；也解释了 0 块后为何还可能需要尾部首部
MIME 类型形如 type/subtype，由 IANA 跟踪官方类型RFC 6838 定义媒体类型的注册树与命名语法，规定 type/subtype 的命名规则、结构化后缀（如 +xml、+json）与各类注册流程理解 +xml/+json 后缀和「为何不能随便造类型」，就懂了 application/vnd.* 厂商类型的来路，也为第 3 讲内容协商打底
浏览器可能在类型缺失时用 MIME 嗅探猜测；nosniff 可阻止嗅探嗅探的判定算法不在核心 HTTP RFC 中，而由 Fetch 规范与浏览器实现定义；nosniff 的处理规则在那里被精确规定知道「这条规则归谁管」，排查时用对文档：语法查 9112、语义查 9110、类型查 6838、嗅探行为查 Fetch

把这张表读薄，只留一句：MDN 告诉你「是什么」，RFC 告诉你「精确到字节是什么」。本讲所有结论都能在 MDN 找到对应说法；而当你需要写解析器、判定重试、争论某个类型是否合法时，最终要落到右边那列的规范字句。这个「指南—规范」的双层视角，是全课程反复使用的读法。

💡 关键一跃

把 RFC 的 ABNF 当成「报文的语法图」来读，而不是当成天书：chunk-size CRLF chunk-data CRLF 这一行，就直接解释了例子④里每块的读法；start-line → field-line* → CRLF → body 这一串，就是图 2.1 的解析流水线。规范不是额外的负担，而是你已经在用的规则的精确版本。

⚠️ 常见误区

「MDN 和 RFC 说法不一致时，必有一方错了」——通常不是。MDN 是面向开发者的指南，会做合理简化（比如把实体首部并入表示首部、把四种请求目标写成通俗例子）；RFC 是 normative 规范，逐字严谨。二者是抽象层级不同，不是互相矛盾。真正要警惕的是拿旧资料里的 HTTP/1.0 或早期 RFC（如已被取代的 7230 系列）当现行口径——本系列的现行规范是 RFC 9110 系列。

定义长度已知用 Content-Length 读固定字节；未知用 Transfer-Encoding: chunked 逐块读，0 块结束。

直觉Content-Length 是先数好页数，chunked 是一页一页边写边交、最后一页标「完」。
误区块大小按十进制读（应按十六进制）；或把长度写错而不意识到会错乱连接。
何时用2.3 逐块手算；L2 习题定界；第 6 讲范围请求也依赖长度。
概念卡 5
状态码（Status code）五类
点击翻面 →
定义状态行里的三位数字，按首位分 1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错、5xx 服务端错。
解决问题一句话告诉客户端「成了没有、下一步该谁行动」，是重试与缓存判定的依据。
直觉1xx 继续、2xx 收下、3xx 去别处、4xx 你改、5xx 我修。
误区把 304 当错误；把 403 与 401、404 混为一谈；依赖状态文本而非数字判断。
何时用2.2 分流判定表；第 5、6 讲缓存与条件请求、第 12 讲重定向反复使用。
概念卡 6
MIME 类型（Media type）与 type/subtype
点击翻面 →
定义形如 type/subtype 的媒体类型标签，由 Content-Type 声明，可带 charset 等参数，由 RFC 6838 注册。
解决问题同一串字节可能是文本、图片或程序，必须显式声明该用哪个解析器。
直觉包裹上的「易碎/冷藏」标签，决定拆包方式；+xml/+json 后缀说明内容有结构。
误区靠扩展名猜类型；漏写 charset 导致乱码；把 charset 当 Content-Encoding。
何时用2.4 判定表；第 3 讲内容协商据此选择表示。
概念卡 7
内容嗅探、nosniff 与两种「编码」
点击翻面 →
定义嗅探是类型缺失时浏览器读字节猜类型；nosniff 禁止之。Content-Type 说类型，Content-Encoding 说变换。
解决问题防止可控内容被猜成可执行类型；把「是什么」与「做了什么变换」分开表达。
直觉nosniff 是「别猜、按标签来」；压缩编码是外衣、类型是内容身份。
误区以为 nosniff 会自动修好错误类型（它只是拒绝嗅探）；把 gzip 压缩与 UTF-8 字符集混为一谈。
何时用2.3 与 2.4 的正交分工；第 3 讲压缩、第 10 讲安全策略均涉及。

📝分层习题

L1 概念辨析有人说：「请求目标就是 URL 里的路径，永远是 / 开头；Host 首部只是把目标 IP 换成了域名。」请分别指出这两句话的错处，并说出正确规则。
提示

回想请求目标的四种形式，以及 Host 与 TCP 连接的关系：IP 由谁决定？

完整解答
第一句错：请求目标有四种形式，/ 开头的原始形式只是最常见的一种。经代理的 GET 用绝对形式（完整 URL），CONNECT 用 authority form（域名+端口），OPTIONS 问整体能力用星号形式 *。第二句错：Host 并非「目标 IP 的域名写法」。客户端先由 DNS 与 TCP 层确定并连上某个 IP，Host 首部携带的是用户原本访问的主机名，用于让同一 IP 上的服务器区分虚拟主机。IP 在网络层/传输层已经确定，Host 是 HTTP 层额外携带的语义信息。两句话都把「HTTP 层的声明」误当成了「网络层的地址」。
L1 概念辨析某响应同时带有 Content-Type: text/html; charset=utf-8 与 Content-Encoding: gzip，Content-Length: 843。请回答：843 是压缩前还是压缩后的字节数？客户端应按什么顺序处理这三条信息？如果把 charset 误当成 Content-Encoding 会怎样？
提示

分清「类型 / 变换 / 长度」三件事，并想清楚客户端解码与解析的先后。

完整解答
843 是压缩后的字节数：Content-Length 计的是线上实际传输的主体字节，而主体此时是 gzip 数据。处理顺序：① 按 Content-Length 读出 843 字节；② 按 Content-Encoding: gzip 解压，得到原始 HTML 字节；③ 按 Content-Type: text/html; charset=utf-8 把字节解释为 UTF-8 编码的 HTML 并渲染。若把 charset 误当 Content-Encoding，就会试图对 HTML 做一种叫「utf-8」的内容解码（并不存在这样的压缩变换），或者反过来忽略真正的 gzip，结果要么解压失败、要么把 gzip 字节当 HTML 解析成乱码。正确认知：charset 是 Content-Type 的参数（字符如何解释），Content-Encoding 是独立的首部（字节做过什么变换），二者维度不同。
L2 手算推导下面是一段分块编码的响应主体（每行后的 CRLF 已省略显示，空格用一个可见的「␠」标记以便计数）。请逐块解析，把拼接出的完整主体写出来，并指出主体一共解码出多少字节。
4 / Welc / 6 / ome␠to / 4 / ␠you / 0 / （空行）
提示

块大小是十六进制；每块数据后有一个不计入大小的 CRLF；0 块后是尾部与空行。这里所有块大小都在 10 以内，十六进制值与十进制相同。

完整解答
按「读块大小 → 读对应字节 → 跳过 CRLF」的循环：
① 第一行 4，十六进制 4 = 4 字节，读 Welc（W、e、l、c 共 4 字节），累计 Welc。
② 下一行 6，6 字节，读 ome␠to（o、m、e、␠、t、o 共 6 字节，空格也算 1 字节），累计 Welcome to。
③ 下一行 4，4 字节，读 ␠you（␠、y、o、u 共 4 字节），累计 Welcome to you。
④ 下一行 0，大小为 0，主体结束；随后空行表示无尾部首部，整条消息解析完毕。
完整主体 = Welcome to you，逐字符数得 14 字节（Welcome 7 + 空格 1 + to 2 + 空格 1 + you 3 = 14）。校验各块：4 + 6 + 4 = 14，与解码出的字符串长度完全一致。
关键结论：每块的「大小」必须与随后数据的字节数严格相等，空格也占 1 字节；接收方靠长度精确切片，不靠寻找特殊字符，这正是分块编码能承载任意二进制内容的原因。
L2 手算推导一条 POST 请求主体是 UTF-8 编码的中文 你好世界（4 个汉字）。请手算它作为主体时 Content-Length 应写多少；若误写成 10，会发生什么？若改用 chunked，且把这 4 个汉字拆成两块（每块 2 个汉字），写出对应的分块报文片段（块大小用十六进制）。
提示

UTF-8 下一个常用汉字占 3 字节；先算总字节，再想长度写错时字节流会怎样。

完整解答
手算长度：UTF-8 下每个常用汉字 3 字节，4 个汉字 = 4 × 3 = 12 字节，所以 Content-Length: 12。
写成 10 的后果：声明 10 小于实际 12。接收方读完 10 字节就认为主体结束，剩下的 2 字节仍留在字节流里；在持久连接上，这多出的 2 字节会被当作下一条报文的起始行开头，导致后续解析错乱（典型表现是莫名其妙的「非法起始行」）。反之若写大于 12，接收方会一直等那些不来的字节，连接挂起直到超时。根因：TCP 是字节流，长度是唯一边界。
改用 chunked（每块 2 汉字 = 6 字节，十六进制为 6）：
Transfer-Encoding: chunked
空行后主体：
6 CRLF 你好 CRLF
6 CRLF 世界 CRLF
0 CRLF （空行）
解析：第一块大小 6（十六进制）= 6 字节，正好两个汉字；第二块同理；0 块结束。总字节仍为 12，与 Content-Length 方案一致，只是把「一次数总长」换成了「逐块报长度」。
L3 建模应用你在为一个下载站设计响应策略：站点既有已知大小的静态安装包，也有服务端实时生成、事先无法统计长度的报表；同时站点曾被告警「有 API 返回的 JSON 被浏览器当成 HTML 执行」。请综合本讲知识给出方案：两类内容各用什么主体定界？JSON 响应应带哪些首部、为什么？并说明 Content-Type 与 Content-Encoding 应如何配合压缩。
提示

把「定界二选一」「嗅探与 nosniff」「类型与变换正交」三块拼到一起。

完整解答
主体定界：静态安装包大小已知，用 Content-Length 精确声明字节数，客户端按长度读、可显示进度；实时报表长度未知，用 Transfer-Encoding: chunked，服务端边生成边发送，每块报十六进制大小，0 块收尾，避免先全量缓存到内存数长度。
JSON 安全：正确设置 Content-Type: application/json; charset=utf-8，并加 X-Content-Type-Options: nosniff。前者让浏览器按数据处理而非渲染成页面；后者阻止浏览器在类型异常时嗅探成 HTML 而执行其中可控文本。只写对类型仍不够——若某些链路把类型改错，nosniff 是第二道防线。
类型与压缩配合：若对 JSON 做 gzip，则 Content-Type: application/json 描述解压后的数据本身，Content-Encoding: gzip 描述线上施加的变换，Content-Length（若用）记压缩后的字节数。客户端先解压再按 JSON 解析。
一致性检查：三条信息互不替代——类型管解析、编码管逆变换、长度/分块管定界，三者齐全且互相匹配，才算一条能被正确、安全处理的响应。

自测 1
关于 HTTP 报文的空行，哪一句正确？
  • A. 空行只是排版美化，删掉不影响解析
  • B. 空行标志着主体传输结束
  • C. 空行标志首部结束、主体开始，是解析器停止读首部的唯一语法信号
  • D. 空行只在响应报文中出现，请求报文没有
解析：C 对。A 错在空行是语法的一部分（CRLF CRLF），缺失会导致主体首行被误当首部；B 错在空行标志的是「首部结束」而非「主体结束」，主体结束靠 Content-Length 或 0 块；D 错在请求与响应都用空行分隔首部与主体。
自测 2
客户端要通过 HTTP 代理用 GET 取一个资源，请求目标应采用哪种形式？
  • A. 原始形式，如 GET /path HTTP/1.1
  • B. 绝对形式，如 GET http://example.com/path HTTP/1.1
  • C. authority form，如 GET example.com:80 HTTP/1.1
  • D. 星号形式，如 GET * HTTP/1.1
解析：B 对。经代理时必须给完整 URL，代理才知道要向哪个源站转发。A 的原始形式用于直连源站；C 的 authority form 仅用于 CONNECT 建隧道，且这里方法是 GET 而非 CONNECT；D 的星号形式仅配合 OPTIONS 询问服务器整体能力，不用于 GET 取资源。
自测 3
一段分块编码中出现 1A 这个块大小行，紧接着的数据块应读多少字节？
  • A. 1 字节
  • B. 10 字节
  • C. 11 字节
  • D. 26 字节
解析：D 对。块大小按十六进制读，1A = 1×16 + 10 = 26 字节，随后数据块 CRLF 之前恰好 26 字节。A 把它当成十进制首位、B 当成 A=10、C 当成 1 与 A 拼接，都是没有按十六进制规则换算所致；数据块后的 CRLF 不计入这 26 字节。
自测 4
某 API 响应带 Content-Type: application/json 与 X-Content-Type-Options: nosniff。关于 nosniff，哪一句正确？
  • A. 它阻止浏览器在类型缺失或异常时嗅探，强制按声明的保守类型处理，降低被猜成可执行内容的风险
  • B. 它会自动把写错的 Content-Type 修正为正确类型
  • C. 它压缩响应内容，减小 JSON 体积
  • D. 它是 Content-Encoding 的一种，表示某种压缩算法
解析：A 对。nosniff 只是「禁止猜测」，并不修正类型（B 错），也不压缩内容（C 错），更不是内容编码算法（D 错）。它要求浏览器按已声明的类型保守处理：类型缺失时不嗅探成可执行类型，类型不符时（如脚本被发成 text/plain）拒绝执行。
自测 5
下列哪一组说法全部正确？
  • A. 403 表示「没登录」，401 表示「知道你是谁但不给」；304 是 4xx 客户端错误
  • B. 状态码文本是机器判断成败的依据，客户端应读文本而非数字
  • C. 401 要求先认证，403 是理解但拒绝授权；304 是缓存再验证成功、无主体；5xx 属服务端故障
  • D. 请求目标只有原始形式一种；Host 首部就是目标服务器的 IP 地址
解析：C 对。A 把 401 与 403 说反了，且 304 属 3xx 而非 4xx；B 错在客户端判成败只读三位状态码，状态文本只是给人看的注释；D 错在请求目标有四种形式，且 Host 是主机名而非 IP。C 四项均与 MDN 口径一致。
