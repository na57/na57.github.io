10.1CSP 给页面立一份「能加载什么」的白名单，_inline_ 脚本是头号目标

前面两讲讲的是服务器如何识别与授权用户：认证确认「你是谁」，CORS 划出「哪个源能读我的响应」。本讲转向一个正交的问题——浏览器把这个页面加载进来之后，允许它做什么。先看一个最朴素的攻击现场。

假设你经营一个博客，评论区允许访客留 HTML 片段。你对输入做了过滤，但百密一疏，攻击者还是塞进了这样一段内容：

<script src="https://evil.example.com/hacker.js"></script> <script>console.log("你已被入侵！")</script> <img onmouseover="console.log('你已被入侵！')" src="thumb.jpg" alt="" />
注入的恶意代码可能伪装成三种模样：外链脚本、内联脚本、内联事件处理器。过滤一旦漏掉任意一种，代码就会在站点的上下文里执行，拿到用户的 cookie 与权限。

这类攻击叫跨站脚本攻击（Cross-site scripting，XSS）：攻击者能在目标网站的上下文里执行自己的代码，而这段代码能做网站自身代码能做的任何事——改动页面内容、读写本地存储、带着用户凭据发请求。网站当然应当在把输入放进页面之前净化它；但净化是容易出错的第一道防线，于是需要第二道：即使恶意代码混进来了，也让它跑不起来。

MDN 给内容安全策略（Content Security Policy，CSP）的定义是：一项有助于防范或降低特定类型安全威胁风险的特性，由网站向浏览器发出的一系列指令（directive）组成，这些指令要求浏览器对构成该站点的代码被允许执行的操作施加限制。它的主要用途是控制文档允许加载哪些资源，尤其是 JavaScript，以此防御 XSS；此外还能防点击劫持、升级不安全请求、强制可信类型。这几类用途互不依赖，你只想加点击劫持防护，就只写对应的那条指令。

CSP 通过 Content-Security-Policy 响应首部送达浏览器，MDN 强调它应设置在所有请求的所有响应上，而不只是主文档。也可以用 <meta> 元素的 http-equiv 属性指定，这对纯静态、客户端渲染的单页应用有用，但并非所有 CSP 特性都支持。策略由分号分隔的若干指令组成，每条指令是「指令名 + 空格 + 值」，不同指令的语法不同：

HTTP/1.1 200 OK Content-Type: text/html; charset=utf-8 Content-Security-Policy: default-src 'self'; img-src 'self' example.com （主文档的响应里，两条指令用分号隔开）
一条最小 CSP：default-src 'self' 让所有资源默认只能同源；img-src 'self' example.com 单独给图片开口子，允许同源与 example.com。

这句例子里的 default-src 是全场最重要的一条 Fetch 指令（fetch directive）：它为所有没有显式列出指令的资源类型设置后备策略。MDN 列出 script-src（JavaScript）、style-src（CSS）、img-src（图片）、connect-src（fetch / XHR / WebSocket 等连接）、font-src、media-src 等等；一旦某类资源有专门指令，就用专门指令，否则回落到 default-src。每条 Fetch 指令的值要么是关键字 'none'，要么是一个或多个空格分隔的源表达式（source expression）——列出多个时，任一表达式允许，该资源就被允许。

源表达式的写法决定策略的强弱，MDN 给出的主要形式有：关键字 'self'（与文档同源）与 'none'（全部拒绝）；主机名如 example.com、带通配符的 *.example.org；方案如 https:；以及用于内联代码的 'nonce-…' 与 'sha256-…'。还有两个「后门」关键字 'unsafe-inline' 与 'unsafe-eval'，后面会讲为什么应当避开它们。

现在把例子放大到一条完整的响应首部，逐指令拆解——这是本节要交的第一个完整手算。

HTTP/1.1 200 OK Content-Type: text/html; charset=utf-8 Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-416d1177-4d12-4e3b-b7c9-f6c409789fb8'; style-src 'self'; img-src 'self' example.com; connect-src 'self'; report-uri /csp-report （为便于阅读折成了多行；真实首部是一行，指令间用分号分隔）
一条带 nonce 与上报端点的完整 CSP。前五条是 Fetch 指令，最后一条 report-uri 负责把违规报告送回 /csp-report。
指令允许的来源逐条解读
default-src 'self'仅同源兜底。凡没单独列指令的资源类型（字体、media、object 等）都只准同源。
script-src 'self' 'nonce-416d…'同源脚本，或带匹配 nonce 的脚本标签覆盖 default-src 对脚本的后备；nonce 让服务器认可的特定内联脚本得以执行。
style-src 'self'仅同源样式表样式单独指定，因此不继承 default-src，也不继承 script-src 的 nonce。
img-src 'self' example.com同源图片 + example.com 的图片给图片开了一个外部域名的口子；其余资源类型不受影响。
connect-src 'self'仅同源连接限制 fetch / XHR / WebSocket / EventSource 的目标，阻止数据外传到恶意域名。
report-uri /csp-report不适用（上报指令）发生违规时，浏览器把报告 POST 到本站的 /csp-report；它不参与放行判定。

现在推演那条内联脚本的命运。页面里有这样一段：

<script>console.log("你好，来自内联脚本")</script>
没有任何属性的内联脚本。在含 script-src 的 CSP 下，它默认不被允许执行。

第一步，直接执行：被拦截。策略里有 script-src，而内联脚本既不同源加载、又不带 nonce 或散列，MDN 明确说：只要 CSP 含 default-src 或 script-src，内联 JavaScript 默认不被允许执行。浏览器拒绝运行它，并按 report-uri 生成一条违规报告。内联事件处理器（如 onmouseover）与 javascript: URL 同样在拦截之列。

第二步，加 nonce：放行。服务器为每个响应生成一个不可预测的随机值，既写进首部的 script-src，又作为 nonce 属性写到它信任的脚本标签上：

Content-Security-Policy: script-src 'self' 'nonce-416d1177-4d12-4e3b-b7c9-f6c409789fb8' <script nonce="416d1177-4d12-4e3b-b7c9-f6c409789fb8"> console.log("你好，来自内联脚本") </script>
浏览器比较首部里的 nonce 与标签的 nonce 属性，两者一致才加载。攻击者不知道本次响应的随机值，注入的脚本无法伪造这个属性。

这里藏着一个硬约束：MDN 指出，攻击者必须无法猜出 nonce，因此每个 HTTP 响应的 nonce 都必须不同、且不可预测。服务器因此不能提供静态 HTML，必须用模板引擎在每次响应里插入新值；而且要用模板机制只给自己的脚本标签插入 nonce，否则可能手滑把 nonce 也塞进攻击者注入的标签里。nonce 只对带 nonce 属性的元素生效，也就是只有 <script> 与 <style>。

第三步，改用散列：同样放行。散列（hash）路线的做法是：用 SHA-256 / SHA-384 / SHA-512 之一计算脚本内容的散列，做 Base64 编码，再加算法前缀 sha256- 等，放进 script-src：

Content-Security-Policy: script-src 'sha256-H/eahVJiG1zBXPQyXX0V6oaxkfiBdmanvfG9eZWSuEc=' <script>console.log("你好！")</script>
浏览器对脚本内容重新计算散列并与首部比对，一致则加载。与 nonce 不同，内容不变则散列不变，所以 CSP 与页面都可以是静态的——更适合静态站点。

代价是：脚本内容哪怕改一个字符，都必须重算并重填散列；而外部脚本要启用散列校验，标签上还得带 integrity 属性。MDN 由此给出选择建议——能动态生成响应（含内容）时用 nonce 更易维护，否则用散列。把这套判定画成流程图更直观：

✅ 判定规则

判断一段脚本能不能跑，按三步走：① 有没有针对脚本的指令（script-src 或兜底的 default-src）？没有就放行。② 有，则看它是不是同源外部脚本、或带匹配 nonce、或内容散列匹配？满足任一即放行。③ 都不满足就拦截。记住 CSP 是纵深防御：MDN 反复强调它不能替代输入净化，正确姿势是「净化 + CSP」双管齐下。

⚠️ 常见误区

「嫌麻烦，加个 'unsafe-inline' 放行内联脚本算了」——MDN 明确建议避免，因为它会破坏设置 CSP 的大部分意义，而内联 JavaScript 正是最常见的 XSS 向量。还要注意两条容易踩的细节：其一，指令里一旦出现 nonce 或散列，浏览器会忽略 'unsafe-inline'；其二，'none' 不能与任何其他源表达式组合，旁边若还写了别的表达式，那些表达式会被直接忽略。把 'none' 和 'self' 写在一起的指令，实际效果只有 'none'。

10.2先把 CSP 调成「只报告不拦截」，再读懂它寄回来的违规单

上一节给页面立了白名单，但一份配错的 CSP 会先把自己的脚本、样式全挡在门外——线上直接开启等于自断手脚。这一节回答：怎样在不影响真实用户的前提下试出一份正确的策略，以及违规发生之后服务器能拿到什么。

MDN 给的部署办法是仅报告模式：用 Content-Security-Policy-Report-Only 首部下发策略，此时策略不被强制执行，但任何违规都会被送到策略里指定的报告端点。它还能与 Content-Security-Policy 同时出现在同一响应里——前者生成报告但不拦截，后者照常拦截：

Content-Security-Policy: default-src 'self'; script-src 'self'; report-to csp-endpoint Content-Security-Policy-Report-Only: default-src 'self'; script-src 'self' 'nonce-abc123'; report-to csp-endpoint
两条策略并存：正式的 CSP 强制执行现有规则，Report-Only 里则是准备上线的 stricter 版本，先收集一段时间报告再决定要不要转正。注意仅报告策略不能通过 meta 元素送达。

于是部署流程变成四步：先用 Report-Only 挂上候选策略 → 收集报告找出会误伤自己的规则 → 修正策略直到报告干净 → 把策略搬到正式的 Content-Security-Policy 上执行。整个过程用户毫无感知。

那么报告到底长什么样？这里有两代格式，MDN 都写了，而它们正是本节第二个完整例子。先看老一代——由 report-uri 指令触发、以 application/csp-report 类型 POST 的 JSON：

POST /csp-report HTTP/1.1 Host: example.com Content-Type: application/csp-report { "csp-report": { "document-uri": "https://example.com/post/1", "referrer": "https://www.google.com/", "violated-directive": "script-src 'nonce-416d1177-4d12-4e3b-b7c9-f6c409789fb8'", "effective-directive": "script-src-elem", "original-policy": "default-src 'self'; script-src 'nonce-416d1177-4d12-4e3b-b7c9-f6c409789fb8'; report-uri /csp-report", "blocked-uri": "inline", "status-code": 200, "script-sample": "console.log(\"你已被入侵\")" } }
一条由 report-uri 上报的违规报告。浏览器把「在哪一页、违反了哪条指令、被拦的是什么、策略原文是什么」打包成 JSON 发回服务器。

逐字段解释这份报告：

字段含义在这条报告里的读法
document-uri发生违规的文档地址https://example.com/post/1，定位到具体页面。
referrer该文档的来源页来自 Google 搜索，可判断流量入口。
violated-directive被违反的指令及其值script-src 带 nonce 的那条，说明脚本没带对凭据。
effective-directive实际生效、真正拦下资源的指令script-src-elem，是 script-src 在元素场景下的具体化。
original-policy触发违规时页面的完整策略原文便于复核当时到底下发了什么，避免版本错位。
blocked-uri被拦截资源的地址值为 inline，表示是内联脚本而非外链。
status-code被保护文档响应的状态码200，说明是正常页面。
script-sample被拦截代码的前若干字符给出片段内容，帮助判断是自有代码还是注入内容。

新一代报告走的是 报告 API（Reporting API）：服务器先用 Reporting-Endpoints 首部声明端点，再用 CSP 的 report-to 指令把某个端点指定为报告目标：

Reporting-Endpoints: csp-endpoint="https://example.com/csp-reports" Content-Security-Policy: default-src 'self'; report-to csp-endpoint
report-to 不直接写 URL，而是引用一个在 Reporting-Endpoints 里预先命名好的端点；这样多类报告可以共用同一套端点声明。
POST /csp-reports HTTP/1.1 Content-Type: application/reports+json { "age": 53531, "body": { "blockedURL": "inline", "columnNumber": 39, "disposition": "enforce", "documentURL": "https://example.com/csp-report", "effectiveDirective": "script-src-elem", "lineNumber": 121, "originalPolicy": "default-src 'self'; report-to csp-endpoint", "referrer": "https://www.google.com/", "sample": "console.log(\"lo\")", "sourceFile": "https://example.com/csp-report", "statusCode": 200 }, "type": "csp-violation", "url": "https://example.com/csp-report", "user_agent": "Mozilla/5.0 …" }
report-to 上报的 CSPViolationReport：外层是带 type、url、age、user_agent 的信封，真正的违规详情装在 body 里，字段名也换成了驼峰式。

两代机制的区别是本节的第二个完整例子，归纳成表：

对比维度report-uri（老）report-to（新，推荐）
端点怎么写指令值直接是 URL：report-uri /csp-report先声明 Reporting-Endpoints 命名端点，指令引用名字：report-to csp-endpoint
Content-Typeapplication/csp-reportapplication/reports+json
JSON 结构单个对象，包在 csp-report 键下，字段连字符命名信封结构，含 type（值为 csp-violation）、url、age、user_agent，详情在 body 里驼峰命名
状态MDN 标注为已弃用MDN 推荐的报告方式，基于报告 API
迁移建议在所有浏览器都支持 report-to 之前，应同时声明两者，以覆盖不同版本。

除了上报，MDN 还介绍了严格 CSP与 strict-dynamic：当页面用第三方脚本、而第三方脚本又会动态创建别的脚本时，那些新脚本不会带上你分配的 nonce 或散列，于是被拦。给 script-src 加上 'strict-dynamic' 后，带 nonce 或散列的脚本获得的信任会传递给它加载的后续脚本。它让基于 nonce / 散列的策略在第三方脚本场景下可用，代价是安全性下降——如果你引入的脚本基于不可信输入创建 <script>，CSP 就保护不到那些新元素。

💡 关键一跃

违规报告不只是「谁违规了」的日志，它是 CSP 的反馈回路：Report-Only 让策略先在影子模式里跑，报告告诉你哪条规则会误伤自己，修好后再转正。没有这条回路，写 CSP 就只能靠猜——而一份误伤自己的严格策略，比没有 CSP 更糟，因为页面会直接坏掉。

⚠️ 常见误区

「写了 report-to 就该收到报告」——错。report-to 引用的端点必须先用 Reporting-Endpoints 首部声明，否则报告无处可发；迁移期还要注意 report-to 与 report-uri 的 JSON 格式、Content-Type 都不同，接收端得两种都能解析。另外 script-sample 可能包含页面里的代码片段，若日志对外可见，注意别把敏感信息一起泄露出去。

10.3权限策略：CSP 管能加载什么，它管能调用什么能力

前两节的 CSP 管住的是「页面能加载什么资源」。但页面加载进来之后还有另一个维度：它（以及它嵌入的第三方 iframe）能不能调用摄像头、麦克风、全屏、地理定位这些能力？这正是权限策略（Permissions Policy）要回答的问题。

设想一个页面嵌了广告网络的 iframe。就算 CSP 限制了它加载什么，这个 iframe 仍可能试图读取用户的地理位置。权限策略提供的机制，是让站点明确声明哪些特性可以或不可以在网站上使用——它定义一组策略，限制网站代码能访问哪些 API，或修改浏览器对某些特性的默认行为。MDN 说它和 CSP 很像，但控制的是特性而非安全行为。典型用途包括：改变自动播放默认行为、限制相机麦克风等敏感设备、允许 iframe 使用全屏 API、以及在项目不可见时停止脚本以省性能。

一个重要的历史注脚：权限策略曾叫特性策略（Feature Policy），名字改了，HTTP 首部的语法也跟着变了，但 <iframe allow="…"> 属性的语法保持不变。旧文章里的写法今天多半对不上，查资料要留意。

还要分清它与权限 API（Permissions API）的分工：权限策略让服务器设定某特性能否在某个文档或其 iframe 里使用（这些叫策略控制的特性）；权限 API 则依据用户授予的权限把关。两者识别特性的字符串一致，例如 geolocation 同时指地理定位。一般来说，当权限策略拦下某强大特性时，用户根本不会被弹出询问，权限 API 的 query() 会直接返回 denied——策略挡在了征求用户意见之前。

策略由两部分组成：指令确定要控制的特性名（camera、microphone、geolocation、fullscreen、payment 等），允许列表规定这条特性对哪些源生效。允许列表的取值是本节要记牢的核心：

允许列表取值含义能否与其它值组合
*本文档及所有嵌套 iframe 都可用，无论什么源只能单独使用
()（空）顶层与所有嵌套环境都禁用；等价于 iframe 的 'none'只能单独使用
self仅本文档与同源 iframe 可用；跨源 iframe 不可，是 https://你的域名 的简写可与一个或多个源组合
src只要 iframe 里加载的文档与它 src 同源即可用；只用于 iframe 的 allow，且是它的默认值可与一个或多个源组合
"<origin>"允许特定的源，如 "https://a.example.com"；源之间用空格隔开可与 self / src 组合

头语法是 Permissions-Policy: <directive>=<allowlist>；多个特性可写在一个头里用逗号分隔，也可各发一个头，两者等价：

Permissions-Policy: picture-in-picture=(), geolocation=(self "https://example.com"), camera=* 等价于下面三个头分别发送： Permissions-Policy: picture-in-picture=() Permissions-Policy: geolocation=(self https://example.com) Permissions-Policy: camera=*
允许列表写在圆括号里；* 与 () 独占括号，self 和具体源可以并列。还支持通配符源如 "https://*.example.com"，但它不匹配 "https://example.com" 本身。

iframe 一侧则用 allow 属性，语法沿用旧特性策略的样子（关键字带引号），多个特性用分号分隔：

<iframe src="https://partner.example" allow="fullscreen *; geolocation 'self' https://a.example.com"></iframe>
iframe 的 allow 里，'self' 与 'none' 带单引号、源不加引号——这与响应首部里 self 不加引号、空列表写成 () 的写法不同，别混用。

最关键的是继承规则，它决定了第三方 iframe 到底能不能用某项能力。MDN 说：所有 iframe 都继承父页的策略；若 iframe 有 allow 属性、父页又有 Permissions-Policy 首部，则两者合并，取最严格的子集。一个特想要在 iframe 里启用，它的源必须同时出现在父页的允许列表和 allow 的允许列表里。而且「禁用是单向的」：子框架被父框架禁用的特性，它自己不能重新启用，它的后代也不能。

下面给出本节的完整判定表——给定一条父页策略和一个第三方 iframe 的 allow 属性，逐项判断三项能力是否可用。

Permissions-Policy: camera=(self), fullscreen=(self "https://partner.example"), geolocation=() <iframe src="https://partner.example" allow="camera *; fullscreen *; geolocation 'self'"></iframe>
场景：父页对摄像头只放行同源、对全屏放行同源与 partner.example、对地理定位全局禁用；iframe 来自 partner.example，allow 里三项都想要。
特性父页首部允许列表iframe allow 属性iframe 源 partner.example 是否在两者交集中判定
摄像头 camera(self) 仅同源* 任意源否——父页只给 self，partner.example 是跨源，不在父页列表不可用。allow 再宽也越不过父页这道更严的关卡
全屏 fullscreen(self "https://partner.example")* 任意源是——父页显式列出 partner.example，* 也覆盖它可用。交集含该源，且未被任何一方禁用
地理定位 geolocation() 空列表，全局禁用'self'（指 iframe 自己的源）否——父页空列表意味着谁都不给不可用。禁用是单向的，子框架无法重新开启

三条判定各有侧重：摄像头演示了「allow 不能放大父页未授予的权限」；全屏演示了「两边都放行才可用」；地理定位演示了「一旦父页用 () 关掉，allow 无力回天」。记住一句话：最终权限 = 父页允许列表 ∩ iframe allow，且任一方的显式禁用不可被覆盖。

✅ 判定规则

MDN 建议的做法是：在 HTTP 首部里给出最广泛的可接受支持，再在每个具体 iframe 的 allow 里收窄到它真正需要的子集。这样一个第三方框架想越权也做不到。判断某 iframe 能否用某特性，就问两点——它的源在不在父页列表里？在不在 allow 里？两个都是「在」才可用。

⚠️ 常见误区

把头语法和 iframe 语法混用：头里写 (self)、()（self 不带引号、空列表是括号），iframe allow 里写 'self'、'none'（带引号）——照抄错的那一套会静默失效。还有两个坑：src 只在 iframe allow 里有效，响应首部里没有这个值；若 iframe 之后导航到另一个源，策略默认不会跟过去，除非你在 allow 里把导航目标的源也列出来。

10.4Fetch 元数据让请求自证来源，服务器据此挡下 CSRF

前三节的策略都是「服务器 → 浏览器」方向：用响应首部约束页面能加载什么、能用什么 API。Fetch 元数据反过来，是「浏览器 → 服务器」方向——请求自带一组上下文首部，让服务器看懂这个请求是从哪来、要干什么。先看它要解决的问题。

假设用户在银行站点处于登录状态，攻击者诱导他打开一个恶意页面，页面里藏着一个自动提交的表单：请求把用户的钱转到攻击者账户。因为请求从用户浏览器发出，银行站点种下的 cookie 会被自动带上，服务器看到的是「一个带合法身份的请求」，很难分辨这是用户本意还是偷偷发的。这就是跨站请求伪造（Cross-site request forgery，CSRF）。MDN 把这类攻击统称为跨源攻击——因为「来源」比「站点」约束更强，攻击者的子域名也能发起跨源但同站的攻击，所以用跨源这个词更严谨。

Fetch 元数据（Fetch metadata）就是一组向服务器提供「发起请求的相关上下文」的 HTTP 请求首部。规范定义了四种，它们都带 Sec- 前缀，属于禁止修改的请求首部（forbidden request header）——前端 JavaScript 不能设置或修改。这一点是它能作为安全判据的根本：攻击者再狡猾，也没法用脚本把 Sec-Fetch-Site 从 cross-site 改成 same-origin。

首部回答的问题主要取值
Sec-Fetch-Site请求方与被请求资源是什么关系cross-site / same-site / same-origin / none
Sec-Fetch-Mode请求以什么模式发起navigate / no-cors / cors / same-origin / websocket
Sec-Fetch-Dest返回的资源将用在哪里document / image / script / style / iframe / font / empty 等
Sec-Fetch-User是否由用户行为触发用户触发时取值恒为 ?1，否则不携带

逐个拆开。Sec-Fetch-Site 判定「请求方来自哪」，MDN 用 https://books.example.org/authors 页面里点链接的例子说明：目标 https://books.example.org/titles 是 same-origin（同源）；目标 https://login.example.org/ 是 same-site（不同源但同一站点，都是 example.org 的子域）；目标 https://books.example.com/titles 是 cross-site（不同站点）。地址栏输入或点书签这类「没有站点作为请求方」的情况取值 none，规范称为用户直接发起的请求。

Sec-Fetch-Mode 中，navigate 表示文档间导航；no-cors 允许跨域请求即使服务端没给 CORS 首部也发出去，但响应对 JS 是不透明的——这是加载图片、字体、脚本等子资源的默认模式，也解释了为什么你不配 CORS，别的站点也能引用你的图片；cors 是 fetch() 跨域读取 JSON 时常用，服务端必须给合适的 CORS 首部；same-origin 只接受同源请求。Sec-Fetch-Dest 说目标用途：document 是顶层导航加载的新文档，image 是给 <img>、CSS background-image 等用的图片，empty 常见于 fetch() 发起、未明确指定目标的请求。

服务器拿这四个首部做什么？MDN 介绍了一类常见做法叫资源隔离策略（resource isolation policy）：只放行同源请求、来自其他源的顶层导航请求（否则别人就没法从外部链接跳进你的网站了）、以及专门为跨源设计的特定端点。下面的完整判定表给出几种典型请求的具体取值组合与判定——这是本节的手算。

GET /home HTTP/1.1 Sec-Fetch-Site: none Sec-Fetch-Mode: navigate Sec-Fetch-Dest: document Sec-Fetch-User: ?1 用户在地址栏敲入网址，浏览器自动附加这些首部
用户直接发起的导航：site=none、mode=navigate、dest=document、user=?1。四个首部都由浏览器自动加上，JS 无法伪造。

看清最后两行为什么能挡 CSRF 了。判据是：对有副作用的请求（转账、改资料这类 POST），要求 Sec-Fetch-Site 为 same-origin（信任子域时放宽到 same-site）；跨站的 navigate + GET 可以放行，让人能从外站点进来，但跨站的 POST、或 cors/no-cors 模式、或 dest=empty 的脚本请求一律拒绝。攻击者无法伪造这些首部，所以跨站请求会被忠实标记为 cross-site，无处遁形。

MDN 给出的资源隔离示例逻辑可以浓缩成三步：先看 Sec-Fetch-Site 是否 same-origin 或 none，是则放行（同源请求、用户直接发起）；否则看是否 Sec-Fetch-Mode == navigate 且方法为 GET，是则放行（跨站导航）；其余一律拒绝，返回 403。服务器还应在响应里带上 Vary: sec-fetch-site, sec-fetch-mode，保证缓存只把这些首部取值相同的请求混为一谈——否则缓存可能把发给导航请求的响应错误地服务给别的上下文。

✅ 判定规则

Fetch 元数据与 CORS / Origin 是互补关系：Origin 只在跨源请求里出现，而 Sec-Fetch-* 连同源请求也带，且额外说明「是导航还是子资源、目标是什么、是否用户触发」。因此它能做出比 CORS 更细的策略。记住核心分工：CORS 决定「JS 能不能读响应」，Fetch 元数据帮助服务器决定「这个请求该不该受理」。

⚠️ 常见误区

「有了 Sec-Fetch-* 就不用做 CSRF 防护了」——错。这些首部只有支持的浏览器才发送；面对缺首部的请求，应当按不可信处理或回退到 CSRF token 等传统手段，而不是默认放行。另外别忘 Vary：如果响应会随 Fetch 元数据首部变化，却没在 Vary 里声明，共享缓存可能串味。最后，MDN 强调即使拒绝跨站请求，也要放行跨站导航，否则外部链接全都进不来——「拒绝一切跨源」是过度防御。

10.5延伸：规范怎么写：这三套策略分属 IETF 与 W3C，普通首部规则归 RFC 9110

前面四节按 MDN 的工程口径讲清了 CSP、权限策略与 Fetch 元数据。当你需要实现服务器、判定边界行为或核对某个字段的合法性时，就得去看规范。这里有个容易被忽略的事实：这三套策略并非 IETF 的 RFC，而是 W3C 的浏览器安全规范；它们只在「首部怎么传输」这一层复用 RFC 9110 的通用规则。把规范体系理顺，是本节的收束。

这张表要传达的是一条判断原则：把「字段怎么在网上传输」和「字段对浏览器意味着什么」分开看。前者是 RFC 9110 的通用首部框架，后者分属 CSP Level 3、Permissions Policy、Fetch Metadata 三份 W3C 规范。MDN 把两者揉成开发者视角的连续叙述，读起来顺畅，但当 MDN 说「通常」「建议」而你需要确定的对错时，就得回到相应规范找规范性措辞。

💡 关键一跃

本讲三条策略其实构成一套完整的浏览器侧防线，方向却不同：CSP 与权限策略是服务器下发给浏览器的约束（一个管资源、一个管能力），Fetch 元数据是浏览器回给服务器的线索（让请求自证来源）。它们都借 HTTP 首部这个通用载体，但语义各自独立——认清「传输归 RFC 9110、语义归 W3C 规范」这个二分，你就不会再把 CSP 当成某个 RFC 编号，也不会误以为 Sec-Fetch-* 能被前端改写。

⚠️ 常见误区

别把这三套策略当成 IETF RFC 去搜索——它们是 W3C 规范，用 RFC 编号查不到正确条文。反过来也别以为「符合 RFC 9110 字段语法」就等于「CSP 配置正确」：语法合法但语义写错的策略照样形同虚设。还有一点贯穿三节：这些首部只在支持它们的浏览器里生效，配置时必须有缺首部时的回退方案，绝不能默认「浏览器一定会带上」。

回忆 10.5-1
CSP、权限策略、Fetch 元数据各由哪套规范定义？RFC 9110 在其中管什么？
点击翻面 →
参考答案
三者都是 W3C 规范：CSP Level 3、Permissions Policy、Fetch Metadata Request Headers，不是 IETF RFC。RFC 9110 §5 只管字段的通用语法——大小写不敏感、同名字段合并、ABNF 描述；缓存相关的 Vary 在 §12.5.5。语义归各自的 W3C 规范。
回忆 10.5-2
为什么说「传输格式」与「安全语义」要分开看？这对排查 CSP 或 Sec-Fetch-* 问题有什么实际意义？
点击翻面 →
参考答案
首部怎么编码、合并、缓存由 RFC 9110 统一规定，但指令或取值到底意味着什么由 W3C 各规范定义。排查时先确认字段语法合法（传输层），再核对指令语义与浏览器支持（语义层）；MDN 说「建议」而你要确定对错时，回相应规范找 MUST/SHOULD，并记得为不支持的浏览器准备回退。

概念卡 1
内容安全策略 CSP（Content Security Policy）
点击翻面 →
定义由响应首部下发的一组指令，限制文档能加载与执行哪些资源，主要用于纵深防御 XSS。
解决问题输入净化一旦失守，仍能阻止注入的脚本、事件处理器、javascript: URL 运行。
直觉给页面一份访客名单，不在名单上的资源一律不许进门。
误区以为 CSP 能替代净化；它只是第二道防线，且不能通过 meta 用全部特性。
何时用任何承载用户内容、引入第三方脚本的站点；部署先用 Report-Only 试运行。
概念卡 2
Fetch 指令与 default-src（Fetch Directive / default-src）
点击翻面 →
定义按资源类型限制来源的指令；default-src 是所有未单列类型的后备策略。
解决问题对脚本、样式、图片、连接等分别设定松紧，实现最小权限。
直觉default-src 是默认规矩，各类资源的专门指令是特批条款，特批盖过默认。
误区以为 script-src 的 nonce 会传给 style-src；指令之间彼此独立。
何时用写第一条 CSP 时先定 default-src，再按需用更具体的指令覆盖。
概念卡 3
nonce 与散列（Nonce / Hash）
点击翻面 →
定义让特定内联脚本通过的两种凭据：随机一次性值写在标签 nonce 属性上，或脚本内容的 Base64 散列写进指令。
解决问题在不放开 unsafe-inline 的前提下，允许可信的内联脚本执行。
直觉nonce 是一次性口令，每次换；hash 是内容指纹，内容不变就不变。
误区以为 nonce 可以固定或预测；必须每次响应随机且给攻击者猜不到。
何时用能动态生成页面用 nonce；静态页面用 hash，外部脚本记得加 integrity。
概念卡 4
report-to 与 report-uri（Reporting Endpoints）
点击翻面 →
定义CSP 违规上报的两种机制：report-to 引用 Reporting-Endpoints 声明的端点，report-uri 直接写 URL 且已弃用。
解决问题把线上违规收集回来，配合 Report-Only 形成部署的反馈回路。
直觉策略是刹车，报告是仪表盘；没仪表盘就只能猜哪里会撞墙。
误区以为两代格式一样；Content-Type 与 JSON 结构都不同，迁移期要都收。
何时用上线 CSP 前先 Report-Only + 报告；正式策略与报告端点同时配置。
概念卡 5
权限策略 Permissions-Policy
点击翻面 →
定义用首部与 iframe allow 声明哪些源可用哪些浏览器特性，曾名 Feature Policy。
解决问题限制第三方内容与自家代码调用摄像头、地理定位、全屏等敏感或强大能力。
直觉CSP 管能拿什么资源，权限策略管能按哪些按钮。
误区把它和权限 API 混为一谈；策略拦截时用户不会被询问，query() 直接 denied。
何时用嵌入第三方 iframe、或要收紧敏感设备访问时；头给宽范围，allow 逐帧收窄。
概念卡 6
允许列表与继承（Allowlist / Inheritance）
点击翻面 →
定义允许列表用 *、()、self、src、具体源表示范围；iframe 权限取父页与 allow 的最严格子集。
解决问题让父页能约束第三方框架，即使框架自己写了 allow 也不能越权。
直觉两把锁串联，哪把更紧就按哪把；关掉的门不能从里面再打开。
误区把头语法 (self) 与 iframe 语法 'self' 混用；src 只在 allow 里有效。
何时用判断某 iframe 能否用某能力时，逐项查它是否在父页与 allow 两边都在列表里。
概念卡 7
Fetch 元数据（Sec-Fetch-* / Fetch Metadata）
点击翻面 →
定义浏览器自动附加、JS 不可伪造的一组请求首部，说明来源关系、模式、目标与是否用户触发。
解决问题让服务器区分导航、子资源与跨站写操作，构建资源隔离策略挡 CSRF 与 XS-Leaks。
直觉请求自带身份证，写明「我从哪来、要干什么、是不是你点的」。
误区以为它替代 CSRF token；缺首部的老浏览器要按不可信处理并配合 Vary。
何时用服务端入口做资源隔离：放行同源与跨站 GET 导航，拒绝跨站写操作。

✍️分层习题：先自己写，再点开核对

L1 概念辨析判断下列说法的正误并说明理由：①「CSP 只要设置了就能替代输入净化，不用再做 XSS 过滤」；②「权限策略和权限 API 是一回事，都是问用户要权限」；③「Sec-Fetch-Site 可以用 fetch() 的 headers 手动设置成 same-origin 来绕过检查」。
提示

逐句定位被混淆的概念：纵深防御 vs 替代、策略控制 vs 用户授权、禁止修改首部 vs 普通首部。

完整解答
① 错。MDN 明确 CSP 是纵深防御，不能替代净化；正确做法是净化输入并且设置 CSP，净化失败时 CSP 才作为第二道防线兜底。② 错。权限策略由服务器设定某特性能否用在特定文档或 iframe，是策略控制的特性；权限 API 依据用户授予的权限把关。二者识别字符串一致但职责不同，且策略拦截时用户根本不会被询问，query() 返回 denied。③ 错。Sec-Fetch-* 带 Sec- 前缀，属于禁止修改的请求首部，前端代码不能设置或修改，由浏览器按真实上下文自动附加；正是这一点让它能作为服务器的安全判据。
L1 概念辨析有人说：「我给 script-src 加了 nonce，所以页面里所有内联脚本、内联事件处理器、eval() 都能用了。」这句话有几处错？分别说明 CSP 对这些情形的真实处理。
提示

把「内联 script 标签」「内联事件处理器」「javascript: URL」「eval()」分开，逐项对照 nonce 与 unsafe-inline / unsafe-eval 的规则。

完整解答
三处都错。第一，nonce 只放行带匹配 nonce 属性的 <script> 标签，不是所有内联脚本；攻击者注入的脚本拿不到本次响应的随机 nonce，仍被拦。第二，内联事件处理器（如 onmouseover）与 javascript: URL 不属于带 nonce 的 script 标签，nonce 帮不了它们；要放行只能靠 unsafe-inline（但一旦指令含 nonce，浏览器反而会忽略 unsafe-inline），正确做法是重构为 addEventListener()。第三，eval()、Function() 以及 setTimeout 的字符串参数属于另一类，要靠 unsafe-eval（或可信类型）处理，nonce 对它们无效；注意 unsafe-eval 在含 nonce 的指令里仍然有效，而 unsafe-inline 会被忽略。
L2 手算推导某页面下发如下 CSP：
default-src 'self'; script-src 'self' 'nonce-N7'; style-src 'self'; img-src 'self' cdn.example.net; connect-src 'self'
页面包含：① <script src="/a.js"></script>；② <script nonce="N7">console.log(1)</script>；③ <script>console.log(2)</script>；④ <img src="https://cdn.example.net/x.png">；⑤ <img src="https://evil.example.com/y.png">；⑥ fetch("https://api.other.com/data")。请逐项判定放行或被拦截，并写出依据的指令。
提示

先确定每类资源该看哪条指令——有专门指令就用它，否则回落 default-src；再逐个比对源表达式。

完整解答
① 放行：/a.js 是同源外部脚本，script-src 含 'self'。② 放行：内联脚本的 nonce="N7" 与 script-src 里的 'nonce-N7' 匹配。③ 拦截：内联脚本无 nonce、无散列，而 script-src 存在，内联 JS 默认不允许。④ 放行：图片走 img-src，其中列了 cdn.example.net。⑤ 拦截：evil.example.com 不在 img-src 的 'self' 与 cdn.example.net 之内。⑥ 拦截：fetch 属于连接，走 connect-src 'self'，api.other.com 是跨源。注意各指令彼此独立：script-src 里的 nonce 不影响 style-src，图片能访问 cdn 也和 connect-src 无关。默认回落的只有那些没单列的类型。
L2 手算推导父页下发 Permissions-Policy: camera=(self), fullscreen=(self "https://widget.example"), geolocation=("https://widget.example")，页面里有 <iframe src="https://widget.example" allow="camera 'self'; fullscreen 'none'; geolocation 'self'"></iframe>。iframe 的源是 widget.example（跨源）。请逐项判定摄像头、全屏、地理定位是否可用，并说明「合并取最严格子集」如何起作用。
提示

对每项特性，分别看 widget.example 这个源在不在父页允许列表、在不在 allow 列表里，两项都在才可用。

完整解答
判定方法：把 iframe 的源 https://widget.example 代入父页允许列表与 allow 列表求交集，两边都在且无人显式禁用才可用。摄像头 camera：不可用。父页 camera=(self) 只给同源，widget.example 相对父页是跨源，不在父页列表；allow 里的 'self' 指 iframe 自己的源，不能放大父页没给的权限。全屏 fullscreen：不可用。父页允许列表确实含 widget.example，但 allow 写了 'none'（空列表，等于全禁），两边交集为空；任一方显式禁用都不可被覆盖。地理定位 geolocation：可用。父页允许列表 ("https://widget.example") 含 iframe 的源，allow 写 'self' 指 iframe 自己的源也正是 widget.example，两边都覆盖它且无人禁用，故交集非空、可用。三项结论依次为：不可用、不可用、可用。这题的教训是别凭直觉，要逐项把 iframe 的源代入两边列表老老实实求交集。

提示

把 CSP、权限策略、Fetch 元数据分别套到三个需求上，再统一考虑浏览器兼容回退。

完整解答
① 设 Content-Security-Policy：default-src 'self'；script-src 用 nonce 或散列而非 unsafe-inline；style-src 'self'；img-src 'self' 允许的 CDN；connect-src 'self'；report-to 指向上报端点。评论内容照常净化，CSP 作纵深防御；确需的内联脚本由服务器逐响应插入不可预测 nonce。先用 Report-Only 试运行再转正。② 权限策略在头里给最小集，例如 camera=()、geolocation=()、fullscreen=(self)，只给地图确实需要的源；iframe 的 allow 再收窄到该地图源，并牢记最终取两边交集、禁用不可覆盖。③ 转账接口检查 Sec-Fetch-Site：只允许 same-origin（信任子域才放宽 same-site）且非跨站的写请求；跨站 navigate + GET 可放行以保留外链跳转，跨站 POST、cors/no-cors 脚本请求一律 403；响应带 Vary: sec-fetch-site, sec-fetch-mode 防缓存串味。④ 回退原则统一为「缺支持即按不可信处理」：CSP 靠格式良好的降级与 Report-Only 观察；权限策略缺首部时按各指令默认允许列表，敏感项显式写 ()；Fetch 元数据缺首部时回退到 CSRF token / Origin 校验，绝不默认放行。三套机制方向互补——CSP 与权限策略是服务器下发给浏览器的约束，Fetch 元数据是浏览器回给服务器的线索，配合起来覆盖「能加载什么、能用什么能力、该不该受理请求」三个面。

参考答案：回答「浏览器加载页面之后允许它做什么」——用 CSP 限定能加载与执行什么资源，用权限策略限定能调用什么能力，用 Fetch 元数据让请求自证来源供服务器判定是否受理。
句2：核心机制是什么？——
参考答案：CSP 由响应首部的指令与 source list 组成，default-src 兜底、nonce 与 hash 放行特定内联脚本、违规走报告回路；权限策略用允许列表并取父页与 iframe 的最严格子集；Fetch 元数据是浏览器自动附加、JS 不可伪造的 Sec-Fetch-* 首部，服务器据此做资源隔离挡 CSRF。
句3：它和前后讲怎么分工？——
参考答案：第 8 讲认证确认「你是谁」、第 9 讲 CORS 划出「哪个源能读我的响应」，本讲补上「加载后能做什么、请求该不该受理」；下一讲第 11 讲进入代理与隧道。三套机制在规范上分属 W3C，传输层复用 RFC 9110 的普通首部规则。
