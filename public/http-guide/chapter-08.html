8.1认出你、证明你是你、允许你做什么，是三件不同的事

上一讲的 cookie 解决了一个具体问题：让无状态协议「认出」这是同一个浏览器。但认出来之后，服务器还会追问两个更硬的问题——「你凭什么说你是 alice？」以及「就算你是 alice，你能看这份报表吗？」本讲就把这三件事拆开，再讲 HTTP 用来回答前两件事的通用框架。

先立三个概念，它们天天被混着用。第一个是识别（Identification）：你声称自己是谁，报出一个用户名或工号就好，它只是一句「我是 alice」的声明，谁都能说。第二个是认证（Authentication）：你要证明这句声明成立，通常靠口令、令牌或生物特征——「我是 alice，这是只有 alice 才知道的口令」。第三个是授权（Authorization）：确认身份之后，决定你能访问什么——「alice 可以看报表，但不能改报表」。MDN 这一页标题叫「HTTP 身份验证」，其通用框架主要解决的是中间那一环：用一套标准化流程把凭据从客户端送到服务器去校验。

用一个生活场景把它们钉牢。你走进一栋写字楼：在前台报出「我是 alice」是识别；前台核对你的工牌和身份证是认证；刷卡后电梯只让你上 3 楼、进不了 12 楼的机房，是授权。cookie 类似于前台发给你的访客手环——它让保安「认出」你，但手环本身不能证明你没把它借给别人。HTTP 认证要做的，是每次进门前让你出示一次真正的凭证，而不是只戴着手环。

接下来是 MDN 反复强调的通用框架。它本质上是一个质询—响应（challenge–response）的握手：服务器先拒绝，并说明「你要用什么方式证明自己」；客户端据此提供凭据，再请求一次。注意一个反直觉的设计——客户端不会主动在第一条请求就带上凭据，而是先发一条裸请求，等服务器挑战后再带。这么做的直接好处是：凭据不必在每次访问每个 URL 时都无谓地出现，只在确实需要保护的页面上才传递。

把这条主线落到真实报文上，看得最清楚。下面是完整的一次交互，也是本讲第一个必须掌握的亲手例子：从 401 挑战到带凭据重试的全过程。

第 1 步：客户端先发一条不带凭据的请求。

GET /admin/report HTTP/1.1 Host: app.example.com User-Agent: DemoClient/1.0 Accept: text/html （空行：本请求没有任何凭据首部）
裸请求：客户端不知道这个路径受保护，所以没有 Authorization 首部。它并不知道自己马上会被挑战。

第 2 步：服务器拒绝并挑战。返回 401 状态码，并用 WWW-Authenticate 首部告诉客户端「用 Basic 方案，realm 叫 Admin Area」。

HTTP/1.1 401 Unauthorized Date: Mon, 16 Nov 2026 00:30:00 GMT WWW-Authenticate: Basic realm="Admin Area" Content-Length: 63 Content-Type: text/html; charset=utf-8 <html><body><h1>401 Unauthorized</h1></body></html>
401 挑战：状态码 401 说明「未提供有效凭据」，WWW-Authenticate 说明用哪种方案以及哪个保护区域。注意主体里的尖括号已按 HTML 规则转义为 &lt; 与 &gt;。

第 3 步：客户端提示用户，.compute 出凭据并重试。浏览器弹出登录框，用户输入 user / pass。客户端把它们拼成 user:pass，做 Base64 编码（下一节手算）得到 dXNlcjpwYXNz，放进 Authorization 首部重发：

GET /admin/report HTTP/1.1 Host: app.example.com User-Agent: DemoClient/1.0 Authorization: Basic dXNlcjpwYXNz Accept: text/html （空行：凭据已随本次请求发出）
重试请求：Authorization 首部的格式是「方案名 + 空格 + 凭据」。Basic 后面那串就是 Base64(user:pass)。

第 4 步：服务器校验通过，返回资源。

HTTP/1.1 200 OK Date: Mon, 16 Nov 2026 00:30:01 GMT Content-Type: text/html; charset=utf-8 Content-Length: 42 <html><body>季度报表数据…</body></html>
校验成功返回 200。整个交互用了两条请求、两条响应——这就是通用框架的最小完整闭环。

这里要顺带记住一个状态码家族的分工，它是 401 的「邻居」：401 Unauthorized 表示「你没证明身份，请再试」；403 Forbidden 表示「我知道你是谁，但你没权限，别再试了」。MDN 特别指出，服务器常常干脆用 404 来回应无权限请求，以隐藏页面的存在——对攻击者来说，「404 不存在」比「403 你没权限」泄露的信息更少。把 401、403、404 放进同一张判定表，排障时才不会混：

状态码服务器想表达什么客户端会怎么做是否带挑战首部
401 Unauthorized未提供或提供了无效凭据提示用户重新输入，可重试必须带 WWW-Authenticate
403 Forbidden凭据有效，但权限不足不再尝试，直接告知失败不需要
404 Not Found可能真实不存在，也可能是刻意隐藏当作资源不存在不需要
✅ 判定规则

看到响应先分两类：401 是「身份认证没过」——去找 WWW-Authenticate，看它要求什么方案；403 是「认证过了但授权没过」——提示用户换账号或申请权限，重试无意义。若你明明带了正确凭据却一直收到 401，要怀疑编码是否出错、realm 是否对得上、或是否被中间代理拦下，而不是继续傻等。

⚠️ 常见误区

「HTTP 认证 = 登录表单」——错。登录表单是应用层自己设计的流程：你 POST 用户名口令到 /login，服务器返回一个 cookie，之后靠 cookie 识别你（上一讲的机制）。而本讲的 HTTP 认证是协议内置的质询—响应框架，凭据走的是专门的 Authorization 首部，由浏览器或客户端自动处理。二者可以并存但机制完全不同：前者把状态放进 cookie，后者每条请求都显式携带凭据。

8.2Basic 把「用户名:口令」做了一次 Base64——编码不是加密

上一节我们看到重试请求里那串 Authorization: Basic dXNlcjpwYXNz。这一节把那串字符彻底拆开：它怎么算出来、为什么人人都能算、以及这为什么是一个安全陷阱。MDN 说得很直白——「Basic」方案对凭据进行编码，但并不加密；除非通过 HTTPS/TLS 的安全连接，否则极其不安全。

先给 方案（Scheme）一个定义。通用框架只规定了「401 挑战 + Authorization 凭据」的骨架，具体「凭据长什么样、怎么编码」由不同的认证方案决定。MDN 列出了 Basic、Bearer、Digest、HOBA、Mutual、Negotiate/NTLM、VAPID、SCRAM、AWS4-HMAC-SHA256 等一长串。Basic（Basic authentication scheme）由 RFC 7617 定义，是其中最不安全但支持最广、最容易配置的一个：它把「用户名:口令」用 Base64（Base64 encoding）编码后放进首部。

这里必须立刻纠正一个致命误解：Base64 是编码（Encoding），不是加密（Encryption）。编码是把数据换成另一种表示形式以便安全传输，不需要密钥，任何人都能反向还原；加密需要密钥，没有密钥的第三方无法还原。Base64 的字母表是公开的、算法是公开的，把 dXNlcjpwYXNz 贴到任何一个在线工具里，一秒就能还原成 user:pass。所以 Basic 的凭据在网络上等价于明文——MDN 的原话是「用户 ID 与密码以明文形式在网络中传输（尽管采用了 Base64 编码，但 Base64 算法是可逆的）」。

现在做本讲第二个必会例子：手工把 user:pass 编码成 Base64。分三步走，一步步都能用纸笔完成。

第一步：逐字符查 ASCII 字节。把 user:pass 的每个字符换成 ASCII 码（注意中间的冒号是 ASCII 58，不是字母）：

第三步：把三组结果顺次拼接。第一组 dXNl，第二组 cjpw，第三组 YXNz，合起来就是 dXNlcjpwYXNz——和上一节报文里的那串完全一致。这个过程反过来就是解码：把每 4 个字符还原成 3 个字节，所以任何人都能还原，没有任何秘密可言。

补齐规则的边界也值得知道。Base64 每次处理 3 字节输出 4 个字符；如果原文长度不是 3 的倍数，末尾会用 = 补位：剩 2 字节时补 1 个 =，剩 1 字节时补 2 个 =。比如 alice:s3cr3t 是 12 字节（3 的倍数），编码结果是 YWxpY2U6czNjcjN0，没有补位；而一个 11 字节的口令串就会以单个 = 结尾。看到 = 就知道原文长度不能被 3 整除，仅此而已，它不提供任何安全性。

MDN 还提到一个容易被忽略的细节：字符编码。浏览器用 UTF-8 编码用户名和密码（Firefox 早年用 ISO-8859-1，后来为了与其他浏览器一致也改为 UTF-8）。这意味着用户名或口令里若有中文，先按 UTF-8 变成多字节，再做 Base64——这也解释了为什么有些老服务器面对非 ASCII 口令会对不上：两端的字符编码假设不一致。

💡 关键一跃

把「编码」和「加密」分家，是理解所有认证方案安全性的钥匙。Base64、URL 编码、十六进制都是编码——可逆、无密钥、只为传输方便；真正保护口令要靠 TLS 在传输层加密整条报文，或靠 Digest 这类方案用哈希挑战避免口令直接上线。Basic 之所以「安全性很差」，正是因为它把可逆编码当成了唯一的保护，把全部安全责任推给了 TLS。

⚠️ 常见误区

「Base64 之后是一堆看不懂的字符，所以口令被藏起来了」——错得最典型的一条。看不懂不等于不可读：Base64 是纯可逆变换，还原不需要任何密钥，抓包后一行命令就能解出口令。同理，MDN 明确反对在 URL 里写 https://username:password@host/ 这类凭据：它已被弃用，Chrome 会移除这部分，Firefox 会警告「该站点并不需要认证」，因为这种写法既泄露口令到历史记录与日志，又常被钓鱼页面利用。

8.3realm 不是一枚标签，它和源站一起圈定了凭据的复用范围

上一节解决了「凭据怎么编码」，但浏览器什么时候该自动带上它、什么时候该重新弹框？答案藏在 401 挑战的 realm 参数里。MDN 的说法是：realm 用来描述进行保护的区域或范围，让用户知道自己正在访问哪个空间，例如 Access to the staging site。这一节把它从一个「提示文字」升级成一个「缓存判据」。

先明确语法。MDN 给出挑战首部的形式是 WWW-Authenticate: <type> realm=<realm>，凭据首部的形式是 Authorization: <type> <credentials>。这里的 <type> 就是方案名（Basic、Bearer 等），realm 是一个区分大小写的字符串。一个真实挑战长这样：

HTTP/1.1 401 Unauthorized WWW-Authenticate: Basic realm="Admin Area" Content-Length: 0 （主体为空，关键信息全在首部里）
挑战里的 realm="Admin Area" 既是给用户看的提示，也是浏览器缓存凭据时要记录的键的一部分。

关键问题来了：保护空间（Protection Space）到底由什么决定？规范口径是——realm 值与「规范化根 URI」（即 scheme、host、port）共同定义一个保护空间。换句话说，浏览器缓存凭据时的键，是「协议 + 主机名 + 端口 + realm」这个四元组，路径不在键里。这一点极反直觉：很多人以为 /admin/a 的凭据不会发给 /admin/b，其实只要 realm 相同、源站相同，浏览器就会自动带上；反过来，即便路径相同，只要 realm 不同，浏览器也会当作另一个保护空间，重新挑战。

现在做本讲第三个必会例子：realm 与凭据缓存范围的判定。设定场景如下：用户在 https://app.example.com/admin/login 被 realm="Admin Area" 挑战并输入了 alice 的口令，浏览器因此缓存了保护空间 (https, app.example.com, 443, "Admin Area") → alice 的凭据。同一台服务器的 /docs/ 目录则用 realm="Docs Area" 保护。现在逐个判定后续请求会不会自动带上 Admin Area 的凭据：

后续请求 URL该路径的挑战 realm与已缓存四元组是否相同是否自动带 Admin 凭据
https://app.example.com/admin/page2Admin Areascheme/host/port/realm 全同会，直接带上
https://app.example.com/admin/deep/reportAdmin Area同四元组（路径更深不影响）会，路径不是键的一部分
https://app.example.com/docs/apiDocs Arearealm 不同不会，视为另一保护空间，另行挑战
https://app.example.com:8443/admin/page2Admin Areaport 8443 ≠ 443不会，端口不同即不同源站
http://app.example.com/admin/page2Admin Areascheme http ≠ https不会，协议不同即不同源站
https://other.example.com/admin/page2Admin Areahost 不同不会，主机名不同即不同源站

逐行看判据：第 1、2 行只看 realm 与源站四元组，路径深浅完全不影响，所以自动带上；第 3 行 realm 变了，浏览器把它当另一个「房间」，Admin 的钥匙开不了 Docs 的门；第 4、5、6 行分别改了端口、协议、主机名，任何一个变化都会改变「规范化根 URI」，于是保护空间不同，凭据不会复用。记住一句口诀：同源 + 同 realm 才复用，路径无关。

MDN 还提醒了一个与凭据自动发送相关的安全修复：跨源图片的认证。过去，如果页面里嵌入了来自另一个源的图片，加载该图片可能触发 HTTP 认证对话框，攻击者若能把你想要的图片塞进第三方页面，就可能诱导你输入凭据、造成泄露。从 Firefox 59 起，跨源加载图片不再触发 HTTP 认证对话框，正是为了堵住这条路。这提醒我们：浏览器对「什么时候允许自动发送凭据/弹认证框」的控制，本身就是安全边界的一部分。

✅ 判定规则

判断凭据是否复用，只画一张四元组表：scheme、host、port、realm。四项全等，浏览器自动带；任一不同，重新挑战。别被路径迷惑——/a 与 /b 只要 realm 同名，就属于同一保护空间。排障时若「凭什么这次没带凭据」，第一反应就是核对这四项中到底哪一项变了。

⚠️ 常见误区

「realm 只是给用户看的提示文字，没有技术含义」——错。它确实会显示在登录框里，但它同时是凭据缓存键的一部分，直接决定浏览器会不会把口令发给某个请求。把 realm 当成纯装饰，就会在拆分后台与文档站时误用同一个 realm 字符串，导致本应隔离的两套凭据被浏览器混用；给不同安全等级的区域起同一个 realm 名，等于主动拆掉隔离。

8.4401 属于源站，407 属于代理：两条平行的挑战链，与明文口令的代价

前三节默认「挑战你的就是目标服务器」。但真实网络里，客户端和源站之间常常还夹着代理——公司网关、学校出口、抓包调试工具都可能要求你先证明身份。MDN 专门指出：资源认证与代理认证可以并存，它们用不同的首部和不同的状态码。这一节把两条链并列，再推演 Basic 凭据离开 TLS 后会发生什么。

代理认证遵循完全相同的质询—响应原理，只是换了一组「车道」：源站用 401 和 WWW-Authenticate / Authorization，代理用 407 和 Proxy-Authenticate / Proxy-Authorization。两套首部互不干扰——代理只关心 Proxy- 系列，源站只关心不带前缀的那一套，因此一条请求可以同时满足「向代理证明我是员工」和「向源站证明我是 alice」。

下面是本讲第四个必会例子的第一半：401 源站认证与 407 代理认证的对照表。

维度401 源站认证407 代理认证
挑战方目标源服务器路径上的代理服务器
状态码401 Unauthorized407 Proxy Authentication Required
挑战首部（响应）WWW-AuthenticateProxy-Authenticate
凭据首部（请求）AuthorizationProxy-Authorization
凭据挑战语法Basic realm="..."Basic realm="..."
典型场景登录网站后台、受保护接口公司/学校出网代理、调试代理
能否并存可以：两者首部独立，一次请求可分别向代理与源站证明身份

用两条报文对照看，差异一目了然。先是代理发起的 407 挑战：

HTTP/1.1 407 Proxy Authentication Required Proxy-Authenticate: Basic realm="Corporate Proxy" Content-Length: 0 （由代理返回，要求先向代理证明身份）
407 挑战：注意首部名带 Proxy- 前缀，表明这是代理而非源站的要求。

客户端随后在请求里同时带上两套凭据：

GET http://example.com/report HTTP/1.1 Host: example.com Proxy-Authorization: Basic YWxpY2U6czNjcjN0 Authorization: Basic dXNlcjpwYXNz （前者给代理，后者给源站，互不混淆）
两套凭据并存：Proxy-Authorization 交给代理，Authorization 由代理转发给源站。这也是为什么代理不能随意吞掉或错转这些首部。

接下来是第四个例子的第二半：推演 Basic 凭据在没有 TLS 时被中间人窃取的完整攻击链。这是本讲最重要的安全结论，请一步步跟住。

前置条件。用户访问的是 http://intranet.example.com/report——注意是 http，没有 TLS。攻击者位于客户端与服务器之间（同一个不可信 WiFi 的恶意热点、被控制的路由器、或链路上的任意节点），能够被动监听并主动转发流量。源站用 Basic 保护该路径。

攻击链推演：

步骤发生了什么攻击者获得什么
1客户端发裸 GET 到明文 http 地址看到请求路径与目标，可确认有受保护资源
2源站返回 401 + WWW-Authenticate: Basic realm="Intranet"知道需要 Basic 凭据
3浏览器弹框，用户输入 alice / s3cr3t用户毫无察觉，以为只是普通登录
4客户端计算 Base64 并发送 Authorization: Basic YWxpY2U6czNjcjN0抓到整条报文，读到那一串 Base64
5攻击者对 Base64 做逆向，还原出 alice:s3cr3t拿到明文用户名与口令，无需任何密钥
6攻击者用该凭据直接向源站重放请求，或去其他系统撞库完全冒充 alice，访问、篡改数据，横向扩大战果

整条链要成立，只需一个条件：凭据在链路上以可被监听的形式传输。Base64 可逆，等于把口令写在明信片背面——邮递员和沿途每个人都能翻过来看。攻击者甚至不必主动伪造任何东西，只要「听」就够了；这一步叫被动窃听，成本低、不留痕迹。

把 TLS 加进来，链条在第 4 步就断了。HTTPS 下，Authorization 首部连同整条 HTTP 报文被封装进 TLS 记录，用协商出的会话密钥加密；链路上的观察者只能看到目标 IP、端口，以及握手阶段暴露的域名（SNI），但看不到首部里的任何内容，更还原出口令。同时，TLS 的证书校验让客户端能确认「对面确实是 app.example.com，而不是伪装成它的中间人」，从而挡住主动冒充。这正是 MDN 那句警告的落点：Basic 必须搭配 HTTPS/TLS，没有这层保护就不该用它保护敏感或有价值的信息。

💡 关键一跃

分清「谁在挑战」和「谁在保护」：407 只是把 401 的问法换成了代理版本，安全性质一点没变——Basic 在代理链上同样是明文凭据。所以无论是发给源站还是发给代理，只要方案是 Basic，就必须假设整条路径都不可信，用 TLS 把凭据关进加密通道。想不依赖 TLS 又避免口令上线，就得换方案（如 Digest 用哈希挑战、Bearer 用短期令牌），而不是指望 Base64。

⚠️ 常见误区

「内网/局域网用 http 就没事，Basic 也安全」——错。攻击面往往就在「你以为可信」的那段链路上：共享 WiFi、被攻陷的路由器、恶意代理都在内网这一跳。MDN 的态度很明确：Basic 应当与 HTTPS/TLS 搭配使用，缺乏这些增强时不该用来保护敏感或高价值信息。另一个误区是以为「407 是 401 的笔误」——它们是两套首部、两个挑战方，混用会导致代理或源站收不到本该属于自己的凭据。

8.5延伸：规范怎么写：MDN 的认证框架对应 RFC 的哪一段

前面四节按 MDN 的工程口径讲清了「怎么用」。但如果你想实现客户端、写服务器，或判定某个边界行为的对错，就得看规范。这里做本讲的「延伸：规范怎么写」——把 MDN 的每段话对齐到具体的 RFC。认证这一块有三份关键文档：认证框架在 RFC 9110，Basic 在 RFC 7617，Bearer Token 在 RFC 6750。要注意 MDN 页面正文仍写着「RFC 7235 定义了 HTTP 身份验证框架」——那是被 RFC 9110 取代的旧文档，2022 年 IETF 重整 HTTP 规范后，原来的 RFC 7235 已并入 RFC 9110 的第 11 章。这正是延伸板块要补的口径差。

MDN 的说法RFC 怎么写为什么值得知道
RFC 7235 定义了 HTTP 身份验证框架，服务器质询、客户端提供凭据现行框架在 RFC 9110 §11：challenge 与 credentials 是抽象模型，WWW-Authenticate / Authorization 是其 HTTP 首部表达；401 = §15.5.2，403 = §15.5.4，407 = §15.5.3MDN 引用的 RFC 7235 已被 9110 取代。写实现要查现行编号，否则对着作废文档写代码；「质询—响应」在规范里是一组可复用的抽象，不只服务 Basic
Basic 用 base64 编码凭据，不安全，应与 HTTPS/TLS 搭配RFC 7617 定义 Basic：凭据 = base64(user-id ":" password)，user-id 不得含冒号；realm 用引号包裹且区分大小写；可用 charset 参数声明编码（实际约定为 UTF-8）「用户名里不能有冒号」「realm 区分大小写」这类边界只有规范写死。实现解析器时按 RFC 处理，才能和别的客户端互通
realm 描述受保护的区域或范围RFC 7617 §2 与 RFC 9110 §11.5：realm 值大小写敏感，与规范化根 URI（scheme/authority）共同定义 protection space；客户端可在同空间内复用凭据MDN 只说「提示文字」，规范才给出缓存键的精确定义。这解释了为什么改端口或 realm 就会重新挑战，是 8.3 节判定表的规范依据
Bearer 令牌通过 OAuth 2.0 保护资源RFC 6750 定义 Bearer：凭据是「持有即有权」的令牌，形式为 Authorization: Bearer <token>；可由首部、form body 或 URI 查询携带（后者不推荐）Bearer 与 Basic 的关键差异是凭据从「用户名口令」换成「短期令牌」，且同样强制要求 TLS。理解这一点才能接上后续的 OAuth / API 鉴权
凭据有效但权限不足返回 403；服务器也可能返回 404 隐藏页面RFC 9110 §15.5.4 定义 403 为「理解请求但拒绝授权」；§15.5.2 要求 401 响应必须发送 WWW-Authenticate；隐藏资源用 404 是安全实践而非规范要求「401 必须带挑战首部」是 MUST 级别的规范约束，不是可选优化；而 404 隐藏属于工程权衡。分清「规范要求」与「实践建议」，排障与评审才有依据

这张表想传达的核心，和前几讲的延伸板块一致：MDN 告诉你「通常怎么做」，RFC 告诉你「到底必须怎么做」。RFC 里的 MUST / SHOULD / MAY 是有严格区别的——比如「401 必须带 WWW-Authenticate」是 MUST，缺少它服务器就是不合规范；而「用 404 隐藏资源」只是推荐的安全实践，你可以选择不用。当 MDN 说「通常」「建议」，而你需要一个确定的对错时，就去 RFC 找规范性措辞。

💡 关键一跃

把三份文档按职责摆好，整块认证知识就立住了：RFC 9110 定义通用框架（挑战—响应的抽象与状态码语义），RFC 7617 填进 Basic 方案的具体编码与 realm 规则，RFC 6750 填进 Bearer 方案的令牌规则。框架与方案是「插槽与插件」的关系——MDN 那串长长的方案列表，本质都是往同一个 9110 框架里插不同的插件。

⚠️ 常见误区

别把「Basic 必须搭配 TLS」记成「Basic 自带加密」。RFC 7617 全文没有给 Basic 定义任何加密或哈希保护，它只规定了一次可逆的 Base64 编码；保密性完全依赖外部 TLS。也别再引用 RFC 2617 或 RFC 7235 当现行认证规范——它们分别已被 RFC 7617 系列与 RFC 9110 取代。查规范先认清编号与章节，是写对实现的第一步。

🃏概念卡：本讲概念的一分钟画像

翻面前先自问：这个概念我能用一句话讲清楚吗？

概念卡 1
识别 / 认证 / 授权（Identification / Authentication / Authorization）
点击翻面 →
定义识别是声称身份，认证是证明身份，授权是确认身份后决定可访问的范围。
解决问题把「你是谁」「凭什么信」「能做什么」三个常被混淆的问题分开处理。
直觉报名字是识别，查工牌是认证，刷卡只开 3 楼是授权。
误区把 cookie「认出你」当成认证；持有会话 cookie 并不能证明操作者就是原用户。
何时用本讲主线讲认证；403 / 404 处涉及授权；第 7 讲 cookie 属于识别与会话维持。
概念卡 2
质询—响应框架（Challenge–Response Framework）
点击翻面 →
定义服务器先用 401 + WWW-Authenticate 发起挑战，客户端再用 Authorization 提供凭据的通用流程。
解决问题让凭据只在确有必要时才传递，并把「用什么方式证明」的决定权交给服务器。
直觉门卫先问「出示证件」，你才掏证件；而不是见门就先把证件递出去。
误区以为客户端会在首条请求就主动带凭据；标准流程是先裸请求、被挑战后再带。
何时用所有 HTTP 认证方案的共同骨架，规范在 RFC 9110 §11。
概念卡 3
WWW-Authenticate / Authorization
点击翻面 →
定义前者是 401 响应首部，声明方案与 realm；后者是请求首部，携带方案名与凭据。
解决问题把挑战说什么、凭据怎么送，用两个标准首部固定下来，客户端服务器得以互通。
直觉一个是考卷上的题目，一个是答卷上的答案。
误区以为凭据首部叫 Authentication；正确的是 Authorization，且 401 响应必须带 WWW-Authenticate。
何时用8.1 报文闭环与 8.4 代理对照里成对出现，代理版本加 Proxy- 前缀。
概念卡 4
Basic 与 Base64
点击翻面 →
定义Basic 是 RFC 7617 的认证方案，把「用户名:口令」做 Base64 编码后放进 Authorization。
解决问题支持最广、配置最简单，能快速给目录加一道口令门。
直觉把「alice:口令」写成可逆的暗号，人人都能译回原文。
误区以为 Base64 是加密、凭据被藏住了；它可逆无密钥，等价于明文，必须配 TLS。
何时用内部工具、临时保护；涉及敏感数据时只在 HTTPS 下使用，或改用更强方案。
概念卡 5
realm 与保护空间（Realm / Protection Space）
点击翻面 →
定义realm 是挑战里的区分大小写字符串，与规范化根 URI 共同定义一组凭据可复用的保护空间。
解决问题让同一站点能划分多个独立保护区，并决定浏览器何时自动带凭据。
直觉realm 是房间名，源站是楼；同一间房的钥匙通用，换房或换楼就得重新领钥匙。
误区以为 realm 只是登录框上的提示语，或以为路径不同凭据就不复用；路径不在缓存键里。
何时用8.3 判定表按 scheme/host/port/realm 四元组判断凭据复用。
概念卡 6
401 / 403 / 404 / 407
点击翻面 →
定义401 认证未过并附挑战，403 认证过但授权拒绝，404 隐藏存在，407 是代理版 401。
解决问题用不同状态码区分「再试一次」与「别试了」，并把代理与源站的挑战分开。
直觉401 是「证件不合格请重出示」，403 是「证件没错但这层不让你进」。
误区把 401 与 403 都当「登录失败」；也别把 407 当成 401 的笔误，它属于代理。
何时用排障时先分流：看状态码与挑战首部，再决定重试、换账号还是查代理配置。
概念卡 7
Bearer Token 与 TLS
点击翻面 →
定义Bearer 用「持有即有权」的令牌作凭据，形式 Authorization: Bearer <token>，由 RFC 6750 定义；TLS 提供传输层加密与身份认证。
解决问题用短期令牌替代口令直接上线，配合 OAuth 2.0 做 API 鉴权；TLS 保护任何方案的首部不被窃听。
直觉Basic 交的是身份证复印件，Bearer 交的是限时通行证；TLS 是密封的运钞车。
误区以为 Bearer 令牌泄露也无所谓，或以为 Basic 自带加密；令牌同样机密，Basic 同样依赖 TLS。
何时用现代 API 与开放平台鉴权多用 Bearer；任何在公网传凭据的场景都必须先上 TLS。

✍️分层习题：先自己写，再点开核对

L1 概念辨析判断下列说法的正误并说明理由：①「HTTP 认证就是登录表单」；②「401 和 403 都表示登录失败，处理方式一样」；③「Base64 是一种加密，所以 Basic 的口令是安全的」。
提示

逐句找出被混淆的那对概念：协议框架 vs 应用层表单、认证未过 vs 授权拒绝、编码 vs 加密。

完整解答
① 错。登录表单是应用层自己设计的流程（POST 到 /login，换回 cookie），靠 cookie 识别用户；HTTP 认证是协议内置的质询—响应框架，凭据走 Authorization 首部，由浏览器自动处理，两者机制不同。② 错。401 是认证未过，响应必须带 WWW-Authenticate，客户端应重新提供凭据并重试；403 是凭据有效但权限不足，重试没有意义，应换账号或申请权限；服务器还可能用 404 隐藏页面存在。③ 错。Base64 是公开可逆的编码，不是加密，不需要密钥就能还原。Basic 的凭据等价于明文，只有搭配 HTTPS/TLS 才安全，MDN 明确称 Basic 安全性很差。
L1 概念辨析有人说：「realm 只是登录框上给用户看的一句话，浏览器发不发凭据跟它没关系。」这句话错在哪？请说出凭据缓存键的构成，并举出两种会让浏览器重新挑战的变化。
提示

回到 8.3 的四元组口诀：同源 + 同 realm 才复用。想哪些字段一变就不再「同源同 realm」。

完整解答
realm 不只是提示文字，它是凭据缓存键的一部分。按 RFC 7617，保护空间由「规范化根 URI（scheme、host、port）+ realm」共同定义，四项全等浏览器才自动复用凭据。会让浏览器重新挑战的变化例如：① 把 realm 从 Admin Area 改成 Docs Area（realm 不同，另一保护空间）；② 把访问从 https 改成 http，或把端口从 443 改成 8443，或换到另一个主机名（根 URI 变化）。注意路径深浅不在键里——同 realm 的 /a 与 /b 会复用同一份凭据。
L2 手算推导请手工把字符串 alice:s3cr3t 编码成 Base64，写出每组 3 字节的 ASCII 十六进制、24 位二进制、拆成 4 组 6 位及最终字符。并回答：结果末尾有没有补位符 =？为什么？
提示

先数字符个数、判断是否 3 的倍数；再逐字符查 ASCII，按 3 字节一组、每 24 位拆 4 个 6 位，对照字母表 A–Z=0–25、a–z=26–51、0–9=52–61。

完整解答
alice:s3cr3t 共 12 个字符，是 3 的倍数，可分 4 组，故末尾没有补位符（只有长度不被 3 整除时才补 =）。ASCII：a=61 l=6C i=69 / c=63 e=65 :=3A / s=73 3=33 c=63 / r=72 3=33 t=74。四组 24 位与 6 位拆分：
ali → 01100001 01101100 01101001 → 011000/010110/110001/101001 → 24/22/49/41 → Y/W/x/p → YWxp
ce: → 01100011 01100101 00111010 → 011000/110110/010100/111010 → 24/54/20/58 → Y/2/U/6 → Y2U6
s3c → 01110011 00110011 01100011 → 011100/110011/001101/100011 → 28/51/13/35 → c/z/N/j → czNj
r3t → 01110010 00110011 01110100 → 011100/100011/001101/110100 → 28/35/13/52 → c/j/N/0 → cjN0
拼接结果：YWxpY2U6czNjcjN0。这正是 8.4 节代理报文里 Proxy-Authorization 所用的那串值。
L2 手算推导用户在 https://shop.example.com:443/account/ 被 realm="Member Area" 挑战并输入了凭据。对下列每个请求，判断浏览器是否自动带上凭据，并写出判据：① https://shop.example.com/account/orders；② https://shop.example.com:443/admin/（假定返回 realm="Staff Area"）；③ http://shop.example.com/account/；④ https://shop.example.com:8443/account/。
提示

逐项对比四元组 (scheme, host, port, realm) 是否与缓存的 (https, shop.example.com, 443, Member Area) 完全相同；默认端口 443 与省略端口等价。

完整解答
缓存的保护空间是 (https, shop.example.com, 443, Member Area)。
① 自动带上：scheme、host、port 全同，路径 /account/orders 更深不影响，realm 未变（隐含仍为 Member Area），四元组一致。
② 不带：虽 scheme/host/port 相同，但该路径挑战的 realm 是 Staff Area，与缓存的 Member Area 不同，属另一保护空间，浏览器会重新挑战。
③ 不带：scheme 从 https 变成 http，规范化根 URI 变化，保护空间不同；而且明文传输凭据有安全风险。
④ 不带：port 从 443 变成 8443，源站不同，保护空间不同。结论——四项完全一致才复用，任一变化（含 realm 与端口）都要重新提供凭据。
L3 建模应用你要给一个内部系统做认证方案评审：一部分是给员工用的网页后台（有用户名口令），一部分是给合作伙伴调用的 API（发放短期令牌），链路经过一台公司出网代理。请综合本讲回答：① 两处分别适合用哪种认证方案，凭据首部怎么写？② 代理那一跳用什么状态码与首部，会不会和源站认证冲突？③ 从威胁建模角度，列出至少三条必须落实的安全约束，并说明它们各自挡住哪类攻击。
提示

把「方案选择」「401/407 并存」「Base64 明文风险与 realm 缓存」三个维度分别套进去；安全约束优先考虑 TLS、令牌时效、凭据不进 URL。

完整解答
① 员工后台可用 Basic，凭据首部写 Authorization: Basic <base64(user:pass)>，但必须全程 HTTPS；合作伙伴 API 更适合 Bearer，写 Authorization: Bearer <token>，令牌短期有效、可撤销，同样依赖 TLS。② 代理那一跳用 407 + Proxy-Authenticate 挑战、Proxy-Authorization 提供凭据；它与源站的 401/Authorization 是两套独立首部，不会冲突，一条请求可同时带 Proxy-Authorization 和 Authorization 分别向代理与源站证明身份。③ 安全约束示例：(a) 全链路强制 HTTPS/TLS——挡住被动窃听与中间人冒充，因为 Basic 与 Bearer 凭据都不能明文上线；(b) API 令牌短期有效并支持吊销——即使令牌泄露也限制可用窗口，降低重放与撞库损失；(c) 禁止把用户名口令或令牌写进 URL（弃用的 user:password@ 形式、或查询参数）——避免凭据进入浏览器历史、服务器日志与 Referer；(d) 不同安全等级区域使用不同 realm——防止浏览器在同源下把高权限凭据复用到低信任区域；(e) 有效凭据但权限不足返回 403、必要时用 404 隐藏资源存在——减少信息泄露。这些约束共同弥补 Basic 本身不提供机密性的短板。

✅本章自测：每题只选一个答案

自测 1
关于 HTTP 通用认证框架，下列说法正确的是？
  • A. 客户端在首条请求就主动带上凭据，服务器只需校验
  • B. 服务器先用 401 + WWW-Authenticate 挑战，客户端再用 Authorization 提供凭据
  • C. 认证框架是 Basic 方案特有的，其他方案不用
  • D. 401 表示凭据有效但权限不足
解析：B 对。A 错在标准流程是先裸请求、被挑战后才带凭据；C 错在框架是通用的（RFC 9110 §11），Basic、Bearer、Digest 等都往同一框架里插；D 错在 401 是认证未过，权限不足是 403。
自测 2
字符串 user:pass 的 Base64 编码结果是？
  • A. dXNlcnBhc3M=
  • B. dXNlcjpwYXNz
  • C. dXNlcjpwYXNz=
  • D. dXNlcjpwdHNz==
解析：B 对。user:pass 共 9 字节、可被 3 整除，分组 use→dXNl、r:p→cjpw、ass→YXNz，拼接得 dXNlcjpwYXNz，且无补位符。A 是漏掉冒号、按 userpass 编码的结果（dXNlcnBhc3M=），是最容易混淆的干扰项；C 凭空多出一个 =，长度能被 3 整除时不应补位；D 的末组字符算错且错加两个 =，既算错了 ass 的 6 位分组，也误判了补位。
自测 3
浏览器在下列哪种情况下会自动带上已缓存的 Basic 凭据？
  • A. 同 scheme、同 host、同 port、同 realm，但路径更深
  • B. realm 从 Admin Area 改为 Docs Area，其余不变
  • C. 从 https 改为 http，其余不变
  • D. 端口从 443 改为 8443，其余不变
解析：A 对。保护空间由规范化根 URI 与 realm 四元组决定，路径不在键里，所以同源同 realm 的更深路径会复用凭据。B 改 realm、C 改 scheme、D 改 port 都会改变保护空间，浏览器将重新挑战，故都不带。
自测 4
关于代理认证，下列说法正确的是？
  • A. 代理认证用 401 和 WWW-Authenticate
  • B. 代理认证与源站认证互相冲突，只能二选一
  • C. 代理凭据放在 Authorization 首部里发给源站
  • D. 代理用 407 和 Proxy-Authenticate 挑战，凭据放 Proxy-Authorization
解析：D 对。A 把代理说成源站（401/WWW-Authenticate 属于源站）；B 错在两套首部独立、可以并存；C 错在代理凭据应放 Proxy-Authorization，Authorization 是给源站的。
自测 5
Basic 认证凭据被中间人窃取的根本原因是？
  • A. 用户名里含冒号导致解析出错
  • B. realm 字符串区分大小写
  • C. Base64 编码可逆且无密钥，凭据在明文链路上等价于明文
  • D. 浏览器缓存凭据时把路径也算进键
解析：C 对。Basic 把用户名口令做可逆 Base64 编码，无 TLS 时任何旁路监听者都能还原明文口令并重用——这是必须搭配 HTTPS/TLS 的原因。A 是编码时的格式约束（用户名不得含冒号），不是被窃原因；B 是 realm 的正常属性；D 说法本身错误，路径并不进缓存键。
