5.1同一 URL 为何给出两种答案：缓存放在谁手里，决定谁能看到它

第 4 讲让连接不必每次重建，省下的是握手的时间；本讲要省的是重复传输的字节。顺着主线往下走，连接复用回答的是「这条路要修几次」，而缓存（Cache）回答的是「同一份东西要不要再送一遍」。但缓存一旦开始替服务器回答请求，就立刻撞上一个更要紧的问题：这份副本该放在谁手里？放对了地方，省下带宽又减轻源站；放错了地方，省下的字节会换来一次货真价实的信息泄露。

先看一个反例，它把「放错地方」的后果摆得很直白。某站内登录后返回一个带用户名的页面片段，源站把它发给了路径上的一台共享缓存：

GET /dashboard HTTP/1.1 Host: app.example.com Cookie: session=alice-token HTTP/1.1 200 OK Content-Type: text/html; charset=utf-8 Set-Cookie: session=alice-token; HttpOnly; Secure Cache-Control: max-age=600 <h1>你好，Alice</h1>
危险配置：响应里带着 Alice 的个性化内容，却只写了 max-age，没有 private。共享缓存会把这份副本按 URL 存下来。

十分钟内，另一个用户 Bob 请求同一个 GET /dashboard。共享缓存发现 URL 相同、副本还新鲜，于是把 Alice 的「你好，Alice」原样递给了 Bob。这里没有黑客，没有注入，只有一条配错的 Cache-Control。MDN 把这件事说得很清楚：如果个性化内容被存进私有缓存以外的缓存，其他用户就可能取到它，从而造成无意的信息泄露。

要钉住「谁能看到副本」这件事，先得给缓存分类。MDN 依据缓存是否与特定客户端绑定，把 HTTP 缓存分成两大类。

第一类，私有缓存（Private Cache）。它绑定到特定客户端，典型就是浏览器缓存（Browser Cache）：这份副本只为这一个用户服务，不会与其他人共享。正因为不共享，私有缓存可以存该用户的个性化响应。如果一份响应含个性化内容、且你只希望特定客户端保存它，就必须显式写出 Cache-Control: private。

第二类，共享缓存（Shared Cache）。它位于客户端和服务器之间，能存储可在用户之间共享的响应。MDN 又把它细分为两种：一是代理缓存（Proxy Cache），由路径上的代理实现，用来减少网络流量，通常不由服务开发人员管理，只能靠恰当的 HTTP 首部去约束；二是托管缓存（Managed Cache），由服务开发人员明确部署以降低源站负载、高效交付内容，例子包括反向代理、内容分发网络（CDN, Content Delivery Network）以及 service worker 与 Cache API 的组合。

浏览器缓存与 CDN 缓存的决策差异是本讲反复要用的判断。它们虽都叫缓存，但服务的目标不同，因而对同一条首部的反应也不同。浏览器缓存归单个用户私有，可以存带身份的响应；CDN 缓存归成千上万用户共享，一旦存了个性化内容就是事故。反过来，CDN 擅长的是那些「所有人拿到都一样」的静态资源，可以 aggressively 地缓存很久；浏览器则要在「省流量」和「看到最新版」之间替用户反复权衡。

还有一个极易踩的坑必须在这里点破：cookie 的存在本身并不说明响应是私有的。MDN 明确讲，个性化内容通常由 cookie 控制，但「带了 cookie」与「是私有响应」是两件事。所以不能指望缓存看见 Set-Cookie 就自动帮你隔离；要靠你自己写 private。同理，想阻止别人复用个性化内容，正确做法是 Cache-Control: private，而不是去 Vary 里塞一个 Cookie。这个对比会在 5.4 节展开。

✅ 判定规则

拿到一份响应，先只问一句：它是否因用户身份而不同？不同 → 它是个性化响应，只能进私有缓存，写 private；所有用户拿到都一样 → 可以进共享缓存，用 max-age 决定放多久。这个问题答错，后面所有新鲜度计算都白搭。

⚠️ 常见误区

「HTTPS 加密了，代理看不到响应，所以个性化内容不会被共享缓存存下来」——只对了一半。HTTPS 普及后，路径上的代理缓存往往只能隧道传输、确实无法缓存；但如果企业用 TLS 桥接代理（在终端装上组织 CA 证书、以中间人方式解密），代理就能看见内容并缓存它。更关键的是，CDN 这类托管缓存本来就能被服务方配置成读取特定首部。把安全性寄托在「别人看不见」上，不如自己写清楚 private。

5.2「能存」不等于「能直接用」：四条最容易混淆的 Cache-Control 指令

上一节解决了副本放在哪里，接下来要解决副本放多久、以及用之前要不要再问一句。承上启下地说，类型判断决定「谁可以存」，而 Cache-Control（Cache-Control）首部决定「存下来之后怎么用」。MDN 把这套首部里最常被搞混的四条指令——no-cache、no-store、must-revalidate、immutable——分在「验证」「不使用缓存」「避免重新验证」几个不同话题下讲；这里把它们摆到同一张判定表里，一次性钉死。

先看一条把四条的用法都串起来的响应。假设这是一份内容可能变化的主资源 HTML：

HTTP/1.1 200 OK Content-Type: text/html; charset=utf-8 Content-Length: 1024 Date: Tue, 22 Feb 2022 22:22:22 GMT Last-Modified: Tue, 22 Feb 2022 22:00:00 GMT ETag: "deadbeef" Cache-Control: no-cache <!doctype html>…
no-cache 并不阻止存储：这份响应会被存进缓存，只是每次复用前都必须先向源站再验证。

逐条拆开这四条指令的准确含义：

no-cache：MDN 的原话是「不会阻止响应的存储，而是阻止在没有重新验证的情况下重用响应」。也就是说它是「可存，但用之前必须验证」。配合 Last-Modified / ETag，资源更新了就返回 200 OK，没更新就返回 304 Not Modified。它并不省掉请求，只省掉主体字节。

no-store：这条才是「禁止存到任何缓存里」。MDN 强调，它阻止的是存储，而且不会删除同一 URL 已经存过的旧响应。换句话说，把一条响应改成 no-store，并不能让之前存在缓存里的旧副本消失；要强制客户端在复用前先验证，得用 no-cache。

must-revalidate：MDN 的解释是「一旦响应过期，就不得在没有重新验证的情况下重用它」。注意它管的是过期之后的行为——新鲜期内照常用缓存，一旦陈旧就必须验证，不能拿陈旧副本糊弄。它常与 max-age=0 搭配，max-age=0, must-revalidate 的语义与 no-cache 相同，但那是 HTTP/1.1 之前的旧实现不认识 no-cache 时的兼容写法；MDN 明确说，如今符合 HTTP/1.1 的服务器已广泛部署，没有理由再用这个组合，直接用 no-cache。

immutable：这条是「内容永远不会变，因此不必再验证」。MDN 指出，做了缓存破坏（URL 里带版本号或散列）的资源内容恒定，但用户按下重新加载时，浏览器仍会发验证请求；加上 immutable 就能明确告诉缓存「不必验证」，从而消除重新加载期间那次无谓的请求。

指令存不存用之前要不要再验证典型场景
no-cache存（可进私有缓存，配合 private 才不进共享）每次复用前都必须验证主资源 HTML、频繁变化的接口
no-store不存，任何缓存都不存无从谈起——不存就谈不上复用；且不删除已存旧副本高敏感数据、隐私内容
must-revalidate存新鲜期直接用；一旦过期，必须验证后才能用有严格时效要求、不能接受陈旧副本的数据
immutable存（通常配长 max-age 与 public）新鲜期内不验证，重新加载也不验证带内容散列、永不改变的静态 JS / CSS

把这张表读成一句话：no-cache 管「用之前问」，no-store 管「根本别存」，must-revalidate 管「过期后别放行」，immutable 管「新鲜期别来问」。四条指令作用在「存储 / 验证」这条时间轴的不同点上，所以它们根本不是近义词。

这里还要顺手解决另一个高频问题：Expires 与 max-age 的优先级。Expires（Expires）是 HTTP/1.0 时代的产物，用一个绝对的 GMT 时间点声明有效期；max-age（max-age）是 HTTP/1.1 随 Cache-Control 引入的，用一个相对的秒数声明「从生成起能活多久」。MDN 给的理由很实在：绝对时间格式难解析、容易出现实现错误，还可能被人故意拨动系统时钟来诱发问题。因此规范定义，当两者同时出现时 max-age 优先。既然 HTTP/1.1 已被广泛使用，MDN 的结论是「无需特地提供 Expires」。

HTTP/1.1 200 OK Date: Tue, 22 Feb 2022 22:22:22 GMT Expires: Tue, 28 Feb 2022 22:22:22 GMT Cache-Control: max-age=604800 <!doctype html>…
两条都给出时以 max-age=604800（一周）为准；Expires 那一行被忽略。而且 22 日加一周正是 3 月 1 日附近，与 Expires 写的 28 日并不一致——以 max-age 计算才不会错。
💡 关键一跃

把「存储」和「复用」拆成两个阶段，四条指令就各归其位：no-store 卡在存储阶段；no-cache、must-revalidate、immutable 都作用在复用阶段，只是分别要求「每次验」「过期才验」「永远别验」。MDN 还提醒，随意加 no-store 会让你丢掉浏览器的后退/前进缓存等一整套能力；想「总是最新」又不想丢这些能力，no-cache 配合 private 通常更合适。

⚠️ 常见误区

把 no-cache 读成「不缓存」——这是缓存领域最贵的一个误读。它存，只是用前验证；真正「不存」的是 no-store。另一个误区是以为 no-store 能当「撤销键」：它不会删除同一 URL 已存的旧响应，所以把出问题的响应改成 no-store 之后，缓存里那份旧的仍可能被复用。要强制每次回源验证，用 no-cache。

5.3新鲜度是一道算术题：用 Date、Age 与 max-age 手算响应是否过期

上一节解决了「用之前问不问」，但如果不问，缓存凭什么判断这份副本还能不能用？承上启下地说，no-cache 把判断权交给了源站，而 max-age 把判断权交给了本地的一道算术题：算出这份响应已经「活」了多久，再和它允许活多久比一比。MDN 把存储的响应分成两种状态——新鲜（Fresh）与过期（Stale，也叫陈旧）：新鲜通常意味着仍有效、可复用，过期则意味着副本已经不新鲜了。

判断的标准叫存活时间（Age）：响应自生成以来经过的时间，类似其他缓存机制里的 TTL。MDN 用 TTL 作类比，就是想让你把它想成一个不断增长的计数器。

看一条带短 max-age 的响应：

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 1024 Date: Tue, 22 Feb 2022 22:22:22 GMT Cache-Control: max-age=3600 <!doctype html>…
Date 指出响应生成时刻，max-age=3600 表示它可新鲜存活一小时。判断式：存活时间 < 3600 秒 → 新鲜；≥ 3600 秒 → 过期。

例①　给定 Date、Age 与 max-age，手算过期时刻与当前是否新鲜。下面这条响应由一个共享缓存转发给客户端，请完整判定它的新鲜度。

HTTP/1.1 200 OK Content-Type: text/html Content-Length: 1024 Date: Tue, 22 Feb 2022 22:22:22 GMT Cache-Control: max-age=604800 Age: 86400 <!doctype html>…
MDN 给出的经典例子：max-age=604800（一周），Age=86400（一天，由共享缓存告知已存活的时间）。

按 MDN 的口径逐步算，一步不跳：

  1. 读出两个时间量。Date: Tue, 22 Feb 2022 22:22:22 GMT 是响应生成时刻；max-age=604800 秒 = 7 天 = 604800 ÷ 86400 = 7，确实是一周。
  2. 求过期时刻（绝对时间）。过期时刻 = Date + max-age = 2022-02-22 22:22:22 + 7 天 = 2022-03-01 22:22:22 GMT。注意 2 月只有 28 天，加 7 天要跨月，写成 2 月 29 日就错了。
  3. 读出当前已存活时间。共享缓存用 Age: 86400 告诉客户端「这份副本已经在路上/在我这里存了一天」。客户端收到它时，至少已经活了 86400 秒。
  4. 求剩余有效时间。MDN 给出关系式：剩余有效时间 = max-age − Age = 604800 − 86400 = 518400 秒。换成天：518400 ÷ 86400 = 6 天。也就是说客户端收到时，这份响应还能再当新鲜副本用整整 6 天。
  5. 写全判定式。令 age 为当前存活时间，freshness_lifetime 为允许的新鲜寿命：
    age < freshness_lifetime → 新鲜，可直接复用 age ≥ freshness_lifetime → 过期，需再验证或重取 本例：86400 < 604800 → 当前新鲜 剩余 = 604800 − 86400 = 518400 秒 = 6 天
    新鲜度判定式：把「已活多久」与「能活多久」比大小；等号落在过期一侧。
  6. 交叉验证。若客户端在整个 6 天里都不验证，第 6 天结束时 age = 86400 + 518400 = 604800，恰好等于 max-age，落在判定式下半支——此时响应转为过期，正好与第 2 步算出的 3 月 1 日 22:22:22 过期时刻吻合。两条路径互相印证，计算无误。

这里有一个容易被忽略的细节：Age 是累计的。每经过一跳共享缓存，副本又多存了一段时间，Age 就该继续增长，而不是被重置。MDN 强调 Age 是「响应生成以来经过的时间」，源站生成时它是 0，之后每存一跳、每过一秒都在累加。共享缓存把响应交给下游时，用 Age 把这份「已经欠下的时间」传递下去，下游才能算出准确的剩余寿命。这也是为什么第 5.5 节的 RFC 9111 要给 Age 一个完整的校正公式——真实网络里，各节点时钟并不同步，光靠 Date 减时间会算错。

那么，如果一份响应既没有 Cache-Control 也没有 Expires，缓存是不是就「不缓存」了？答案是否定的，这就引出启发式缓存（Heuristic Caching）。MDN 说得很直接：HTTP 旨在尽可能多地缓存，即使没有 Cache-Control，只要满足条件，响应也会被存储和重用。它举的例子是一份 Last-Modified 显示「最后一次更新在一年前」的 HTML——按经验法则，一年没变的内容接下来一段时间大概率也不变，于是客户端会存下它并在一段时间内复用，时长取决于具体实现，而规范建议约为「存储后时间的 10%」（本例约 0.1 年）。

启发式缓存是一种历史遗留的变通方案，诞生于 Cache-Control 尚未普及的年代。MDN 的结论因此很明确：原则上所有响应都应显式指定 Cache-Control。把新鲜度交给启发式规则，等于把自己的内容更新节奏交给了一个「猜」字。

✅ 判定规则

手算新鲜度只走三步：① 过期时刻 = Date + max-age；② 当前 age 由 Age 首部读出（共享缓存逐跳累计）；③ 比大小，age < max-age 新鲜，否则过期。若两者都没有，缓存会退回启发式缓存去「猜」，这正是要显式写 Cache-Control 的原因。

⚠️ 常见误区

「Age 是缓存自己存的时长，重新转发时从 0 开始」——错。Age 是响应自生成以来的总存活时间，逐跳累加并向下传递；把它重置会让下游以为响应很新鲜，从而超额复用。另一个错是把 age = max-age 也算作新鲜：判定式里等号落在过期一侧，恰好相等时响应已经不新鲜。

5.4缓存键不止是 URL：Vary 如何把请求首部编进钥匙，以及漏写它会怎样发错表示

前面三节都默认「一个 URL 对应一份响应」。承上启下地说，新鲜度算得再准，如果缓存连「这是不是同一份东西」都判错了，算术就失去了意义。MDN 指出，缓存区分响应本质上基于 URL——不同的 URL 指向不同的响应体。但内容协商（Content Negotiation）打破了这个前提：同一个 URL，服务器可能依据 Accept、Accept-Language、Accept-Encoding 这些请求首部返回不同表示（Representation）。于是问题变成：缓存凭什么知道「这个 URL 有好几个版本」？

答案是 Vary（Vary）首部。MDN 的示例是语言：一份带 Accept-Language: en 缓存下来的英文内容，不该被复用于 Accept-Language: ja 的请求。做法是在响应里写出：

HTTP/1.1 200 OK Content-Type: text/html Content-Language: en Vary: Accept-Language Cache-Control: max-age=3600 <!doctype html>…
Vary: Accept-Language 让缓存按「URL + Accept-Language 的值」组合建键，而不是只用 URL。

MDN 的结论是：加上这一行，缓存就会基于「响应 URL 与 Accept-Language 请求首部的组合」来键控，而不只是基于 URL。换成本讲的说法，缓存键（Cache Key）从「URL 一把钥匙」变成「URL + Vary 列出的请求首部值」这把组合钥匙。

没有 Vary（仅按 URL 建键）有 Vary: Accept-Language（按组合建键）
/index.html → 一份响应体/index.html + ja-JP → 日语响应体
英文请求与日文请求共用同一副本/index.html + en-US → 英文响应体
后者会拿到前者的错误语言每个语言各自命中自己的副本

例③　Vary: Accept-Encoding 参与缓存键的分步推演，以及漏写它的故障链。这是线上最高发的一类缓存事故，逐帧走一遍。

正确配置的情况：

  1. 请求 A 到达。客户端 A 发 GET /app.js，带 Accept-Encoding: gzip, br，表明它支持 br 压缩。共享缓存按 URL 查键，未命中，转发源站。
  2. 源站协商并标注。源站看出 A 支持 br，返回 br 压缩后的 JS，并在响应里写明 Content-Encoding: br 与 Vary: Accept-Encoding，再配 Cache-Control: max-age=3600。
  3. 缓存按组合键存储。因为 Vary 指定了 Accept-Encoding，缓存把键记为 (/app.js, Accept-Encoding=gzip, br) → br 版本。关键就在这一步：首部的值成了键的一部分。
  4. 请求 B 到达。客户端 B 发同一个 GET /app.js，但它的 Accept-Encoding: identity，只认未压缩内容。缓存算出的键是 (/app.js, Accept-Encoding=identity)，与 A 的键不同，于是未命中，回源取回未压缩版本，单独存一份。A、B 各取所需，正确。
  5. 后续命中。再来一个支持 br 的客户端 C，键与 A 相同，直接命中 br 副本，既快又省字节。

漏写 Vary 的故障链：

  1. 源站图省事，只回了压缩内容，忘了写 Vary。Content-Encoding: br 有，Vary: Accept-Encoding 没有。
  2. 缓存退化为按 URL 建键。没有 Vary 指路，缓存只能把 /app.js 当成唯一键，于是把 br 版本记为 /app.js → br 字节。
  3. 请求 B 命中了不属于它的副本。B 的请求 URL 同样是 /app.js，缓存认为键相同，直接把 br 字节发给一个声明只接受 identity 的客户端。
  4. 客户端解码失败。B 按未压缩 JS 去解析 Content-Encoding: br 的字节流，得到一堆无法识别的字符，脚本语法错误，页面交互直接瘫痪——用户看到的是白屏或按钮全部失灵。
  5. 定位极难。刷新、换网络、清缓存都可能「碰巧好用」，因为下一次命中的究竟是哪份副本取决于谁先请求。根因不在 JS，而在一个缺失的响应首部。

MDN 对 User-Agent 还补了一条实用提醒：如果你基于用户代理做内容优化（例如响应式设计），可能想把 User-Agent 加进 Vary；但 User-Agent 变体极多，会大幅降低缓存命中率。因此如果可能，应改用特性检测而不是依据 User-Agent 来改变行为。至于个性化内容，MDN 的态度很坚决：想用 cookie 防止别人复用缓存内容，应该用 Cache-Control: private，而不是在 Vary 里指定 cookie。原因很清楚——private 直接禁止共享缓存存储；Vary: Cookie 只是把 cookie 值编进键，共享缓存照样会存下每个用户的副本，既浪费空间又留下泄露面。

✅ 判定规则

只要一个 URL 会「看请求首部下菜碟」，响应就必须用 Vary 列出那些首部：按压缩协商就写 Vary: Accept-Encoding，按语言就写 Vary: Accept-Language。判据一句话：哪些请求首部改变了响应体，就把哪些写进 Vary。而「因用户身份不同而不同」不属于协商，属于个性化，用 private 而不是 Vary。

⚠️ 常见误区

「内容协商的请求会自动带 Vary，缓存不用我操心」——错。Vary 必须由源站响应显式声明，缓存不会替你猜。另一个错是把 Vary: Cookie 当成个性化内容的保护伞：它只会让缓存按 cookie 值分键存储，共享缓存里依旧躺着每个用户的私人副本。正确做法是 private。第三个坑是往 Vary 里塞 User-Agent：变体爆炸会让命中率暴跌，能用特性检测就别用 UA。

5.5延伸：规范怎么写：MDN 给了结论，RFC 给出了算法与边界

前面四节的所有结论都来自 MDN 中文《HTTP 缓存》指南，它已经把「怎么用」讲得很完整。但 MDN 是指南，刻意省略了不少规范性细节。本节按惯例做延伸：规范怎么写，把这些细节补齐——你会看到，MDN 的一句「剩余时间 = max-age − Age」，在规范里其实是一整套校正公式；MDN 没提的几条指令，规范里早有正式定义。

MDN 的说法RFC 怎么写为什么值得知道
剩余有效时间 = max-age − Age；Age 是响应生成以来经过的时间RFC 9111 给出完整 current_age 算法：apparent_age = max(0, response_time − date_value)；corrected_age_value = age_value + response_delay；corrected_initial_age = max(apparent_age, corrected_age_value)；current_age = corrected_initial_age + resident_time各节点时钟并不同步，简单减法会算错。排查「CDN 返回的 Age 忽大忽小」时，要看的正是这套校正式，尤其是 apparent_age 对负时钟偏差的兜底
Expires 与 max-age 同时出现时以 max-age 优先；HTTP/1.1 下无需再写 ExpiresRFC 9111 定义共享缓存可用 s-maxage 覆盖 max-age 与 Expires，专门给共享缓存设定新鲜寿命CDN 场景能靠 s-maxage 给边缘缓存单独定一个寿命，而不影响浏览器私有缓存的判断，这是 MDN 正文没展开的实用开关
no-cache 会强制验证；max-age=0 + must-revalidate 是旧兼容写法RFC 9111 把 no-cache 定义为可带字段名参数，形如 no-cache="Set-Cookie"，表示只对列出的字段强制验证能精细化控制：只让某些敏感字段必须回源校验，其余部分仍可复用，避免整份响应都失去缓存价值
immutable 表示内容永不改变，可防止重新加载时的验证RFC 8246 将 immutable 独立成规范，明确响应在其新鲜期内不会变化，客户端不应发起条件再验证把「谁承诺不变」写进标准，实现者据此安心跳过验证；配合带散列的 URL 才成立，否则内容真变了却声明 immutable 会造成长期陈旧
MDN 未展开「陈旧了又不想让用户等回源」该怎么优化RFC 5861 定义两条扩展指令：stale-while-revalidate 允许在陈旧期间先返回旧副本、后台异步再验证；stale-if-error 允许在回源出错时于宽限期内继续返回旧副本把「新鲜 / 过期」的二元判定变成带宽限的策略：弱网或源站抖动时用户体验不断档，是大型站点常用的韧性手段
MDN 未列出「这次请求到底有没有命中缓存」的诊断首部RFC 9211 定义 Cache-Status 响应首部，用 hit、miss、fwd、stale、refreshing、revalidated、bypass 等参数描述缓存如何处理本次请求线上排障不必再靠刷新碰运气，响应头直接告诉你命中、回源还是再验证，是缓存可观测性的基石
没有 Cache-Control 时可能触发启发式缓存，规范建议约 10%RFC 9111 允许启发式过期，但要求它不得覆盖显式的 freshness 信息，且对含认证等特征的响应不应套用启发式解释了「为什么带身份的响应必须显式写 no-cache / private」——否则缓存可能凭 Last-Modified 猜出一个新鲜期，把不该缓存的内容缓存下来

表中还要点明一处版本沿革：RFC 9111 是现行的 HTTP 缓存规范，它取代了早期的 RFC 7234。MDN 在文首链接的就是 RFC 9111。你在旧资料里常看到的「RFC 7234 规定……」，如今都应改口为 RFC 9111。这也提醒我们，读缓存资料要先看它依据的是哪一版规范。

两条 RFC 扩展指令值得单独展开，因为它们弥补了 MDN 正文的空白。stale-while-revalidate 的思路是：响应刚过期的一小段宽限时间里，缓存可以先把旧副本发给用户（用户立刻看到内容），同时在后台发起再验证；验证完更新副本，下次就是新的。stale-if-error 的思路是：当回源请求失败（如 5xx 或网络错误）时，在宽限期内继续用旧副本顶上，宁可给旧内容也不给用户一个错误页。二者都带一个以秒为单位的宽限时长，都是「过期不等于立即不可用」这一判断的制度化。

最后，关于条件请求本身：本讲只把它作为「陈旧响应的下一步」引出来——当响应过期、缓存需要向源站确认内容是否变化时，会用到 If-Modified-Since / If-None-Match 这类条件请求，源站用 304 Not Modified 表示「没变，继续用你的副本」。这里你只要记住结论：条件请求让「再验证」只传首部、不传主体，把带宽省到极致。它的完整报文结构、ETag 与 Last-Modified 的选择、以及范围请求如何续传，都在第 6 讲展开，本讲不抢那部分内容。

💡 关键一跃

MDN 给的是「怎么做」，RFC 给的是「为什么这样做、边界在哪」。当你需要排查 Age 异常、给 CDN 单独设寿命、做弱网韧性或加缓存可观测性时，MDN 的指南会不够用，而 RFC 9111 / 8246 / 5861 / 9211 正是这些问题的答案所在。记住这条分界，就知道什么时候该从指南走向规范。

⚠️ 常见误区

「MDN 没写的指令就是不存在」——错。s-maxage、stale-while-revalidate、stale-if-error、Cache-Status 都是正式规范里的东西，只是 MDN 这篇指南没逐条展开。反过来也要警惕：给内容会变的资源错加 immutable，或给个性化响应错加 public，会让「承诺不变」「允许共享」这两个判断长期生效，酿成比不用缓存更糟的陈旧与泄露事故。

🧪落地例④：为带散列的静态 JS 与登录后的个性化接口各配一套首部

前面把所有零件都拆开讲过了，这里用一个完整的落地例把它们装起来。例④要为空分两类资源各写一套可直接抄用的响应首部，并逐条说明理由。这两套配置正好覆盖 MDN「常见的缓存模式」里的两个极端：一个追求「尽可能久地缓存」，一个追求「绝不外泄、总是最新」。

场景一：带内容哈希的静态 JS。文件名里带内容散列，例如 bundle.YsAIAAAA-QG4G6kCMAMBAAAAAAAoK.js。内容一变，散列就变，URL 也随之改变——这就是 MDN 说的缓存破坏（Cache Busting）。因为 URL 唯一对应一份永不变的内容，可以放心缓存很久。

HTTP/1.1 200 OK Content-Type: text/javascript; charset=utf-8 Content-Length: 1024 Date: Tue, 22 Feb 2022 20:20:20 GMT Last-Modified: Tue, 22 Feb 2022 20:20:20 GMT ETag: "YsAIAAAA-QG4G6kCMAMBAAAAAAAoK" Cache-Control: public, max-age=31536000, immutable /* bundle content */
带散列的静态 JS 的完整响应首部组合：长 max-age + public + immutable，并附 ETag 与 Last-Modified 作为验证器。

逐条说明：

  • max-age=31536000：一年（31536000 秒）。内容永不改变，缓存越久越省带宽；MDN 还指出这个值正是 QPACK 预定义表里的常用值之一，走 HTTP/3 时能压到 1 个字节。
  • public：明确允许共享缓存（CDN）存储。MDN 特别说明，只有在响应带 Authorization 首部、而你仍希望它被存储时才需要 public；否则只给 max-age 就会被共享缓存存下。这份静态 JS 按 URL 公开可取，加上 public 更稳妥。
  • immutable：告诉缓存连重新加载都不必验证。因为内容随 URL 里的散列绑定、永不变化，省掉用户每次刷新时的那次条件请求。注意前提是「URL 一变内容就变」必须严格成立。
  • ETag 与 Last-Modified：MDN 提醒别忘带验证器，它们是内容的散列与最后修改时间。虽然 immutable 让正常访问不验证，但保留验证器对缓存之外的生态（CMS、爬虫）与降级场景仍有价值；RFC 9110 也建议 200 响应尽量同时给出这两者。
  • Content-Type 带 charset：JS 用 text/javascript 并声明 utf-8，避免编码猜测问题（呼应第 2 讲）。

场景二：登录后的个性化接口。例如 GET /api/account，返回当前用户的余额与资料，带 Cookie 或 Authorization。内容因用户身份而异，绝不能进共享缓存；含敏感数据，也不该落到磁盘缓存里长期保存。

GET /api/account HTTP/1.1 Host: app.example.com Cookie: session=alice-token HTTP/1.1 200 OK Content-Type: application/json; charset=utf-8 Cache-Control: no-store, private Pragma: no-cache Vary: Accept-Encoding {"balance": 12345}
登录后的个性化接口：no-store 禁止任何缓存存储，private 兜底阻止共享缓存，Vary 只针对压缩协商而非身份。

逐条说明：

  • no-store：主指令，禁止响应被存入任何缓存——含敏感数据的接口不该在任何缓存里留副本。MDN 也承认实践里「不缓存」的理由之一是隐私，此时 no-store 才是对的选择。
  • private：第二道防线。MDN 明确说，即使设置了 no-store，也必须设置 private，以确保个性化响应不会被共享缓存意外留存。它针对的是那些可能忽略 no-store 的缓存，以及浏览器自身的各类缓存分区。
  • Pragma: no-cache：兼容 HTTP/1.0 时代旧实现的写法，现代 HTTP/1.1 缓存以 Cache-Control 为准；这里作为防御性的补充，呼应 MDN 提到的「大杂烩式标头」思路，但不用堆上 max-age=0 等一长串。
  • Vary: Accept-Encoding：这条不是为了身份隔离，而是为了让 JSON 的 gzip / br 版本正确分键（呼应 5.4 节）。身份隔离交给 private，别写成 Vary: Cookie。
  • 为什么不用 no-cache：no-cache 允许存储（只是用前验证），对余额这类敏感数据意味着副本仍会落盘；而 MDN 指出，若希望「总是最新」且数据敏感，no-store 更贴切。若数据没那么敏感、又想保留浏览器后退/前进的即时返回，可退而用 no-cache, private 并附 ETag——这正是 MDN 给「登录后个性化 HTML」的推荐组合。
💡 关键一跃

两套配置是同一套判断推向两个极端的结果：内容随 URL 变化且永不变 → 长 max-age + public + immutable（能存多久存多久）；内容随身份变化且敏感 → no-store + private（一点别存）。中间态（如主资源 HTML）才用 no-cache + ETag/Last-Modified，个性化时再叠加 private。先定「内容与什么绑定」，首部组合自然浮现。

点击翻面 →

📝分层习题

L1 概念辨析有人说：「no-cache 就是不缓存，所以既安全又省带宽。」请指出这句话的两个错误，并说明 no-cache 与 no-store 各自的实际含义。
提示

把「存储」和「复用」两个阶段分开想，再问 no-cache 到底卡在哪一步。

完整解答
错误一：no-cache 不是「不缓存」。MDN 明确说它不阻止存储，只阻止在没有重新验证的情况下重用响应，所以副本照样会存。错误二：它不省掉请求——每次复用前都要发验证请求，省的是主体字节而非请求本身。正解：no-cache = 可存，但用前必须验证；no-store = 完全不存到任何缓存，且不会删除同 URL 已存的旧副本。若要「一点别留」，该用 no-store；若想「总是最新又保留后退/前进缓存」，用 no-cache 更合适。
L1 概念辨析共享缓存里出现了一份 Alice 的个性化页面，Bob 也取到了它。请回答：① 根因是什么指令缺失？② 为什么 Vary: Cookie 不是正确修法？③ 正确修法是什么？
提示

区分「按身份分键」与「禁止共享存储」两种思路，谁才能真正阻止泄露。

完整解答
① 根因是缺少 private：个性化响应被存进了共享缓存，其他用户按相同 URL 命中后即泄露。MDN 说得很清楚，个性化内容只应存进私有缓存，必须显式指定 private；而 cookie 的存在本身不代表响应私有。② Vary: Cookie 只是把 cookie 值编进缓存键，共享缓存照样会为每个用户存一份副本，既占空间又留下泄露面，它没有「禁止共享存储」的语义。③ 正确修法是用 Cache-Control: private，直接禁止共享缓存存储该响应；若同时要求总是最新，用 no-cache, private。若数据敏感还要禁止一切存储，加 no-store。
L2 手算推导一份响应首部为 Date: Tue, 22 Feb 2022 22:22:22 GMT、Cache-Control: max-age=604800、Age: 86400。请手算：① 绝对过期时刻；② 客户端收到时剩余有效秒数与天数；③ 写出当前是否新鲜的判定式。要求逐步不跳。
提示

过期时刻用 Date 加 max-age；剩余用 max-age 减 Age；注意 2 月只有 28 天。

完整解答
① max-age=604800 秒 = 604800÷86400 = 7 天。过期时刻 = Date + 7 天 = 2022-02-22 22:22:22 + 7 天。2 月只有 28 天：22 + 7 = 29 超出 28，跨月得 3 月 1 日（2022 非闰年），故过期时刻 = 2022-03-01 22:22:22 GMT。② 剩余有效时间 = max-age − Age = 604800 − 86400 = 518400 秒；518400 ÷ 86400 = 6 天。③ 判定式：age < freshness_lifetime → 新鲜；age ≥ freshness_lifetime → 过期。代入：86400 < 604800 成立，故当前新鲜。校验：再过 518400 秒后 age = 86400 + 518400 = 604800，恰等于 max-age，落入过期分支，与①的 3 月 1 日 22:22:22 一致。注意相等时算过期，不能算新鲜。
L2 手算推导缓存中已有两条记录：键① (/app.js, Accept-Encoding=gzip, br) → br 版本，键② (/app.js, Accept-Encoding=identity) → 未压缩版本。源站声明了 Vary: Accept-Encoding。现有三个请求：甲 Accept-Encoding: gzip, br；乙 Accept-Encoding: identity；丙 Accept-Encoding: br（与甲的取值字符串不同）。请逐一判定命中哪条键、返回什么，并说明若源站漏写 Vary 会怎样。
提示

Vary 参与键的是请求首部的「值」，按值精确匹配；再想漏写时键会退化成什么。

完整解答
Vary: Accept-Encoding 让键 = URL + 该首部的值。甲的值 gzip, br 与键①完全一致 → 命中键①，返回 br 版本。乙的值 identity 与键②一致 → 命中键②，返回未压缩版本。丙的值 br 与键①的 gzip, br 字符串不同，也不等于键② → 两条都不命中，回源；源站按其支持 br 返回 br 版本，缓存新建键 (/app.js, Accept-Encoding=br)。这说明 Vary 按值的精确字符串匹配，变体越多键越多、命中率越低。若源站漏写 Vary，缓存退化为仅按 /app.js 建键，三条请求全被视为同一个键：谁先请求就把谁的版本存成唯一副本，随后 identity 客户端可能收到 br 字节，解码失败、脚本瘫痪——这就是 5.4 节的故障链。
L3 建模应用一个站点有三类资源：① 文件名带内容散列的 JS/CSS；② 全站共用的主资源 HTML；③ 登录后的账户接口（返回余额，敏感）。请为三者各给出一套响应首部组合，说明每条指令的理由，并指出哪类该进 CDN、哪类绝不能进共享缓存。
提示

先问「内容与什么绑定、会不会变、是否因身份而异」，再决定存不存、存多久、验不验。

完整解答
① 带散列的静态资源：Cache-Control: public, max-age=31536000, immutable，并附 ETag、Last-Modified、带 charset 的 Content-Type。理由：URL 随内容散列变化、内容永不改变，故长 max-age 缓存一年；public 允许 CDN 存储；immutable 免掉刷新验证。最适合进 CDN，尽快把字节推到边缘。
② 主资源 HTML：Cache-Control: no-cache，附 ETag 与 Last-Modified；若 HTML 因登录而个性化，改为 no-cache, private。理由：URL 不能做缓存破坏，必须每次验证以免用户看到旧版；no-cache 保证回源确认，ETag/Last-Modified 让未变更时返回 304 省主体；private 阻止个性化 HTML 进共享缓存。主资源通常由浏览器私有缓存持有，CDN 若要缓存需配合主动清除。
③ 账户接口：Cache-Control: no-store, private，可加 Pragma: no-cache；Vary: Accept-Encoding 仅用于压缩协商。理由：内容随身份变化且敏感，no-store 禁止任何缓存留存，private 兜底阻止共享缓存意外保存，绝不进 CDN 或任何共享缓存；Vary 不为身份隔离，只保证压缩版本分键正确。
三者串起同一套判断：先看内容绑定什么，再定首部——随 URL 变且不变→久存；随版本变→验证；随身份变且敏感→别存。
