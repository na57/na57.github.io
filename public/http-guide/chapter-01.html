1.1HTTP 不负责把字节送到，它负责说清这次事务是什么意思

先别背协议格式。设想一个最朴素的问题：浏览器和服务器之间已经能用 TCP 收发字节了，为什么还要在中间再插一层 HTTP（Hypertext Transfer Protocol，超文本传输协议）？

MDN 对 HTTP 的定义里有两个关键词：客户端—服务器协议和获取资源。但这两个词都预设了一件事——双方对「这次交互是什么意思」有共同理解。TCP 恰恰不提供这种理解。它只承诺把字节流按序、不丢、不重复地送到对端，至于这些字节是一条请求、一张图片还是一段乱写的文本，TCP 一个字也不关心。

把问题具体化。假如没有 HTTP，客户端发过去 GET /index.html 和发过去一整个 JPEG 文件，在 TCP 眼里是同一种东西：一串长度不定的字节。服务器因此答不出下面这些决定性的问题：

服务器必须回答的问题TCP 能不能回答实际由谁回答
你要的是哪一份资源？不能，只有字节流请求目标（URL 的路径部分）
你是想「读」还是想「改」？不能方法：GET / POST / PUT…
事情办成了没有？没成是谁的锅？不能状态码：2xx / 4xx / 5xx
这段字节是 HTML、JSON 还是 JPEG？不能Content-Type 首部
主体到哪儿结束？不能，字节流没有天然消息边界Content-Length 或分块编码
你用的是哪个版本的语法？不能版本字段：HTTP/1.1 等

这张表给出了本讲的第一个结论：HTTP 是在可靠字节流之上，用报文补上的一套语义约定。MDN 把这套约定拆成三个基本对象——资源（resource）、消息（message）与会话（session）。本讲把它们摆上桌面，后面 11 讲逐一展开。

💡 关键一跃

HTTP 不是「传网页的协议」，而是「在客户端与服务器之间约定一次事务语义」的协议。传的可以是 HTML、图片、API 返回的 JSON、一段视频，甚至一次远程过程调用；变的是承载的内容，不变的是「请求—响应」这个事务模型。MDN 把这些统称为资源与表示，第 3 讲会专门拆开这对概念。

⚠️ 常见误区

「HTTP 负责把数据安全可靠地送到」——错，而且错在三个层次。可靠性由 TCP（或 HTTP/3 的 QUIC）负责；机密性与完整性由 TLS 负责；HTTP 只负责说清楚这次事务是什么意思。把三层的职责混在一起，就会得出「HTTPS 是一种新的 HTTP 协议」这类错误结论——HTTPS 只是 HTTP over TLS，语义完全一样。

1.2一次典型会话的三阶段：连接、请求与等待、服务器应答

上一节把 HTTP 定位成「语义层」，但语义必须挂在一个具体的过程上。MDN 的《典型的 HTTP 会话》把这个过程分成三个阶段：客户端建立连接、客户端发送请求并等待应答、服务器处理请求并返回响应。注意 MDN 是按教学顺序分的——连接关闭或复用发生在第三阶段之后，属于连接管理的话题，第 4 讲展开。

阶段一：建立连接。在客户端—服务器模型里，通信必须由客户端发起。用户在地址栏输入 https://example.com/index.html 之后，浏览器先把域名交给 DNS 解析成 IP 地址，再与服务器的 443 端口建立 TCP 连接；如果是 HTTPS，还要在 TCP 之上完成 TLS 握手，确认对方身份并协商出会话密钥。这一步里 HTTP 还没出场——它只是这场通信的「乘客」，TCP 与 TLS 才是「车」和「铅封」。

阶段二：客户端发送请求并等待。连接就绪后，浏览器把用户意图编码成一条请求报文发出。一个最小的 GET 请求长这样：

GET /index.html HTTP/1.1 Host: example.com User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) Accept: text/html,application/xhtml+xml Accept-Encoding: gzip, deflate, br （空行：首部到此结束，本请求没有主体）
一条典型的浏览器请求：起始行给出方法、目标与版本；首部行补充说明身份、可接受的类型与压缩算法；空行标志首部结束。

这里有一个新手极易忽略的细节：Host 首部在 HTTP/1.1 里是强制的。因为一台物理服务器可能同时托管几百个域名，TCP 连接只告诉它「有人连到了 443 端口」，只有 Host 才能告诉它「这个请求是给哪个站点的」。MDN 特别强调每个请求都必须携带 Host，正是这个原因。缺了它，服务器无法决定该返回哪个站点的内容。

阶段三：服务器处理并返回响应。服务器解析请求，找到资源，按约定格式回一条响应：

HTTP/1.1 200 OK Date: Mon, 16 Nov 2026 00:30:00 GMT Content-Type: text/html; charset=utf-8 Content-Length: 74 Cache-Control: max-age=60 <!doctype html><html lang="zh-CN"><body>你好，HTTP</body></html>
响应同样分四段：状态行、首部、空行、主体。200 表示请求成功，Content-Type 告诉浏览器按 UTF-8 编码的 HTML 来解析这 74 个字节。

浏览器收到响应后并不是结束了。一个网页通常包含 CSS、JS、图片等几十个子资源，浏览器会在连接上继续发请求（或建立少量并行连接）把它们取回来，最后才渲染出完整页面。MDN 把这整个过程称为一次会话：它不是「一次请求—一次响应」，而是从建立连接到取齐资源、连接关闭或复用的完整过程。第 4 讲会算清楚「重复建连」到底有多贵，以及持久连接和 HTTP/2 多路复用各自省掉了什么。

阶段谁发起这一层在做什么失败时用户看到什么
建立连接客户端DNS 解析、TCP 握手、必要时 TLS 握手「无法访问此网站」、连接超时、证书告警
客户端发送请求并等待客户端把意图编码成请求报文发出，阻塞等待应答页面转圈、请求 pending
服务器处理并返回响应服务器解析请求、定位资源、生成状态码与首部、写回主体4xx / 5xx 页面、空白页
✅ 判定规则

排查网络问题时，先按这三阶段定位：连接都建不起来，去看 DNS / TCP / TLS；连接好了但请求迟迟不返回，去看请求是否发出、服务器是否在等主体；返回了但页面不对，去看状态码与表示首部。三阶段对应三种完全不同的故障域，混着查会浪费大量时间。

⚠️ 常见误区

「一次 HTTP 会话 = 一次请求—响应」——错。网页往往要几十次请求—响应才组装完成；这些请求可能复用同一条连接，也可能走不同连接。把「事务」（一次请求加一次响应）和「会话」（完整过程）分开，才能理解第 4 讲的持久连接与第 5 讲的缓存命中。

1.3无状态是设计选择，不是缺陷：Web 应用靠额外的层记住你

上一节的会话过程里藏着一个容易被忽略的事实：第三阶段结束后，服务器对刚才那个客户端没有任何记忆。MDN 的措辞很直接——HTTP 是一种无状态（stateless）协议：服务器不会在两个请求之间保留关于客户端的信息。

这句话经常被误解。它说的不是「浏览器不记得你」，而是「协议本身不要求服务器记得」。每一次请求都是一条独立的、自包含的事务：服务器处理它只需要这一条报文里的信息，不需要知道这是不是同一个客户端的第几次请求。用两个请求做对比最清楚：

GET /cart HTTP/1.1 Host: shop.example User-Agent: DemoClient/1.0 HTTP/1.1 200 OK Set-Cookie: session=abc123; Path=/; HttpOnly Content-Length: 28 购物车是空的。
第一次请求：服务器在响应里用 Set-Cookie 发给客户端一个会话标识。协议并没有要求它记住这件事。
GET /cart HTTP/1.1 Host: shop.example User-Agent: DemoClient/1.0 Cookie: session=abc123 HTTP/1.1 200 OK Content-Length: 34 购物车里有 2 件商品。
第二次请求：客户端主动把标识带回来。服务器看到 Cookie 才知道「还是你」，从而恢复购物车状态。

请注意这两个请求的关系：是客户端把状态带回给服务器的，不是服务器自己记住的。这正是无状态协议的精髓——状态被显式地放在请求里传递，而不是隐含在服务器的连接记忆里。

MDN 指出，虽然 HTTP 本身无状态，但 cookie 的引入让「用无状态协议记录稳定状态」成为可能。除了 cookie，常见的状态承载方式还有三类：把会话标识写进 URL（MDN 称为胖 URL，fumbling URL，今天基本不再推荐）、在表单里放隐藏字段、以及用 Web Storage 在浏览器本地保存数据。它们都遵循同一个模式——状态在客户端，每次请求显式携带。第 7 讲会专门讲 cookie 的属性与安全边界。

无状态带来的好处对应的代价补上代价的机制
服务器不保存连接状态，横向扩容只需加机器每次请求都要重新携带身份信息cookie / Authorization 首部
请求失败后可以重试，不依赖「这条连接的历史」服务器无法凭连接判断用户是谁会话标识 + 服务端会话存储
中间代理、缓存可以自由转发和复用响应状态放在请求里，可能泄露到日志与 RefererHttpOnly / Secure / SameSite 等属性
协议实现简单，互操作成本低业务逻辑必须自己处理状态一致性应用层的会话与数据库设计
💡 关键一跃

「HTTP 无状态」和「Web 应用有会话」不但不矛盾，前者恰恰是后者的基础：因为协议不替你记状态，你才能自由选择把状态放在 cookie、token 还是服务端，也才能让任意一台服务器接手任意一次请求。MDN 把 cookie 称作「让无状态协议记录稳定状态」的机制，就是这个意思。

⚠️ 常见误区

「无状态 = 用户每次都要重新登录」——错。登录状态是通过在后续请求里携带 cookie 或 Bearer Token 恢复的；无状态说的是服务器不靠连接记忆，不是用户得反复输密码。反过来说，把会话标识塞进 URL 虽然能工作，但会出现在浏览器历史、服务器日志和 Referer 里，这是它能被弃用的根本原因。

1.4从 0.9 到 3：地基换了三次，事务语义一次没换

前三节建立了本讲的主线：会话三阶段承载请求—响应事务，而无状态让这套事务可以被任意中间层转发。但 HTTP 并不是一成不变的：从 HTTP/1.0 到 1.1、2、3，连接管理、代理与缓存的实现细节一直在变，而请求—响应模型、方法与状态码这套语义几乎没动——换的是地基，不是房子。MDN 的《HTTP 的发展》把这个演进过程讲得很清楚，值得逐个版本对照。

版本关键变化留下的问题今天的地位
HTTP/0.9（1991）只有一行 GET，无首部、无状态码，响应只能是 HTML无法表达类型、错误与复杂请求早已废弃，现代服务器默认关闭
HTTP/1.0（1996）引入首部、状态码、方法、版本号，可传任意类型资源每个事务都要新建连接仍见于老设备与嵌入式系统
HTTP/1.1（1997，1999 修订）持久连接、Host 首部、管道化、chunked 定界、缓存控制队头阻塞，首部重复且冗长至今仍大量在用，尤其 API 调用
HTTP/2（2015）二进制帧、多路复用、HPACK 首部压缩、优先级多条 stream 仍共享一条 TCP，丢包会拖累全部主流网站与 CDN 的标配
HTTP/3（2022）换用 QUIC over UDP，流之间独立，连接迁移中间设备对 UDP 的支持仍不齐浏览器与主流 CDN 已广泛支持

看这张表要抓住一条判据：方法、状态码、首部含义、URL、缓存语义，从 1.0 到 3 一直没有变。变的只是「这些语义怎么编码到线上」和「字节怎么在连接上跑」。同一个 GET /index.html，在三个版本里的待遇完全不同：

HTTP/1.1：一行纯文本起始行 + 一行行首部 GET /index.html HTTP/1.1 Host: example.com Accept: text/html HTTP/2：改成带编号的 HEADERS 帧，首部小写并加伪首部 HEADERS (stream=1, END_HEADERS) :method: GET :scheme: https :authority: example.com :path: /index.html accept: text/html HTTP/3：帧格式延续 HTTP/2，但承载在 QUIC 流上 QUIC stream 0 → HEADERS (:method GET, :path /index.html…)
三次换地基的对照：1.1 把语义写成可读文本；2 保留语义只换二进制编码；3 保留 2 的帧语义，把传输从 TCP 换成 QUIC。

这正是 HTTP/2 能大规模铺开的原因：它没有改变应用语义，浏览器和服务器只要换掉编码层，上层代码几乎不用动。MDN 在《HTTP 的发展》里也强调，HTTP/2 并没有废弃 HTTP/1.1 的方法与状态码，而是通过帧和流让它们传得更快。相比之下，当年试图同时重做语义与传输的 HTTP-NG 方案就因为要求全链路同时升级而失败——这条历史教训在第 11 讲讲协议升级时还会回来。

✅ 判定规则

遇到「新版本 HTTP 会不会让我的代码失效」这类问题，先问：变的是语义还是编码？HTTP/2 与 HTTP/3 只换编码与传输，GET 还是 GET，404 还是 404，缓存首部还是那几个。真正会改变你代码的是新增的语义（如 SameSite、CORS、CSP），它们与版本号无关。

⚠️ 常见误区

「升级到 HTTP/2 就要改造应用」——错。要改的是服务器与中间设备的配置，应用层语义不变。反过来也别以为「HTTP/1.1 已经过时」：它仍在大量 API 场景里工作良好，很多性能问题出在应用层而不是协议版本。版本是工具，不是信仰。

因为 HTTP/2 保留全部语义只换编码，两端与中间设备可以分别升级、协商使用；若语义和传输一起改，要求链路上所有节点同时升级，任何一个环节不支持就全链路失败。

1.5延伸：规范怎么写：MDN 的三阶段对应 RFC 的哪一段

MDN 是面向开发者的工作文档——它按「你需要知道什么」组织，刻意省略了规范性细节。当你需要写客户端、实现服务器或者判定一个边界行为时，就得去看 IETF 的规范。2022 年 6 月，IETF 把 HTTP 规范重新整理成 RFC 9110 系列：RFC 9110 定义与版本无关的语义，RFC 9111 定义缓存，RFC 9112 / 9113 / 9114 分别定义 HTTP/1.1、HTTP/2、HTTP/3 的线上格式。这套文档一次性作废了 RFC 2616、RFC 7230–7235 和 RFC 7540。

MDN 的说法RFC 怎么写为什么值得知道
一次会话分三个阶段：建立连接、发请求并等待、服务器返回响应RFC 9110 把事务建模为请求与响应消息，不规定连接如何建立；连接模型分别写在 RFC 9112 §2、RFC 9113、RFC 9114 中MDN 按教学顺序讲，RFC 按实现责任分文件。实现客户端要同时读 9110 与你用的那个版本文档，只读一本不够
HTTP 是无状态协议RFC 9110 §3.1 明确写：HTTP is a stateless request/response protocol；cookie 由独立的 RFC 6265 定义「无状态」是核心规范的性质，而「记住用户」是扩展规范的能力。混淆二者会做出把会话状态塞进核心协议的错设计
请求与响应由起始行、首部、空行、主体组成这套四段结构只属于 RFC 9112 的 HTTP/1.1 语法；RFC 9113/9114 定义的是帧与流，没有「起始行」这个概念抓包看到 HTTP/2 的 HEADERS 帧时不要去找起始行；报文四段是 1.x 的实现，不是 HTTP 的定义
每个 HTTP/1.1 请求都必须带 HostRFC 9112 §3.2 要求客户端在所有 HTTP/1.1 请求中发送 Host；RFC 9110 §7.2 定义其语义与「权威」判断缺失 Host 在 1.1 下应返回 400，这是规范要求而不是某个服务器的偏好；写反向代理时必须正确处理它
资源由 URL 标识，同一资源可以有不同表示RFC 9110 §7.1 讲 URI 引用，通用语法在 RFC 3986；表示与内容协商在 RFC 9110 §12写重定向和相对链接解析要按 RFC 3986 的算法，不能靠字符串拼接；这正是第 12 讲重定向的规范基础

这张表不是让你去啃 RFC 原文，而是给你一个判断依据：当 MDN 说「通常」「建议」而你需要一个确定的对错时，去 RFC 找规范性措辞（RFC 里 MUST / SHOULD / MAY 是有严格区别的）。本讲义后续每一讲的末尾都会做这件事——把 MDN 的工程口径与 RFC 的规范口径对齐，这正是这套讲义与普通教程的区别。

💡 关键一跃

RFC 9110 系列最重要的结构变化是把语义与线上格式彻底分开。「404 是什么意思」只在 RFC 9110 里写一次，HTTP/1.1、/2、/3 都引用它；「404 这段字节怎么编码」才分别写在三个版本文档里。理解这个二分，你就能判断任何一条新知识属于哪一层，不会把版本差异错当成语义差异。

⚠️ 常见误区

不要拿旧文章里的 RFC 编号当现行规范。RFC 2616、RFC 7230–7235、RFC 7540 都已被 2022 年的 RFC 9110 系列取代；网上大量教程仍在引用旧编号，并不意味着它们还有效。查规范先看 httpwg.org/specs 的现行列表，再读具体章节。

HTTP（Hypertext Transfer Protocol）
点击翻面 →
定义在字节流之上约定请求/响应事务语义的应用层协议，采用客户端—服务器模型。

直觉TCP 是货车，HTTP 是货单：写清收件人、动作和回执。

概念卡 2
资源与表示（Resource / Representation）
点击翻面 →
定义资源是被命名的事物，表示是某次响应实际返回的字节及其类型。
解决问题同一个 URL 按客户端能力返回 HTML 或 JSON 时，语义上仍是同一份资源。
直觉资源是一道菜，表示是摆在盘里的那一版。

概念卡 3
会话与事务（Session / Transaction）
点击翻面 →
定义事务 = 一条请求 + 一条响应；会话 = 从建立连接到取齐资源、连接关闭或复用的完整过程。
解决问题把「一次浏览」拆成可测量的单位，便于定位故障与优化性能。
直觉事务是一通电话里的一次问答，会话是整通电话。
误区以为一次会话只有一次请求；网页通常有几十次。
何时用第 4 讲连接复用，第 5 讲缓存命中，第 12 讲重定向跳数。
概念卡 4
无状态（Stateless）
点击翻面 →
定义服务器不保留两次请求之间的信息，每条请求自包含。
解决问题让任意服务器接手任意请求，使横向扩展与失败重试变得简单。
直觉每次对话都重新自我介绍，而不是指望对方记得你。
误区以为无状态等于用户不能登录；状态由 cookie/token 显式携带。

概念卡 5
Host 首部
点击翻面 →
定义请求首部，给出目标主机的域名与可选端口，HTTP/1.1 强制要求。
解决问题一台服务器托管多个站点时，靠它决定把请求交给哪个站点。
直觉TCP 把你送到写字楼，Host 告诉前台你找哪家公司。
误区以为 Host 可从 URL 里省略；缺了它在 1.1 下应返回 400。

语义与线上格式（Semantics / Wire Format）
点击翻面 →
定义语义是方法与状态码等含义，线上格式是把它们编码成字节的方式。
解决问题让 HTTP/1.1、/2、/3 共用同一套语义，升级传输不必重写应用。

✍️分层习题：先自己写，再点开核对

L1 概念辨析有人说：「HTTPS 比 HTTP 更可靠，因为它会重传丢失的数据包。」这句话错在哪？分别指出可靠性、机密性、事务语义各由谁负责。
提示

把 TCP / TLS / HTTP 三层拆开，逐层问「它承诺了什么」。

完整解答
可靠性（丢包重传、按序、去重）由 TCP 提供；HTTP/3 换成 QUIC，但可靠性仍由传输层负责。机密性与完整性由 TLS 提供。请求/响应的语义由 HTTP 提供。HTTPS 只是 HTTP over TLS，既不额外重传，也不改变方法、状态码的含义。这句话把三层的职责压进一个缩写，所以三个判断全错。
L1 概念辨析判断下列说法的正误并说明理由：①「HTTP 无状态，所以浏览器不记得我访问过哪些页面」；②「一条 HTTP 报文就是一次 HTTP 会话」；③「HTTP/2 已经不用 GET 方法了』」。
提示

逐句找出被混淆的那对概念：无状态 vs 浏览器记忆、事务 vs 会话、语义 vs 线上格式。

完整解答
① 错。无状态说的是服务器不保留请求之间的信息；浏览器的历史记录、cookie 与 Web Storage 都是浏览器本地的记忆，与协议性质无关。② 错。一条请求加一条响应是事务；一次会话包含建立连接、多次事务和连接收尾，一个网页通常有几十次事务。③ 错。HTTP/2 只把首部编码成二进制帧并加伪首部 :method: GET，GET 的语义原样保留；换的是线上格式，不是语义。
L2 手算推导给出下面这条请求，逐行解析并回答四个问题：① 请求目标是什么？② 客户端声明能接受哪些表示？③ 这条请求为什么必须带 Host？④ 若把 Host 删掉，在 HTTP/1.1 下服务器应当如何响应？

GET /docs/guide.html HTTP/1.1
Host: example.org
Accept: text/html,application/xhtml+xml
Accept-Encoding: gzip, br
提示

按「起始行 → 各首部 → 空行」顺序读；再想一台服务器托管多个站点时靠什么区分。

完整解答
① 请求目标是 /docs/guide.html，这是 origin-form 形式，只带路径不含域名。② Accept 声明能接受 text/html 与 application/xhtml+xml；Accept-Encoding 另声明能解码 gzip 与 Brotli 压缩，两者是不同维度——前者说「什么类型」，后者说「什么编码」。③ TCP 连接只给出 IP 与端口，无法区分同一台机器上的多个虚拟主机；Host 告诉服务器这个请求属于哪个站点，HTTP/1.1 因此强制要求携带。④ 缺少 Host 时服务器无法确定目标站点，按 RFC 9112 的要求应返回 400 Bad Request；这不是可选优化，而是协议合规性要求。
L2 手算推导某用户先请求 GET /login，服务器在响应里返回 Set-Cookie: sid=xyz; HttpOnly；随后他请求 GET /cart，但请求里没有 Cookie 首部。请分步推演：服务器能不能知道这是同一个用户？如果想让他保持登录，正确的机制是什么？分别说明「状态存在哪」与「谁负责带回来」。
提示

回到第 1.3 节的两条报文对比，逐条问「服务器凭什么判断」。

完整解答
第一步：Set-Cookie 只是响应首部，它把标识交给客户端，并没有要求服务器自己保存连接状态。第二步：第二条请求没有 Cookie 首部，服务器收到的信息只有方法、路径与 Host，无法与第一次请求关联，因此不知道这是同一个用户。第三步：正确机制是客户端在后续请求里主动带回 Cookie: sid=xyz，服务器再据此查服务端会话存储恢复登录态。结论：会话标识存在客户端（cookie 里），由客户端在每次请求中显式携带；服务器只负责校验标识并查找对应的会话数据。这正是无状态协议维持状态的通用模式。
L3 建模应用你要为一个读多写少的内容站点设计 HTTP 层：资源用 /api/articles/{id} 定位，同一篇文章可以返回 HTML 页面或 JSON 数据，还要支持登录用户看到草稿。请用本讲的概念回答：① 哪部分是资源，哪部分是表示？② 哪些机制让你能把静态副本放到离用户更近的 CDN 上？③ 为什么无状态特性有助于横向扩容？给出至少三条具体设计决策。
提示

把「资源 / 表示」「客户端携带状态」「语义与传输分离」三个概念分别套到设计上。

完整解答
① /api/articles/123 是资源标识；返回的 HTML 或 JSON 是它的两种表示，由 Content-Type 区分，语义上指向同一篇文章。② 能放 CDN 的前提是响应可复用：给公开的已发布文章设置明确的 Cache-Control（第 5 讲），并把「返回 HTML 还是 JSON」这个差异写进 Vary 或改用不同 URL，避免把一种表示发给要另一种表示的客户端；草稿属于个性化内容，应标记 private 或 no-store，不进共享缓存。③ 因为服务器不依赖连接历史，任意一台应用服务器都能处理任意请求，扩容只需增加实例并把会话状态放在 cookie/token 或共享存储里；请求失败也能安全重试 GET。三条决策示例：URL 只标识资源不编码用户身份；认证信息放 Authorization 或 cookie 而非 URL；缓存策略按「公开内容 / 个性化内容」分组配置，不搞一套全局规则。

TCP 已保证可靠传输，HTTP 主要补上的是哪一类信息？
  • A. 丢包重传与流量控制

  • C. 客户端发送 Cookie
  • D. 浏览器渲染页面

  • B. 浏览器不保存任何历史记录
  • C. 每次请求都必须重新建立 TCP 连接
  • D. 服务器不能返回个性化内容

自测 4

  • A. 废弃了 GET 与 POST 方法
  • B. 重新定义了 404 状态码的含义
  • C. 取消了 Host 首部
  • D. 用二进制帧与多路复用取代文本行与串行请求
解析：D 对。HTTP/2 保留方法、状态码与首部语义，只更换线上编码与连接模型。A、B、C 都是把「换地基」误读成「换语义」的典型错误；事实上 :method 伪首部仍然表达 GET，Host 由 :authority 承担。

同一个 URL 有时返回 HTML、有时返回 JSON，这说明？
