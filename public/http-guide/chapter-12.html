12.1服务器用一条 3xx 加 Location 把请求改道，用户几乎察觉不到

第 11 讲把代理、隧道与协议升级讲完，客户端与源站之间的中间层似乎已经清点完毕。其实还差最后一种、也是日常最常见的一种干预：服务器不在原地交出资源，而是回一条特殊响应，请客户端「去另一个地址取」。这就是本讲的主角——HTTP 重定向（HTTP Redirect）。它恰好是全书主线的收束处：一次请求从建立连接、交换报文，到连接复用或结束，中途可能被重定向改写去向，但最终仍要落到一个能返回 2xx 的资源上，这条 journey 才算闭合。

先看为什么需要它。假设站点重构，文章从 https://www.example.com/blog/post-42 搬到了 https://www.example.com/articles/42。站内链接你可以逐个改，但用户的书签、搜索引擎收录的条目、别的网站引用你的外链，你一个也改不了。旧地址若直接回 404，用户以为站点坏了，搜索引擎也会把这条收录慢慢降级。更好的做法是让旧地址回一条响应，意思是「这东西搬家了，请去新地址拿」。MDN 把这类技术称为 URL 重定向（URL Redirect，也叫 URL 转发），而 HTTP 为它准备了一整类专门的响应。

MDN 的原理描述很简洁：重定向由服务器向请求发送一条特殊的重定向响应触发，这条响应包含以 3 开头的状态码（Status Code），以及一个 Location 首部（Location Header），其中保存着重定向的目标 URL。浏览器接收到重定向时，会立刻加载 Location 中提供的新 URL。除了额外往返带来的一小部分性能损失之外，重定向操作对用户是不可见的——地址栏最后显示的是新地址，用户只会觉得页面「慢了一点点」。

把三个术语钉牢：3xx 是重定向状态码所在的类别；状态码是响应起始行里那个三位数；Location 首部是携带目标地址的首部。一条最小的重定向响应长这样：

HTTP/1.1 301 Moved Permanently Date: Mon, 16 Nov 2026 00:30:00 GMT Location: https://www.example.com/articles/42 Content-Length: 0 （空行：首部结束；这类响应通常没有主体）
一条最小的重定向响应：状态行给出 301 与原因短语，Location 告诉客户端新地址。浏览器不会把这条响应渲染给用户，而是直接朝新地址再发一次请求。

注意这条响应和一条 200 响应的差别：它没有可渲染的主体，Location 才是重点。客户端拿到它之后的行为，等于把用户原本的请求「照原样、换个地址」再发一遍——方法、主体、大部分首部都带过去，只是请求目标换成 Location 指向的 URL。这一步叫「自动重定向」，由浏览器或 HTTP 客户端库完成，不需要用户点任何东西。

MDN 把重定向映射划分为三个类别：永久重定向、临时重定向与特殊重定向。这个分类不是学术偏好，而是直接决定状态码怎么选、以及客户端会不会把它记下来：

Location 的值并不总是完整 URL。它可以是相对 URL（Relative URL），客户端要以当前请求的 URL 为基准把它解析成绝对地址。MDN 在「HTTP 的发展」与 URI 相关文档里都强调，这件事要按标准的引用解析算法做，而不是简单字符串拼接。下面做一次完整手算。

给定基准请求 URL：https://www.example.com/docs/guide/intro.html。先把它拆成标准组成部分：scheme = https，authority = www.example.com，path = /docs/guide/intro.html，query = 空，fragment = 空。解析相对引用有四条判据：① 若引用带 scheme，直接整体采用；② 否则若引用以 // 开头带 authority，沿用基准 scheme、采用引用的 authority 与 path；③ 否则若引用 path 以 / 开头，直接替换整个 path；④ 否则把「基准 path 去掉最后一段」作为目录，拼上引用 path，再消除 . 与 .. 段。query 与 fragment 单独处理：引用带了就用引用的，没带则 query 在引用 path 为空时沿用基准、fragment 一律不沿用基准。

基准：https://www.example.com/docs/guide/intro.html Location: /new/guide.html → https://www.example.com/new/guide.html Location: ./next.html → https://www.example.com/docs/guide/next.html Location: ../index.html → https://www.example.com/docs/index.html Location: ?page=2 → https://www.example.com/docs/guide/intro.html?page=2 Location: #section-3 → https://www.example.com/docs/guide/intro.html#section-3 Location: //cdn.example.com/a.css → https://cdn.example.com/a.css
相对 Location 的解析手算：逐一以基准 URL 各组成部分为参照，套用「scheme → authority → 绝对 path → 相对 path → query/fragment」的优先级，得到右侧绝对目标。

逐条说明推导。第一条 /new/guide.html 以斜杠开头，属判据③，直接替换 path，scheme 与 authority 不变，得到 https://www.example.com/new/guide.html。第二条 ./next.html 是相对路径，基准 path 去掉最后一段 intro.html 得目录 /docs/guide/，拼上 next.html 并消除 . 段，得 /docs/guide/next.html。第三条 ../index.html 同理，目录 /docs/guide/ 拼上 ../index.html 后消掉 guide/..，回退一级得 /docs/index.html。第四条只带 query，引用 path 为空，于是 path 沿用基准、query 改为 page=2，得到同一个页面带新查询串。第五条只带 fragment，其余全部沿用基准，仅追加 #section-3。第六条以 // 开头，属判据②，沿用基准 scheme https、authority 换成 cdn.example.com，于是协议跟着基准走——这也是「协议相对 URL」的历史用法。

HTTP 不是定义重定向的唯一方式。MDN 列出另外两种：HTML 的 <meta> 元素把 http-equiv 设为 refresh，例如 <meta http-equiv="Refresh" content="0; URL=http://example.com/" />，content 开头的数字是等待秒数，建议设为 0 以照顾无障碍；以及 JavaScript 设置 window.location = "https://example.com/";。当三种方式同时出现，MDN 给出的优先级是：HTTP 重定向永远最先触发，甚至页面还没传输就已经存在；HTML 重定向在没有 HTTP 重定向时才触发；JavaScript 重定向是最后手段，且只在客户端开启脚本时生效。

💡 关键一跃

把重定向想成「服务器给请求换了个收件地址，然后客户端重投一次」，很多细节就顺了：既然是重投，就存在「这次重投还算不算原来的方法」这个天然问题——这正是 307/308 要回答的。既然要多一次投递，就存在性能开销与「投错成环」的风险。MDN 反复劝「优先用 HTTP 重定向、尽量少用、能改内部链接就别做内部重定向」，本质都是围绕这两件事。先记住「换地址 + 重投」这个心像，后面三节都从它长出来。

⚠️ 常见误区

「在 HTTP 层做了重定向，再在页面里加一条 <meta> 或 JS 跳转做双保险」——这是制造无限循环的常见手法。MDN 明确提醒：如果开发者改了 HTTP 重定向却忘了改 HTML 里的重定向，二者就会不一致，结果不是无限循环就是别的噩梦。因为 HTTP 重定向先触发，meta 跳转型同虚设；一旦两边目标不同且互相指回，浏览器就会在两个地址间反复弹跳。正确做法是只在 HTTP 层做重定向，并且只做一处。

12.2永久与临时不是措辞之分：它决定缓存、SEO 和「能不能反悔」

上一节建立了「换地址 + 重投」的心像，也留下一个关键问题：服务器凭什么告诉客户端「这次搬家是永久的还是临时的」？答案就在状态码里。MDN 把 301 / 308 归入永久重定向，把 302 / 303 / 307 归入临时重定向。这一字之差不是学术分类，而是直接决定了三件要命的事：浏览器与代理会不会把这条跳转记下来、搜索引擎会不会更新收录、以及你哪天改主意时能不能反悔。先看 MDN 对这两类的原始分工。

永久重定向表示原 URL 不应再被使用，应选用新 URL 替换它。MDN 特别指出：搜索引擎机器人、RSS 阅读器以及其他爬虫会据此更新资源原始的 URL。换句话说，永久重定向是一次「对外发布变更声明」——你等于告诉全世界「旧地址作废了，请改记新地址」。临时重定向则说资源只是暂时无法从标准地址访问，但可以从别处访问；搜索引擎和其他爬虫不会记录这个临时的新 URL。它是一次「暂时借用一下别处」的说明，不改变资源的正式身份。

维度永久（301 / 308）临时（302 / 303 / 307）
给爬虫的信号旧地址作废，更新收录到新地址不记录新地址，保留旧地址收录
给缓存的信号可被长期缓存，浏览器可能记住跳转默认不缓存，每次重新问服务器
能否反悔难：旧跳转已被缓存与收录，回退代价高易：改回配置后一般立即生效
典型场景站点重构、域名永久迁移、强制 HTTPS维护停机、进度页、POST 提交后跳转

MDN 列出几类典型应用场景，正好用来体会「永久 / 临时」的选择。域名别称：站点在 www.example.com，希望 example.com 也能访问，于是从后者重定向到前者；公司改名后希望旧域名仍能把人带到新域名；把 http:// 的请求重定向到 https:// 版本。这些都是长期决定，通常用永久重定向。保持链接有效：重构时外部链接指向旧地址，你无法改别人的站点，于是建立旧到新的重定向映射保住流量与 SEO；但 MDN 特意加了一句备注——这项技术虽也能用于内部链接，却应尽量避免，因为重定向会带来不小的性能开销，内部链接能直接改就直接改。不安全请求与耗时请求的临时响应：这两类都用 303，放到 12.3 节连同方法改写一起讲。

现在看一个真实的故障链——永久重定向被长期缓存之后，一次误配会怎样在「修好之后」继续作祟。这也是 course 里要求你特别记住的长期影响。

第 1 步，误配发生。运维把活动页 https://old.example.com/sale 配成永久重定向，指向 https://new.example.com/sale：

GET /sale HTTP/1.1 Host: old.example.com HTTP/1.1 301 Moved Permanently Date: Mon, 16 Nov 2026 00:30:00 GMT Location: https://new.example.com/sale Cache-Control: max-age=31536000 Content-Length: 0
误配的永久重定向：本意只是临时把流量导到新活动页，却用了 301 并给出长达一年的缓存时间。

第 2 步，浏览器把它记下来。301 属于默认可缓存的响应（RFC 9111 的口径下一节详述），加上显式的 max-age=31536000，浏览器会把「/sale → new.example.com/sale」这条映射存进缓存，有效期一年。此后用户再次输入旧地址，浏览器在发出任何请求之前就从缓存里命中这条跳转，直接去新地址——旧地址的服务器根本收不到请求，也就没有机会纠正它。

第 3 步，问题被发现并「修好」。运维意识到活动做完了，把 old.example.com/sale 改回正常的 200 页面，甚至把 Location 撤掉。但那些已经缓存了 301 的浏览器毫不知情：它们仍旧从本地缓存里取出旧跳转，跳到可能已经下线的 new.example.com/sale，看到 404。用户向客服抱怨「旧地址打不开」，运维抓日志却发现旧地址一条请求都没有——因为请求被浏览器缓存拦在了半路。这就是永久重定向最阴险的地方：修复发生在服务端，症状却留在客户端。

第 4 步，清除与预防。清除手段按作用域从小到大：用户可在开发者工具 Network 面板勾选 Disable cache 后重试，或清除该站点的缓存与站点数据；共享缓存（CDN、代理）一侧要在控制台主动 purge 对应 URL；但浏览器里那条 301 若没有可靠过期时间，用户自己往往清不干净，最后一招是换一个全新 URL（例如给路径加版本号 /sale-v2）彻底绕开旧缓存。预防手段更值得记住：只在「确定永不回头」时才发永久重定向；拿不准先用 302 观察一段时间，稳定后再升级为 301/308；给重定向设置你真正想要的 Cache-Control（而不是顺手写一年）；上线前用 curl -I 核对返回的到底是什么状态码。

✅ 判定规则

选 301/308 还是 302/303/307，用一句话判断：「这个新地址，我愿不愿意让搜索引擎和浏览器记一年？」愿意（永久迁移、强制 HTTPS、重构后的固定新路径）才用永久；只是维护、活动、进度页、POST 后跳转，一律临时。拿不准就当临时处理——临时发错了顶多少一次往返，永久发错了要让缓存和收录慢慢消化。

⚠️ 常见误区

「我把服务端的 301 改回 302 了，用户马上就会走新配置」——错。缓存了旧 301 的浏览器不会再问服务器，你的修改对它们完全无效。另一个误区是把 MDN 说的「爬虫会更新 URL」当成即时生效——收录更新需要时间，而错误的永久重定向一旦被收录，纠正周期以周计。永久这两个字，签下去就要负责到底。

12.3POST 被重定向时方法会不会变：301/302/303 与 307/308 的分水岭

上一节讲清了「永久 vs 临时」这条维度，但还留着一个更危险的维度没碰：重定向之后，原来那个 POST 还是不是 POST？这看似细节，实则是线上事故的高发地——一个把表单 POST 重定向成 GET 的配置，轻则让参数跑到 URL 里，重则让「下单」「转账」被重复提交。 MDN 在永久与临时两族里都反复提到同一句耐人寻味的话：「规范无意使方法发生改变，但在实际应用中用户代理会更改其方法」，并说明 308 与 307 正是为了消除这种歧义才被创建。这一节把这句话彻底拆开。

先把背景钉牢。安全方法（Safe Method）指不修改服务器状态的方法，如 GET、HEAD；POST、PUT、DELETE 则是不安全的，会改变服务器状态。MDN 在「不安全请求的临时响应」里提醒：你通常不希望用户重复发送 PUT、POST、DELETE——若服务器直接返回正常页面，用户点一下刷新就可能把同一个操作再提交一次。重定向正好被用来打断这个链条：提交成功后回一个 303，让浏览器改为 GET 去取结果页，刷新时只会刷新那个 GET 页面，不会重投表单。这就是著名的「提交后重定向」（PRG，Post/Redirect/Get）模式。

问题在于：并非所有重定向都会把 POST 改成 GET。到底改不改，取决于状态码。下面给出完整的判定表，基准请求统一为 POST /submit，主体为 name=alice&city=sz。

把四种重投结果放在一起看，差别一目了然：301/302 下浏览器「通常改成 GET」（规范本意不改，但历史实现改了，属于不可靠行为）；303 下「按规范改成 GET」（可靠，主体丢失是有意的）；307/308 下「严格保持 POST 与主体」（可靠）。MDN 说 303 用于 PUT 或 POST 请求完成之后重定向、防止刷新导致操作重复触发，又说 307 在站点支持非 GET 方法的链接或操作时优于 302——这两句话合起来，就是选择指南。

还有一个常被问到的边界：304 Not Modified 算不算重定向？MDN 把它归入「特殊重定向」，但它并不让客户端去另一个地址，而是让页面跳到本地缓存副本（可能已过时），表示缓存的响应仍然是新的、可以使用。它是第 6 讲条件请求的产物，与 Location 无关。300 Multiple Choice 则是「手动重定向」：服务器把可选链接以 HTML 主体列出来让用户自己选，并鼓励在 Link 首部里放机器可读的 rel=alternate。特殊这一族只是被归在同一状态码段，并不遵循「Location + 重投」那套流程。

💡 关键一跃

方法改写问题的本质，是「重投一次」时客户端要决定：这次是照抄原请求，还是降级成 GET 取页面？MDN 用两个新增状态码把模糊地带钉死——要保方法就用 307/308，要改 GET 就用 303，而 301/302 因为历史实现不统一，只能算「赌浏览器心情」。记住这条，你就不会在下单接口上误用 302 而让客户的 POST 变成一次无害却无效的 GET。

⚠️ 常见误区

「重定向反正都是跳到新页面，方法无所谓」——这是最贵的一个误解。给接收 POST 的支付回调、表单提交、文件上传配 302，浏览器可能把 POST 改成 GET，参数从请求主体跑到 URL 里，既可能泄露敏感信息，又会让服务端收不到预期数据。反过来，在提交成功后本该用 303 的地方用了 307，用户一刷新就会重投表单。方法这件事，必须按状态码精确选择。

12.4当重定向的箭头指回自己：重定向循环与一次请求的终点

前三节都在讲「重定向怎么把请求正确送到新地址」，这一节讲它失灵的极端情形，并借此把全书的主线合拢。既然重定向就是「收到 3xx 就朝新地址重发一次」，那么只要这条重发链永远指不到一个 2xx 资源，客户端就会一直重发下去——这就是重定向循环（Redirect Loop），MDN 称之为「重定向死锁」。它是这一讲最该警惕的故障，也是「一次请求全程闭合」这个承诺的反面教材。

MDN 的定义很直接：当后续的重定向路径重复之前的路径时，循环就产生了，换句话说陷入了无限循环，不会有一个最终的页面返回。多数情况下这属于服务器端错误。下面按 A→B→C→A 做一次完整的分步推演，看报文怎么走、浏览器怎么发现、用户看到什么。

设三个地址分别是 https://site.example/a、/b、/c，服务器被误配成 a 指 b、b 指 c、c 又指回 a。浏览器依次发出并收到：

第 1 次请求 GET /a HTTP/1.1 Host: site.example ← HTTP/1.1 302 Found Location: /b 第 2 次请求 GET /b HTTP/1.1 Host: site.example ← HTTP/1.1 302 Found Location: /c 第 3 次请求 GET /c HTTP/1.1 Host: site.example ← HTTP/1.1 302 Found Location: /a 第 4 次请求 GET /a HTTP/1.1 ← HTTP/1.1 302 Found，Location: /b …如此往复，永远等不到 2xx
A→B→C→A 的报文序列：每一跳都是合法的 302 + Location，但地址集合首尾相接，重发链无法收敛到任何资源。

浏览器怎么发现？MDN 说分两种情况。第一种：服务器自己能检测到，例如同一台服务器发现路径又要回到已访问过的地址，于是返回 500 Internal Server Error。第二种：服务器检测不到——循环发生在多台服务器之间，每台都只看见自己那一跳，没有全局视野。这时由浏览器负责检测：它跟踪这条重定向链，一旦发现目标地址重复出现、或自动重定向次数超过自身上限（不同浏览器阈值不同），就中止跳转并给出错误。MDN 给出的用户可见文案是：Firefox 显示「检测到该服务器正在将指向此网址的请求无限循环重定向」，Chrome 显示「该网页将你重定向的次数过多」。MDN 还补了一句很现实的话：无论哪种场景，用户对此都无能为力，除非客户端发生突变（例如缓存或 Cookie 不匹配）。

为什么会形成这样的环？最常见的手法正是前面提醒过的：HTTP 层、<meta>、JavaScript 三处重定向互相指，或者改了其中一处忘了另两处；其次是 HTTPS 强制跳转写反——本该「http 跳 https」，却让 https 也跳向 http，于是两边互踢；再就是 12.2 节那种缓存了旧 301、与当前配置目标互相矛盾的残留。定位方法也直接：用 curl -I 跟住每一跳的 Location（或用浏览器 Network 面板看重定向链），画一张「地址→目标」的有向图，出现环的那个节点就是故障点；清掉冲突的 meta/JS、修正协议跳转方向、purge 掉陈旧缓存即可打破。

flowchart LR A["地址 A"] --> B["地址 B"] B --> C["地址 C"] C --> A C --> D["浏览器计数超限"] D --> E["显示重定向次数过多"]
图 12.2 A→B→C→A 收不敛：浏览器靠跟踪重复地址与跳转次数上限，在途中断并报错。

讲到这里，全书的主线刚好合拢。回想第 1 讲，MDN 把一次典型会话分成三个阶段：客户端建立连接 → 客户端发送请求并等待应答 → 服务器处理并返回响应，之后连接关闭或复用。这一讲讲的重定向，全部发生在第二阶段与第三阶段之间——客户端发出请求（阶段二），服务器不直接给资源，而是用 3xx + Location 回一条「去别处」（阶段三的变体），客户端于是开启新一轮的「建立连接（若换了主机）+ 发送请求 + 等待响应」。一次重定向，就是把第 1 讲那套三阶段再走一遍；重定向循环，则是这套三阶段被卡在中间、永远走不到终点。

把这条闭合路线完整走一遍：用户在地址栏输入网址（第 1 讲的起点）→ DNS 解析、TCP 与 TLS 建连（阶段一）→ 浏览器把意图编码成请求报文发出、携带 cookie 与认证凭据（阶段二，第 7、8 讲补上的状态与身份）→ 请求可能经代理转发、必要时 CORS/CSP 判定边界（第 9、10、11 讲）→ 服务器返回 3xx 与 Location，本讲登场 → 客户端按状态码决定是否改写方法、按相对 URL 规则算出目标（12.1、12.3）→ 重发请求，可能命中缓存里的旧跳转（12.2，第 5、6 讲的缓存机制在此显形）→ 若地址成环则被浏览器截断（12.4）→ 最终拿到一份 2xx 表示，按 MIME 类型渲染（第 2、3 讲）→ 连接复用或关闭（第 4 讲），一次请求全程闭合。这就是 course 开篇那句话的完整落地：连接、缓存、cookie、认证、CORS、代理与重定向，都是在这条主线上插入的规则。第 12 讲把这些规则里最后一个「把请求送到正确地方」的环节补齐，于是全书闭环。

✅ 判定规则

排查「页面一直转圈最后报重定向次数过多」：先看是不是 http/https 互跳（协议写反）、再看是不是 HTTP/meta/JS 三处重定向目标不一致、最后查是不是缓存了旧的永久重定向与当前配置打架。用 curl -I -L 打印完整跳转链，出现重复地址即为环。修正后记得清缓存，否则「修好了却仍跳旧的」会让你以为是配置没生效。

⚠️ 常见误区

「重定向只是性能优化的小问题，多一次往返而已」——平时确实只是小开销，MDN 也劝尽量少用；但一旦成环或撞上永久缓存，它就能让整个站点对特定用户完全不可用，而且因为故障发生在浏览器端，服务端日志一片正常，排查难度远超普通 4xx/5xx。把重定向当成「会写进客户端状态的路由决策」来对待，才不会在上线后被它反咬。

12.5延伸：规范怎么写：RFC 9110 的 3xx 家族与永久重定向缓存

MDN 是面向开发者的指南，它告诉你「301/308 永久、302/303/307 临时」「浏览器会缓存永久重定向」，但刻意没写「凭什么」。当你要实现客户端的自动重定向、决定某条响应能不能缓存、或者判定一个边界行为时，就要看 IETF 的规范口径。HTTP 语义集中在 RFC 9110：3xx 状态码整体定义在 §15.4，301 在 §15.4.2、302 在 §15.4.3、303 在 §15.4.4、307 在 §15.4.7、308 在 §15.4.8；缓存行为在 RFC 9111；Location 首部在 RFC 9110 §10.2.2；相对引用的解析算法在 RFC 3986 §5.2。这一节把 MDN 的工程说法与规范逐条对齐。

MDN 的说法RFC 怎么写为什么值得知道
3xx 表示需要客户端进一步动作才能完成请求，Location 给出目标 URLRFC 9110 §15.4 定义：3xx 类状态码表示用户代理需要采取进一步动作才能完成请求；Location 的值是一个 URI 引用（§10.2.2），可为绝对或相对「进一步动作」是规范性定义，不是描述；明白 Location 是 URI 引用而非必填绝对 URL，才知道相对解析为何必须按算法走
301/302「规范无意改方法，但实际用户代理会改」，307/308 消除歧义RFC 9110 §15.4.2/§15.4.3 允许出于历史原因把 POST 改为 GET（MAY）；§15.4.7 307 与 §15.4.8 308 要求用户代理不得自动改变方法（MUST NOT change the method）MAY 与 MUST NOT 是规范里完全不同强度的措辞。这解释了为何 301/302 的行为不可靠、而 307/308 可作为严格保证——实现客户端时必须照此办理
303 用于 POST/PUT 完成后重定向，防止刷新重复提交RFC 9110 §15.4.4：303 指示用户代理执行GET 或 HEAD 取回目标资源，且目标通常与原始 URI 不同；这是 PRG 模式的规范基础「改成 GET」不是浏览器好心，而是规范要求；据此可放心用 303 打断重复提交，而不必担心各浏览器实现不一
浏览器会缓存永久重定向RFC 9111 §3 规定可缓存性：301/308 这类响应用户代理可长期存储（若无明确禁止），并可在后续请求中直接复用；缓存新鲜度与再验证按 §4 计算MDN 的「会缓存」在规范里是「默认可缓存 + 按缓存规则计算」，所以你能用 Cache-Control 精确控制它，也理解 12.2 节那条误配 301 为何能长期作祟
互相指向会形成重定向循环，浏览器负责检测RFC 9110 §15.4 首段要求用户代理应当检测无限重定向循环（SHOULD detect），并对自动重定向做限制；检测到即视为错误SHOULD 而非 MUST 解释了各浏览器阈值不同、文案不同；也说明检测责任在客户端，服务端只能尽量自查并返回 500

这张表想传达的元规则只有一条：MDN 说「通常」「建议」的地方，规范里往往藏着 MAY / SHOULD / MUST 的精确分级。301/302 方法改写的「看浏览器心情」，规范写作 MAY；307/308 的「必须保持方法」，规范写作 MUST NOT；循环检测的「浏览器会管」，规范写作 SHOULD。看懂这几个词，你就能判断一条行为是「可靠保证」还是「尽力而为」，这在实现客户端或排查疑难杂症时是决定性的。

💡 关键一跃

把 RFC 9110 的语义层与 RFC 9111 的缓存层分开看，重定向的许多困惑会一次性解开：状态码决定「方法怎么处理、是否永久」（这是 9110 的语义），Cache-Control 与缓存规则决定「这条跳转被记多久」（这是 9111 的缓存）。301/308 之所以危险，正是因为它的语义（永久）与缓存的默认行为（可长期存）叠加——语义说「别再来了」，缓存说「我替你记着」，于是服务端即使改了，客户端也不再来问。这正是全书反复强调的「语义与传输分离」在重定向上的具体体现。

⚠️ 常见误区

别把 MDN 的「浏览器会缓存永久重定向」理解成「所有重定向都会缓存」。临时重定向（302/303/307）默认不缓存，除非另有首部指示；只有 301/308 这类才默认可长期存储。反过来也别以为「有 Cache-Control 就一定不缓存」——要看具体指令，no-store 才是禁止存储，no-cache 只是每次要再验证。这些精确口径都在 RFC 9111，而不是凭经验猜。

回忆 12.5-1
RFC 9110 用哪组措辞区分 301/302 与 307/308 的方法处理？各在哪一节？
点击翻面 →
参考答案
§15.4.2/§15.4.3 用 MAY 允许 301/302 出于历史原因把 POST 改 GET；§15.4.7 307 与 §15.4.8 308 用 MUST NOT 要求不得自动改变方法。MAY 不可靠，MUST NOT 是保证。
回忆 12.5-2
「永久重定向被缓存」在规范上由哪两层共同决定？Location 的相对解析依据哪份 RFC？
点击翻面 →
参考答案
语义层 RFC 9110（301/308 的永久语义）+ 缓存层 RFC 9111（可缓存性与新鲜度计算）。Location 作为 URI 引用，其相对解析按 RFC 3986 §5.2 的引用解析算法。

🃏概念卡：本讲概念的一分钟画像

翻面前先自问：这个概念我能用一句话讲清楚吗？作为全书最后一讲，这七张卡也顺带把散落各讲的概念串成一条闭合的线。

概念卡 1
HTTP 重定向（Redirect）与 3xx
点击翻面 →
定义服务器用 3xx 状态码加 Location 首部，指示客户端换地址重发请求的机制。
解决问题资源换了地址后，让旧链接、书签与外部引用继续可用，而不必返回 404。
直觉快递单改了收件地址，邮局按新地址重投一次。
误区以为重定向无成本；每次多一次往返，成环或撞上永久缓存时更会致命。
何时用域名别称、强制 HTTPS、站点重构保链接；能改内部链接就别做内部重定向。
概念卡 2
Location 首部与相对 URL 解析
点击翻面 →
定义重定向响应里保存目标地址的首部，其值是一个 URI 引用，可为绝对或相对。
解决问题告诉客户端「去哪」，并允许用简短的相对写法指向同一站点的其它资源。
直觉路牌既可以写完整地址，也可以写「往左再走两条街」。
误区用字符串拼接解析相对 URL；应按 RFC 3986 §5.2 以请求 URL 为基准逐段合并。
何时用每次读 3xx 响应、实现客户端跳转、或做相对链接解析时。
概念卡 3
永久重定向（301 / 308）
点击翻面 →
定义声明原 URL 作废、应由新 URL 取代的重定向；爬虫会更新收录，响应默认可被长期缓存。
解决问题站点永久重构或强制 HTTPS 后，把权重与流量整体迁移到新地址。
直觉旧门牌彻底拆掉，邮局和地图都改成新门牌。
误区把临时活动也发成永久；一旦被缓存与收录，改回 200 也救不回已记住跳转的用户。
何时用确定永不回头的迁移；308 在需要保持非 GET 方法与主体时优于 301。
概念卡 4
临时重定向（302 / 303 / 307）
点击翻面 →
定义声明资源只是暂时不在标准地址的重定向；爬虫不记录新地址，默认不缓存。
解决问题维护停机、进度页、POST 提交后跳转等「临时借用别处」的场景。
直觉门店装修，临时在隔壁营业，装修完就回来。
误区以为三者方法行为一样；303 明确改 GET，307 严格保持，302 介于两者之间不可靠。
何时用拿不准永久与否时先用临时；支持非 GET 操作且要保方法时用 307。
概念卡 5
方法保持与 307 / 308
点击翻面 →
定义重定向后严格保留原请求方法与主体的语义，由 307（临时）与 308（永久）明确承诺。
解决问题消除 301/302 历史上被浏览器改成 GET 的歧义，保护 POST/PUT 等不安全请求。
直觉换地址重投时原封不动地照抄整张单据，而不是偷偷改成「只看一眼」。
误区给会被 POST 的端点配 302；方法可能被改、主体丢失，导致请求无效或参数泄漏。
何时用API 端点迁移、表单/文件上传跳转等任何「方法必须保持」的场合。
概念卡 6
303 与 PRG（提交后重定向）
点击翻面 →
定义303 明确要求客户端改用 GET 取目标资源、丢弃原主体；由此形成 Post/Redirect/Get 模式。
解决问题提交表单或下单后跳到结果页，用户刷新只刷新 GET 页面，不重复触发不安全请求。
直觉交完表给你一张回执号，再让你去另一个窗口凭号看结果。
误区在提交成功后用 307 保方法，结果一刷新就重复下单；该改 GET 时就要用 303。
何时用POST/PUT 完成后的结果展示、耗时操作的进度页与取消页。
概念卡 7
重定向循环（Redirect Loop）与缓存残留
点击翻面 →
定义重定向路径首尾相接、永远到不了 2xx；服务器可返 500，否则由浏览器检测并报错。
解决问题识别 http/https 互跳、HTTP/meta/JS 目标冲突、陈旧永久缓存这三类常见成因。
直觉两个路牌互相指路，你在原地绕圈，直到巡逻的浏览器把你拦下。
误区以为改好服务端就立刻生效；缓存了旧 301 的浏览器不再来问，必须一并清缓存。
何时用排查「重定向次数过多」时，用 curl -I -L 追链画有向图找环，再清缓存。

✍️分层习题：先自己写，再点开核对

L1 概念辨析判断下列说法正误并说明理由：①「301 和 302 都是临时重定向」；②「304 Not Modified 会让浏览器去另一个 URL」；③「308 与 301 都是永久重定向，但 308 明确保持方法与主体」。
提示

回到 12.1 的三分类表与 12.3 的方法判定表，逐句对照状态码的类别与方法承诺。

完整解答
① 错。301 是永久重定向（Moved Permanently），302 才是临时重定向（Found）。二者方法行为相似（都可能被浏览器改成 GET），但「永久/临时」的语义与缓存行为完全不同，不可混为一谈。② 错。304 属于特殊重定向，它让页面跳到本地缓存副本（可能已过时），表示缓存响应仍新鲜可用，并不携带 Location 指向另一个 URL；它是条件请求的产物。③ 对。308 与 301 同为永久重定向，但按 MDN 与 RFC 9110，308 明确要求方法与消息主体都不变化，而 301 只是「GET 不变、其他方法可能变 GET」，308 正是为消除这一歧义而创建。
L1 概念辨析某同学说：「既然 HTTP 重定向、<meta> 和 JS 都能跳转，那我三个都写上最保险。」这句话为什么危险？请按 MDN 给出三者的优先级，并说明会发生什么故障。
提示

想想三者同时存在时谁先触发，以及改了一处忘了另两处会怎样。

完整解答
MDN 的优先级是：① HTTP 重定向永远最先触发，甚至页面还没传输就已存在；② HTML 的 <meta> 重定向在没有 HTTP 重定向时才触发；③ JavaScript 重定向最后，且只在客户端开启脚本时生效。三者都写并不会「更保险」，反而制造不一致：HTTP 跳转先生效，meta 与 JS 基本没机会执行；一旦开发者只改了其中一处的目标地址，两处目标就可能互相指回，形成无限循环（MDN 明确警告这会带来「无限循环或其他噩梦」）。正确做法是只在 HTTP 层做一处重定向。
L2 手算推导基准请求 URL 为 https://shop.example.com/a/b/c.html。请逐一算出下列 Location 值对应的绝对目标 URL，并写出每一步依据：① /login；② ./../img/logo.png；③ ?sort=price&page=2；④ //static.example.com/x.css。
提示

按「scheme → authority → 绝对 path → 相对 path → query/fragment」优先级；相对 path 先去掉基准末段得目录，再拼接并消除 . 与 .. 段。

完整解答
基准拆分：scheme=https，authority=shop.example.com，path=/a/b/c.html，query 与 fragment 为空。
① /login 以 / 开头，直接替换整个 path，scheme 与 authority 不变 → https://shop.example.com/login。
② ./../img/logo.png 是相对路径：基准 path 去掉末段 c.html 得目录 /a/b/，拼接得 /a/b/./../img/logo.png，消除 . 得 /a/b/../img/logo.png，再消 b/.. 回退一级得 /a/img/logo.png → https://shop.example.com/a/img/logo.png。
③ 只带 query、引用 path 为空，故 path 沿用基准 /a/b/c.html，query 改为 sort=price&page=2 → https://shop.example.com/a/b/c.html?sort=price&page=2。
④ 以 // 开头带 authority，沿用基准 scheme=https，authority 换成 static.example.com，path 取 /x.css → https://static.example.com/x.css。
L2 手算推导一个下单接口收到 POST /order，主体 item=book&qty=1。服务器要把它迁到 /order-v2，且要求「方法严格保持、主体不丢」；随后下单成功页希望用户刷新时不重复提交。请回答：① 迁移跳转该用哪个状态码，写出响应报文与该重投的方法/主体；② 成功后跳结果页又该用哪个状态码，写出随后请求的方法；③ 若迁移误用 302，最可能发生什么？
提示

用 12.3 的方法判定表：要保方法看 307/308，要改成 GET 看 303；注意迁移的 permanence。

完整解答
① 迁移要求方法严格保持，应选 307 或 308；若这次迁移是永久的，选 308（方法与主体都不变且语义永久）。响应：HTTP/1.1 308 Permanent Redirect + Location: /order-v2 + Content-Length: 0。随后浏览器重发 POST /order-v2，主体仍是 item=book&qty=1。
② 成功后跳结果页要「改成 GET、防刷新重投」，应选 303：HTTP/1.1 303 See Other + Location: /order/result?id=42，随后浏览器发出 GET /order/result?id=42，主体为空；刷新只刷新这个 GET 页面。
③ 若迁移误用 302，按 MDN/RFC 的口径，302 下的 POST 可能被用户代理改成 GET，主体 item=book&qty=1 丢失，参数从主体跑到 URL 或干脆消失，服务端收不到下单数据，请求实际上失败。这正是必须用 307/308 保方法的原因。
L3 建模应用你要把一个站点整体迁到新域名并强制 HTTPS：http://old.example.com 与 https://old.example.com 都要最终落到 https://www.new.example.com，站点里有接收 POST 的 /api/order 接口；此外还要保留若干只在活动期间使用的临时落地页 /campaign。请用本讲概念给出一套方案：① 每类跳转选哪个状态码；② POST 接口迁移如何保证不丢请求；③ 如何避免永久缓存与循环；④ 上线后如何验证。
提示

把「永久 / 临时」「方法保持」「缓存」「循环」四个维度分别套到每类跳转上。

完整解答
① 旧域名到新域名、http 到 https 都是长期决定，用永久重定向：301 Moved Permanently（GET 场景）或 308（需保方法的场景）；强制 HTTPS 时确保只在 http 上跳 https、绝不让 https 再跳回 http，否则形成互跳环。临时活动落地页 /campaign 用 302 或 303，活动结束即可撤掉，不进缓存、不改收录。
② /api/order 接收 POST，迁移必须用 308：它与 301 同为永久，但明确要求方法与主体都不变，客户端会把 POST 与请求体原样发到新域名；若误用 301/302，POST 可能被改成 GET、主体丢失，订单提交失败。下单成功后如需跳结果页，再用 303 改为 GET。
③ 永久缓存：只在这些跳转确定永不回头时才发 301/308，并显式设置你真正想要的 Cache-Control；上线前确认没有给临时页面误发永久码。循环：只在 HTTP 层做一处重定向，不要叠加 meta/JS；画「旧→新」有向图确认无环，尤其核对 http/https 跳转方向。
④ 验证：用 curl -I 逐条核对每个 URL 返回的状态码与 Location；用 curl -I -L 跟踪完整跳转链，确认最终落到 2xx 且无重复地址；对 POST 接口用带主体的请求实测 methods 是否被保持；浏览器清缓存后与带旧缓存两种情形都测一遍，确认「修好即生效」而非被旧 301 卡住。

自测 1
一条 HTTP 重定向响应，最关键的两个组成部分是？
  • A. 200 状态码与 Content-Type 首部
  • B. 以 3 开头的状态码与 Location 首部
  • C. Set-Cookie 首部与主体
  • D. Host 首部与 Content-Length 首部
解析：B 对。MDN 明确：重定向响应包含以 3 开头的状态码，以及保存目标 URL 的 Location 首部。A 是普通成功响应；C 属于 cookie 机制（第 7 讲）；D 是请求的必需首部与主体定界（第 1、2 讲），都不是重定向的构成要素。
自测 2
POST /order 被重定向，哪种状态码能最可靠地保证方法与主体都不丢失？
  • A. 301 Moved Permanently
  • B. 302 Found
  • C. 307 Temporary Redirect
  • D. 303 See Other
解析：C 对。307 明确要求方法与主体都不变化，是四个选项里唯一可靠的「保方法」临时重定向。A、B 虽规范无意改方法，但历史上浏览器常把 POST 改成 GET、主体丢失，不可靠；D 的 303 恰恰是明确要改成 GET、丢弃主体，用于提交后跳结果页，与「保持方法」相反。永久场景下同等可靠的是 308，但本题选项里没有。
自测 3
关于永久重定向与临时重定向，下列说法正确的是？
  • A. 爬虫会更新永久重定向的旧 URL，而临时重定向的新 URL 不会被记录
  • B. 临时重定向会被浏览器长期缓存，永久重定向不会
  • C. 301 与 302 都是临时重定向
  • D. 永久重定向一旦发出就能随时无损回退
解析：A 对，正是 MDN 的原文口径。B 说反了：默认可长期缓存的是 301/308 这类永久重定向，临时重定向默认不缓存。C 错：301 永久、302 临时。D 错：永久重定向会被缓存与收录，改回配置后已记住跳转的浏览器与搜索引擎不会立刻更新，回退代价高、并不「无损」。
自测 4
基准 URL 为 https://www.example.com/docs/guide/intro.html，Location 为 ../index.html，解析后的绝对地址是？
  • A. https://www.example.com/docs/guide/index.html
  • B. https://www.example.com/index.html
  • C. https://www.example.com/docs/guide/intro.html/index.html
  • D. https://www.example.com/docs/index.html
解析：D 对。相对路径先去掉基准末段 intro.html 得目录 /docs/guide/，拼上 ../index.html 得 /docs/guide/../index.html，消除 .. 回退一级得 /docs/index.html。A 忽略了 .. 的回退作用；B 多退了一级（把 docs 也退掉了）；C 把相对路径当成相对文件名直接拼接，完全没有消除 .. 段，属于典型的「字符串拼接」错误做法。
自测 5
用户报「该网页将你重定向的次数过多」，最不可能的原因是？
  • A. http 与 https 互相跳转，方向写反形成环
  • B. 服务器返回了一条带正确 Location 的 301，跳转到全新且有效的地址
  • C. HTTP、meta、JS 三处重定向目标不一致、互相指回
  • D. 缓存了旧的永久重定向，与当前配置目标互相矛盾
解析：B 对（最不可能）。一条正确且指向有效新地址的 301 只会产生一次正常跳转，最终落到 2xx，不会成环。A 是经典的协议互踢环；C 是 MDN 明确警告的多机制不一致；D 是 12.2 节讲过的陈旧缓存与当前配置打架——三者都能让重发链首尾相接，触发浏览器的循环检测并报「次数过多」。

句1：这讲解决什么问题？——
参考答案：解决「资源换了地址、旧链接还要能用」的问题——服务器用 3xx 加 Location 让客户端换地址重发一次，并区分永久与临时、决定方法是否改写、防止成环与永久缓存反噬。
句2：核心机制是什么？——
参考答案：状态码决定语义与缓存（301/308 永久且默认可缓存，302/303/307 临时；307/308 保方法、303 改 GET、301/302 不可靠），Location 用相对 URL 算法给出目标，客户端据此重投；地址首尾相接就成了循环，永久跳转被缓存后客户端不再来问。
句3：它和前后讲怎么分工？——
参考答案：本讲补上第 1 讲会话「服务器返回响应」之后、「客户端重新发起请求」之前的那一跳。一次重定向就是把第 1 讲的三阶段——建立连接、发送请求并等待应答、服务器返回响应——再走一遍；成环就是卡在这三阶段中间到不了终点。至此，从第 1 讲的会话骨架，到第 4 讲连接、第 5/6 讲缓存、第 7/8 讲状态与身份、第 9/10 讲边界、第 11 讲代理、第 12 讲重定向，一次请求从发起到落地全程闭合。
